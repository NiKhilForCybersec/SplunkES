Handling Missing Fields After Add-ons

📋 Page Status: HARDENED — ES DATA LAYER

Last Audit: 2024-02 | Auditor: Detection Engineering Team

Purpose: You installed the Technology Add-on. You ran the validation checks. Some CIM fields are still missing or null. This page explains why that happens, how to identify exactly what's missing and where, and provides a decision framework for choosing the right fix — ranked from safest to most risky.

Ownership: Detection Engineering

Preconditions: You've completed Validating ES Data and have identified specific missing fields. You know which data model and which sourcetype has the gap.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: The correct TA for your data source is installed and enabled on search heads. Verify first: | rest /services/apps/local | search title="TA-*" OR title="Splunk_TA_*" | table title, version, disabled. If the TA is missing, install it before trying any field fixes.
  • Assumption: The TA is the correct version for your data format. Reality: Source devices get firmware updates that change log formats. A TA that worked 6 months ago may not parse today's logs correctly.
  • Assumption: You will NOT modify default/ files. All fixes go in local/ directories. This is a hard rule for production safety.

Why Add-ons Often Do NOT Populate All CIM Fields

This is the most common surprise for detection engineers. You install the vendor TA, you see data flowing, you assume CIM is handled. Then validation reveals half the fields are null. Here's why:

Reason Explanation How Common Example
TA doesn't cover all CIM fields The TA vendor mapped the most common fields but not every CIM field. CIM has dozens of fields per model; TAs often map 5-10. Very common TA maps src and dest but not bytes_in, bytes_out, or transport for Network_Traffic.
Source device doesn't log the data The CIM field exists in the spec, but the source device simply doesn't include that information in its logs. Common A basic firewall logs src/dest/port but not app (only NGFW does application identification).
Log format variant not handled The TA was built for one version of the device's log format. Your device sends a slightly different variant (different firmware, different syslog template, different severity level). Common Palo Alto TA handles TRAFFIC logs perfectly but misses THREAT log field mappings because the format differs.
TA is community-developed (not Splunk-supported) Community TAs are often built for a specific use case and may not aim for full CIM compliance. Common for niche sources A community TA for a specialty WAF or cloud service may extract key fields but skip CIM aliases entirely.
Eventtypes / tags are incomplete The TA maps fields but doesn't create eventtypes or assign all required tags. Fields exist but the data model can't see them. Moderately common TA creates field alias for src but no eventtype/tag for network + communicate. Network_Traffic model is empty.
TA version mismatch with CIM version The TA was built for an older CIM version. Newer CIM fields don't exist in the TA. After CIM or ES upgrades CIM v5 added a new field. TA built for CIM v4 doesn't include it. Field appears null after ES upgrade.
TA installed on wrong tier TA is on the indexers (for index-time extractions) but not on the search heads (where search-time field aliases are needed for CIM), or vice versa. Common in distributed deployments TA on indexers extracts srcip at index time. But the field alias srcip AS src is in props.conf that's only on the SH — which only works if the TA is also on the SH.

How to Identify Exactly What's Missing

Step 1: Identify the gap from validation

Your Gate 3 validation showed a specific CIM field at 0% or low population for a specific sourcetype. You have: the field name, the sourcetype, and the data model.

Step 2: Check if the raw data contains the information

Common Missing Fields by Source Type

These are the most frequently missing CIM fields encountered in enterprise environments, with the typical fix.

Source Missing CIM Field Why Typical Fix
Windows Security (4624/4625) app Windows logs don't have an "app" field. LogonType is the closest equivalent. EVAL-app: Map LogonType to app names (2→Interactive, 3→Network, 10→RemoteInteractive)
Windows Security (4624/4625) authentication_method Not directly present. AuthenticationPackageName is the closest. FIELDALIAS: AuthenticationPackageName AS authentication_method
Azure AD Sign-In src Field is named ipAddress or ClientIP in Azure AD logs. FIELDALIAS: ipAddress AS src
Azure AD Sign-In action Azure uses "Status.errorCode" — 0=success, non-zero=failure. EVAL-action: if(errorCode=0 OR errorCode="0", "success", "failure")
Palo Alto Firewall action (value mismatch) Palo Alto uses "allow"/"deny" but CIM expects "allowed"/"blocked". EVAL-action: case(action="allow","allowed", action="deny","blocked", 1=1,action)
Generic Syslog (Firewall) transport Device logs protocol as a number (6=TCP, 17=UDP). CIM expects text. EVAL-transport: case(proto=6,"tcp", proto=17,"udp", proto=1,"icmp")
WAF (Akamai, Cloudflare) src WAF logs may use "client_ip", "true_client_ip", or "X-Forwarded-For". FIELDALIAS: true_client_ip AS src or use EVAL with coalesce
WAF (Akamai, Cloudflare) url Field may be "request_uri", "cs-uri-stem", "path", "uri". FIELDALIAS: request_uri AS url
O365 / Cloud Audit user Field may be "UserId", "UserPrincipalName", "userPrincipalName" (case-sensitive). FIELDALIAS: UserId AS user
VPC Flow Logs (AWS/Azure) bytes_in / bytes_out Flow logs have "bytes" (total) but not split in/out. Direction must be inferred. EVAL: Derive based on traffic direction field, or accept total bytes only.
Any source tag (missing entirely) TA never created eventtypes.conf or tags.conf. Fields are mapped but data model is empty. Create eventtypes.conf + tags.conf in local/ with correct constraints and tags. See Safe Add-on Tuning.

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • REQUIRED CIM fields (action, user, src) are missing and the vendor field also doesn't exist in the raw event. This means the data source itself doesn't provide the information. You can't fix it with a field alias. Escalate to the data source team to enable verbose logging, or accept the gap and document it.
  • The TA's default/props.conf has incorrect extractions. Do NOT modify default/. Report the issue to the TA vendor (Splunk or community). Apply a workaround in local/ while waiting for a fix.
  • A field fix requires index-time changes (LINE_BREAKER, SHOULD_LINEMERGE, TRANSFORMS for index-time extraction). Index-time changes affect live data ingestion and are irreversible for already-indexed data. Escalate to Splunk admin. Do not attempt without platform engineering approval.
  • More than 5 CIM fields are missing for a single sourcetype. This suggests the TA is fundamentally inadequate for CIM compliance. Consider: Is this the right TA? Is there a better one? Do you need to build custom extractions?
  • Someone proposes fixing a field gap by modifying the data model definition. Never do this. Data models are managed by the CIM add-on. Changing them breaks upgrades and can affect all users of that model.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"I'll just add all possible field aliases at once" Adding aliases that map to nonexistent vendor fields does nothing but clutter. Adding aliases that conflict with existing ones can break extractions. Add one alias at a time. Verify the vendor field exists first. Test. Then add the next.
"I'll fix it in default/ so it's consistent" Next TA update overwrites default/. Your fix disappears. Production breaks silently. ALWAYS use local/. Add a comment in the file noting what you changed and why.
"The TA should handle everything — I won't customize" TAs are starting points, not complete solutions. Waiting for perfect TAs means waiting forever. Meanwhile detections don't work. Accept that local/ customizations are normal and expected. Document them. Review them during upgrades.
"I'll fix the field in every correlation search's SPL" If 10 searches need the same field, you maintain 10 copies of the fix. One gets missed on the next update. Fix at the TA level (alias or EVAL) so it applies globally. Search-time eval in SPL is a last resort for complex cases only.
"I found a gap, but nobody asked me to fix it — I'll leave it" Every undocumented gap is a silent detection failure waiting to happen. Log it in the gap register immediately. Even if you can't fix it now, documenting it makes it visible and trackable.
