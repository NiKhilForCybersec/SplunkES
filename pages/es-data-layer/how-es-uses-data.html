How Splunk ES Uses Data

📋 Page Status: HARDENED — ES DATA LAYER

Last Audit: 2024-02 | Auditor: Detection Engineering Team

Purpose: Explains the complete data pipeline inside Splunk ES — from raw event ingestion through CIM normalization, data model acceleration, correlation search execution, to notable event creation. This is the foundation you must understand before touching any detection content. If you don't understand this page, do not proceed to enabling detections.

Ownership: Detection Engineering (understanding) + Platform Engineering (infrastructure)

Preconditions: Basic familiarity with Splunk concepts (indexes, sourcetypes, search). No ES-specific knowledge required — this page builds it.

🚨 Why This Matters — Production Safety

Splunk ES is not a standalone detection tool — it is a data-dependent framework. Every correlation search, every dashboard, every notable event depends on data flowing correctly through a multi-layered pipeline. When data is wrong at any layer, ES produces one of three outcomes: silent failures (detections return nothing), false positives (detections fire on bad data), or platform instability (broken searches consume resources). Understanding this pipeline is not optional — it is the difference between a working SOC and a broken one.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: Splunk ES is installed and operational on your search heads. Verify: Navigate to Enterprise Security app. If it doesn't load, ES is not installed or you don't have the role.
  • Assumption: At least some data is flowing into Splunk. Verify: | tstats count WHERE index=* BY index | sort -count | head 10 — you should see indexes with data.
  • Assumption: You do NOT have perfect CIM compliance. This is the expected state. Most environments have partial compliance. This section teaches you how to assess, fix, and work within that reality.
  • Assumption: Breaking production is not acceptable. This section is designed for zero-risk assessment. All validation queries are read-only. No configuration changes until later pages.

The ES Data Pipeline — End to End

ES consumes data through six distinct layers. A failure at any layer breaks everything downstream. Understanding where you are in this pipeline is the first step to diagnosing any ES issue.

What Each Layer Does — And Where It Breaks

Layer What It Does Common Failure Symptom When Broken Who Fixes It
L1 — Raw Events Data arrives in Splunk indexes from forwarders, syslog, HEC, or API pulls Data stops flowing. Index doesn't exist. Forwarder misconfigured. Source system changed format. Zero events. Searches against the index return nothing. Detections fire zero results. Platform Engineering / Infrastructure
L2 — Field Extraction TAs parse raw events and extract named fields (src_ip, user, action, etc.) using props.conf and transforms.conf TA not installed. Wrong TA version. Source format changed and TA's regex no longer matches. TA installed but not on search heads. Raw events exist but fields are missing. | fields src_ip returns null. Detections that filter on fields find nothing. Detection Engineering / Platform Engineering
L3 — CIM Normalization TAs map vendor-specific fields to CIM standard names using field aliases, calculated fields, eventtypes, and tags TA doesn't map all CIM fields. CIM field alias points to wrong vendor field. Eventtype tag missing (data doesn't appear in data model). Partial CIM compliance. Data model queries return zero or incomplete results. Some CIM fields are null even though vendor fields exist. Events are invisible to data model-based correlation searches. Detection Engineering
L4 — Data Model Acceleration Splunk pre-computes data model summaries (TSIDX files) so that | tstats queries run in seconds instead of minutes Data model acceleration disabled. Acceleration backlog (not caught up). Acceleration failed (permissions, disk space). Search head cluster (SHC) not replicating acceleration. | tstats returns zero results even though | search on the same data works. Correlation searches that depend on tstats silently fail. Platform Engineering / Splunk Admin
L5 — Correlation Searches Scheduled SPL searches run on a cron, query data models or raw indexes, evaluate conditions, and trigger notable events Search skipped (concurrency limit). Search errors (SPL syntax, missing macro). Threshold too low (noise) or too high (misses events). Notable action not configured. No notables appear. Or too many notables appear. Search scheduler shows skips or errors. SOC has no alerts or is flooded. Detection Engineering
L6 — Notable Events Correlation search results are written to the notable index as notable events, visible in Incident Review Notable action not configured on the search. Suppression hiding events. KV store failure. Permissions issue. Correlation search runs and returns results, but nothing appears in Incident Review. Detection Engineering / Splunk Admin

Raw Events vs Normalized Fields — The Core Concept

This distinction is fundamental. Every piece of ES functionality depends on understanding the difference between what a device sends and what ES expects to find.

Concept What It Is Example How ES Uses It
Raw event The original log line exactly as the source device sent it, stored in _raw Feb 15 14:30:01 fw01 TRAFFIC,allow,srcip=10.1.2.3,dstip=192.168.1.5,srcport=54321,dstport=443,proto=tcp ES does NOT directly consume raw text. Raw events are the source material that must be parsed into fields.
Extracted field A named field extracted from the raw event by a TA's props.conf/transforms.conf regex or automatic key-value extraction srcip=10.1.2.3, dstip=192.168.1.5, dstport=443 These are vendor-specific. ES doesn't know what "srcip" means. It needs CIM field names.
CIM-normalized field A standard field name defined by the Common Information Model, mapped from the vendor field via a TA's field alias or calculated field src=10.1.2.3, dest=192.168.1.5, dest_port=443, transport=tcp This is what ES actually consumes. Data models are built on CIM fields. Correlation searches query data models. If a CIM field is null, the detection is blind.
Data model field A field defined in a data model (e.g., Network_Traffic.All_Traffic.src) that maps to the CIM field All_Traffic.src, All_Traffic.dest, All_Traffic.dest_port | tstats queries reference these data model field paths. If the CIM field is populated AND the data model is accelerated, tstats finds the data.
🚨 The Critical Chain of Dependencies

Raw event exists → TA extracts vendor field → TA maps vendor field to CIM field → Eventtype + tag includes event in data model → Data model acceleration indexes the CIM field → | tstats query finds the data → Correlation search evaluates results → Notable event is created.

If ANY link in this chain is broken, the detection silently fails. There is no error message. The correlation search runs, finds zero results, and moves on. The SOC sees nothing. You think you have coverage. You don't.

What Makes Data Visible to ES

Data doesn't automatically appear in ES dashboards and data models just because it's in a Splunk index. Four conditions must ALL be true:

# Condition How to Check What Happens If Missing
1 Data exists in a Splunk index index=YOUR_INDEX sourcetype=YOUR_ST earliest=-1h | stats count No data at all. Nothing downstream works.
2 A TA extracts CIM-compliant fields index=YOUR_INDEX sourcetype=YOUR_ST | head 10 | table src, dest, user, action — fields should have values, not be null Raw data exists but CIM fields are empty. Data model doesn't see the data.
3 Events are tagged with the correct eventtype/tag for the data model index=YOUR_INDEX sourcetype=YOUR_ST | head 10 | table eventtype, tag — should show relevant tags (e.g., authentication, network, communicate) CIM fields are populated but events have no tags. The data model's constraint (which uses tags) doesn't match. Events are invisible to the data model.
4 The data model is accelerated | rest /services/datamodel/model | search title="Authentication" | table title, acceleration — should show acceleration=1 Events are correctly tagged and CIM-mapped, but | tstats can't find them because acceleration is off or behind. Correlation searches using tstats return zero.
SPL: Quick Layer-by-Layer Health Check (Safe — Read Only) 
`comment("Replace YOUR_INDEX and YOUR_SOURCETYPE with actual values")`
`comment("This query checks all four conditions for a single data source")`
`comment("SAFE: Read-only query. Does not modify anything.")`

index=YOUR_INDEX sourcetype=YOUR_SOURCETYPE earliest=-4h latest=now
| head 1000
| eval has_src = if(isnotnull(src), 1, 0),
    has_dest = if(isnotnull(dest), 1, 0),
    has_user = if(isnotnull(user), 1, 0),
    has_action = if(isnotnull(action), 1, 0),
    has_eventtype = if(isnotnull(eventtype), 1, 0),
    has_tag = if(isnotnull(tag), 1, 0)
| stats count AS total_events,
    sum(has_src) AS src_populated,
    sum(has_dest) AS dest_populated,
    sum(has_user) AS user_populated,
    sum(has_action) AS action_populated,
    sum(has_eventtype) AS eventtype_count,
    sum(has_tag) AS tag_count
| eval L1_data = if(total_events > 0, "✅ L1 PASS — Data exists", "❌ L1 FAIL — No data"),
    L2_fields = case(
        src_populated > 0 AND dest_populated > 0, "✅ L2 PASS — Core fields populated",
        src_populated > 0 OR dest_populated > 0, "🟡 L2 PARTIAL — Some core fields populated",
        true(), "❌ L2 FAIL — No CIM fields extracted"
    ),
    L3_tags = if(tag_count > 0, "✅ L3 PASS — Tags present", "❌ L3 FAIL — No tags (data model won't see this data)")
| table L1_data, L2_fields, L3_tags, total_events, src_populated, dest_populated, user_populated, action_populated, tag_count

How Correlation Searches Consume Data

There are two fundamentally different ways a correlation search can query data. Understanding the difference is essential because they have different prerequisites and different failure modes.

Attribute | tstats (Data Model–Based) | search (Raw Event–Based)
What it queries Pre-computed TSIDX summaries from accelerated data models Raw events directly from Splunk indexes
Speed Very fast (seconds) — queries pre-indexed summaries Slower — must scan and parse raw events
Prerequisites All 4 conditions must be true: data exists + CIM fields + tags + DM acceleration Only condition 1: data exists in the index. Fields can be extracted at search time.
Failure mode Silent failure. Returns zero results with no error. Looks like "no events matched" when actually the data model chain is broken. More visible failures. If data exists, you'll at least see events (even if field parsing is wrong).
Resource cost Low — uses acceleration summaries (one scheduled search slot) Higher — scans raw data (more I/O, more CPU, longer run time)
Field availability Only fields in the data model are available. Can't reference arbitrary fields. All fields in the raw event are available (if extracted).
Most OOTB/ESCU content uses ✅ Yes — majority of ES and ESCU detections use tstats Some custom detections and older OOTB searches use direct search
🚨 The #1 Silent Failure in ES

A | tstats correlation search returns zero results, and you assume there are no matching events.

In reality, the events exist in the raw index, but one of these is broken: CIM field mapping (Layer 3), tag assignment (Layer 3), or data model acceleration (Layer 4). The search runs, finds nothing in the pre-computed summaries, and reports "0 results." There is no warning. The SOC sees no alerts. You believe you have coverage. You don't.

This is why Validating ES Data is a hard gate before enabling any detection.

What NOT to Touch in Production

🔴 Never Touch Why What Breaks
Data model definitions in default/ folders These are managed by Splunk. Editing them breaks upgrades and will be overwritten. Data model structure breaks. All tstats queries against it fail. Every detection that uses that data model dies.
CIM add-on default/ files The Splunk CIM add-on defines the data model schemas. Editing default files breaks upgrades. CIM field definitions change. Data model constraints break. Acceleration may fail.
TA default/ props.conf or transforms.conf TA vendor files. Edits are overwritten on update. Will also break CIM mapping if done incorrectly. Field extractions break. CIM mapping breaks. Data model sees null fields. Detections die silently.
Data model acceleration settings on shared search heads Changing acceleration affects all users and all searches. Disabling acceleration kills all tstats-based detections. Every correlation search using tstats against that model returns zero results. Mass detection failure.
Index-time transforms on live data pipelines Index-time changes affect data at write time. Bad changes corrupt data permanently. Unlike search-time changes, there is no undo — you must re-index. Indexed data is permanently corrupted. Can't fix retroactively. May require full data re-ingestion.
🟢 Safe to Modify (With Process) How Details
TA local/ props.conf — field aliases Add new field aliases to map vendor fields to CIM fields that the TA missed See Safe Add-on Tuning
TA local/ props.conf — calculated fields Add calculated fields to derive CIM fields from existing vendor fields See Safe Add-on Tuning
TA local/ eventtypes.conf + tags.conf Add missing eventtypes and tags so data is visible to data models See Missing Fields After Add-ons
Custom correlation searches (your own clones) Modify SPL, thresholds, schedules in searches you created with CUSTOM - prefix See Enablement Mechanics

Mistake #3 (missing tags) is the most insidious. An analyst might run index=auth user=jsmith | stats count and see results, concluding the data is fine. But without the correct eventtype/tag, the Authentication data model doesn't include those events. A tstats-based correlation search sees nothing. The gap is invisible unless you specifically test data model population.

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • A data model shows zero events for a data source that has data in the raw index. This means the CIM chain (fields → tags → data model) is broken. Do NOT enable detections against this data model until the chain is fixed and validated.
  • Data model acceleration is disabled and nobody knows why. This may be intentional (performance issue) or accidental. Escalate to Splunk admin to understand the reason before re-enabling.
  • Someone modified default/ files in a TA or the CIM add-on. Assess impact immediately. Check if field extractions and CIM mappings are still working. Plan to revert and move changes to local/ folders.
  • Multiple correlation searches return zero results simultaneously. This is likely a data model acceleration failure, not a detection logic problem. Check Layer 4 first.
  • An ES or TA upgrade is planned without a validation plan. Any upgrade can change field extractions, CIM mappings, or data model definitions. Require a post-upgrade validation check (see Validating ES Data).

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"I can see events in search, so ES can too" Ad-hoc search queries raw events. ES primarily queries data models. Data visible in search may be invisible to data models if CIM mapping or tags are broken. Always validate at the data model level, not just the raw index. Use | tstats count from datamodel=X to confirm ES visibility.
"The TA is installed, so CIM is handled" TAs vary widely in CIM coverage. Many TAs extract vendor fields but do NOT map all CIM fields or apply all required tags. Installation ≠ compliance. After installing any TA, explicitly validate CIM field population and tag assignment for every sourcetype. See CIM Fundamentals.
"Data model acceleration is an admin thing — I don't need to check it" If acceleration is broken, every tstats-based detection fails. This is a detection engineering concern, not just an admin concern. Include data model acceleration checks in your pre-detection-enablement validation. Make it part of the lifecycle.
"I'll fix the data layer later — let me enable detections first" Enabling detections against broken data creates false confidence. You believe you have coverage. Auditors believe you have coverage. You don't. Data validation is a hard gate. Fix data first, then enable detections. No exceptions.
"I'll edit the TA's default/props.conf to fix the field" Next TA update will overwrite your fix. You'll lose the change and may not notice until a detection silently fails weeks later. Always make changes in the TA's local/ directory. Local files survive upgrades. See Safe Add-on Tuning.
