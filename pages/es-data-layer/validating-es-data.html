Validating ES Data & Data Models

⛔ THIS PAGE IS A HARD GATE

If the checks on this page fail, DO NOT create or enable correlation searches.

Enabling detections against unvalidated data creates false confidence: the SOC believes it has coverage that doesn't actually exist. Auditors see enabled searches and assume protection. But zero notables fire because the data pipeline is broken. This is worse than having no detections at all — because at least with no detections, you know you're blind.

Complete this validation for every data model you plan to use. Capture evidence. Get sign-off. Then proceed.

Gate 1: Data Model Acceleration

SPL: Check Data Model Acceleration Status (All Models) 
`comment("SAFE: Read-only query")`
`comment("Checks acceleration status for all data models")`

| rest /services/datamodel/model splunk_server=local
| table title, acceleration, "acceleration.earliest_time", eai:acl.app
| eval status = case(
    acceleration="1", "✅ ON",
    acceleration="0", "❌ OFF",
    true(), "❓ Unknown"
)
| sort title
| rename title AS "Data Model",
    status AS "Acceleration",
    acceleration.earliest_time AS "Accel Window",
    eai:acl.app AS "App"
SPL: Check Acceleration Backlog & Health 
`comment("SAFE: Read-only")`
`comment("Shows if acceleration is current or backlogged")`

| rest /services/admin/summarization splunk_server=local
| search title="*DM_*" OR title="*datamodel*"
| table title, summary.is_inprogress, summary.latest_time, summary.complete,
    summary.access_count, summary.size
| eval is_current = case(
    'summary.complete' > 0.95, "✅ Current (>95%)",
    'summary.complete' > 0.50, "🟡 Catching up (" . round('summary.complete'*100) . "%)",
    'summary.complete' > 0, "🔴 Significantly behind (" . round('summary.complete'*100) . "%)",
    true(), "❌ No acceleration data"
)
| sort title

Gate 1 Acceptance Criteria

Check ✅ PASS ❌ FAIL Action on Fail
Acceleration enabled acceleration=1 for the target data model acceleration=0 ⛔ STOP. Escalate to Splunk admin to enable acceleration. You cannot validate further until acceleration is on.
Acceleration current summary.complete > 0.95 (95%+ complete) summary.complete < 0.95 If recently enabled: wait for catch-up (may take hours to days). If persistently behind: escalate — may need more resources.
Acceleration window covers detection lookback acceleration.earliest_time covers at least the detection's scheduled lookback (e.g., -24h) Acceleration window is shorter than detection lookback Adjust acceleration window or adjust detection lookback. Typically acceleration should cover at least 7 days.

Gate 2: Data Model Population

SPL: Verify Data Model Has Events from Expected Sources 
`comment("SAFE: Read-only")`
`comment("Replace DATAMODEL_NAME with: Authentication, Network_Traffic, Web, or Endpoint")`
`comment("Shows which sourcetypes contribute events and how many")`

| tstats count FROM datamodel=DATAMODEL_NAME
    WHERE earliest=-24h latest=now
    BY sourcetype
| sort - count
| eval status = if(count > 100, "✅ Good volume", if(count > 0, "🟡 Low volume", "❌ No events"))
| table sourcetype, count, status
SPL: Compare Data Model Population vs Raw Index Population 
`comment("SAFE: Read-only")`
`comment("This comparison reveals events that exist in raw but are NOT in the data model")`
`comment("Replace INDEX and SOURCETYPE with your data source values")`

| tstats count AS dm_count FROM datamodel=DATAMODEL_NAME
    WHERE sourcetype=YOUR_SOURCETYPE earliest=-4h latest=now

| appendcols [
    | tstats count AS raw_count WHERE index=YOUR_INDEX sourcetype=YOUR_SOURCETYPE
        earliest=-4h latest=now
]

| eval coverage_pct = round((dm_count / raw_count) * 100, 1) . "%"
| eval gap = raw_count - dm_count
| eval status = case(
    coverage_pct >= 95, "✅ PASS — ≥95% of raw events in data model",
    coverage_pct >= 50, "🟡 PARTIAL — Significant gap. Some events not tagged.",
    coverage_pct > 0, "🔴 LOW — Most events missing from data model. Tag issue.",
    dm_count=0, "❌ FAIL — Zero events in data model despite raw data existing."
)
| table raw_count, dm_count, gap, coverage_pct, status

Gate 2 Acceptance Criteria

Check ✅ PASS ❌ FAIL Action on Fail
Expected sourcetypes present All sourcetypes you expect to feed this model appear in the sourcetype contribution query One or more expected sourcetypes missing ⛔ STOP for that source. Check tag assignment. See Missing Fields.
Coverage percentage ≥ 90% of raw events appear in the data model < 90% coverage Investigate. Some event subtypes may lack tags. Not all events need to be in the model — but you need to understand why the gap exists.
Non-zero event count dm_count > 0 dm_count = 0 ⛔ STOP. Data model is empty for this source. Tags missing. Fix before proceeding.

Gate 3: CIM Field Population

SPL: CIM Field Population — Per Data Model 
`comment("SAFE: Read-only")`
`comment("Authentication Model — Check field population percentages")`
`comment("Adapt BY clause and field names for other data models")`

| tstats count AS total,
    dc(Authentication.action) AS action_vals,
    dc(Authentication.user) AS user_vals,
    dc(Authentication.src) AS src_vals,
    dc(Authentication.dest) AS dest_vals,
    dc(Authentication.app) AS app_vals
    FROM datamodel=Authentication
    WHERE earliest=-4h latest=now
    BY sourcetype

| eval action_status = if(action_vals > 0, "✅", "❌"),
    user_status = if(user_vals > 0, "✅", "❌"),
    src_status = if(src_vals > 0, "✅", "❌"),
    dest_status = if(dest_vals > 0, "✅", "❌"),
    app_status = if(app_vals > 0, "✅", "❌")

| eval required_pass = if(action_status="✅" AND user_status="✅" AND src_status="✅", "✅ REQUIRED PASS", "❌ REQUIRED FAIL")

| table sourcetype, total, action_status, user_status, src_status, dest_status, app_status, required_pass
| sort - total
SPL: Detailed Field Population Percentage (Per Sourcetype) 
`comment("SAFE: Read-only")`
`comment("Shows exact population percentage for each field")`
`comment("Replace INDEX and SOURCETYPE with your data source")`

index=YOUR_INDEX sourcetype=YOUR_SOURCETYPE earliest=-4h latest=now
| head 5000
| eval f_action = if(isnotnull(action) AND action!="" AND action!="unknown", 1, 0),
    f_user = if(isnotnull(user) AND user!="" AND user!="-", 1, 0),
    f_src = if(isnotnull(src) AND src!="" AND src!="0.0.0.0", 1, 0),
    f_dest = if(isnotnull(dest) AND dest!="" AND dest!="0.0.0.0", 1, 0),
    f_app = if(isnotnull(app) AND app!="", 1, 0),
    f_dest_port = if(isnotnull(dest_port) AND dest_port!="" AND dest_port!="0", 1, 0),
    f_transport = if(isnotnull(transport) AND transport!="", 1, 0),
    f_url = if(isnotnull(url) AND url!="", 1, 0),
    f_status = if(isnotnull(status) AND status!="", 1, 0)
| stats count AS total,
    sum(f_action) AS action_pop,
    sum(f_user) AS user_pop,
    sum(f_src) AS src_pop,
    sum(f_dest) AS dest_pop,
    sum(f_app) AS app_pop,
    sum(f_dest_port) AS dest_port_pop,
    sum(f_transport) AS transport_pop,
    sum(f_url) AS url_pop,
    sum(f_status) AS status_pop
| foreach *_pop [eval <>_pct = round((<> / total) * 100, 1)]
| table total,
    action_pop_pct, user_pop_pct, src_pop_pct, dest_pop_pct,
    app_pop_pct, dest_port_pop_pct, transport_pop_pct,
    url_pop_pct, status_pop_pct

Gate 3 Acceptance Criteria

Check ✅ PASS ❌ FAIL Action on Fail
REQUIRED fields (action, user/src depending on model) Population ≥ 90% for each REQUIRED field Any REQUIRED field < 90% ⛔ STOP. Fix field alias or calculated field in TA local/props.conf. See Safe Add-on Tuning.
HIGH fields Population ≥ 50% for each HIGH field HIGH field < 50% Document gap. Detections needing this field have reduced effectiveness. Fix if possible; accept with risk if not.
No bogus values Field values are meaningful (not "unknown", "N/A", "0.0.0.0" everywhere) Most values are placeholders or garbage Field is technically populated but useless. Treat as ❌ FAIL. Investigate extraction logic.

Gate 4: Time Coverage

SPL: Check for Gaps in Data Flow (Time Continuity) 
`comment("SAFE: Read-only")`
`comment("Shows event volume per hour over the last 24 hours")`
`comment("Gaps (hours with 0 events) indicate data flow interruptions")`

| tstats count FROM datamodel=DATAMODEL_NAME
    WHERE sourcetype=YOUR_SOURCETYPE earliest=-24h latest=now
    BY _time span=1h
| timechart span=1h count
| eval status = if(count > 0, "✅ Data present", "❌ GAP — No events this hour")

Gate 4 Acceptance Criteria

Check ✅ PASS ❌ FAIL Action on Fail
Continuous data flow (24h) Every hour in the last 24h has events (or expected low-volume hours, e.g., overnight, are documented) Multiple consecutive hours with zero events Investigate. Could be: forwarder down, data source offline, ingestion pipeline issue. Fix before enabling time-sensitive detections.
Volume consistency Hourly volume is roughly consistent (no sudden 90%+ drops) Volume drops to near-zero and recovers Intermittent data flow. Detections during gaps will miss events. Document. May need infrastructure fix.

Gate 5: Detection-Specific Field Verification

This gate is unique to each detection. Before enabling a specific correlation search, verify that every field it references is populated in the data model.

Procedure: Verify Fields for a Specific Correlation Search 
`comment("Step 1: Read the correlation search SPL")`
`comment("Find the search in: Settings > Searches, Reports, Alerts")`
`comment("Or: | rest /services/saved/searches | search title='YOUR_SEARCH_NAME' | table search")`

`comment("Step 2: Identify EVERY field the SPL references")`
`comment("Look for fields in: WHERE clauses, BY clauses, eval, stats, rename")`
`comment("Example: | tstats count FROM datamodel=Authentication")`
`comment("  WHERE Authentication.action='failure'")`
`comment("  BY Authentication.user, Authentication.src")`
`comment("→ Fields needed: action, user, src")`

`comment("Step 3: For EACH field, verify it's populated:")`

| tstats dc(Authentication.user) AS user_values,
    dc(Authentication.src) AS src_values,
    dc(Authentication.action) AS action_values
    FROM datamodel=Authentication
    WHERE Authentication.action="failure" earliest=-4h latest=now

| eval user_ok = if(user_values > 0, "✅", "❌"),
    src_ok = if(src_values > 0, "✅", "❌"),
    action_ok = if(action_values > 0, "✅", "❌")
| eval gate5_result = if(user_ok="✅" AND src_ok="✅" AND action_ok="✅",
    "✅ ALL FIELDS PASS — Detection can be enabled",
    "❌ FIELD(S) MISSING — DO NOT enable this detection")
| table user_ok, src_ok, action_ok, gate5_result

Gate 5 Acceptance Criteria

Check ✅ PASS ❌ FAIL Action on Fail
All fields in the search SPL are populated Every field referenced in the correlation search has > 0 distinct values in the data model for the relevant time range Any field returns dc=0 ⛔ DO NOT enable this detection. Options: (1) Fix the missing field, (2) Modify the detection to work without it, (3) Defer the detection and document.
Filter values exist If the detection filters on a specific value (e.g., action="failure"), that value exists in the data Filter value doesn't exist (e.g., data has "fail" instead of "failure") Fix the CIM field mapping (e.g., EVAL-action to normalize to "failure"), or adjust the detection SPL.

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • Gate 1 fails and acceleration cannot be enabled. This may require Splunk licensing review, hardware resources, or architecture changes. Escalate to Splunk admin and Security Manager.
  • Gate 2 fails for a data source that was previously working. This is a regression. Something changed (TA upgrade, config change, data source change). Treat as a P1 incident for detection coverage.
  • Gate 3 shows REQUIRED fields below 50% population. This is not a minor gap — it's a fundamental CIM failure. The TA may be wrong, the data format may have changed, or the wrong TA is installed.
  • Gate 4 shows data gaps longer than 4 hours. This is an infrastructure issue. Data is not flowing reliably. Detections cannot be trusted.
  • Someone asks to skip validation and "just enable the detections." Escalate. Explain the risk. Document the request and your objection. This is a professional responsibility — enabling unvalidated detections creates false security reporting.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Validation takes too long — skip it for now"An unvalidated detection creates false confidence. The SOC reports coverage that doesn't exist. Auditors are misled.Validation takes 1-2 hours per data model. This is negligible compared to the weeks of false confidence an unvalidated detection creates.
"The search runs without errors, so it's working"A correlation search can run perfectly, return zero results, and that's a "successful" execution — it just found nothing. The question is whether it SHOULD have found something.Zero results is only acceptable after you've validated that data flows through all 6 layers. Without validation, zero results might mean the pipeline is broken.
"We validated last quarter — no need to check again"TAs get updated. Data sources change format. Acceleration silently fails. A quarterly-old validation may not reflect current state.Re-validate after every change event (upgrade, new source, config change) and quarterly as a standing check.
"Partial pass is good enough"Partial pass means some detections work and some don't. If you enable all detections, some will silently fail. You need to know WHICH ones work and WHICH don't.Enable only the detections whose specific fields are validated (Gate 5). Document and defer the rest.
"I'll validate after deployment and fix issues then"Post-deployment fixes are reactive. The gap between deployment and fix is a window where the SOC has false confidence.Validate first. Deploy only what passes. Fix what fails. Then deploy more.
