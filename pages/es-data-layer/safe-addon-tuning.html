Safe Add-on Tuning & Field Fixes

📋 Page Status: HARDENED — ES DATA LAYER

Last Audit: 2024-02 | Auditor: Detection Engineering Team

Purpose: Exact procedures for safely modifying Technology Add-ons to fix CIM field gaps. Covers how add-ons parse data, which files you can touch, which you cannot, how to test changes without breaking production, and how to roll back if something goes wrong. This is the "hands-on-keyboard" companion to Missing Fields After Add-ons.

Ownership: Detection Engineering (changes) + Platform Engineering (deployment to production)

Preconditions: You've identified a specific missing CIM field, you know the vendor field that should map to it (from Missing Fields), and you've chosen Fix 1, Fix 2, or Fix 2b as your approach.

🚨 Production Safety — Cardinal Rules
  1. NEVER modify files in a TA's default/ directory. Ever. For any reason. These are vendor-managed and overwritten on updates.
  2. ALL changes go in the TA's local/ directory. Create it if it doesn't exist.
  3. Test in a non-production environment first if one is available. If no test environment exists, test with minimal, reversible changes.
  4. Document every change before deploying: what, where, why, rollback plan.
  5. One change at a time. Deploy. Validate. Then proceed to the next change.

Splunk's configuration precedence: local/ overrides default/ for the same stanza and key. This means your local/ changes take effect without modifying the vendor's default files. If a key exists in both default/ and local/ for the same stanza, local/ wins.

Procedure: Adding a Field Alias (Fix 1)

When to Use

The vendor field exists with the correct value — it just has the wrong name. You need to create a CIM alias.

Step-by-Step

Step Action Detail
1 Confirm vendor field exists and has correct values index=X sourcetype=Y | head 20 | table vendor_field — verify it has the data you expect
2 Check for existing alias conflicts | rest /services/configs/conf-props | search title="YOUR_SOURCETYPE" | table FIELDALIAS* — make sure no other alias already maps to the same CIM field
3 Create or edit local/props.conf in the TA directory Navigate to $SPLUNK_HOME/etc/apps/TA-vendor-name/local/. Create the directory and file if they don't exist.
4 Add the field alias under the correct stanza See configuration example below
5 Restart Splunk (or wait for config reload on SHC) On a search head cluster, deploy via the deployer. On standalone, restart splunkd or use | debug refresh for search-time changes.
6 Validate the fix index=X sourcetype=Y | head 20 | table vendor_field, cim_field — both should now have values. Then re-run Gate 3 validation.
7 Document the change Record in change management: what was added, which file, which TA, why, rollback plan.
Configuration: local/props.conf — Field Alias Example 
# TA-vendor-name/local/props.conf
# 
# Purpose: Add CIM field alias for missing 'src' field
# Date: 2024-02-15
# Changed by: [analyst name]
# Reason: Validation Gate 3 failed — src field null. Vendor uses 'client_ip'.
# Rollback: Delete this stanza. Restart Splunk.
# Ticket: DET-1234

[your_sourcetype_name]
FIELDALIAS-cim_src = client_ip AS src
⚠️ Field Alias Gotchas
  • Stanza name must match exactly: The stanza [your_sourcetype_name] must match the sourcetype exactly as it appears in Splunk (case-sensitive).
  • Alias name must be unique: The -cim_src suffix in FIELDALIAS-cim_src must be unique within that stanza across all config files (default + local).
  • Multiple aliases for same CIM field: If you need to alias from different vendor fields (one sourcetype uses "client_ip", another uses "sourceIP"), use different alias names for each stanza.
  • Alias doesn't overwrite: If the CIM field already has a value from another alias, adding a second alias for the same CIM field creates a multivalued field. This is usually not what you want.

Procedure: Adding a Calculated Field (Fix 2)

When to Use

The vendor field exists but the value needs transformation — e.g., "permit" needs to become "allowed", or a numeric protocol needs to become a text name.

Configuration: local/props.conf — Calculated Field Examples 
# TA-vendor-name/local/props.conf
#
# Purpose: Normalize vendor-specific values to CIM standard values
# Date: 2024-02-15
# Changed by: [analyst name]
# Rollback: Delete these EVAL lines. Restart Splunk.

[your_sourcetype_name]

# Example 1: Normalize action values
# Vendor uses: permit, deny, drop, reset
# CIM expects: allowed, blocked
EVAL-action = case(action="permit" OR action="allow", "allowed", action="deny" OR action="drop" OR action="reset", "blocked", 1=1, action)

# Example 2: Normalize protocol numbers to text
# Vendor logs: proto=6, proto=17, proto=1
# CIM expects: transport=tcp, transport=udp, transport=icmp
EVAL-transport = case(proto="6" OR proto=6, "tcp", proto="17" OR proto=17, "udp", proto="1" OR proto=1, "icmp", isnotnull(proto), "other")

# Example 3: Derive app from Windows LogonType
EVAL-app = case(LogonType="2", "Interactive", LogonType="3", "Network", LogonType="4", "Batch", LogonType="5", "Service", LogonType="7", "Unlock", LogonType="8", "NetworkCleartext", LogonType="9", "NewCredentials", LogonType="10", "RemoteInteractive", LogonType="11", "CachedInteractive", isnotnull(LogonType), "LogonType_".LogonType)

# Example 4: Coalesce multiple possible source fields
EVAL-src = coalesce(client_ip, true_client_ip, source_ip, src_ip)
⚠️ Calculated Field Gotchas
  • EVAL-fieldname: the fieldname after the dash IS the output field. EVAL-action creates/overwrites the action field. If the TA's default/ already has an EVAL-action, your local/ version will override it completely.
  • Always include a catch-all in case(): The 1=1, action or isnotnull(x), "other" fallback prevents the field from becoming null for unexpected values.
  • Test with a variety of events: Your case() logic needs to handle all real-world values the vendor sends, not just the ones in the first 10 events you checked.
  • Performance consideration: Calculated fields run at search time for every event. Complex EVAL logic on high-volume sourcetypes adds search overhead. Keep it simple.

Procedure: Adding Missing Eventtypes & Tags (Fix 2b)

When to Use

CIM fields are mapped correctly, but events don't appear in the data model because the eventtype/tag chain is missing.

Configuration: local/eventtypes.conf — Add Event Classification 
# TA-vendor-name/local/eventtypes.conf
#
# Purpose: Classify events for data model inclusion
# Date: 2024-02-15
# Changed by: [analyst name]
# Rollback: Delete these stanzas. Restart Splunk.

# Example: Make a firewall sourcetype visible to Network_Traffic data model
[custom_vendor_firewall_traffic]
search = sourcetype="vendor:firewall:traffic"

# Example: Make auth logs visible to Authentication data model
[custom_vendor_auth_success]
search = sourcetype="vendor:auth" result="Success"

[custom_vendor_auth_failure]
search = sourcetype="vendor:auth" result="Failure"
Configuration: local/tags.conf — Assign Data Model Tags 
# TA-vendor-name/local/tags.conf
#
# Purpose: Tag events so data models include them
# Date: 2024-02-15
# Changed by: [analyst name]
# Rollback: Delete these stanzas. Restart Splunk.

# Network_Traffic requires BOTH 'network' AND 'communicate'
[eventtype=custom_vendor_firewall_traffic]
network = enabled
communicate = enabled

# Authentication requires 'authentication'
[eventtype=custom_vendor_auth_success]
authentication = enabled

[eventtype=custom_vendor_auth_failure]
authentication = enabled
🚨 Tag Precision Is Critical

The eventtype search constraint determines WHICH events get tagged. If the constraint is too broad, you'll tag events that don't belong in the data model (causing false positives). If too narrow, you'll miss events.

Always verify after adding tags:

  • | tstats count from datamodel=X WHERE sourcetype=Y — should show events now
  • Spot-check: index=X sourcetype=Y tag=authentication | head 5 — verify these are actually auth events

`comment("Captures current state for comparison")`

| tstats count AS dm_events FROM datamodel=YOUR_DM
    WHERE sourcetype=YOUR_SOURCETYPE earliest=-4h latest=now

| appendcols [
    index=YOUR_INDEX sourcetype=YOUR_SOURCETYPE earliest=-4h latest=now
    | head 1000

What NOT to Modify — Explicit List

🔴 Do Not Touch File Why What Breaks
Any file in default/ TA-vendor/default/* Overwritten on TA update. Changes silently lost. Your fix disappears. Production regresses. May not be noticed for weeks.
LINE_BREAKER props.conf Controls how raw data is split into events at INDEX TIME Changes how events are segmented. Can cause event merging or splitting. Affects ALL future data. Cannot be undone for already-indexed data.
SHOULD_LINEMERGE props.conf Controls whether Splunk merges adjacent lines into single events at INDEX TIME Same as LINE_BREAKER — affects event boundaries permanently.
TIME_FORMAT / TIME_PREFIX props.conf Controls timestamp parsing at INDEX TIME Wrong timestamps on all new events. Searches by time become unreliable. Cannot be fixed retroactively.
TRANSFORMS-* (index-time) props.conf + transforms.conf Index-time field extractions write to TSIDX Wrong fields permanently embedded in index. Requires re-indexing to fix.
Data model definitions Splunk_SA_CIM/default/data_models/ Managed by the CIM add-on. Defines data model schemas. Breaking schema breaks all tstats queries, all correlation searches, all ES dashboards.
Existing eventtype/tag DELETION eventtypes.conf / tags.conf Other searches, dashboards, and data model population may depend on them Removing an eventtype or tag can make existing data invisible to data models. Correlation searches silently fail.

TA Upgrade Safety — Protecting Your Local Changes

When a TA is upgraded, default/ files are replaced with the new version. Your local/ files are preserved. However, you must verify that your local/ customizations still work correctly with the new default/ behavior.

Step Action Why
Before upgrade 1. List all local/ customizations: find $SPLUNK_HOME/etc/apps/TA-vendor/local/ -type f
2. Copy the list to your change documentation
3. Run pre-change baseline validation SPL		 Know exactly what you've customized so you can verify post-upgrade
After upgrade 1. Check if new default/ includes fixes for any of your local/ workarounds
2. Run post-change validation for ALL affected sourcetypes
3. If new default/ conflicts with local/, resolve (usually by removing your local/ workaround if the vendor fixed it)		 New TA version may fix issues you worked around, or may introduce new conflicts

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • Your change causes errors in index=_internal. Revert immediately. Configuration syntax errors can cascade and affect other sourcetypes or apps.
  • Your change fixes one field but breaks another. Revert. Investigate the interaction. There may be a conflicting alias or EVAL in default/ that you're inadvertently overriding.
  • You need to modify index-time settings. STOP. These changes affect data ingestion and are irreversible. Escalate to Platform Engineering / Splunk admin.
  • You're unsure which stanza to use. Wrong stanza = change has no effect (best case) or applies to wrong sourcetype (worst case). Verify the exact sourcetype name: | metadata type=sourcetypes index=YOUR_INDEX | table sourcetype
  • More than 3 local/ changes are needed for a single sourcetype. This suggests the TA is fundamentally inadequate. Evaluate whether a different TA, a custom TA, or a different approach is warranted.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"I'll batch all my fixes into one deployment"If something breaks, you don't know which change caused it. Rollback is all-or-nothing.One change per deployment cycle. Validate after each. Then deploy the next.
"I'll skip the rollback plan — this is simple"Simple changes can have unexpected interactions. Without a rollback plan, you're scrambling under pressure.Write the rollback step BEFORE deploying. It takes 30 seconds. It saves hours of stress.
"I tested on 5 events, looks good — deploy"5 events may not cover all value variations. The 6th event variant may hit an unhandled case in your EVAL.Test against at least 100-1000 events, covering the full range of event subtypes for that sourcetype.
"I don't need to document this — it's obvious"In 6 months, nobody (including you) will remember why this local/ file exists. During a TA upgrade, it becomes a mystery.Comment every change in the config file: who, when, why, ticket number, rollback plan.
"The change works — no need to re-validate the data model"The field may be populated but the data model may not reflect it yet (acceleration needs to catch up). Or the tag chain may still be incomplete.After any field fix, re-run the full 5-gate validation for the affected data model and sourcetype.
