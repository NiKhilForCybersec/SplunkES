CIM Fundamentals for ES

📋 Page Status: HARDENED — ES DATA LAYER

Last Audit: 2024-02 | Auditor: Detection Engineering Team

Purpose: Practical guide to the Common Information Model (CIM) as it applies to Splunk ES. Not CIM theory — CIM practice. Which fields ES actually depends on, what "compliance" really means, why add-ons don't guarantee it, and how to assess your CIM status without breaking anything.

Ownership: Detection Engineering (assessment + gap identification)

Preconditions: You've read How ES Uses Data and understand the 6-layer pipeline.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: The Splunk CIM add-on (Splunk_SA_CIM) is installed. Verify: | rest /services/apps/local | search title="Splunk_SA_CIM" | table title, version. If missing, data models don't exist and nothing in ES works.
  • Assumption: You have partial CIM compliance. Some fields work, some don't. This is the expected state. Perfect CIM compliance is rare. This page teaches you how to assess what you have and what you need.
  • Assumption: You will NOT achieve 100% CIM compliance for all fields across all data sources. That's fine. The goal is to have the right fields for the detections you want to run — not theoretical completeness.

What CIM Actually Is — Practical Definition

The Common Information Model (CIM) is a set of field naming standards. That's it. It defines that no matter what device or vendor produced a log, certain types of information should be stored in standard field names. When a firewall log says srcip=10.1.2.3 and a Windows log says IpAddress=10.1.2.3, CIM says both should map to src=10.1.2.3.

CIM is implemented through three mechanisms in Splunk:

CIM Mechanism Where It Lives What It Does Example
Field Aliases props.conf in the TA Maps a vendor field name to a CIM field name at search time. The vendor field still exists; the CIM field becomes an alias. FIELDALIAS-src = srcip AS src — Now src returns the value of srcip
Calculated Fields props.conf in the TA Creates a new CIM field by evaluating an expression against existing fields. Used when the CIM field can't be a simple rename. EVAL-action = if(status="allow", "allowed", "blocked") — Derives the CIM action field from a vendor status field
Eventtypes + Tags eventtypes.conf + tags.conf in the TA Classifies events into categories that data models use as constraints. Without the right tags, events are invisible to data models even if CIM fields are present. Eventtype: cisco_asa_traffic → Tags: network, communicate — These tags match the Network_Traffic data model's constraint.
🚨 CIM Is Three Things — All Three Must Work

A common mistake is fixing only the field aliases and declaring CIM compliance. But without the correct eventtypes and tags, your data still won't appear in data models. All three mechanisms must be correctly configured:

  1. Fields: CIM field names are populated (via alias or calculated field)
  2. Eventtypes: Events are classified into named types
  3. Tags: Eventtypes have the correct tags that match data model constraints

Missing any one of these = events invisible to data models = detections silently fail.

Which CIM Fields ES Actually Depends On

The CIM defines hundreds of fields. ES does NOT use all of them. Here are the fields that matter for each major data model — split into "required for any detection to work" and "needed for enrichment but not blocking."

Level Definition Can You Enable Detections? Action
⛔ Level 0: None Data exists in Splunk but has no CIM tags. Data model doesn't see it. NO. Zero detections will work against this data via tstats. Fix tags first (Missing Fields). Or use raw-event-based detections only.
🟡 Level 1: Tagged Only Events appear in data model but CIM fields are null. tstats returns event counts but can't filter. NO. Detections that filter on fields (all useful detections) will fail. Fix CIM field mappings (Safe Add-on Tuning).
🟠 Level 2: Partial Some CIM fields populated, others null. Some detections work; others silently fail. ONLY for detections whose required fields are all populated. Must verify per-detection. Document which fields work. Enable only validated detections. Fix remaining fields as capacity allows.
🟢 Level 3: Core All REQUIRED fields populated. HIGH fields may be partial. Most detections work. YES — for most detections. Verify individual detections if they need specific HIGH fields. Standard operating state. Continue improving HIGH fields. Enable detections through lifecycle.
✅ Level 4: Full All REQUIRED and HIGH fields populated. All detections for this data model are supported. YES — unrestricted. Maintain through upgrades. Monitor for regression.

Common CIM Myths — Debunked

Myth Reality Impact of Believing the Myth
"Installing the TA gives me full CIM compliance" TAs vary enormously in CIM coverage. Some map 90% of CIM fields; others map 30%. Older TAs may not have been updated for current CIM versions. Some TAs are community-developed with inconsistent quality. You assume data is ready. You enable detections. They silently fail on unmapped fields. You report coverage that doesn't exist.
"CIM compliance is all-or-nothing" CIM compliance is a spectrum (Level 0–4 above). Partial compliance is the norm and is workable. You can run detections that only need the fields you have. Teams delay detection engineering indefinitely, waiting for "full CIM" that may never come. Or they give up and build everything as raw-event searches.
"I only need field aliases — tags don't matter" Tags are the mechanism that includes events in data models. Without correct tags, events with perfect CIM fields are invisible to tstats queries. Tags are equally as important as field aliases. You fix all the fields but data model still shows 0 events. Confusing and time-consuming to diagnose.
"The CIM add-on does the CIM mapping" The CIM add-on (Splunk_SA_CIM) defines the data model schemas — the structure. The actual field mapping is done by the Technology Add-ons (TAs) for each vendor/source. The CIM add-on doesn't know about your Palo Alto or Windows logs. You install Splunk_SA_CIM and expect CIM fields to appear. They don't. Because the CIM add-on provides the schema, not the mapping.
"CIM fields are the same across all Splunk versions" CIM evolves. New fields are added, some are deprecated. Field names occasionally change between CIM versions. The CIM version must match the TAs and ES version. A TA built for CIM 4.x may not properly map fields for CIM 5.x. Field aliases may point to wrong names after a CIM update.

How to Assess Your CIM Status (Safe Queries)

SPL: CIM Field Population Report for a Specific Sourcetype 
`comment("Replace INDEX and SOURCETYPE with your values")`
`comment("SAFE: Read-only query. Does not modify anything.")`
`comment("Shows which CIM fields are populated and what percentage")`

index=YOUR_INDEX sourcetype=YOUR_SOURCETYPE earliest=-4h latest=now
| head 2000
| eval has_action = if(isnotnull(action) AND action!="", 1, 0),
    has_user = if(isnotnull(user) AND user!="", 1, 0),
    has_src = if(isnotnull(src) AND src!="", 1, 0),
    has_dest = if(isnotnull(dest) AND dest!="", 1, 0),
    has_src_port = if(isnotnull(src_port) AND src_port!="", 1, 0),
    has_dest_port = if(isnotnull(dest_port) AND dest_port!="", 1, 0),
    has_app = if(isnotnull(app) AND app!="", 1, 0),
    has_transport = if(isnotnull(transport) AND transport!="", 1, 0),
    has_bytes_in = if(isnotnull(bytes_in) AND bytes_in!="", 1, 0),
    has_bytes_out = if(isnotnull(bytes_out) AND bytes_out!="", 1, 0),
    has_url = if(isnotnull(url) AND url!="", 1, 0),
    has_status = if(isnotnull(status) AND status!="", 1, 0),
    has_http_method = if(isnotnull(http_method) AND http_method!="", 1, 0)
| stats count AS total,
    avg(has_action) AS pct_action,
    avg(has_user) AS pct_user,
    avg(has_src) AS pct_src,
    avg(has_dest) AS pct_dest,
    avg(has_dest_port) AS pct_dest_port,
    avg(has_app) AS pct_app,
    avg(has_transport) AS pct_transport,
    avg(has_bytes_in) AS pct_bytes_in,
    avg(has_bytes_out) AS pct_bytes_out,
    avg(has_url) AS pct_url,
    avg(has_status) AS pct_status,
    avg(has_http_method) AS pct_http_method
| foreach pct_* [eval <> = round(<> * 100, 1) . "%"]
| table total, pct_action, pct_user, pct_src, pct_dest, pct_dest_port,
    pct_app, pct_transport, pct_bytes_in, pct_bytes_out,
    pct_url, pct_status, pct_http_method
SPL: Check Tag Assignment for a Sourcetype 
`comment("Shows what tags are assigned to events from this sourcetype")`
`comment("SAFE: Read-only. No modifications.")`
`comment("If no tags appear, events are invisible to data models.")`

index=YOUR_INDEX sourcetype=YOUR_SOURCETYPE earliest=-4h latest=now
| head 100
| eval tag_list = mvjoin(tag, ", ")
| eval eventtype_list = mvjoin(eventtype, ", ")
| stats dc(tag_list) AS unique_tag_combos,
    values(tag_list) AS tags_found,
    values(eventtype_list) AS eventtypes_found
| eval status = case(
    isnull(tags_found) OR tags_found="", "❌ NO TAGS — Events invisible to data models",
    match(tags_found, "authentication"), "✅ Auth tags present — Authentication DM",
    match(tags_found, "network.*communicate"), "✅ Network tags present — Network_Traffic DM",
    match(tags_found, "web"), "✅ Web tags present — Web DM",
    true(), "🟡 Tags found but may not match a standard data model — verify manually"
)
| table status, tags_found, eventtypes_found

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • A data source is at CIM Level 0 (no tags) and detections are expected against it. Tags must be fixed before any tstats-based detection can work. This is a hard prerequisite.
  • A critical CIM field (action, user, src) is null across all events for a key data source. This blocks the majority of detections for that source. Escalate as a data quality issue to be resolved before detection work.
  • The CIM add-on (Splunk_SA_CIM) version is mismatched with ES. This can cause data model schema inconsistencies. Verify version compatibility.
  • Someone reports "detection is working" but the data source is Level 0 or Level 1. The detection is either using raw search (not tstats) or it's actually returning zero results and nobody checked.
  • A TA upgrade changed CIM field mappings. After any TA upgrade, re-run the CIM field population report for affected sourcetypes. Regressions are common.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Wait for perfect CIM before any detection work" Perfect CIM may never come. You wait indefinitely while threats go undetected. Assess per-detection. If the fields for THIS detection are populated, enable it. Don't hold everything for theoretical completeness.
"CIM is the TA vendor's problem" TA vendors provide best-effort CIM mapping. They don't know your specific data format variants, index configurations, or ES requirements. Treat CIM validation as a Detection Engineering responsibility. Verify after every TA install. Fix gaps in local/ configs.
"Just add field aliases for everything" Field aliases without corresponding eventtypes/tags means data still doesn't appear in data models. You've done half the work. When fixing CIM gaps, always address all three: field aliases + eventtypes + tags. See Safe Add-on Tuning.
"Run the CIM Validator once and you're done" CIM status changes. TA upgrades, ES upgrades, new data sources, log format changes — all can break CIM compliance. Schedule quarterly CIM validation. Re-validate after every TA or ES upgrade.
"We'll fix CIM after we deploy detections" You deploy detections that silently fail. SOC thinks they're protected. Auditors think you have coverage. Reality: no alerts fire. CIM validation is a HARD GATE before detection enablement. See Validating ES Data.
