Section 1 — Why Data Models Exist (The ES Perspective)

To understand data models, start with the problem they solve.

The Performance Problem

Splunk stores events as raw text in indexes. When you run a search like index=firewall src=10.0.0.1, Splunk reads raw event data from disk, extracts fields, and evaluates your criteria — for every single event. This works fine for ad-hoc investigation, but it becomes a problem at scale.

Enterprise Security runs dozens of correlation searches continuously — every 5, 10, or 15 minutes — across potentially billions of events. If each correlation search had to scan raw events, the search heads would be overwhelmed. Searches would queue, dashboards would time out, and detections would fall behind real time.

Data models solve this by creating pre-computed summaries. Instead of scanning every raw event, ES queries a compact summary that already contains the fields it needs, organized for fast retrieval. This is called acceleration, and it is the primary reason data models exist in ES.

The Consistency Problem

A large enterprise might send authentication logs from 15 different sources — Active Directory, Azure AD, Okta, VPN concentrators, Linux PAM, web applications. Each source uses different field names:

SourceField for "Username"Field for "Source IP"
Windows SecurityTargetUserNameIpAddress
Azure ADuserPrincipalNameipAddress
Oktaactor.alternateIdclient.ipAddress
Linux PAMusersrc_ip

If you wrote a correlation search for "brute force login attempts," you would need separate logic for every source. Data models solve this by defining a single schema — the user is always user, the source IP is always src. Technology Add-ons (TAs) translate vendor-specific field names into these standard names at search time. The correlation search queries the data model and gets consistent fields regardless of the original source.

Why ES Dashboards and Correlation Searches Prefer Data Models

Most ES dashboards and out-of-the-box correlation searches are written as | tstats queries against data models. This is a deliberate design choice:

BenefitWhat It Means in Practice
Speed| tstats queries against accelerated data models return in seconds, even across weeks of data. The same query against raw indexes could take minutes.
ConsistencyThe query | tstats count from datamodel=Authentication WHERE Authentication.action="failure" by Authentication.user works regardless of whether the events came from AD, Okta, or VPN — as long as the TA maps fields correctly.
ScalabilityRunning 50 correlation searches every 5 minutes is only feasible with pre-computed summaries. Raw searches at that frequency would cripple the search heads.

Why Raw Search Still Matters — Especially Early On

⚠️ Important: Do Not Rush Into Data Models

Data models are powerful, but they are the last layer in a chain. If your events are not arriving (ingestion), not parsed (field extraction), or not CIM-mapped (normalization), then data models will be empty — and you will waste time troubleshooting the wrong layer.

During early project phases (onboarding, initial validation), raw index searches are your primary tool. You use them to verify that events exist, fields are extracted, and CIM mapping works. Only after those layers are healthy do you validate data models.

Think of data models as the roof of a house. You do not troubleshoot the roof before confirming the foundation (ingestion), walls (parsing), and plumbing (CIM mapping) are solid.

Section 2 — What a Data Model Actually Is (No Myths)

The Simple Definition

A data model is a structured definition that describes what events look like when they are normalized. It defines:

ComponentWhat It Is
A nameAn identifier like "Authentication," "Network_Traffic," or "Web." This is how queries reference the data model.
A set of fieldsThe expected field names (e.g., src, dest, user, action). These are the CIM field names.
A constraintA search filter that defines which events belong in this model. Typically tag-based (e.g., tag=authentication).
Datasets (child objects)Sub-categories within the model. For example, the Authentication model has sub-datasets for "Default_Authentication" and may distinguish between VPN, cloud, and host-based auth depending on tags.

The data model itself does not contain data. It is a definition — a template that says "if an event matches my constraint AND has the fields I expect, it belongs to me." The data stays in the index. The data model is a lens that looks at the index through a specific shape.

Data Models and CIM — The Relationship

People often confuse data models with CIM. They are related but different:

ConceptWhat It Is
CIMA naming standard. It says "the source IP should be called src." CIM is a dictionary — it defines the vocabulary.
Data ModelA structured view that uses CIM vocabulary. It says "Authentication events have fields src, user, action, and match the constraint tag=authentication." The data model is a sentence built from the dictionary.
TA (Add-on)The translator that converts vendor-specific fields into CIM vocabulary. Without a TA, your events may have a field called clientIP — but the data model needs it to be called src.

Fields Existing vs. Fields Being Modeled

This is where most confusion lives. Consider this scenario:

✓StateVisible to Data Model?
1Events exist in index=firewall.❌ Not yet. Events exist, but they are just raw events.
2A TA extracts vendor fields: srcAddr, dstAddr.❌ Not yet. Fields are extracted, but they are vendor-specific names, not CIM names.
3The TA maps CIM fields: src=srcAddr, dest=dstAddr.❌ Not yet. CIM fields exist, but the data model still cannot see these events.
4The TA assigns the correct eventtype and tags: tag=network, tag=communicate.✅ Now the Network_Traffic data model can see these events, because the constraint matches.
5Data model acceleration is enabled and current.✅ Now | tstats queries return these events quickly.

The critical insight: Having logs in Splunk does NOT mean the data model is populated. Having CIM fields does NOT mean the data model is populated. The data model only includes events that match its constraint — which is almost always a tag combination. The tags come from the TA.

Section 3 — Where Data Models Live in Splunk Cloud

Who Owns the Data Model Definitions?

In a standard ES deployment, data model definitions come from two sources:

SourceWhat It ProvidesExamples
Splunk_SA_CIM (CIM Add-on)The core CIM data model definitions. This is the "master list" of data models that ES uses.Authentication, Network_Traffic, Web, Endpoint, Change, Malware, Intrusion_Detection, etc.
ES App (SplunkEnterpriseSecuritySuite)Some additional data models and customizations specific to ES (e.g., Threat Intelligence, Risk).Threat_Intelligence, Risk, Notable, Identity

These definitions live in datamodels.conf files within these apps. In Splunk Cloud, these files are on the search head. You cannot edit them directly, but you can view their settings through the UI and REST API.

Where Acceleration Summaries Live

When a data model is accelerated, Splunk creates TSIDX summary files on the indexers. These are compact binary indexes that make | tstats fast. In Splunk Cloud:

AspectSplunk Cloud Reality
Storage locationTSIDX files live on the indexer tier. You cannot see them, access them, or manage their disk usage directly.
Build processSplunk Cloud manages the summarization schedule. When you enable acceleration, Splunk's internal scheduler builds summaries in the background.
Rebuild triggersSummaries rebuild automatically when: a TA is updated (field definitions change), the data model definition changes, or you click "Rebuild" in the UI.
MonitoringYou can view acceleration status, completion percentage, and time coverage through the UI (Settings → Data Models) or via | rest /services/admin/summarization.

What You Can Control

✅Action
✅Enable or disable acceleration for a specific data model (Settings → Data Models → Edit Acceleration).
✅Trigger a rebuild of acceleration summaries (Settings → Data Models → expand → Rebuild).
✅Set which indexes a data model searches (CIM Setup page: Apps → Manage Apps → Splunk Common Information Model → Set Up).
✅Adjust the acceleration time range (how far back summaries cover).
✅Install or update TAs that define the fields, eventtypes, and tags that feed data models (via SSAI).
✅View acceleration health via the UI or | rest queries.

What You Cannot Control

❌Action
❌Edit datamodels.conf on the indexers — you have no OS access. File a support ticket for advanced changes.
❌Tune parallelization or resource allocation for summarization — Splunk Cloud manages this infrastructure.
❌Access TSIDX files directly or manage their disk footprint.
❌Restart indexers to force re-evaluation. Splunk Cloud does not allow user-initiated restarts of indexer services.

Section 4 — When to Care About Data Models (Project Phases)

Data models are not relevant at every stage of a project. Trying to validate them too early wastes time. Ignoring them too late means broken detections. This table maps exactly when data models matter.

Project PhaseDM Relevant?What You Should Be Doing
Log Onboarding (Phase 1)⚠️ Not yetFocus on getting events into the correct index with a consistent sourcetype. Do not think about data models. Validate using index=<your_index> | stats count.
Parsing & Field Extraction⚠️ Not yetFocus on ensuring vendor fields are extracted correctly. Install the TA on the search head. Validate using fieldsummary. Data models are still downstream.
CIM Mapping⚠️ Getting closerVerify that CIM fields (src, dest, user, action) are populated. Verify that the TA assigns the correct eventtypes and tags. This is the prerequisite layer for data models.
ES Dashboards✅ YesES dashboards query data models. If dashboards show empty panels, check data model population first — then trace backward to CIM, parsing, and ingestion.
Correlation Searches✅ CriticalMost ES correlation searches use | tstats. If the data model is not populated and accelerated, correlation searches produce zero results — no detections fire, no notables are created.
RBA (Risk-Based Alerting)✅ CriticalRBA risk rules often use | tstats against data models to generate risk events. If data models are broken, the entire RBA pipeline produces nothing. (Note: the client is not using RBA yet — this is future state.)
💡 The Rule of Thumb

If you are not yet at the "ES dashboards" or "correlation searches" phase, you do not need to validate data models. Focus on the upstream layers first. Data models will not populate if the foundation is broken, and troubleshooting them will lead you back to parsing and CIM anyway.

Section 5 — How Data Models Get Populated

Data models do not magically fill up when you install ES. Each event must pass through a specific chain of transformations before the data model includes it.

The Four Requirements (All Must Be True)

#RequirementWho Provides ItWhat Happens If Missing
1CIM fields exist on the events at search timeA Technology Add-on (TA) installed on the search head. The TA defines FIELDALIAS, EVAL, and LOOKUP rules in props.conf.The data model definition references CIM fields. If those fields do not exist on the event, the event matches the constraint but has empty field values — useless for detection.
2Correct tags are assigned to events at search timeThe same TA. It defines eventtypes.conf (search filter → eventtype name) and tags.conf (eventtype name → tag values).The data model's constraint is typically tag-based (e.g., tag=authentication). Without the correct tags, the data model cannot find the events. This is the most common reason a data model is empty.
3The index is allowed in the data model's scopeCIM Setup page configuration (Apps → Manage Apps → Splunk CIM → Set Up). This controls which indexes each data model searches.If your events are in an index that the data model does not search, it will never find them. Common when new indexes are created without updating the CIM Setup.
4Acceleration is enabled and currentSettings → Data Models → Edit Acceleration. Splunk Cloud manages the summarization schedule.Without acceleration, | tstats still works (it falls back to scanning raw events), but it is much slower. Most ES correlation searches have time limits — if tstats is too slow without acceleration, correlation searches time out and produce no results.

The Role of Add-ons (TAs)

Technology Add-ons are the engine that powers data models. A good TA does three things for a specific sourcetype:

#WhatConfiguration FileExample
1Extracts vendor fieldsprops.conf → EXTRACT, REPORT, KV_MODEParses JSON and creates attackData.clientIP
2Maps CIM fieldsprops.conf → FIELDALIAS, EVAL, LOOKUPFIELDALIAS-src = attackData.clientIP AS src
3Assigns tagseventtypes.conf + tags.confeventtype=akamai_waf_attack → tags: web, attack

If the TA only does #1 (extracts fields) but not #2 (CIM mapping) or #3 (tags), the data model will NOT be populated. Many older or basic TAs do extraction only. Check before assuming.

Can You Use eval/rename Instead of a TA?

Yes — but with limitations. If no TA exists for your data source, you can create CIM fields manually:

MethodHowLimitation
Search-time evalAdd EVAL-src = clientIP in a custom props.conf stanza on the SH (deployed via SSAI).Creates CIM fields but does NOT create tags. You also need eventtypes.conf and tags.conf for data model population.
Search-time FIELDALIASAdd FIELDALIAS-src = clientIP AS src in props.conf.Same limitation — aliases fields but does not create tags.
Custom eventtypes + tagsCreate eventtypes.conf with a search filter and tags.conf with tag assignments. Deploy via a custom app through SSAI.This completes the chain, but requires careful testing to avoid tagging unrelated events.

Index-Time Parsing Is NOT Required

A common misconception is that data model population requires index-time field extraction. This is false. In Splunk Cloud, most parsing happens at search time (when you run a query). CIM fields, FIELDALIASes, EVALs, and tags are all search-time operations. The TA on the search head applies them dynamically.

What index-time parsing provides is the sourcetype and timestamp — these are set when the event enters Splunk (by the HEC token, the collector, or the forwarder). The TA's search-time rules key off the sourcetype to know which extraction rules to apply. So the sourcetype must be correct at ingest time, but the CIM field mapping does not need to happen at ingest time.

Section 6 — Safe Validation Workflow

📋 Safety Note

Every query in this section is read-only. Nothing enables, disables, rebuilds, or modifies anything. You are only looking.

Step 6.1 — Discover What Data Models Exist

Do NOT assume which data models are installed. Discover them:

| rest /services/datamodel/model splunk_server=local
| table title description acceleration eai:acl.app
| sort title

What this returns: Every data model installed on the search head, which app owns it, and whether acceleration is enabled. Record the exact title values — these are the names you will use in all subsequent queries.

⚠️ Do Not Guess Data Model Names

Data model names are case-sensitive and use underscores. It is Network_Traffic, not network_traffic or NetworkTraffic. Always discover the exact name from the REST query above before using it in | tstats.

Step 6.2 — Discover Your Sourcetypes and Indexes

Before checking data models, know what data you have:

| tstats count WHERE index=* earliest=-24h by index sourcetype
| sort -count
| head 30

Record the index/sourcetype combinations you want to validate against data models. These are your <your_index> and <your_sourcetype> values for the rest of this section.

Step 6.3 — Check If Your Events Populate a Specific Data Model

Pick a candidate data model (discovered in Step 6.1) and check if your sourcetype appears in it:

| tstats count FROM datamodel=<candidate_dm>
    WHERE (index=<your_index>) earliest=-4h
    by sourcetype
| sort -count
ResultMeaningNext Step
Your sourcetype appears, count > 0✅ Events are in the data model.Go to Step 6.4 to inspect what fields are available.
Empty / no results❌ Events are NOT in the data model.Go to Step 6.5 to diagnose why.
Other sourcetypes appear, but not yoursThe data model is working for other sources but not yours.Go to Step 6.5 — your sourcetype is missing tags or CIM mapping.

Step 6.4 — Inspect Available Fields in the Data Model

If Step 6.3 showed population, verify which fields are actually available:

| tstats count FROM datamodel=<candidate_dm>
    WHERE (index=<your_index> sourcetype=<your_sourcetype>) earliest=-1h
    by <candidate_dm>.src <candidate_dm>.dest <candidate_dm>.action
| head 10

Note: Field names in | tstats are prefixed with the data model name (e.g., Authentication.src, Network_Traffic.dest). Replace the field names above with fields relevant to the data model you are checking. Consult the Data Models Deep Dive for per-model field lists.

Step 6.5 — Diagnose Why a Data Model Is Empty

Work through this checklist in order. The first check that fails is where your problem is.

Check 1: Do raw events exist?

index=<your_index> sourcetype=<your_sourcetype> earliest=-1h
| stats count

If zero: No events in Splunk. This is an ingestion problem, not a data model problem. Fix ingestion first.

Check 2: Do CIM fields exist on the events?

index=<your_index> sourcetype=<your_sourcetype> earliest=-1h
| head 10
| table src dest user action http_method url status

If all columns are empty: No CIM mapping. The TA is either not installed, not targeting this sourcetype, or not providing CIM aliases. Go to Missing Fields After Add-ons.

Check 3: Are the correct tags assigned?

index=<your_index> sourcetype=<your_sourcetype> earliest=-1h
| head 10
| table sourcetype eventtype tag

If tag is empty: The TA does not define eventtypes or tags for this sourcetype. This is the most common reason data models are empty even when CIM fields exist. The TA needs eventtypes.conf and tags.conf entries.

If tags exist but the data model is still empty: The tags may not match what the data model expects. Compare the tags you see against the data model constraint. For example, the Authentication data model typically requires tag=authentication. If your events have tag=auth instead, the constraint does not match.

Check 4: Is your index in the data model's scope?

WHERE: Apps → Manage Apps → Splunk Common Information Model → Set Up.

Look for the data model you are targeting. Check the index constraint. If it says "All Indexes" or includes your index, the scope is correct. If it restricts to specific indexes that do not include yours, add your index.

Check 5: Is acceleration enabled and current?

| rest /services/admin/summarization splunk_server=local
| search title="*<candidate_dm>*"
| table title summary.complete summary.is_inprogress summary.earliest_time summary.latest_time
FieldWhat It MeansHealthy Value
summary.completeFraction of the acceleration time range that has been summarized.Close to 1.0 (100%).
summary.is_inprogressWhether summarization is currently running.0 (idle) or 1 (actively building — normal after changes).
summary.earliest_timeOldest time covered by the summary.Should match the configured acceleration range (e.g., -7d).
summary.latest_timeMost recent time covered by the summary.Should be within the last 1–2 hours.

If summary.complete is 0 or very low: Acceleration is either disabled, recently enabled (still building), or failing. Check Settings → Data Models in the UI for error messages.

Section 7 — Common Failure Modes

These are the patterns you will encounter repeatedly. Each one has a specific diagnostic path.

#FailureSymptomRoot CauseFix
F1 Fields exist but DM empty CIM fields populate in raw search (src, dest are visible). | tstats returns nothing. Tags are missing. The TA provides FIELDALIAS but no eventtypes.conf / tags.conf. The data model constraint cannot match the events. Update the TA to one that provides full CIM compliance (extraction + aliases + tags). Or create custom eventtypes/tags via a custom app on the SH (deployed via SSAI).
F2 DM exists but acceleration off | tstats is slow or times out. Correlation searches produce no results due to time limits. Acceleration was never enabled, was disabled for troubleshooting and not re-enabled, or was turned off by a Splunk update. Settings → Data Models → find the model → Edit Acceleration → check "Accelerate." Verify via | rest /services/admin/summarization.
F3 Sourcetype mismatch TA is installed. Events exist. But the TA's props.conf stanza targets a different sourcetype than what your events use. The HEC token or collector sends events with sourcetype akamai:siem, but the TA expects akamai_siem. The TA's rules never fire. Align the sourcetype — either change the HEC/collector to match the TA, or create a custom props.conf stanza for your actual sourcetype.
F4 Wrong event semantics Events appear in the data model, but with wrong values. For example, authentication events show action=allowed instead of action=success. The TA maps the field but does not normalize the values. CIM expects specific values (e.g., success, failure for authentication action). Add search-time EVAL in a custom props.conf stanza: EVAL-action = case(action=="allowed","success", action=="denied","failure"). Deploy via SSAI.
F5 Index not in DM scope Events have correct tags and CIM fields. | tstats with WHERE index=<your_index> returns nothing. | tstats without the index filter returns data from other indexes. The CIM Setup page restricts the data model to specific indexes that do not include yours. CIM Setup page → find the data model → add your index to the allowed list.
F6 Acceleration stale or failed summary.latest_time is hours or days behind. summary.complete is well below 1.0. Summarization failed due to resource constraints, a broken search in the DM definition, or a conflicting app. In Splunk Cloud, infrastructure issues may also cause stalls. Try "Rebuild" in the UI (Settings → Data Models → expand → Rebuild). If stale for > 24 hours, file a Splunk support ticket.
F7 TA installed on wrong tier TA is installed but no fields or tags appear. In Splunk Cloud, the TA must be on the search head for search-time extraction. If it was only deployed to indexers (via a previous admin or migration), its search-time rules do not execute on the SH. Install the TA on the SH via SSAI.
F8 Multiple TAs conflict Some events populate the data model, others do not. Inconsistent field values. Two TAs define overlapping extraction rules for the same sourcetype with different field mappings or tags. Identify conflicting TAs: | rest /services/configs/conf-props/<your_sourcetype> splunk_server=local | transpose. Remove or disable the incorrect one.

Section 8 — What NOT to Do in Splunk Cloud

🚨 These Actions Will Cause Problems in Splunk Cloud

Splunk Cloud is a managed platform. Several common troubleshooting actions from Splunk Enterprise documentation do not apply — or are actively harmful — in Cloud environments.

#Do NOT Do ThisWhy It Is DangerousWhat to Do Instead
1 Force-rebuild all data models at once Rebuilding all data models simultaneously consumes massive summarization resources. In Cloud, this can impact search performance for all users and trigger resource throttling by Splunk's infrastructure management. Rebuild one data model at a time. Start with the one you are actively troubleshooting. Wait for completion before rebuilding the next.
2 Enable correlation searches before verifying the data model If you enable a correlation search that queries a data model that is empty or misconfigured, it will either: (a) generate zero results silently (giving false confidence that no threats exist), or (b) generate false positives from partial data. Validate data model population (Section 6, Step 6.3) BEFORE enabling any correlation search that depends on it. Use the Data Model → Correlation page for the safe path.
3 Follow Splunk Enterprise CLI procedures Enterprise docs reference btool, splunk restart, editing conf files on the filesystem, and accessing indexer storage. None of these work in Splunk Cloud. Attempting them wastes time and creates confusion. Use the UI and | rest API equivalents documented throughout this handbook. For changes that require indexer-level conf edits, file a Splunk support ticket.
4 Assume data model names or structures Data model names are case-sensitive and version-dependent. Guessing datamodel=network_traffic instead of datamodel=Network_Traffic returns zero results and wastes troubleshooting time. Always discover data model names from | rest /services/datamodel/model (Step 6.1). Never hardcode names from memory or documentation examples.
5 Disable acceleration to "fix" a data model Disabling acceleration does not fix data model population — it only removes the pre-computed summaries. The root cause (missing tags, wrong sourcetype, index not in scope) remains. Meanwhile, all | tstats queries against that model become slow, potentially breaking correlation searches. Diagnose the root cause using the Section 6 workflow. Fix the upstream issue (tags, CIM mapping, index scope). Acceleration is the last thing to touch.
6 Install unvetted TAs via CLI or direct file upload Splunk Cloud requires apps to be installed via SSAI (Self-Service App Installation) or through Splunk support. Installing an unvetted app can break the search head, conflict with ES, or be rejected by Cloud's security controls. Check that the TA is Cloud-vetted (look for the "Cloud Compatible" badge on Splunkbase). Install via SSAI only.
7 Modify the CIM Setup page without understanding the impact Changing the index constraint on the CIM Setup page affects ALL users and ALL correlation searches that use that data model. Adding too many indexes inflates acceleration size and slows summarization. Removing indexes drops events from the data model without warning. Before modifying the CIM Setup page: document current settings, understand which indexes are included, and coordinate with the team. Add one index at a time and verify acceleration remains healthy.

When You Do NOT Need Data Models

Not every detection requires | tstats. You can write effective detections using raw index searches if:

The data volume is low enoughIf the source generates < 1,000 events/hour, a raw search completes in seconds. Acceleration overhead is not justified.
You need fields outside the data modelData models only contain CIM-mapped fields. If your detection logic depends on vendor-specific fields (e.g., ruleMessages from Akamai), you must use raw searches.
You are writing a custom correlation searchCustom searches can use | search or | from against raw indexes. Only convert to | tstats when the search needs to be fast at scale.
The data source is new and the TA does not provide tagsIt is better to write working raw searches now than to wait weeks for full data model compliance.
💡 The Goal

Data models are an optimization, not a requirement. The goal is working detections with accurate data. If raw searches achieve that today, use them. Migrate to | tstats when the data model layer is healthy and the performance benefit justifies the effort.
