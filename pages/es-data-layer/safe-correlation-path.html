From Data Model → Correlation Search (Safe Path)

📋 Page Status: HARDENED — ES DATA LAYER

Last Audit: 2024-02 | Auditor: Detection Engineering Team

Purpose: The complete safe path from a validated data model to a working correlation search. How to choose between data model–based and raw-event–based detections. How to prototype, backtest, transition to monitoring-only, and finally enable notables — all without breaking anything. Includes a worked example built clause-by-clause.

Ownership: Detection Engineering

Preconditions: You've passed all 5 gates in Validating ES Data. The data model is populated. Fields are confirmed. You are ready to build or enable a detection.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: You have completed the 5-gate validation for the target data model and sourcetypes. If not: Go back to Validating ES Data. This page assumes the data layer is ready.
  • Assumption: You will NOT go directly from "idea" to "enabled in production." Every detection follows the lifecycle: prototype → backtest → monitoring-only → production. There are no shortcuts.
  • Assumption: The client has zero tolerance for breaking production. Every step in this page is designed for maximum safety and minimum blast radius.

Approach SPL Pattern When to Use Advantages Disadvantages
Data Model (tstats) | tstats count FROM datamodel=X WHERE ... BY ... All fields needed are in the data model. DM is validated. This is the default choice. Fast (seconds). Low CPU. Scales to millions of events. Consistent with OOTB/ESCU content. Limited to fields in the data model. Requires acceleration. Silent failure if DM chain breaks.
Hybrid (tstats + search) | tstats ... FROM datamodel=X ... | search ... | eval ... Need DM fields for filtering but also need fields outside the model for enrichment or final evaluation. Gets speed of tstats for initial filter. Access to additional fields for context. More complex SPL. The | search step is slower for large result sets.
Raw Event (search) index=X sourcetype=Y ... | stats ... | where ... Data model not available. Need fields not in any model. Temporary while DM is being fixed. Access to all fields. No DM dependency. Works even with zero CIM compliance. Slower (minutes). Higher CPU. Doesn't scale well for large time ranges. Must specify index/sourcetype explicitly.

Step 1: Prototype — Write the SPL in Search Bar

Build your correlation search interactively in the Splunk search bar. Do NOT save it yet. This is your sandbox.

Prototyping Rule Why
Start with a short time range (1-4 hours)Faster feedback. Less resource impact. You'll expand later in backtesting.
Build clause by clauseRun after each addition. Verify the result makes sense. Don't write the whole search and then debug.
Check result counts at each stageIf a WHERE clause drops results to zero, investigate immediately. Is the filter wrong, or is the data wrong?
Verify field values, not just countsUse | table and | stats values(field) to see actual values. Ensure they make sense.
Don't optimize yetGet the logic right first. Performance tuning comes later.

Step 2: Backtest — Run Against Historical Data

Procedure: Backtesting a Correlation Search 
`comment("Step 1: Run the prototype SPL over 7 days")`
`comment("Change earliest=-7d latest=now in the time picker")`
`comment("Observe: How many results? Are they all true positives?")`

`comment("Step 2: Assess volume")`
YOUR_CORRELATION_SPL earliest=-7d latest=now
| stats count
`comment("If count > 100 per day → threshold too low or needs tuning")`
`comment("If count = 0 → either no matching events (good?) or detection is broken (bad)")`

`comment("Step 3: Assess accuracy — sample results")`
YOUR_CORRELATION_SPL earliest=-7d latest=now
| head 20
| table _time, user, src, dest, action, count
`comment("Manually review: Are these real security events or noise?")`

`comment("Step 4: Check for known false positive patterns")`
YOUR_CORRELATION_SPL earliest=-7d latest=now
| stats count BY user
| sort - count
| head 10
`comment("If one user dominates, it may be a service account or scanner")`

`comment("Step 5: Estimate daily notable volume")`
YOUR_CORRELATION_SPL earliest=-7d latest=now
| bucket _time span=1d
| stats count BY _time
| stats avg(count) AS avg_daily, max(count) AS max_daily, min(count) AS min_daily

Backtest Acceptance Criteria

Metric ✅ Acceptable 🟡 Needs Tuning ❌ Do Not Enable
Daily notable volume 0-10 per day (manageable for SOC) 10-50 per day (needs tuning or more specific filters) >50 per day (will flood SOC, noise > signal)
True positive rate (sampled) >70% of sampled results are genuine security events 30-70% true positive (needs filter refinement) <30% (detection is mostly noise)
Consistent across days Roughly similar volume each day (± 50%) Spiky — some days 0, some days 100 Triggered by a single event or batch job causing mass alerts

Step 3: Monitoring-Only — Schedule Without Notables

Save the search as a scheduled search but do NOT add the notable event action. This lets you observe what the search produces in production without affecting the SOC.

Step Action Detail
1 Save the search Settings → Searches, Reports, Alerts → New Alert. Name with prefix: MONITORING - [Detection Name]
2 Set schedule Match what the production schedule would be (e.g., every 5 minutes, every 15 minutes). Use the same cron as the eventual production search.
3 Set time range Match the production lookback window. If the production search will look at the last 15 minutes, set earliest=-16m latest=-1m (the 1-minute offset avoids edge-second timing issues).
4 Do NOT add notable action Leave alert actions empty. The search runs and discards results. You can check results via the job inspector or by examining the search scheduler logs.
5 Monitor for 3-7 days Check: index=_internal sourcetype=scheduler savedsearch_name="MONITORING*" | stats count BY savedsearch_name, status
6 Review results Verify the search runs without errors, returns expected volume, completes in reasonable time (< 60 seconds for tstats, < 300 seconds for raw).
SPL: Check Monitoring-Only Search Performance 
`comment("SAFE: Read-only")`
`comment("Shows how your monitoring search is performing")`

index=_internal sourcetype=scheduler savedsearch_name="MONITORING*"
    earliest=-7d latest=now
| stats count AS runs,
    avg(run_time) AS avg_runtime_sec,
    max(run_time) AS max_runtime_sec,
    sum(result_count) AS total_results,
    avg(result_count) AS avg_results_per_run
    BY savedsearch_name, status
| eval avg_runtime_sec = round(avg_runtime_sec, 1)
| eval avg_results_per_run = round(avg_results_per_run, 1)
| table savedsearch_name, status, runs, avg_runtime_sec, max_runtime_sec, total_results, avg_results_per_run

Step 4: Enable Notables — Production Activation

Step Action Detail
1 Clone the monitoring search or create the production version Rename: CUSTOM - [Detection Name] - [Org] Tuned. Disable the MONITORING version.
2 Add the Notable Event action Configure: Title, Description, Severity, Security Domain, Default Owner, Default Status. See Enablement Mechanics for field-by-field guidance.
3 Set initial severity conservatively Start at Medium unless the detection is confirmed high-fidelity (very low false positive rate). You can increase later.
4 Notify the SOC Tell the SOC team: new detection enabled, what it detects, expected daily volume, recommended triage steps.
5 Monitor first 48 hours closely Check Incident Review for the new notables. Verify volume matches backtest expectations. Address any unexpected noise immediately.

Worked Example: Building a Brute Force Detection (Clause by Clause)

This example walks through building a real correlation search from scratch, using the Authentication data model. Each clause is explained.

Detection Goal

Detect when a single source IP generates more than 10 failed authentication attempts against any user within a 15-minute window.

Prerequisites Verified

Gate Status Detail
Gate 1: Acceleration✅ PASSAuthentication model accelerated, 99% complete
Gate 2: Population✅ PASSWinEventLog:Security and azure:aad:signin both contributing
Gate 3: Fields✅ PASSaction=98%, user=97%, src=95%
Gate 4: Time✅ PASS24h continuous, no gaps
Gate 5: Detection✅ PASSaction, user, src all populated for "failure" events

Building the SPL — Clause by Clause

Clause 1: Query the data model 
`comment("Start with the tstats base query")`
`comment("This queries the accelerated Authentication data model")`
`comment("'summariesonly=true' means ONLY use acceleration (fastest, but returns nothing if accel is off)")`
`comment("We use summariesonly=true because we've already validated acceleration in Gate 1")`

| tstats summariesonly=true count
Clause 2: Specify the data model and filter 
`comment("FROM = which data model to query")`
`comment("WHERE = filter conditions")`
`comment("Authentication.action='failure' → only failed login attempts")`

| tstats summariesonly=true count
    FROM datamodel=Authentication
    WHERE Authentication.action="failure"
        earliest=-15m latest=now
Clause 3: Group results by source and target 
`comment("BY = group results. We want to count per source IP and per user.")`
`comment("This gives us: for each (src, user) pair, how many failures in 15 min?")`

| tstats summariesonly=true count
    FROM datamodel=Authentication
    WHERE Authentication.action="failure"
        earliest=-15m latest=now
    BY Authentication.src, Authentication.user, Authentication.dest
Clause 4: Clean up field names 
`comment("Rename data model field paths to simple names")`
`comment("This makes the output readable and the WHERE clause simpler")`

| tstats summariesonly=true count
    FROM datamodel=Authentication
    WHERE Authentication.action="failure"
        earliest=-15m latest=now
    BY Authentication.src, Authentication.user, Authentication.dest
| rename Authentication.src AS src, Authentication.user AS user, Authentication.dest AS dest
Clause 5: Apply the threshold 
`comment("Filter to only show results above the threshold")`
`comment("'where count > 10' → more than 10 failures from this src to this user")`
`comment("This is the detection condition")`

| tstats summariesonly=true count
    FROM datamodel=Authentication
    WHERE Authentication.action="failure"
        earliest=-15m latest=now
    BY Authentication.src, Authentication.user, Authentication.dest
| rename Authentication.src AS src, Authentication.user AS user, Authentication.dest AS dest
| where count > 10
Clause 6 (Final): Count distinct users per source (advanced variant) 
`comment("ADVANCED: Instead of per-user threshold, detect a single source")`
`comment("attacking MULTIPLE users (credential stuffing / password spraying)")`
`comment("dc(user) = distinct count of users targeted by each source IP")`

| tstats summariesonly=true count AS failure_count,
    dc(Authentication.user) AS targeted_users
    FROM datamodel=Authentication
    WHERE Authentication.action="failure"
        earliest=-15m latest=now
    BY Authentication.src
| rename Authentication.src AS src
| where failure_count > 10 AND targeted_users > 3
| eval description = src . " generated " . failure_count . " failed logins against " . targeted_users . " unique users in 15 minutes"

What Each Part Does — Summary

SPL Element Purpose What Happens If Wrong
| tstats summariesonly=trueQuery acceleration only (fastest mode)If acceleration is off, returns zero. Use summariesonly=false to fall back to raw (slower).
countCount matching events—
FROM datamodel=AuthenticationSpecify which data modelWrong model name → error. Non-accelerated model → zero results.
WHERE Authentication.action="failure"Filter to failed logins onlyIf action values don't match (e.g., data has "failed" not "failure"), filter returns zero. Check actual values.
earliest=-15m latest=now15-minute lookback windowMust match the search schedule. If search runs every 5 min with -15m lookback, some events are counted multiple times (overlapping windows).
BY Authentication.srcGroup by source IPIf src is null for some events, those events are grouped into a single "null" bucket — creating false aggregation.
| where count > 10Threshold — minimum failures to triggerToo low → noise. Too high → misses real attacks. Start conservative (higher), tune down based on backtest.

Failure Scenarios — What Can Go Wrong

Failure Symptom Root Cause Prevention Recovery
Detection never fires Zero notables. Scheduler shows "completed" with 0 results. Data model empty, acceleration off, wrong field values in WHERE, or threshold too high. Complete 5-gate validation. Backtest before enabling. Run the SPL ad-hoc over 7 days. If zero results, walk through the tstats diagnostic checklist.
Detection floods SOC Hundreds of notables per day. SOC overwhelmed. Threshold too low. Service accounts triggering. Scanner traffic. Batch jobs. Backtest with 7-day data. Check top contributors (stats count BY user). Raise threshold immediately. Add known-good exclusions (service accounts, scanner IPs). See Tuning & Noise Reduction.
Detection fires on stale data Notables appear for events that happened hours ago. Data ingestion delay. Events arrive in Splunk late. Acceleration backlog. Gate 4 time coverage check. Understand data latency for each source. Adjust lookback window to account for ingestion delay (earliest=-20m latest=-5m instead of earliest=-15m latest=now).
Detection search skipped Scheduler log shows "skipped" status. Search concurrency limit reached. Too many searches running simultaneously. Monitor scheduler health: index=_internal sourcetype=scheduler status=skipped Stagger search schedules. Escalate to Splunk admin if persistent. May need more search slots.
Detection logic correct but notable action missing Search runs, returns results (visible in scheduler log), but nothing in Incident Review. Notable Event adaptive response action not configured on the saved search. Verify notable action is configured before declaring production. Edit search → Trigger Actions → Add Notable Event action. Configure fields. See Enablement Mechanics.
Detection works but can't be triaged Notables appear but SOC analysts can't investigate (no drill-down, no context). Notable title/description don't include relevant fields. No drill-down search configured. Include key fields in notable description template: $result.src$, $result.user$, $result.count$. Edit notable action → update description and drill-down with field tokens.

Hybrid Example: tstats + Raw Enrichment

SPL: Hybrid — tstats for Speed, Raw Search for Context 
`comment("Use case: Detect failed auth brute force AND check if the source IP")`
`comment("has a specific user_agent (a field NOT in the Authentication data model)")`

`comment("PHASE 1: Fast filter using tstats (data model)")`
| tstats summariesonly=true count AS failure_count
    FROM datamodel=Authentication
    WHERE Authentication.action="failure"
        earliest=-15m latest=now
    BY Authentication.src
| rename Authentication.src AS src
| where failure_count > 10

`comment("PHASE 2: Enrich with raw event data for additional fields")`
| map search="search index=proxy sourcetype=bluecoat src=$src$ earliest=-15m latest=now
    | stats values(http_user_agent) AS user_agents BY src"

`comment("PHASE 3: Final evaluation with enriched data")`
| where isnotnull(user_agents)
| eval suspicious_ua = if(match(user_agents, "python|curl|wget|scanner"), "YES", "NO")
⚠️ Hybrid Approach — Performance Consideration

The | map command runs a subsearch for each result from Phase 1. If Phase 1 returns 100 source IPs, that's 100 subsearches. Keep Phase 1 results small (tight thresholds) to avoid performance impact. Alternative: use a lookup table for enrichment instead of live raw search.

summariesonly — When to Use True vs False

Setting Behavior When to Use Risk
summariesonly=true Queries ONLY the acceleration summary (TSIDX). If acceleration is off or behind, returns zero. Production correlation searches where you've validated acceleration (Gate 1 PASS). Silent zero results if acceleration breaks. You must monitor acceleration health.
summariesonly=false Queries acceleration if available, falls back to raw events if not. Slower but more resilient. Prototyping. Non-critical detections. Environments where acceleration stability is uncertain. Slower. Higher resource consumption. May miss the data if CIM/tags aren't configured (falls back to raw but still filtered by DM constraints).

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • Backtest shows > 50 results per day. Do not enable. The SOC cannot absorb this volume. Tune the detection first (raise threshold, add exclusions, narrow scope).
  • Backtest shows 0 results over 7 days and you expected results. The data model chain is broken somewhere. Re-run the 5-gate validation before investigating detection logic.
  • Monitoring-only phase reveals search run times > 300 seconds. The search is too expensive. Optimize the SPL, use a different approach (tstats vs raw), or reduce the time range.
  • Search scheduler shows frequent skips. The Splunk instance is overloaded. Adding more searches makes it worse. Escalate to Splunk admin for capacity planning.
  • Someone asks to skip monitoring-only and go directly to production notables. Push back. The monitoring phase catches problems BEFORE the SOC is affected. 3-7 days of monitoring is cheap insurance.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Copy the SPL from a blog post and enable it"Blog SPL is generic. Your environment has different field names, different values, different noise profile. It won't work as-is.Use blog posts as starting points. Adapt to your data. Validate against YOUR data model. Backtest in YOUR environment.
"I'll set the threshold really low to catch everything"Low thresholds = high volume = SOC fatigue = real alerts ignored = detection is effectively useless.Start with a HIGHER threshold. It's better to miss some edge cases and catch obvious attacks than to drown the SOC in noise.
"The search works, so I'll enable it on 20 data sources at once"Each data source has different noise profiles. What works for Windows auth may flood on Azure AD auth. Bulk enablement = mass noise.Enable per data source. Backtest each. Tune each. Gradually expand coverage.
"summariesonly=false is safer — I'll use it in production"False gives you a fallback to raw search, but it's MUCH slower. In production, this can cause search skips due to long run times.Use summariesonly=true in production after validating acceleration. Monitor acceleration health as part of ongoing operations.
"I built 10 detections — let me enable all of them this week"10 new detections simultaneously = unpredictable SOC impact. You can't tell which detection is causing noise. Can't tune individually.Enable 2-3 per week maximum. Monitor each for a few days. Tune. Then add more. See ESCU rate limiting.
