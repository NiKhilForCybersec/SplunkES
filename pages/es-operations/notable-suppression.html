Notable Suppression & Noise Operations

📋 Page Status: HARDENED — ES OPERATIONS

Last Audit: 2024-02 | Auditor: Detection Engineering Team

Purpose: Defines when, how, and why to suppress notable events. Covers short-term and long-term strategies, per-entity vs global suppression, audit trail requirements, and the critical risks of suppression misuse.

Ownership: Detection Engineering (suppression rules) + SOC Lead (approval)

Preconditions: Notables exist in Incident Review. The detection generating noise has been evaluated per the Tuning Hierarchy. Suppression is being used as a safety valve, not the first response.

🚨 CRITICAL: Suppression Is NOT Tuning

Suppression hides notables. It does NOT fix the detection.

  • The correlation search still runs and consumes concurrency
  • Notable events are still created and stored in the notable index
  • They are just hidden from Incident Review — invisible to analysts
  • If the suppressed entity is compromised, the attack notables are also hidden

Use suppression only as a temporary bridge while the underlying detection is being tuned. Every suppression rule must have an expiration or review date.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: You have the edit_notable_events capability. Verify: Try to suppress a notable from Incident Review. If the option is missing, check your role.
  • Assumption: The Tuning Hierarchy has been evaluated (data quality → logic → threshold → throttle). Risk if wrong: Suppression masks a fixable root cause. See Tuning & Noise Reduction.
  • Assumption: There is a ticketing system to track suppression rules. Risk if wrong: Suppressions accumulate with no review, creating permanent blind spots.

Per-Entity vs. Global Suppression

Strategy What It Does When to Use Risk Example
Per-Entity Suppression Hides notables matching specific field values (e.g., src=10.5.1.1) A specific, identified source is generating known FPs. The detection is otherwise healthy. 🟡 Medium — Blind spot for this specific entity only. If entity is compromised, you miss it. Suppress WAF alerts from src=203.0.113.50 (Qualys scanner) on "CUSTOM - WAF SQLi Burst"
Multi-Field Suppression Hides notables matching a combination of fields (e.g., src=X AND dest=Y) FP only occurs for a specific source-destination pair. Other combinations are valid. 🟢 Lower — Narrow scope reduces blind spot size. Suppress brute force from src=10.1.1.100 AND dest=10.2.2.200 (monitoring server → SIEM)
Global Suppression (by search name) Hides ALL notables from a specific correlation search Almost NEVER. Only valid during emergency storm cleanup while detection is disabled and being fixed. 🔴 Extreme — Equivalent to disabling the detection but worse: it still runs, still consumes resources, and nobody sees the results. Do NOT use. Disable the search instead.
🚨 Never Use Global Suppression as a Noise Fix

If a detection is so noisy that you want to suppress ALL its notables, disable the detection instead. Disabling stops the search from running (saving concurrency). Global suppression leaves the search running and burning resources while hiding every result. It's the worst of both worlds.

Creating a Suppression Rule — Exact Steps

Method 1: From Incident Review (Recommended)

  1. In Incident Review, click on the notable you want to use as the suppression template
  2. In the notable detail pane, click the Actions dropdown
  3. Select Suppress Notable Events
  4. The suppression form opens pre-populated with the notable's fields:
    • Suppression Name: Give it a descriptive name following format: SUPP - [Detection] - [Entity] - [Reason]
    • Description: Explain WHY this suppression exists. Include ticket number.
    • Expiration: Set an expiration date. For short-term: 7 days. For long-term: leave blank but set quarterly review.
    • Suppression Fields: Select which field values to match. Narrower = safer.
  5. Review the field selections. Remove any fields that are too broad (e.g., don't suppress by search_name alone)
  6. Click Save

Method 2: From Configure → Notable Event Suppressions

  1. Navigate to Enterprise Security → Configure → Content → Content Management
  2. Filter by Type: Notable Event Suppression
  3. Click Create New Suppression
  4. Fill in:
    • Name: SUPP - [Detection] - [Entity] - [Reason]
    • Search: The filter criteria, e.g., search_name="CUSTOM - Brute Force" src="10.5.1.1"
    • Expiration: Date/time when suppression auto-expires
    • Description: Full documentation (who, why, ticket #, review date)
  5. Click Save

Suppression Audit Queries

SPL: List All Active Notable Suppressions 
`comment("Audit all active suppressions — run monthly minimum")`
`comment("Any suppression without documentation or expired review date = risk")`

| rest /services/notable_event_suppressions splunk_server=local
| eval created = strftime(updated, "%Y-%m-%d")
| eval expiry = if(isnotnull(expiration), strftime(expiration, "%Y-%m-%d"), "NO EXPIRY ⚠️")
| eval age_days = round((now() - updated) / 86400, 0)
| eval risk = case(
    isnull(expiration) AND age_days > 90, "🔴 HIGH — No expiry, 90+ days old",
    isnull(expiration), "🟡 MEDIUM — No expiry set",
    expiration < now(), "🔴 EXPIRED — Should have been reviewed/removed",
    age_days > 30, "🟡 REVIEW — 30+ days old",
    true(), "🟢 Current"
)
| table title, description, search, created, expiry, age_days, risk
| sort - age_days
SPL: Count Notables Hidden by Each Suppression (Last 30 Days) 
`comment("Shows how many notables each suppression is hiding")`
`comment("High counts on stale suppressions = large blind spots")`

`notable`
| search is_suppressed=1
| stats count AS suppressed_count,
    dc(src) AS unique_sources,
    dc(user) AS unique_users
    BY suppression_name, search_name
| sort - suppressed_count
| table suppression_name, search_name, suppressed_count, unique_sources, unique_users
SPL: Detect Suppressions Without Documentation 
`comment("Find suppressions with empty or minimal descriptions — audit risk")`

| rest /services/notable_event_suppressions splunk_server=local
| where isnull(description) OR len(description) < 20
| table title, description, search, updated
| eval issue = "Missing documentation — who created this and why?"

Failure Modes

Failure Mode Symptom Root Cause Impact Fix
Suppression too broad Legitimate notables for other entities from the same detection are also hidden Suppression matches on search_name only, without entity-specific fields Complete blind spot for the entire detection — equivalent to disabling it Add entity-specific fields to the suppression filter. Never suppress by search_name alone.
Stale suppression (never reviewed) Suppression created 6+ months ago with no review date, no ticket, no documentation No lifecycle process. Nobody tracked it. Permanent blind spot. If the entity is compromised, attack notables are hidden forever. Audit all suppressions monthly. Add expiration or review dates to every rule.
Suppression hides a real attack Post-incident review reveals notables existed but were suppressed Entity was suppressed as "known benign" but was then compromised Missed detection. Incident response delayed. Audit finding. Quarterly review of all long-term suppressions. Verify entity is still benign.
Suppression count creep 30+ active suppression rules. Nobody knows what they all do. Suppressions created as quick fixes and never cleaned up Complex web of blind spots. Audit nightmare. Impossible to understand actual detection coverage. Target: <15 active suppressions. Each must have documentation + review date. Audit quarterly.
Suppression doesn't work Suppression rule exists but notables still appear in Incident Review Field names in suppression don't match notable field names. Typo in value. Case sensitivity mismatch. SOC still sees noise. Suppression provides false sense of "handled". Test suppression: verify the notable fields match EXACTLY. Use is_suppressed field to verify.
Short-term becomes permanent "Temporary" suppression still active 6 months later. Tuning ticket was never completed. No follow-up process. Ticket closed without removing suppression. Intended 7-day bridge becomes permanent blind spot. Suppression removal must be part of the tuning ticket completion criteria. Verify removal at ticket close.

SPL: Suppression Health Score 
`comment("Overall suppression hygiene assessment")`

| rest /services/notable_event_suppressions splunk_server=local
| stats count AS total_suppressions,
    sum(case(isnull(expiration), 1, 0)) AS no_expiry,
    sum(case(len(description) < 20 OR isnull(description), 1, 0)) AS no_docs,

    stale_90d > 0, "🟡 REVIEW — Stale suppressions found",
    true(), "🟢 Healthy"
)
| table total_suppressions, no_expiry, no_docs, stale_90d, health

Rollback Steps

Removing a Suppression

  1. Navigate to Enterprise Security → Configure → Content → Content Management
  2. Filter by Type: Notable Event Suppression
  3. Find the suppression by name
  4. Click the suppression → Click Delete (or Disable if you want to preserve the rule for reference)
  5. Verify: In Incident Review, the previously suppressed notables should now appear (for new events going forward; historical suppressed events may remain hidden)
  6. Update your suppression registry and close the tracking ticket
⚠️ Removing a Suppression May Cause a Burst

If the underlying noise was never fixed, removing the suppression will immediately expose the SOC to all the notables that were previously hidden. Always verify the root cause was fixed BEFORE removing the suppression.

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • Total active suppressions exceed 25. Suppression sprawl is out of control. Freeze new suppressions. Audit and remove stale ones first.
  • A suppression has been "short-term" for more than 30 days. The tuning fix is overdue. Escalate the tuning ticket. Remove the suppression and disable the detection if the fix can't be completed within 1 week.
  • Post-incident investigation reveals a suppression hid attack evidence. Document the finding. Review ALL suppressions immediately. Report to security management.
  • An auditor asks about suppressions and you can't explain what they all do. Immediate audit of all suppressions. Document every rule. Remove any that can't be justified.
  • Someone creates a global suppression (by search_name only). Revoke immediately. Disable the detection instead. This is a process violation.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Suppress instead of tune" Suppression doesn't fix the detection. The search still runs, still uses concurrency, still generates hidden notables. The problem grows silently. Always attempt tuning first (data quality → logic → threshold → throttle). Suppress only as a bridge.
"I'll remove it later" "Later" becomes never. Temporary suppressions become permanent blind spots. Set expiration on every short-term suppression. Tie removal to the tuning ticket close criteria.
"Suppress entire detection" Global suppression = disabling the detection with extra steps and extra resource waste. If the whole detection is noisy, DISABLE it. Tune offline. Re-enable through lifecycle.
"No need to document" In 3 months, nobody will know why this suppression exists, who created it, or whether it's still needed. Every suppression gets a name, description, ticket, creator, reason, and review date. No exceptions.
"SOC can just suppress whatever is noisy" Uncontrolled suppression creation leads to sprawl. Each analyst adds their own, nobody tracks the total. Coverage gaps multiply. Only Detection Engineering creates suppression rules. SOC requests suppression via ticket. SOC Lead approves long-term.
