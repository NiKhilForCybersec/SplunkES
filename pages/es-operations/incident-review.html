⚠️ Assumptions — Verify Before Proceeding
  • Assumption: Incident Review dashboard is accessible at Enterprise Security → Incident Review. Verify: Navigate there. If missing, the ES app may not be installed or the user role lacks permissions.
  • Assumption: Notable events exist. Verify: Run `notable` | head 5. If empty, no detections are firing — see Enablement Mechanics.
  • Assumption: The analyst can change notable status and add comments. Verify: Open a notable, attempt to change status. If greyed out, check role capabilities: edit_notable_events.
  • Assumption: Asset and identity lookups are populated. Risk if wrong: Notables will lack enrichment (no asset criticality, no user department). See Health & Performance.

  1. Open Splunk Web → Select the Enterprise Security app from the app menu (top-left)
  2. In the ES menu bar, click Incident Review (or navigate: Security Intelligence → Incident Review)
  3. The dashboard loads with the default filter: last 24 hours, all severities, status = New or In Progress

Step-by-Step: Claiming & Working a Notable

Step Action Exact UI Navigation Why This Matters
1. Claim Assign to yourself Click notable row → In detail pane, click Edit (or the pencil icon) → Set Owner to your username → Set Status to In Progress → Click Save Prevents other analysts from duplicating work. Creates ownership audit trail.
2. Read Fields Assess the notable In the detail pane: review src, dest, user, action, app, severity. Check the Contributing Events tab if available. Determines your next pivot. Missing fields indicate data quality issues — flag for DE.
3. Asset/Identity Enrichment Check context In the detail pane: Asset section shows criticality, category, owner. Identity section shows department, manager, VIP status. A critical asset or VIP user raises effective urgency. No enrichment = asset/identity lookup is stale.
4. Pivot to Raw Events Investigate the underlying data In the detail pane → Click the View contributing events link → Opens search with pre-populated fields → Widen time range if needed (±30 min) The notable is a summary. Raw events tell the full story.
5. Check Related Notables Look for correlated alerts In Incident Review, filter by src or user from this notable → Look for other alerts involving the same entity in the last 24-48h Multiple different detections firing for the same entity is a strong indicator of real attack.
6. Comment Document your findings Detail pane → Add Comment → Type findings → Save. Comments persist in the notable audit trail. Every notable must have a comment before closing. This is your audit evidence and handoff to the next shift.
7. Disposition & Close Set final status Edit → Set Status to Resolved → Set Disposition to one of: True Positive - Suspicious Activity, Benign Positive, False Positive → Save Disposition drives metrics. Without it, you can't measure detection quality.

What Good Triage Looks Like: WAF Alerts

WAF detections (Akamai-sourced) have unique triage patterns. The volume is high, the context is web-specific, and the enrichment path differs from endpoint or auth alerts.

Triage Step WAF-Specific Action What to Look For Common Disposition
Read the attack classification Check attack_type, rule_id, rule_message fields SQLi, XSS, RCE, path traversal, command injection. Akamai rule ID tells you the specific signature. —
Check the source IP Look up src_ip in threat intel, geo-IP, and known bot lists Known scanner (Shodan, Censys)? Tor exit node? Cloud provider IP range (often legitimate scanners)? Same geo as your customer base? Known scanner → often Benign if blocked by WAF
Check the WAF action Was the request blocked, alerted, or passed? Blocked = WAF handled it. Still investigate for pattern. Passed = potential compromise. Investigate the web server immediately. Blocked + isolated → Benign. Passed → escalate as TP.
Check the target URI Examine uri_path, uri_query Targeting login page? API endpoint? Admin panel? Known-vulnerable path? Or scanning generic paths like /wp-admin on a non-WordPress site? Generic scanning of non-existent paths → FP / Benign
Check for volume pattern Pivot: `notable` | search src_ip="X" | stats count by uri_path Single hit = likely scanner sweep. Sustained hits (>50 in 1 hour to same endpoint) = targeted attack or automated tool. Sustained targeting → TP. One-off → Benign.
Correlate with web server logs Check if the attack reached the origin. Search index=web for same timestamp + URI + source. If the WAF blocked and the request never reached the origin, impact is contained. If it passed, check for signs of successful exploitation. —

What Good Triage Looks Like: MFA Alerts

MFA detections involve identity-centric investigation. The triage path requires understanding of authentication flows, conditional access policies, and user behavior patterns.

Triage Step MFA-Specific Action What to Look For Common Disposition
Identify the user Check user, user_type (human vs service account). Cross-reference identity lookup. Is this a real person? A service account? An admin? Check department, manager, VIP status. Service account triggering human MFA rules → FP
Check MFA method used Look at mfa_method, authentication_method fields Push notification (vulnerable to fatigue), TOTP, FIDO2, phone call. Legacy auth (IMAP/SMTP) bypasses MFA entirely. Legacy protocol auth → escalate immediately
Check location context Review src_ip, geo-location, named_location (Entra ID) VPN IP? Corporate office? Known travel destination? Check if user has a travel request. Impossible travel = two auth events from >500km apart within 1 hour. VPN IP → check if user is known VPN user. Travel → verify with HR if suspicious.
Check conditional access result Review conditionalAccessStatus, failure_reason (Entra ID specific) success = policy allowed. failure = policy blocked. notApplied = no policy matched (potential gap). notApplied on a user that should have MFA → escalate to IAM team
MFA fatigue pattern Count push notifications: | where mfa_method="push" | stats count by user, _time span=10m >5 push requests in 10 minutes that the user didn't initiate = MFA fatigue attack. Check if any were approved. Rapid pushes + one approved → TP. Rapid pushes + all denied → attack failed, monitor user.
Check post-auth activity If MFA was passed/approved, check what the session did next. Pivot to audit logs for same user + 1 hour. Mailbox rules created? Files downloaded from SharePoint? Privilege escalation? These indicate account compromise POST-MFA bypass. Any post-auth anomaly + suspicious auth → TP. Escalate.

Bulk Operations in Incident Review

Bulk Status Update

  1. In Incident Review, apply filters to isolate the target notables (e.g., filter by search_name + time range)
  2. Click the checkbox in the header row to select all visible notables (or select individual rows)
  3. Click Edit Selected (or the batch action button)
  4. Set Status, Owner, and/or Comment for all selected
  5. Click Save
⚠️ Bulk Close Requires a Comment

Never bulk-close notables without a comment. Auditors see unexplained closures as evidence of negligence. Always add: "Bulk closed — [reason]. Example reviewed: [notable ID]. Pattern confirmed as [FP/Benign/Storm cleanup]."

Bulk Close After Alert Storm (Emergency Cleanup)

SPL: Identify Alert Storm Notables for Bulk Close 
`comment("After an emergency disable, find the storm notables")`
`comment("Review a sample BEFORE bulk closing")`

`notable`
| search search_name="STORM_SEARCH_NAME" status_label="New"
| stats count AS storm_count, 
    earliest(_time) AS storm_start,
    latest(_time) AS storm_end
| eval storm_duration_min = round((storm_end - storm_start) / 60, 0)
| table storm_count, storm_start, storm_end, storm_duration_min

Rollback Steps

Notable status changes are logged but can be corrected:

  1. Incorrect status change: Re-open the notable → Edit → Set correct Status and Disposition → Add comment explaining correction: "Reopened — incorrectly closed as FP, re-evaluating."
  2. Accidental bulk close: Filter by the closure time + your username → Re-open affected notables → Add comment: "Bulk close reversed — [reason]."
  3. Wrong owner assignment: Edit → Change Owner → Add comment: "Reassigned from [old] to [new] — [reason]."
⚠️ Notable Audit Trail Is Permanent

Every status change, comment, and owner assignment is logged in the notable event's audit history. You can correct a mistake, but you cannot erase the history. This is by design — it provides audit evidence. Don't panic about mistakes; document the correction.

Validation SPL & Expected Output

SPL: Verify Incident Review Is Operational 
`comment("Run this to confirm IR is functioning and notables are triageable")`

`notable`
| stats count AS total_notables,
    dc(search_name) AS unique_detections,
    dc(status_label) AS status_types,
    dc(owner) AS unique_owners
| eval health = case(
    total_notables = 0, "🔴 NO NOTABLES — check correlation searches",
    unique_detections < 2, "🟡 Very few detections firing",
    status_types < 2, "🟡 No triage happening (all same status)",
    unique_owners < 2, "🟡 Single analyst or unassigned",
    true(), "🟢 Operational"
)
| table total_notables, unique_detections, status_types, unique_owners, health

Expected healthy output:

  • total_notables > 0 (notables exist)
  • unique_detections ≥ 3 (multiple detections active)
  • status_types ≥ 3 (New, In Progress, Resolved all present → triage is happening)
  • unique_owners ≥ 2 (multiple analysts working the queue)
SPL: Triage Quality Check — Closures Without Comments 
`comment("Finds notables closed without analyst comments — audit risk")`

`notable`
| search status_label="Resolved" OR status_label="Closed"
| where isnull(comment) OR comment=""
| stats count AS no_comment_count BY owner, search_name
| sort - no_comment_count
| table owner, search_name, no_comment_count

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • Notable queue exceeds 200 unresolved in 24 hours. SOC is overwhelmed. Disable the noisiest detection (see Tuning & Noise). Escalate to SOC lead + Detection Engineering.
  • Incident Review dashboard fails to load or times out consistently. Escalate to Splunk admin. SOC cannot triage without the dashboard.
  • Multiple true positives from the same source entity in <1 hour. This is likely an active attack. Escalate immediately to incident response. Do not wait to finish triaging all notables.
  • A notable indicates a CDE (cardholder data) system is compromised. Escalate to PCI incident response per your IR plan. Do not attempt remediation from Incident Review alone.
  • Analysts are closing notables as FP without investigation. This is a training issue or a noise problem. Escalate to SOC lead. Review the detection for tuning needs.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Close everything at end of shift" Uninvestigated notables are marked resolved. Real attacks are hidden. Metrics become fiction. Only close what you've investigated. Leave the rest as New for the next shift. Document open items in handoff.
"I know this is FP, no need to check" Pattern recognition without verification leads to missed attacks. Adversaries exploit known FP patterns. Spend 30 seconds verifying. Check at least one unique field before classifying. If it's truly a pattern FP, feed back to Detection Engineering for tuning.
"No comment needed — the disposition says it all" Disposition without context is useless for audit. "False Positive" doesn't explain WHY. Always comment with reasoning: "FP — scheduled vulnerability scanner from 10.1.2.3 triggered WAF SQLi rule. Confirmed with vuln team."
"Let notables age out" Old, unresolved notables clutter the queue, slow the dashboard, and demonstrate zero process to auditors. Triage SLA: Critical ≤ 15 min, High ≤ 1 hour, Medium ≤ 4 hours, Low ≤ 24 hours. Resolve or escalate within SLA.
"Only triage Critical and High" Medium and Low notables pile up. Some real attacks start as Low severity before context reveals impact. Triage all severities per SLA. If volume is too high, escalate for tuning — don't ignore lower severities.
