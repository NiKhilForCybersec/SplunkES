Investigations & Evidence Handling

📋 Page Status: HARDENED — ES OPERATIONS

Last Audit: 2024-02 | Auditor: Detection Engineering Team

Purpose: How to use Splunk ES's Investigation feature to group related notables, attach evidence (queries, notes, context), build repeatable investigation checklists, and maintain an audit-ready evidence chain from alert to resolution.

Ownership: SOC Analysts (investigation creation + evidence collection) + SOC Lead (quality review)

Preconditions: ES Incident Review is operational. Analyst has ess_analyst role. At least one true-positive notable exists that requires deeper investigation beyond single-notable triage.

☁️ Splunk Cloud Safety Box — ES Operations

✅ Allowed in Cloud: All ES operational workflows (Incident Review, triage, investigations, notable suppression, adaptive response actions) are UI-based and work identically in Cloud. No differences from Enterprise.

⚠️ Restricted in Cloud: None for standard ES operations. If this page references filesystem paths or CLI commands for troubleshooting, those do not apply in Cloud.

🔄 Cloud-Safe Alternative: For troubleshooting ES operational issues, use the ES Health dashboard, | rest queries, and internal indexes (index=_internal, index=_audit) — all accessible via search in Cloud.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: The Investigation feature is available in your ES version (ES 5.x+). Verify: Navigate to Enterprise Security → Investigations. If missing, your ES version may not support it or the feature is disabled.
  • Assumption: KV store is operational (investigations are stored in KV store). Verify: Check | rest /services/server/info | table kvStoreStatus — should return ready.
  • Assumption: Your organization requires evidence trails for security incidents (PCI, SOX, internal audit, or incident response policy). Even if not: Building evidence habits now prevents scrambling later.
  • Assumption: Analysts have time allocated for investigation beyond basic triage. Risk if wrong: Investigations will be empty shells — created but never populated. This is worse than not creating them.

Investigation Triggers

Trigger Example Scenario Why Investigation (Not Just Notable Triage)
Multiple related notables 3 different detections fire for the same user in 2 hours: brute force → MFA fatigue → unusual mailbox rule Each notable alone might be dismissed. Together, they indicate a kill chain. Investigation groups them.
True positive requiring containment WAF alert shows successful SQL injection that passed to origin server Containment actions, evidence collection, and remediation tracking need a single workspace.
Escalation to incident response Notable triage reveals compromised admin credentials IR team needs organized evidence. Investigation provides the hand-off package.
Cross-domain correlation WAF attacks from same IP + auth failures from same IP + endpoint detection on web server No single detection captures the full story. Investigation connects the dots across domains.
Management or audit reporting "Show me the evidence for the incident last Tuesday" Investigation provides the structured record with timeline, evidence, and conclusion.

Creating an Investigation — Exact Steps

Method 1: From Incident Review (Recommended)

  1. In Incident Review, click on the notable that triggered the investigation
  2. In the notable detail pane, click the Actions dropdown
  3. Select Add to Investigation
  4. Choose Create New Investigation
  5. Fill in the investigation details:
    • Title: Descriptive name following format: INV-[DATE]-[Entity]-[Summary]
      Example: INV-2024-02-15-JSmith-MFA-Fatigue-Attack
    • Description: Initial assessment: "Multiple MFA push alerts for jsmith@corp.com from unknown IP. Investigating possible credential compromise."
  6. Click Create — the notable is automatically linked to the new investigation
  7. Return to Incident Review and add any other related notables to the same investigation

Method 2: From the Investigations Dashboard

  1. Navigate to Enterprise Security → Investigations
  2. Click Create New Investigation
  3. Fill in Title and Description as above
  4. The investigation is created empty — you'll need to add notables and evidence manually

Adding Notables to an Existing Investigation

  1. In Incident Review, click on a related notable
  2. Actions → Add to Investigation
  3. Select Add to Existing Investigation
  4. Search for the investigation by title or browse the list
  5. Click Add — the notable is now linked

⚠️ Evidence Quality Matters

A note that says "checked logs — looks fine" is useless. Include: what query you ran, what time range, what you found (or didn't find), and why that matters. Your future self, the next-shift analyst, and the auditor will all thank you.

Investigation Closure Requirements

Before closing any investigation, verify:

  1. Summary note added: Clear conclusion explaining what happened, what was found, what actions were taken
  2. All linked notables resolved: Every notable in the investigation has a status of Resolved + disposition set
  3. External ticket linked: If escalated, the IR/ITSM ticket number is recorded
  4. Timeline complete: Key events are documented with timestamps
  5. Feedback loop complete: If the investigation revealed a detection gap, tuning need, or data source issue — a ticket exists for Detection Engineering

Failure Modes

Failure Mode Symptom Root Cause Impact Fix
Empty investigation Investigation created but contains only the initial notable, no notes or evidence Analyst created investigation but didn't have time to populate it Useless for audit or handoff. Creates false sense that investigation happened. Don't create investigations unless you can add evidence. A well-commented notable is better than an empty investigation.
Investigations never closed Dozens of open investigations, some months old No lifecycle process. No review cadence for open investigations. Can't tell what's active vs abandoned. Dashboard becomes unusable. Weekly review of open investigations. Close or update stale ones (>7 days no activity).
Duplicate investigations Two analysts create separate investigations for the same incident Shift handoff gap. No check for existing investigation before creating new. Evidence split across two places. Work duplicated. Always search for existing investigations before creating. Include check in triage workflow.
KV store failure Investigation page fails to load or shows errors KV store service is down or degraded on the search head Cannot create, view, or update investigations Check | rest /services/server/info | table kvStoreStatus. Escalate to Splunk admin. Temporary: document in external tracker.
No feedback loop Investigations close but detection improvements never happen No process connecting investigation conclusions to Detection Engineering backlog Same incidents recur. Same gaps persist. SOC loses faith. Investigation closure checklist includes "Detection Engineering feedback" step. Track follow-up tickets.

Validation SPL & Expected Output

SPL: Investigation Health Check 
`comment("Check investigation operational health")`
`comment("Identifies stale, empty, or orphaned investigations")`

| rest /services/storage/collections/data/investigations splunk_server=local
| rename data.title AS title, data.status AS status, 
    data.owner AS owner, data.updated_time AS updated
| eval age_days = round((now() - updated) / 86400, 0)
| eval issue = case(
    status="open" AND age_days > 14, "🔴 STALE — Open 14+ days without update",
    status="open" AND age_days > 7, "🟡 AGING — Open 7+ days",
    status="open", "🟢 Active",
    status="closed", "⚪ Closed",
    true(), "❓ Unknown status"
)
| stats count BY issue
| sort issue

Rollback Steps

  1. Accidentally closed investigation: Reopen from the Investigations dashboard → Click the investigation → Change status back to Open → Add note explaining the reopening.
  2. Wrong notable added: Open the investigation → Find the notable link → Remove it (if your ES version supports unlinking, otherwise add a note: "Notable [ID] was added in error — not related to this investigation").
  3. Need to merge two investigations: ES does not natively support merging. Workaround: Choose one as primary. Copy key notes from secondary to primary. Close secondary with note: "Merged into [primary investigation title]."

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • Investigation reveals active data exfiltration. Stop investigating, start containing. Escalate to IR team immediately. Every minute counts.
  • Investigation reveals compromised admin/privileged credentials. Escalate to IAM team + IR team. Initiate credential rotation before continuing investigation.
  • Investigation scope expands beyond SOC capability. If you need forensic analysis, legal involvement, or cross-organizational coordination — escalate to IR team. The investigation becomes the evidence package for handoff.
  • More than 10 open investigations with no updates in 7 days. Process breakdown. Escalate to SOC Lead for triage of open investigations.
  • KV store failures preventing investigation access. Escalate to Splunk admin. Fall back to external documentation (shared drive, ticketing system) until resolved.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Create investigation for everything" 50 empty investigations are worse than 5 thorough ones. Volume without quality wastes time. Only create investigations for multi-notable incidents, true positives requiring containment, or escalations. Simple FPs/benigns get a notable comment.
"Investigate in my head, close in the system" If it's not written down, it didn't happen. No evidence = no audit trail = liability. Document every investigative step with a note. Use the checklists above. Future-you will be grateful.
"Investigation = screenshot dump" Screenshots without context are useless. What query produced this? What does it mean? For every piece of evidence: state what you searched, what you found, and what it means for the investigation.
"Someone else will close it" Orphaned investigations clutter the system and suggest process failures to auditors. Investigation owner is responsible for closure. If transferring, hand off explicitly with a note.
"No feedback to Detection Engineering" Every investigation that reveals a gap, a missed detection, or a tuning need is wasted learning if DE never hears about it. Close every investigation with a DE feedback note: "Detection gap identified: [describe]. Ticket: [#]" or "No detection changes needed."
