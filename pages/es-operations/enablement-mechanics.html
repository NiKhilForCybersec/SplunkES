Correlation Search Enablement Mechanics

📋 Page Status: HARDENED — ES OPERATIONS

Last Audit: 2024-02 | Auditor: Detection Engineering Team

Purpose: Exact UI-level procedures for enabling, cloning, and configuring correlation searches to produce notable events. This is the mechanical "how-to" — the strategy for WHAT to enable is covered in OOTB vs Custom Strategy and the lifecycle governance is in Correlation Search Lifecycle.

Ownership: Detection Engineering (execution) + SOC Lead (sign-off per Change Management)

Preconditions: ES is installed and operational. User has ess_admin or sc_admin role. Data sources required by the correlation search exist and are healthy.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: You're working in ES Content Management (not the legacy Saved Searches view). Verify: Navigate to Enterprise Security → Configure → Content → Content Management. You should see a list with Type, App, and Status columns.
  • Assumption: Search concurrency is not at its limit. Verify: Run the concurrency check from Health & Performance. If near limit, enabling additional searches may cause skips.
  • Assumption: Data models used by the correlation search are accelerated (if it uses tstats). Risk if wrong: Search returns no results even though data exists. See Health & Performance — DM acceleration check.
  • Assumption: You have verified the detection through the lifecycle (backtest → monitoring → production). Risk if wrong: Enabling untested detections goes directly to SOC — noise, confusion, trust damage. See Lifecycle.

Enabling a Correlation Search — Exact Steps

Step-by-Step: Enable via Content Management

Step Action Exact UI Navigation What to Verify
1. Navigate Open Content Management Enterprise Security → Configure → Content → Content Management Page loads with list of all content objects
2. Find Locate the correlation search Use the Type filter → Select Correlation Search. Use the search bar to filter by name. Or filter by App to find searches from a specific DA/SA. Search appears in the list with current status (Enabled/Disabled)
3. Open Open the search configuration Click the search name to open its detail page Configuration page loads with Search, Time Range, Scheduling, and Actions tabs/sections
4. Review SPL Read and understand the search logic In the Search field, review the SPL. Check: what indexes does it query? What data models does it use? What are the threshold conditions? You understand what this detection does, what data it needs, and what conditions trigger it
5. Check Schedule Verify cron and lookback Cron Schedule: Verify the interval (e.g., */15 * * * *). Earliest Time / Latest Time: Verify the lookback window. Lookback > cron interval + 1 minute buffer. See Lifecycle — Scheduling.
6. Check Actions Verify Notable Event action is configured Scroll to Adaptive Response Actions section (or Actions tab). Look for Notable or Create Notable Event. Notable action exists with severity set. If missing, add it (see below).
7. Enable Turn on the search Toggle the Enabled switch to ON (or change Status dropdown to Enabled). Click Save. Status changes to "Enabled". Search will run at next cron interval.
8. Verify Confirm the search runs and produces notables Wait one cron interval, then check: `notable` | search search_name="YOUR_SEARCH_NAME" | head 5 Notables appear in the notable index AND in Incident Review

Cloning an OOTB Search — Safely

🚨 Why Clone Instead of Edit OOTB?

If you modify an OOTB search directly, the next ES Content Update will overwrite your changes without warning. Cloning preserves your customizations in a separate search that ES updates won't touch. Always clone, never edit OOTB in place.

Clone Procedure

  1. Navigate to the OOTB search in Content Management
  2. Click the search name to open it
  3. Copy the SPL from the Search field (select all, copy to clipboard or text editor)
  4. Create a new correlation search:
    • Go to Configure → Content → Content Management
    • Click Create New Content → Select Correlation Search
  5. Name the clone following convention: CUSTOM - [Original Name] - [Your Org] Tuned
    Example: CUSTOM - Brute Force Access Behavior Detected - Retail Tuned
  6. Paste the SPL into the Search field
  7. Modify as needed (thresholds, filters, field additions)
  8. Configure Schedule: Set cron and lookback (review Lifecycle — Scheduling)
  9. Configure Notable Action: Add the Notable adaptive response action with appropriate severity
  10. Add version header to the SPL as an inline comment:
    Version Header Template
    `comment("CUSTOM - Brute Force - Retail Tuned")`
`comment("Version: 1.0 | Created: 2024-02-15 | Author: [Name]")`
`comment("Cloned from: Brute Force Access Behavior Detected (OOTB)")`
`comment("Changes: Threshold raised to 25, POS subnet excluded")`
  11. Save the new search (save as DISABLED initially)
  12. Verify the OOTB original remains DISABLED — you don't want both running
  13. Enable the clone after backtest and monitoring lifecycle stages are complete
⚠️ Clone Checklist — Don't Forget
  • ☐ OOTB original is disabled (not both running simultaneously)
  • ☐ Clone has CUSTOM - prefix in the name
  • ☐ Clone has version header in SPL
  • ☐ Notable action is configured on the clone (it does NOT copy automatically)
  • ☐ Clone is saved in the correct app context (typically SplunkEnterpriseSecuritySuite or your custom app)
  • ☐ Clone is added to the detection registry

Configuring the Notable Event Action

A correlation search can run successfully but produce zero notables if the Notable adaptive response action isn't configured. This is the most common reason for "I enabled the search but nothing appears."

Adding Notable Action to a Correlation Search

  1. Open the correlation search in Content Management
  2. Scroll to the Adaptive Response Actions section
  3. Click Add New Response Action → Select Notable (or Create Notable Event)
  4. Configure these fields:
    Field Setting Guidance
    Title Notable event title shown in Incident Review Make it descriptive: Brute Force Detected — $src$ targeting $dest$. Use field tokens ($field$) for dynamic values.
    Description Details shown in notable detail pane Include: what was detected, key fields, suggested triage steps
    Severity Informational / Low / Medium / High / Critical Aligns with your severity matrix. Don't default to Critical — use Lifecycle guidance.
    Security Domain Access, Endpoint, Network, Threat, Identity, Audit Choose the primary domain. WAF = Network or Threat. MFA = Access or Identity.
    Default Owner unassigned (typically) Leave as unassigned unless you have auto-assignment rules
    Default Status New Always New. SOC sets In Progress when they claim it.
    Drill-down Search that runs when analyst clicks "View Contributing Events" Make this useful. Should return the raw events that triggered the detection.
  5. Click Save

Diagnostic SPL Queries

SPL: Check 1 — Is the Search Enabled? 
| rest /services/saved/searches splunk_server=local
| search title="YOUR_SEARCH_NAME"
| table title, disabled, action.correlationsearch.enabled,
    cron_schedule, next_scheduled_time, eai:acl.app
| eval status = if(disabled=0, "✅ ENABLED", "❌ DISABLED")
SPL: Check 3 — Is the Search Running? (Scheduler Log) 
index=_internal sourcetype=scheduler savedsearch_name="YOUR_SEARCH_NAME"
| stats latest(_time) AS last_run,
    latest(status) AS last_status,
    latest(run_time) AS last_runtime_sec
| eval last_run_human = strftime(last_run, "%Y-%m-%d %H:%M:%S")
| eval health = case(
    isnull(last_run), "🔴 NEVER RAN — check scheduling",
    last_status="skipped", "🔴 SKIPPED — concurrency issue",
    last_status="success", "🟢 Running normally",
    true(), "🟡 Check status: " . last_status
)
| table last_run_human, last_status, last_runtime_sec, health
SPL: Check 4 — Does the Search Return Results? (Run Manually) 
`comment("Copy the exact SPL from the correlation search")`
`comment("Paste it in the Splunk Search bar")`
`comment("Set the time range to match the search's lookback window")`
`comment("If zero results: data source or logic issue")`
`comment("If results exist: notable action or throttle issue")`

`comment("Quick data source check for a specific index/sourcetype:")`
index=YOUR_INDEX sourcetype=YOUR_SOURCETYPE earliest=-1h
| stats count
| eval status = if(count > 0, "✅ Data exists", "❌ No data — check ingestion")
SPL: Check 5 — Is Notable Action Configured? 
| rest /services/saved/searches splunk_server=local
| search title="YOUR_SEARCH_NAME"
| table title, action.notable, action.notable.param.severity,
    action.notable.param.security_domain
| eval notable_configured = if(action.notable=1, "✅ Yes", "❌ No — add Notable action")
SPL: Check 6 — Is Throttle Blocking Everything? 
| rest /services/saved/searches splunk_server=local
| search title="YOUR_SEARCH_NAME"
| table title, alert.suppress, alert.suppress.period,
    alert.suppress.fields
| eval throttle_status = case(
    alert.suppress=0, "No throttle configured",
    alert.suppress.period="86400s", "⚠️ 24h throttle — very aggressive",
    true(), "Throttle: " . alert.suppress.period . " on fields: " . alert.suppress.fields
)
SPL: Check 7 — Is a Suppression Rule Hiding the Notables? 
`notable`
| search search_name="YOUR_SEARCH_NAME"
| stats count BY is_suppressed
| eval note = if(is_suppressed=1, "⚠️ Notables exist but are SUPPRESSED", "Notables visible")

Failure Modes

Failure Mode Symptom Root Cause Impact Fix
Both OOTB and clone enabled Duplicate notables for every event (2x volume) Cloned search enabled without disabling the original SOC sees duplicates. Metrics are inflated. Concurrency wasted. Disable the OOTB original immediately. Only the clone should run.
Clone saved in wrong app context Clone not visible in ES Content Management, or permissions errors Saved in search app instead of ES app Search may run but notable may not appear in Incident Review. May break on SHC replication. Recreate the clone in the correct app context (typically SplunkEnterpriseSecuritySuite).
tstats search with no acceleration Search returns zero results even though raw data exists Correlation search uses | tstats but the required data model is not accelerated Detection appears enabled but has zero coverage Check DM acceleration status. Accelerate the required data model. Wait for backfill to complete.
Field name mismatch after CIM update Search stops matching events after ES or TA update CIM field names changed or TA field extractions updated Silent detection failure — search runs, finds nothing After any ES or TA update, verify all custom searches still produce results. Run manual test.
Enabled without lifecycle New detection fires immediately to SOC with unknown FP rate Skipped backtest and monitoring stages SOC flooded with alerts they don't understand. Trust damaged. Disable immediately. Complete lifecycle stages. Re-enable only after monitoring period passes.
Severity misconfigured Informational alerts set to Critical, overwhelming high-urgency queue Default severity not adjusted during enablement SOC priority is distorted. Analysts waste time on false-critical alerts. Review severity against your classification matrix. Adjust and communicate the change to SOC.

Validation SPL & Expected Output

SPL: Full Enablement Validation (Run After Enable) 
`comment("Replace YOUR_SEARCH_NAME with the exact search title")`
`comment("Run this 2 cron intervals after enabling")`

| rest /services/saved/searches splunk_server=local
| search title="YOUR_SEARCH_NAME"
| eval enabled = if(disabled=0, "✅", "❌")
| eval has_notable = if(action.notable=1, "✅", "❌")
| eval severity = coalesce(action.notable.param.severity, "NOT SET ❌")
| table title, enabled, has_notable, severity, cron_schedule
| append [
    search `notable`
    | search search_name="YOUR_SEARCH_NAME"
    | stats count AS notable_count, 
        earliest(_time) AS first_notable,
        latest(_time) AS last_notable
    | eval first_notable = strftime(first_notable, "%Y-%m-%d %H:%M"),
        last_notable = strftime(last_notable, "%Y-%m-%d %H:%M")
]

Expected healthy output: enabled=✅, has_notable=✅, severity is set, notable_count > 0.

Rollback Steps

Scenario Steps Time
Detection causing alert storm 1. Content Management → Find the search → Disable immediately. 2. Bulk-close storm notables with comment. 3. Notify SOC. 4. Root-cause the volume spike. < 5 min
Clone needs to revert to OOTB 1. Disable the clone. 2. Re-enable the OOTB original (if needed). 3. Update registry. 4. Notify SOC of the change. < 10 min
Accidentally enabled wrong search 1. Disable immediately. 2. Close any notables it generated with comment: "Enabled in error — disabling." 3. Enable the correct search. < 10 min
Severity set too high 1. Edit the Notable action → Lower severity. 2. Existing notables keep old severity; new ones will use the corrected value. 3. Notify SOC of the change. < 5 min

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • Enabling a search triggers >50 notables in the first hour. Disable immediately. The threshold is wrong or data patterns weren't understood. Do NOT leave it running while you investigate.
  • Search concurrency is at limit and you need to enable another search. Do NOT enable — it will cause skips for existing searches. Escalate to Splunk admin for capacity review.
  • You can't determine what data source the search needs. Stop. Don't enable blindly. Trace the SPL to identify required indexes and sourcetypes. If the data doesn't exist, the detection will silently fail.
  • OOTB search references a deprecated field or data model. Do NOT enable. Check the Splunk ES release notes for migration guidance. Clone and update to current field names.
  • The search was enabled without lifecycle approval (backtest/monitoring skipped). Disable immediately. Return to the lifecycle process. No exceptions.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Enable everything and see what happens" Instant SOC flood. Hundreds of untested notables. Trust destroyed in one day. Searches competing for concurrency. Enable one detection at a time. Complete lifecycle for each. Monitor volume before enabling the next.
"Edit the OOTB search directly" Next ES content update will overwrite your changes silently. No version history. No rollback path. Always clone. Always prefix with CUSTOM -. Disable the original.
"Enable on Friday afternoon" If the detection has issues, the weekend SOC skeleton crew will bear the impact with minimal support. Enable Tuesday–Thursday, morning preferred. Monitor for at least 4-8 hours before end of day. Never before a change freeze.
"Skip the notable action — we'll add it later" Search runs, burns concurrency, but nobody sees results. When you finally add the notable action, you've wasted days of monitoring time. Configure the notable action BEFORE enabling the search. Always.
"It worked in my test — ship it" Test environments have different data volumes, user populations, and timing patterns than production. Complete the full lifecycle: backtest on production data → monitoring-only → production enablement.
