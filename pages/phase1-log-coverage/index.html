Why This Phase Exists

Business Justification

In a large retail environment with 1,500+ stores, 50,000+ endpoints, and hundreds of applications, log coverage is never complete. Every detection engineering project begins with the same question: "Do we actually have the data to detect this?" The answer is almost always "partially" or "we thought so, but..."

This phase exists because:

  • Detections cannot detect what they cannot see. A credential stuffing detection is useless if authentication logs aren't flowing or are missing the source IP field.
  • Partial data creates false confidence. Seeing "some" events doesn't mean you're seeing "all" events. A 10% data loss means 10% of attacks are invisible.
  • Log ownership is fragmented. In enterprise retail, WAF logs might be owned by Network, authentication logs by IAM, endpoint logs by Desktop Engineering, and application logs by Development. No single team has full visibility.
  • Change happens constantly. Infrastructure changes, vendor updates, network reconfigurations, and certificate rotations can silently break log pipelines without anyone noticing for weeks.

Security Justification

Attackers don't announce themselves. The difference between a successful breach and a detected intrusion is often a single log source:

  • The 2013 Target breach went undetected for weeks partly because security teams weren't monitoring the right logs from the HVAC vendor network segment.
  • MFA fatigue attacks (Uber 2022, Cisco 2022) require MFA prompt logs—many organizations discover they're not collecting these until after an incident.
  • Credential stuffing attacks against retail loyalty programs often bypass detection because customer authentication logs are separate from employee authentication logs.

⚠️ Enterprise Reality Check

In our experience across 50+ enterprise engagements, these items are missing more than 70% of the time. Plan your timeline assuming you'll need to create or discover these yourself:

  • Complete log source inventory: Most organizations cannot produce a definitive list of what's logging to Splunk. You will discover sources during this phase.
  • Field-level documentation: Even when logs exist, documentation of what fields are available and their meanings is rare. Expect to reverse-engineer field mappings.
  • Clear ownership: "Who owns the Akamai logs?" often produces 3 different answers. Budget time for ownership discovery.
  • Consistent naming: Index names like "main", "security", "sec_logs", "security_events", and "prod_security" may all contain similar data. Naming conventions are aspirational.
  • Up-to-date network diagrams: Log flow paths documented 2 years ago may not reflect current architecture. Verify everything.
  • Working credentials for source systems: API keys expire, service accounts get disabled, certificates rotate. Assume you'll need to request new credentials.

Step-by-Step Execution

Step 1: Build the Use Case → Log Source Mapping

For each detection use case, document exactly what data is required. Do not assume—be specific about fields, not just log sources.

💡 Field-Level Thinking

Don't just ask "Do we have authentication logs?" Ask "Do we have authentication logs with source IP, username, timestamp, result code, and MFA method fields populated?"

Example: MFA Fatigue Detection Requirements

Use Case Requirements Template 
USE CASE: MFA Fatigue Attack Detection
MITRE ATT&CK: T1621 - Multi-Factor Authentication Request Generation

DETECTION LOGIC SUMMARY:
Detect when a user receives 5+ MFA push notifications within 10 minutes,
especially when followed by a successful authentication.

REQUIRED DATA:

Log Source 1: Entra ID Sign-in Logs
  - Index: azure_ad (expected)
  - Sourcetype: azure:aad:signin

Step 2: Discover What's Actually in Splunk

Before asking anyone about log sources, first discover what's already flowing. This prevents asking questions you can answer yourself and builds credibility with system owners.

2.1: Full Index and Sourcetype Discovery

SPL: Discover All Data Sources (Run This First) 
| tstats count WHERE index=* earliest=-7d latest=now() BY index, sourcetype, host
| stats 
    sum(count) AS total_events,
    dc(host) AS unique_hosts,
    values(host) AS sample_hosts
    BY index, sourcetype
| sort - total_events
| eval daily_volume = round(total_events / 7, 0)
| eval sample_hosts = mvindex(sample_hosts, 0, 4)
| table index, sourcetype, total_events, daily_volume, unique_hosts, sample_hosts

What to look for:

  • Indexes with security-relevant names: "security", "waf", "azure", "firewall", "auth", "endpoint"
  • Sourcetypes from known vendors: "akamai:*", "azure:*", "pan:*", "crowdstrike:*"
  • Unexpected high-volume sources (may indicate duplicate logging or misconfiguration)
  • Indexes with very low event counts (may indicate broken ingestion)

2.2: Security-Specific Source Discovery

SPL: Find Security-Relevant Sourcetypes 
| tstats count WHERE index=* sourcetype=* earliest=-24h BY sourcetype
| search sourcetype IN (
    "akamai:*", "azure:*", "o365:*", "ms:*",
    "pan:*", "cisco:*", "fortinet:*", "checkpoint:*",
    "crowdstrike:*", "carbonblack:*", "sentinelone:*", "defender:*",
    "okta:*", "duo:*", "cyberark:*", "ping:*",
    "syslog", "linux_secure", "WinEventLog:*"
)
| stats sum(count) AS events BY sourcetype
| sort - events

2.3: Check for Specific Required Source

SPL: Validate Specific Log Source Exists 
| tstats count WHERE index=* sourcetype="azure:aad:signin" earliest=-24h BY sourcetype, index
| append [| makeresults | eval sourcetype="azure:aad:signin", index="NOT_FOUND", count=0]
| stats sum(count) AS event_count, values(index) AS indexes BY sourcetype
| eval status = if(event_count > 0, "✓ DATA FLOWING", "✗ NO DATA - ONBOARDING REQUIRED")

Step 3: Validate Field Availability

Finding events is not enough. You must verify that the specific fields needed for detection logic exist and are populated consistently.

3.1: Field Population Check

SPL: Check Critical Field Population Rate 
index=azure_ad sourcetype="azure:aad:signin" earliest=-24h
| head 10000
| eval has_user = if(isnotnull(userPrincipalName) AND userPrincipalName!="", 1, 0)
| eval has_ip = if(isnotnull(ipAddress) AND ipAddress!="", 1, 0)
| eval has_status = if(isnotnull('status.errorCode'), 1, 0)
| eval has_mfa_method = if(isnotnull('authenticationDetails{}.authenticationMethod'), 1, 0)
| eval has_timestamp = if(isnotnull(createdDateTime), 1, 0)
| stats 
    count AS total_events,
    sum(has_user) AS with_user,
    sum(has_ip) AS with_ip,
    sum(has_status) AS with_status,
    sum(has_mfa_method) AS with_mfa_method,
    sum(has_timestamp) AS with_timestamp
| eval user_pct = round(with_user/total_events*100, 1)."%"
| eval ip_pct = round(with_ip/total_events*100, 1)."%"
| eval status_pct = round(with_status/total_events*100, 1)."%"
| eval mfa_method_pct = round(with_mfa_method/total_events*100, 1)."%"
| eval timestamp_pct = round(with_timestamp/total_events*100, 1)."%"
| table total_events, user_pct, ip_pct, status_pct, mfa_method_pct, timestamp_pct

Acceptance Criteria:

  • Critical fields (user, timestamp): Must be >99% populated
  • Important fields (IP, action): Must be >95% populated
  • Enrichment fields (geo, device): >80% is acceptable

3.2: Sample Field Values

SPL: View Sample Field Values 
index=azure_ad sourcetype="azure:aad:signin" earliest=-1h
| head 100
| stats 
    values(userPrincipalName) AS sample_users,
    values(ipAddress) AS sample_ips,
    values(status.errorCode) AS sample_status_codes,
    values(authenticationDetails{}.authenticationMethod) AS sample_mfa_methods
| eval sample_users = mvindex(sample_users, 0, 9)
| eval sample_ips = mvindex(sample_ips, 0, 9)
| eval sample_status_codes = mvindex(sample_status_codes, 0, 9)
| eval sample_mfa_methods = mvindex(sample_mfa_methods, 0, 9)

What to verify:

  • Username format matches across sources (UPN vs. SAMAccountName vs. email)
  • IP addresses are real IPs, not "unknown" or internal proxy IPs
  • Status codes include the values you need to filter on
  • MFA methods include the specific method you're detecting (push notification, SMS, etc.)

Step 4: Measure Ingestion Latency

Detection latency = Event time to Alert time. If logs arrive 30 minutes after the event occurred, your "real-time" detection is already 30 minutes late.

4.1: Calculate Index-Time Latency

SPL: Measure Ingestion Latency 
index=azure_ad sourcetype="azure:aad:signin" earliest=-4h latest=-1h
| eval latency_seconds = _indextime - _time
| where latency_seconds > 0 AND latency_seconds < 86400
| stats 
    count AS events,
    avg(latency_seconds) AS avg_latency_sec,
    median(latency_seconds) AS median_latency_sec,
    perc95(latency_seconds) AS p95_latency_sec,
    max(latency_seconds) AS max_latency_sec
| eval avg_latency = tostring(round(avg_latency_sec, 0), "duration")
| eval median_latency = tostring(round(median_latency_sec, 0), "duration")
| eval p95_latency = tostring(round(p95_latency_sec, 0), "duration")
| eval max_latency = tostring(round(max_latency_sec, 0), "duration")
| eval status = case(
    p95_latency_sec < 60, "✓ EXCELLENT (<1 min)",
    p95_latency_sec < 300, "✓ ACCEPTABLE (<5 min)",
    p95_latency_sec < 900, "⚠️ MARGINAL (5-15 min)",
    p95_latency_sec < 3600, "✗ POOR (15-60 min)",
    true(), "✗ UNACCEPTABLE (>1 hour)"
)
| table events, avg_latency, median_latency, p95_latency, max_latency, status

4.2: Latency Over Time (Check for Patterns)

SPL: Latency Trend Analysis 
index=azure_ad sourcetype="azure:aad:signin" earliest=-24h
| eval latency_seconds = _indextime - _time
| where latency_seconds > 0 AND latency_seconds < 86400
| bin _time span=1h
| stats 
    avg(latency_seconds) AS avg_latency,
    perc95(latency_seconds) AS p95_latency,
    count AS events
    BY _time
| eval avg_latency_min = round(avg_latency/60, 1)
| eval p95_latency_min = round(p95_latency/60, 1)

What to look for:

  • Latency spikes at specific times (may indicate batch processing)
  • Increasing latency trend (may indicate growing queue backlog)
  • Latency spikes during business hours (capacity issue)

Comprehensive Validation Query

SPL: Full Log Source Health Dashboard 
| makeresults 
| eval sources="azure:aad:signin,akamai:siem,pan:traffic,crowdstrike:event:*"

| mvexpand sources

     | rename sourcetype AS expected_sourcetype

    [| tstats count WHERE index=* earliest=-24h BY sourcetype
     | rename sourcetype AS expected_sourcetype
     | search count > 0
     | append 
        [search index=* earliest=-4h 
         | eval latency = _indextime - _time
         | stats perc95(latency) AS p95_latency BY sourcetype
         | rename sourcetype AS expected_sourcetype]
     | stats values(p95_latency) AS p95_latency BY expected_sourcetype
     | eval latency_status = case(
         isnull(p95_latency), "Unknown",
         p95_latency < 300, "✓ OK",
         p95_latency < 900, "⚠️ Marginal",
         true(), "✗ High"
     )]
| fillnull latency_status value="N/A"
| table expected_sourcetype, data_status, count, p95_latency, latency_status

What "Good" Looks Like

  • All expected sourcetypes show events in last 24 hours
  • Event counts are consistent with expected volume (within 20% of baseline)
  • P95 latency is under 5 minutes (300 seconds)
  • No gaps in timeline when viewed as timechart
  • Critical field population is >95%

What "Bad" Looks Like (And What It Means)

Symptom Likely Cause Investigation
Zero events Log source not onboarded or completely broken Check forwarder status, HEC token, network connectivity
Events exist but count dropped >50% Partial failure: some hosts/components not logging Compare host list to baseline; check for forwarder failures
Critical fields null/empty Parsing failure or source not logging those fields Check raw events; review props.conf; contact source owner
Latency >15 minutes Queue backup, batch processing, network delay Check Splunk internal logs; review forwarder queues

When to Stop and Escalate

  • Gap cannot be filled: Source system doesn't support the logging you need (e.g., MFA provider doesn't log push attempts). Document as risk, escalate for risk acceptance decision.
  • Owner won't cooperate: System owner refuses to enable logging or provide access. Escalate to Security Manager for executive push.
  • Onboarding blocked by change control: Changes require CAB approval and next window is 3 weeks out. Document delay, adjust project timeline, escalate if timeline is unacceptable.
  • License concern: Onboarding new source will exceed Splunk license. Escalate for budget/license discussion before proceeding.

Failure Modes & Fixes

These are the most common issues encountered during Phase 1, based on real enterprise engagements:

Failure Mode 1: Log Source "Exists" But Is Actually Not Flowing

Symptom

Stakeholder says "Yes, we have Akamai WAF logs in Splunk" but your query returns zero events.

Why It Happens:

  • Onboarding was started but never completed
  • Ingestion broke months ago and no one noticed
  • Logs are in a different index than expected
  • Stakeholder confused this environment with another (dev vs. prod)

How to Confirm:

SPL: Deep Search for Any Akamai Data 
index=* earliest=-30d (sourcetype=*akamai* OR source=*akamai* OR host=*akamai*)
| stats count BY index, sourcetype, source
| sort - count

How to Fix:

  1. If data exists in different index/sourcetype: Update your queries to use correct location
  2. If data stopped flowing: Check HEC token expiration, API credential rotation, certificate expiration
  3. If never onboarded: Proceed to onboarding guide

When NOT to Fix: If onboarding requires budget approval or lengthy procurement, document the gap and proceed with available data. Create a risk acceptance document for stakeholder sign-off.

Failure Mode 2: Data Flows But Critical Fields Are Empty

Symptom

Events exist but when you query for specific fields like src_ip or user, they're null or empty.

Why It Happens:

  • Source system logging level is set too low (not logging the fields you need)
  • Splunk parsing (props.conf) doesn't extract those fields
  • Field names changed in vendor update
  • CIM field aliases not configured

How to Confirm:

SPL: Check Raw Event Content 
index=azure_ad sourcetype="azure:aad:signin" earliest=-1h
| head 5
| table _raw

How to Fix:

  1. If field exists in _raw but not extracted: Update props.conf with correct field extraction
  2. If field doesn't exist in _raw: Contact source system owner to enable verbose logging
  3. If field has different name: Create field alias in props.conf

When NOT to Fix: If the source system simply doesn't log the field you need (vendor limitation), document the limitation. Consider alternative detection approaches or different data sources that capture the same activity.

Failure Mode 3: Intermittent Data Gaps

Symptom

Timechart shows regular gaps: data flows for a while, stops, then resumes.

Why It Happens:

  • Scheduled batch jobs (data only sent every N hours)
  • Network intermittent connectivity issues
  • Forwarder restarts or service instability
  • Rate limiting by source system or receiving endpoint
  • Maintenance windows causing expected outages

How to Confirm:

SPL: Visualize Data Gaps 
index=azure_ad sourcetype="azure:aad:signin" earliest=-7d
| timechart span=1h count
| eval gap = if(count < 10, "GAP", "OK")
| where gap="GAP"
| table _time, count, gap

How to Fix:

  1. If batch job: Accept the latency or request streaming integration
  2. If network issue: Engage network team; check firewall rules and routing
  3. If forwarder issue: Check forwarder logs, restart service, increase memory allocation
  4. If rate limiting: Increase rate limits or implement queuing

When NOT to Fix: If gaps align with documented maintenance windows, this may be expected behavior. Document the maintenance schedule and account for it in detection tuning (don't alert on "missing data" during maintenance).

Failure Mode 4: High Latency (>15 Minutes)

Symptom

Events have _time from 30+ minutes ago even though they were just indexed.

Why It Happens:

  • Batch processing at source (API polling on long intervals)
  • Splunk queue backup (indexer overwhelmed)
  • Intermediate system delay (SIEM aggregator, message queue)
  • Timezone misconfiguration causing apparent delay

How to Confirm:

SPL: Analyze Latency Pattern 
index=azure_ad sourcetype="azure:aad:signin" earliest=-24h
| eval latency_min = round((_indextime - _time) / 60, 1)
| bin _time span=1h
| stats avg(latency_min) AS avg_latency, max(latency_min) AS max_latency BY _time
| where avg_latency > 5

How to Fix:

  1. If batch at source: Request more frequent polling or streaming integration
  2. If Splunk queue: Increase indexer capacity, review heavy forwarder queue settings
  3. If intermediate system: Bypass aggregator or tune its forwarding frequency
  4. If timezone: Fix timezone configuration in props.conf

When NOT to Fix: If the source system only supports batch export (e.g., daily log pulls), you cannot achieve real-time detection. Document the latency limitation and adjust detection use cases accordingly (these logs are useful for investigation but not real-time alerting).

Failure Mode 5: Nobody Knows Who Owns the Log Source

Symptom

You need to enable logging or fix an issue, but nobody can tell you who manages the source system.

Why It Happens:

  • Original implementer left the organization
  • System was inherited through acquisition
  • Managed service with unclear internal ownership
  • Shadow IT: system deployed outside normal processes

How to Confirm/Investigate:

  1. Check CMDB/ServiceNow for asset registration
  2. Query Splunk for host metadata: | tstats count BY host WHERE sourcetype=X | lookup cmdb_lookup host OUTPUT owner
  3. Check internal wikis/SharePoint for documentation
  4. Email IT leadership asking "Who manages system X?"

How to Fix:

  1. Escalate to Security Manager to drive ownership discovery
  2. If managed service: Contact vendor account manager for internal escalation path
  3. Create RACI document and get sign-off on ownership going forward

When NOT to Fix: If ownership truly cannot be determined and the system is critical to detection, document this as a risk: "Log source X has no identified owner. Issues cannot be resolved in a timely manner." This is a legitimate finding that security leadership should know about.

Failure Mode 6: "We Can't Enable That Logging—It's a Security Risk"

Symptom

System owner refuses to enable logging or export logs, citing security concerns about exposing sensitive data.

Why It Happens:

  • Legitimate concern: Logs contain PII/PCI data that shouldn't be broadly accessible
  • Misunderstanding: Owner doesn't understand Splunk's RBAC controls
  • Organizational friction: Owner doesn't want security "watching" their system

How to Fix:

  1. Demonstrate Splunk RBAC: Show that data can be restricted to security team only
  2. Propose data masking: Offer to hash/mask sensitive fields at ingest time
  3. Offer dedicated index: Create separate index with restricted access
  4. Executive escalation: If owner remains uncooperative, escalate with business justification

When NOT to Fix: If legitimate compliance requirements prohibit the data export (e.g., contractual restrictions), document the limitation. Work with Legal/Compliance to determine if any workarounds exist. This may require accepting reduced detection capability for that system.

⚠️ Phase 1 Safety Principles

Phase 1 is primarily assessment and onboarding. However, onboarding activities can impact production systems. Follow these safety principles:

What Can Go Wrong During Phase 1

Activity Potential Impact Rollback Action Communication Required
Creating new Splunk index Disk space consumption; no production impact Delete index via CLI: splunk remove index <name> Splunk admin only
Creating HEC token None until used; potential attack surface if token leaked Disable token in Splunk Web → Data Inputs → HTTP Event Collector None required
Enabling SIEM Integration (Akamai/CyberArk) High data volume; license consumption; network traffic Disable connector in vendor portal; disable HEC token Notify SOC if alerts already configured; notify Splunk admin for license tracking
Configuring Azure Diagnostic Settings Event Hub costs; data flow to Splunk Delete diagnostic setting in Azure Portal Notify Azure/Cloud team
Installing Universal Forwarder on DC CPU/memory on Domain Controller; high event volume Stop splunkd service; uninstall UF if needed Notify AD/IAM team; follow change control
Running high-volume SPL queries Search head resource consumption; slow searches for others Cancel search; reduce time range; add | head None unless impacts others

Emergency Rollback Procedures

If Data Volume Exceeds License

Immediate Actions 
1. IDENTIFY the source causing volume spike:
   | tstats count WHERE index=* earliest=-24h BY index, sourcetype
   | sort - count | head 10

2. DISABLE the ingestion source:
   - HEC Token: Splunk Web → Settings → Data Inputs → HTTP Event Collector → [token] → Disable
   - API Polling: Edit inputs.conf, set disabled = 1, restart Splunk
   - SIEM Push/Pull: Disable connector in vendor portal, or stop external collector process (Akamai SIEM connector, CyberArk, etc.)

3. COMMUNICATE:
   - Notify Splunk admin immediately
   - Open ticket if license violation imminent
   - Document what was disabled and why

4. ASSESS before re-enabling:
   - Calculate expected daily volume
   - Confirm license capacity
   - Consider filtering high-volume, low-value events

If Onboarding Breaks Source System

Escalation Path 
1. STOP all onboarding activities for that system
2. DISABLE any agents or connectors installed
3. CONTACT system owner immediately
4. DOCUMENT:
   - What was changed
   - When it was changed
   - What symptoms appeared
   - What rollback was performed
5. DO NOT attempt to "fix forward" without system owner approval
6. ESCALATE to Security Manager if business impact

Safe Testing Practices

  • Always test in dev/staging first if Splunk dev environment exists
  • Start with limited scope: One security config, one tenant, one DC before enabling all
  • Monitor volume for 24 hours before declaring success
  • Keep rollback credentials ready: Have admin access to vendor portals before starting
  • Document before changing: Screenshot existing config before modifications

Timestamp Freshness Deep Dive

Timestamp issues are the #1 silent killer of detections. This section provides comprehensive validation queries.

Understanding _time vs _indextime

  • _time: When the event OCCURRED (extracted from event data)
  • _indextime: When Splunk RECEIVED the event
  • Latency: _indextime - _time = ingestion delay
🚨 Timestamp Red Flags
  • _time in the future: Timezone misconfiguration or clock skew on source
  • _time = _indextime exactly: Timestamp extraction failed; Splunk used index time
  • Latency > 1 hour: Batch processing, queue backlog, or API polling delay
  • Negative latency: Clock skew (source clock ahead of Splunk)

Comprehensive Timestamp Validation Query

SPL: Full Timestamp Health Check 
index=* sourcetype="azure:aad:signin" earliest=-24h
| eval latency_sec = _indextime - _time
| eval timestamp_issue = case(
    latency_sec < -300, "FUTURE_EVENT (clock skew)",
    latency_sec < 0, "MINOR_FUTURE (acceptable skew)",
    latency_sec == 0, "EXACT_MATCH (verify extraction)",
    latency_sec < 60, "EXCELLENT (<1 min)",
    latency_sec < 300, "ACCEPTABLE (<5 min)",
    latency_sec < 900, "MARGINAL (5-15 min)",
    latency_sec < 3600, "POOR (15-60 min)",
    latency_sec < 86400, "VERY_POOR (1-24 hr)",
    true(), "CRITICAL (>24 hr)"
)
| stats 
    count AS events,
    min(latency_sec) AS min_latency,
    avg(latency_sec) AS avg_latency,
    median(latency_sec) AS median_latency,
    perc95(latency_sec) AS p95_latency,
    max(latency_sec) AS max_latency
    BY timestamp_issue
| eval min_latency = tostring(round(min_latency,0), "duration")
| eval avg_latency = tostring(round(avg_latency,0), "duration")
| eval median_latency = tostring(round(median_latency,0), "duration")
| eval p95_latency = tostring(round(p95_latency,0), "duration")
| eval max_latency = tostring(round(max_latency,0), "duration")
| sort timestamp_issue

Check for Timestamp Extraction Failures

SPL: Detect Timestamp Extraction Issues 
| tstats count WHERE index=* sourcetype="azure:aad:signin" earliest=-1h BY _time, _indextime span=1s
| eval time_diff = abs(_indextime - _time)
| where time_diff < 2
| stats count AS potential_extraction_failures
| eval warning = if(potential_extraction_failures > 100, 
    "⚠️ Many events have _time ≈ _indextime - timestamp extraction may be failing",
    "✓ Timestamp extraction appears healthy")

Timezone Validation

SPL: Check for Timezone Issues 
index=* sourcetype="azure:aad:signin" earliest=-1h
| eval event_hour = strftime(_time, "%H")
| eval index_hour = strftime(_indextime, "%H")
| eval hour_diff = (index_hour - event_hour + 24) % 24
| where hour_diff > 0 AND hour_diff < 12
| stats count BY hour_diff
| eval possible_tz_issue = "Events consistently " . hour_diff . " hours behind - check timezone config"

Duplicate Event Detection

Duplicate events inflate statistics, cause false positives in threshold-based detections, and waste license. Common causes: multiple collection paths, HEC retry storms, and misconfigured forwarders.

Check for Duplicates

SPL: Detect Duplicate Events 
index=* sourcetype="azure:aad:signin" earliest=-1h
| eval event_hash = md5(_time . _raw)
| stats count BY event_hash
| where count > 1
| stats 
    sum(count) AS total_duplicate_events,
    dc(event_hash) AS unique_duplicated_hashes,
    avg(count) AS avg_copies_per_event
| eval duplicate_rate = round(total_duplicate_events / (total_duplicate_events + unique_duplicated_hashes) * 100, 2)."%"
| eval status = case(
    total_duplicate_events == 0, "✓ No duplicates detected",
    duplicate_rate < 1, "⚠️ Minor duplicates (" . duplicate_rate . ")",
    duplicate_rate < 5, "⚠️ Moderate duplicates (" . duplicate_rate . ") - investigate",
    true(), "✗ High duplicate rate (" . duplicate_rate . ") - FIX REQUIRED"
)

Identify Duplicate Sources

SPL: Find Which Hosts/Inputs Cause Duplicates 
index=* sourcetype="azure:aad:signin" earliest=-1h
| eval event_hash = md5(_time . _raw)
| stats count, values(host) AS hosts, values(source) AS sources BY event_hash
| where count > 1
| stats 
    sum(count) AS duplicates,
    values(hosts) AS duplicate_hosts,
    values(sources) AS duplicate_sources
| eval diagnosis = case(
    mvcount(duplicate_hosts) > 1, "Multiple hosts sending same events - check forwarder config",
    mvcount(duplicate_sources) > 1, "Multiple inputs collecting same data - disable one",
    true(), "Same host/source sending duplicates - check for retry issues"
)
