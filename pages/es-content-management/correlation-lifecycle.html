This page covers the complete lifecycle of correlation searches from draft through retirement, including scheduling strategy, throttling, versioning, failure modes, and operational health monitoring.

🚨 CRITICAL: Single Production Environment

There is no DEV or UAT for Splunk ES in this environment. Every correlation search change is a production change. This makes the lifecycle stages below non-optional — they are your only safety net.

  • Backtesting replaces what DEV would do
  • Monitoring-only mode replaces what UAT would do
  • Throttling and kill switches replace what rollback infrastructure would do
⚠️ Assumptions — Verify Before Proceeding
  • Assumption: You have permission to create, modify, and schedule saved searches. Verify: Check your role includes schedule_search and edit_correlationsearches capabilities.
  • Assumption: Search concurrency has headroom for new scheduled searches. Verify: Check Health & Performance page for concurrency assessment.
  • Assumption: SOC is aware of the lifecycle and their role in it. Risk if wrong: SOC receives alerts they weren't expecting.

Scheduling Strategy

Scheduling is one of the most impactful decisions for correlation search reliability. Bad scheduling causes skipped searches, missed detections, and performance problems.

Cron Selection Guide

Detection Priority Recommended Cron Lookback Window Use When Concurrency Impact
Critical (real-time-ish) */5 * * * * -6m@m to -1m@m Active attack detection, brute force in progress, DDoS 🔴 HIGH — Use sparingly (max 3-5 at this frequency)
High */15 * * * * -16m@m to -1m@m Privilege escalation, account compromise, MFA bypass 🟡 MEDIUM — Reasonable for 10-15 searches
Standard */30 * * * * or 7,37 * * * * -35m@m to -5m@m Most detections: failed logins, policy violations, anomalies 🟢 LOW — Bulk of detections should be here
Low / Compliance 15 * * * * (hourly) -65m@m to -5m@m Compliance checks, account lifecycle, slow-burn threats 🟢 MINIMAL
Daily reports 30 6 * * * (6:30 AM) -25h@h to -1h@h Daily summaries, trend reports, overnight activity review 🟢 MINIMAL
🚨 NEVER Use These Cron Patterns
  • * * * * * — Every minute. Will overwhelm search concurrency immediately.
  • 0 * * * * — Top of every hour. This is when EVERY other scheduled search runs. Guaranteed concurrency collision.
  • */5 * * * * on more than 5 searches — Five-minute searches compete aggressively for slots. Reserve for truly critical detections only.

Lookback Window Logic

The lookback window determines how much historical data each search run examines. Getting this wrong causes either missed events (gap) or duplicate detections (overlap).

Lookback Rules

  • Lookback window = cron interval + 1 minute buffer. If cron runs every 15 minutes, lookback should be 16 minutes.
  • Always use @m rounding. -16m@m rounds to the minute boundary, preventing sub-minute gaps.
  • The -1m@m end boundary gives a 1-minute buffer for indexing delay. Events that arrived in the last minute may not be fully indexed.
  • When data has high latency (e.g., Azure Event Hubs can have 2-5 min delay), increase the buffer accordingly: -21m@m to -5m@m.

Skew Handling

Search skew is when a scheduled search doesn't run exactly on time due to concurrency or system load. Splunk Cloud has a default skew window.

Situation What Happens Impact Mitigation
Normal skew (< 60 seconds) Search starts a few seconds late None — lookback buffer covers this No action needed
Moderate skew (1-5 min) Search starts significantly late If using now as end time, you examine future-relative data. Use -1m@m instead. Always use static end boundary, never now
Search skipped entirely Concurrency full, search could not start within its window Detection gap — events during this window are not evaluated See skipped search detection SPL below. Reduce concurrency load.

Throttling vs. Suppression vs. Filtering

These three mechanisms reduce alert volume, but they work differently and have very different risk profiles. Choosing the wrong one can hide real attacks.

Mechanism What It Does When to Use Risk Reversibility
Throttling Limits notable creation to one per time window per throttle key (e.g., one notable per src per hour) ALWAYS. Every production detection should have a throttle configured. 🟢 Low — Events still match, just fewer notables. First hit always fires. Instant — change throttle settings
Suppression (Notable Suppression) Hides specific notables from Incident Review based on field values Known false positives from specific sources. Temporary use while tuning. 🟡 Medium — Suppressed notables still exist but are invisible to analysts. Easy to forget. Requires manual removal of suppression rules
Filtering (Search Logic) Adds WHERE or NOT clauses to exclude specific patterns from detection logic Permanent exclusions for known-good patterns (service accounts, known IPs) 🔴 High — Filtered events are NEVER evaluated. If filter is too broad, real attacks are missed permanently. Requires search modification and re-backtest
🚨 The Correct Order of Noise Reduction

Always apply mechanisms in this order:

  1. Throttle first. Reduces duplicate notables without hiding anything. Zero risk.
  2. Suppress second. Hides known FPs temporarily while you plan a proper fix.
  3. Filter last. Only after you've confirmed the filtered pattern is ALWAYS benign. Document heavily.

Never jump to filtering. A broad filter is an unrecoverable blind spot.

Throttle Configuration Examples

Detection Type Throttle Key Fields Throttle Window Rationale
Brute force src, dest 1 hour One alert per source-destination pair per hour. Ongoing attacks don't flood.
Account lockout user 4 hours One alert per user per 4 hours. Repeated lockouts don't stack.
WAF attack burst src_ip, attack_category 30 minutes One alert per attacker per attack type per 30 min. Fast enough for active attacks.
Privilege escalation user, dest 24 hours One alert per user-system pair per day. Privilege changes are not rapid events.
Threat intel match src, threat_match_value 6 hours One alert per source per matched IOC per 6 hours. Persistent connections don't flood.

Description Field as Backup

Splunk's saved search description field can store a previous version of the SPL. Before making changes:

  1. Copy the current SPL to the description field (prefix with BACKUP v1.2:)
  2. Make your change to the search SPL
  3. Update the inline version header
  4. If you need to rollback, copy from description back to SPL
⚠️ Limitation: Description field has a character limit

The description field is limited to ~8000 characters in Splunk Cloud. For complex detections, store the full backup in the detection registry (external document) instead.

Failure Modes

Correlation searches fail silently. If you are not actively monitoring for these failure modes, you have detection gaps and don't know it.

Skipped Searches

🚨 This Is the #1 Silent Killer of Detection Coverage

A skipped search means the search was scheduled to run but didn't, usually because all search concurrency slots were full. During the skipped window, no events were evaluated. Attacks during that window are invisible.

SPL: Detect Skipped Correlation Searches (Last 24 Hours) 
`comment("CRITICAL: Run this daily. Skipped searches = detection blind spots.")`

index=_internal sourcetype=scheduler status="skipped"
| eval search_name=savedsearch_name
| stats count AS skip_count, 
    latest(_time) AS last_skip,
    earliest(_time) AS first_skip
    BY search_name, app
| where skip_count > 0
| eval severity = case(
    skip_count > 20, "🔴 CRITICAL — Persistent skipping",
    skip_count > 5, "🟡 WARNING — Intermittent skipping",
    true(), "🟢 Low — Occasional skip"
)
| sort - skip_count
| table search_name, app, skip_count, severity, first_skip, last_skip

Long-Running Searches

SPL: Correlation Search Runtime Analysis (Last 7 Days) 
`comment("Searches running longer than their cron interval are a problem.")`
`comment("A 15-min cron search that takes 20 min will eventually skip.")`

index=_internal sourcetype=scheduler status="success"
| eval runtime_sec = run_time
| eval runtime_min = round(runtime_sec / 60, 1)
| stats avg(runtime_min) AS avg_runtime,
    max(runtime_min) AS max_runtime,
    p95(runtime_min) AS p95_runtime,
    count AS run_count
    BY savedsearch_name, app
| eval health = case(
    max_runtime > 15, "🔴 CRITICAL — Exceeded 15 min",
    p95_runtime > 10, "🟡 WARNING — P95 above 10 min",
    avg_runtime > 5, "🟡 REVIEW — Avg above 5 min",
    true(), "🟢 Healthy"
)
| sort - max_runtime
| table savedsearch_name, app, run_count, avg_runtime, p95_runtime, max_runtime, health

Concurrency Conflicts

SPL: Search Concurrency Utilization (Last 24 Hours) 
`comment("Shows how many searches are running simultaneously over time.")`
`comment("If this consistently hits the limit, searches WILL skip.")`

index=_internal sourcetype=scheduler
| bin _time span=5m
| stats dc(sid) AS concurrent_searches BY _time
| timechart span=5m max(concurrent_searches) AS peak_concurrent
| eval danger_threshold = 24
| eval status = if(peak_concurrent > danger_threshold, "OVER LIMIT", "OK")

Failure Mode Summary

Failure Mode Symptom Impact Detection Method Remediation
Skipped search No results during expected window Complete detection gap for that time period Scheduler log query above Reduce concurrency load, reschedule, increase priority
Long runtime Search takes longer than cron interval Cascading delays, eventual skipping Runtime analysis query above Optimize SPL, use tstats, reduce lookback, add filters
Data model gap tstats returns zero where raw search finds events Detection uses stale or incomplete accelerated data Compare tstats vs search counts Rebuild data model acceleration, check CIM compliance
Lookup file corruption Detection uses lookup that returns empty or stale Allowlists, asset lookups, or threat intel not applied Check lookup file timestamps and row counts Regenerate lookup, fix context-gen searches
Throttle misconfiguration Either zero notables (over-throttled) or flood (under-throttled) Missed alerts or alert storm Compare search results count vs notable count Review and adjust throttle key fields and window
Ingestion lag Events arrive after the search window has passed Late events never evaluated by any search run Check index time vs event time for data sources Increase lookback end buffer (e.g., -5m@m instead of -1m@m)

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • More than 5 correlation searches are consistently skipping. Escalate to Splunk admin. This is a platform capacity issue, not a detection issue.
  • Any critical-priority search skips even once. This means an active attack could be missed. Investigate concurrency immediately.
  • Average search runtime for any search exceeds its cron interval. The search needs optimization or the schedule needs adjustment before it causes cascading problems.
  • Data model acceleration is behind by more than 1 hour. All tstats-based detections are using stale data. Escalate to Splunk admin.
  • A search has been in monitoring-only mode for more than 4 weeks. It's stuck. Decide: fix it, or kill it. Don't let monitoring-mode searches accumulate indefinitely.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Run everything every 5 minutes" Consumes all concurrency slots. Causes skipping across ALL searches. Degrades entire ES platform. Reserve 5-min cron for 3-5 truly critical detections. Use 15-30 min for the rest.
"Use earliest=-24h to catch everything" Each run scans 24 hours of data. At 15-min intervals, that's 96 redundant scans per day per search. Massive performance waste. Match lookback to cron interval + small buffer. Never lookback farther than necessary.
"No throttle — we want every alert" A single brute force attack generates hundreds of events. Without throttle, that's hundreds of identical notables. SOC drowns. Always throttle. Key on meaningful fields (src, user). Minimum 30-min window.
"Skip monitoring mode — it's just an OOTB search" Even OOTB searches behave differently in YOUR data. Monitoring mode is how you catch this before the SOC does. 1-2 weeks monitoring-only for EVERY new production detection. No exceptions.
"No version tracking — it's just a search" When something breaks, you have no way to know what changed or revert. Debugging becomes guessing. Inline version comments in every search. Change log in detection registry.
