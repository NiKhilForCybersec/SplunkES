Purpose: The complete pipeline for safely taking ESCU content from "installed and disabled" to "running in production." Covers the five-stage ESCU operationalization pipeline: Evaluate → Clone → Tune → Enable → Update Management. Each stage has explicit pass/fail criteria.

Ownership: Detection Engineering (execution) + SOC Lead (production sign-off)

Preconditions: ESCU is installed. You've read ESCU Overview. You know your current log coverage and data quality status.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: Your detection lifecycle process is established. Risk if wrong: ESCU content bypasses governance. See Correlation Search Lifecycle.
  • Assumption: You have capacity for additional correlation searches (concurrency headroom). Verify: Run the concurrency check from Health & Performance. Each new search consumes a slot.
  • Assumption: Data model acceleration is current for the data models ESCU detections reference. Verify: Run the DM acceleration check. If a data model isn't accelerated, tstats-based ESCU detections won't work.
  • Assumption: The SOC has bandwidth to absorb new detections (not already drowning in noise). Risk if wrong: Adding detections to an overwhelmed SOC makes everything worse.

Stage 1: Evaluate

Evaluation determines which ESCU detections are worth pursuing. Most ESCU detections will be skipped — and that's expected. A typical environment can use perhaps 10-20% of ESCU content.

Per-Detection Evaluation Checklist

✅ Evaluation Criterion How to Check Pass / Skip
☐ 1. Threat relevance Does this detection address a threat in your threat model? Is the targeted technique relevant to your industry (retail, manufacturing)? Pass: Relevant to threat model. Skip: Targets threats you don't face (e.g., ICS/SCADA if you're cloud-only).
☐ 2. Data source availability Read the SPL. What index/sourcetype/data model does it query? Do you have that data in Splunk? Pass: Data exists and is CIM-mapped. Skip: Data doesn't exist (flag as Phase 1 gap).
☐ 3. Data model acceleration If the search uses | tstats, is the referenced data model accelerated? Pass: DM accelerated and current. Skip: DM not accelerated (enable acceleration first, then return).
☐ 4. SPL logic review Read the SPL. Do you understand what it does? Are the field names correct for your data? Are thresholds reasonable? Pass: Logic is sound and understandable. Skip: Logic is broken, overly complex, or references fields you don't have.
☐ 5. Existing coverage check Do you already have a detection covering this technique? Is the ESCU version better? Pass: No existing coverage OR ESCU version is better. Skip: Existing detection already covers this adequately.
☐ 6. Dependencies Does this detection require baseline searches, specific lookups, or macros? Are those present and functional? Pass: All dependencies met. Skip: Missing critical dependencies (or plan to address them).
☐ 7. Resource impact What's the expected search cost? Complex joins, wide time ranges, or high-cardinality fields = expensive. Pass: Resource cost is acceptable. Skip: Search is too expensive for current capacity.

Evaluation Decision Outcomes

Outcome Criteria Next Action Registry Entry
✅ Proceed to Clone All 7 checks pass Move to Stage 2 Status: "Evaluating — Approved for clone"
⏸️ Defer — Data Gap Detection is relevant but required data doesn't exist Add data source to Phase 1 backlog. Re-evaluate when data is onboarded. Status: "Deferred — Awaiting [data source]"
⏸️ Defer — Acceleration Gap Data exists but data model is not accelerated Request DM acceleration from Splunk admin. Re-evaluate when acceleration is complete. Status: "Deferred — Awaiting DM acceleration"
⏭️ Skip — Not Relevant Threat not in scope, or existing coverage is adequate Document reasoning. No further action needed. Status: "Skipped — [reason]"
⏭️ Skip — Logic Unsuitable SPL logic is fundamentally flawed or incompatible with your environment If the concept is good, consider building a custom detection from scratch. Status: "Skipped — Logic unsuitable. Custom build considered."

Stage 2: Clone

The clone stage is identical to the standard OOTB clone procedure. See Enablement Mechanics — Cloning for the full step-by-step. Key ESCU-specific additions:

Clone Step ESCU-Specific Guidance
Naming convention CUSTOM - [ESCU Story] - [Detection Name] - [Org] Tuned
Example: CUSTOM - Ransomware - Wevtutil USN Journal Deletion - Retail Tuned
Version header Include ESCU source version: `comment("Cloned from ESCU v4.18.0 — Ransomware Story")`
OOTB original Leave the ESCU original DISABLED. It was already disabled — just confirm it stays that way.
Macro dependencies If the ESCU detection uses ESCU-specific macros, verify the macros exist and resolve correctly. Consider inlining the macro content into your clone to avoid dependency on ESCU updates changing macro definitions.
Baseline searches If the detection requires a baseline search (generates a lookup that the detection references), ensure the baseline is enabled and has run at least once. Check lookup freshness.

Stage 3: Tune

ESCU detections are written for generic environments. Your environment is not generic. Tuning adapts the detection to your data volumes, user behavior, and business patterns.

Common ESCU Tuning Requirements

Tuning Category What to Look For Typical Adjustment Example
Thresholds ESCU uses generic thresholds (e.g., "5 failed logins") that may be too low for your volume Backtest to find your actual data distribution. Set threshold at p95 or p99. ESCU: >5 failures → Retail: >25 failures (high-volume POS environment)
Index/Sourcetype filters ESCU uses generic index references or data model searches that may match unintended data Add explicit index and sourcetype filters to narrow scope Add index=windows sourcetype=WinEventLog:Security to endpoint detections
Environment exclusions Known benign patterns: vuln scanners, monitoring tools, scheduled tasks, service accounts Add NOT clauses for known-good entities. Use lookup tables, not hard-coded IPs. NOT [| inputlookup known_scanners.csv | fields src_ip]
Schedule adjustment ESCU default schedule may conflict with your concurrency or may be too frequent for your needs Adjust cron to fit your scheduling strategy. Maintain lookback > cron + buffer. ESCU: every 5 min → Your env: every 15 min (sufficient for medium-severity detection)
Field name alignment ESCU assumes standard CIM fields. Your TAs may extract to slightly different names. Verify field names in your data match what the SPL references. Adjust if needed. ESCU references process_name but your TA extracts process → rename or update SPL

Backtest Procedure for ESCU Clones

  1. Copy the cloned SPL to the Splunk search bar
  2. Set time range to 7 days (use the same lookback the production search will use, repeated over 7 days of history)
  3. Run the search and review results
  4. Assess volume: How many results per day? If > 50/day at medium severity → threshold needs raising
  5. Assess accuracy: Sample 20 results. What percentage are true positive? If FP rate > 30% → logic needs tuning
  6. Iterate: Adjust thresholds, add filters, re-run. Repeat until FP rate < 30% and daily volume < 20
  7. Document: Record backtest results (dates, volume, FP rate, changes made) in the detection registry

Stage 4: Enable

Enablement follows the standard Correlation Search Lifecycle. No ESCU-specific exceptions. The clone goes through:

  1. Monitoring-Only (7-14 days): Search runs, generates notables, but SOC is informed these are monitoring-only. Volume and FP rate are tracked.
  2. Production (with sign-off): SOC Lead approves. SOC notified per Change Management pre-deployment notification.
⚠️ ESCU Enablement Rate Limit

Maximum 2-3 new ESCU-sourced detections per week. Each new detection adds load to the SOC and search concurrency. Even well-tuned detections have an adjustment period. Spacing out deployments lets the SOC adapt and lets you measure the impact of each addition.

The ESCU Evaluation Sprint

Rather than evaluating ESCU content continuously (which burns out the team), use a quarterly sprint model:

Sprint Phase Duration Activities Output
Prioritize Half day Review new ESCU content since last sprint. Rank analytic stories by threat model relevance. Select top 3-5 stories to evaluate. Prioritized evaluation backlog
Evaluate 1-2 days Run per-detection evaluation checklist for each detection in selected stories. Document pass/defer/skip for each. Evaluation decisions in registry
Clone & Tune 2-3 days Clone approved detections. Tune for environment. Backtest. Iterate until FP < 30%. Tuned clones ready for lifecycle
Enable Ongoing (2-3/week) Deploy tuned clones through monitoring → production lifecycle. Stagger over 2-4 weeks. New production detections
Report Half day Summarize sprint: stories evaluated, detections deployed, coverage gaps identified, Phase 1 data requests. Sprint summary for stakeholders

Baseline search never ran Detection always returns zero or fires for everything (no baseline to compare against) Baseline search dependency wasn't identified during evaluation Anomaly-based detection has no baseline — either dead or flooding Identify and enable baseline search. Wait for it to complete (may take hours/days). Then test detection.
ESCU update breaks an active clone After ESCU update, macro referenced by clone now resolves differently ESCU update changed a macro your clone depends on Clone behavior changes without any change to the clone itself Inline macros into clones to eliminate dependency. ESCU becomes a "checkbox" exercise "We have ESCU installed" reported to management, but no content is operationalized No resources allocated, no sprint model, no ownership False sense of coverage. Rollback Steps

  1. ESCU clone not performing as expected: Disable the clone. Return to Stage 3 (Tune). Backtest again with adjusted parameters.
  2. ESCU update caused issues: Roll back the ESCU app to the previous version. Verify all clones still function. Report the issue.
  3. Entire evaluation sprint produced poor-quality detections: Disable all detections from the sprint. Review evaluation criteria — the bar may need raising. Re-evaluate with stricter thresholds.

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • More than 5 ESCU detections enabled in a single week. Rate limit exceeded. SOC can't absorb that many new alert types simultaneously. Stagger further deployments.
  • ESCU update changed macro behavior affecting active clones. Immediately test all clones that reference ESCU macros. Disable affected clones until verified.
  • Evaluation sprint has been "in progress" for more than 4 weeks without deployments. Evaluation paralysis. Cut scope. Deploy what's ready. Ship 3 good detections rather than evaluating 30.
  • ESCU is being presented to auditors as "coverage" but no detections are in production. This is misleading. Escalate to Security Manager to set correct expectations.
  • Someone enabled ESCU detections directly (not cloned). Disable and clone them properly. Those detections are vulnerable to being overwritten by the next ESCU update.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Enable the whole Analytic Story" Analytic stories contain 5-20+ detections. Enabling all at once creates a noise storm. Some may require data you don't have. Evaluate each detection within a story individually. Deploy the viable ones one at a time.
"Skip the backtest — ESCU already validated it" ESCU validated against their lab data. Your data volumes, naming conventions, and user patterns are different. Always backtest against your production data. Every time. No exceptions.
"Just enable it — we'll tune if it's noisy" Reactive tuning means the SOC gets hit with noise first. SOC trust is damaged first, tuning happens second. Tune BEFORE enabling. Monitoring-only period catches noise before the SOC sees it.
"We evaluated ESCU last year, we're done" ESCU updates continuously. New threats emerge. Last year's evaluation is stale. Quarterly evaluation sprints. Each sprint reviews new content since the last sprint.
"Track ESCU evaluations in my head" When you leave, all evaluation knowledge leaves with you. Auditors can't query your memory. Every evaluation decision goes in the detection registry with reasoning, date, and evaluator.
