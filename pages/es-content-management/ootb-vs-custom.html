OOTB vs Custom Detection Strategy

📋 Page Status: HARDENED — ES CONTENT MANAGEMENT

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This page provides the decision framework for choosing between OOTB, cloned, and custom detections. Every detection in this environment must be justified against this framework.

☁️ Splunk Cloud Safety Box — ES Content Management

✅ Allowed in Cloud: All ES content management workflows are UI-based and work identically in Cloud. Correlation search creation, enablement, tuning, suppression, ESCU deployment, and content lifecycle management all use the ES UI. No differences from Enterprise.

⚠️ Restricted in Cloud: If this page references savedsearches.conf file edits, btool debugging, or filesystem-level backup procedures, those apply only to customer-managed infrastructure. You cannot edit .conf files directly in Splunk Cloud.

🔄 Cloud-Safe Alternative: All correlation search management is via Configure → Content → Content Management. For backup/versioning, export searches via the ES UI or REST API and store in Git. Use | rest /services/saved/searches to inspect search configurations programmatically. Deploy content updates as packaged apps via SSAI.

🚨 CRITICAL: The Goal Is Working Detections, Not Detection Count

5 well-tuned detections that the SOC trusts are worth more than 50 enabled OOTB searches that nobody triages.

  • Do NOT measure success by how many searches are enabled
  • Do NOT build custom when OOTB works after tuning
  • Do NOT enable OOTB when the data reality doesn't support it
  • Every detection must have an owner, a runbook, and a reason to exist
⚠️ Assumptions — Verify Before Proceeding
  • Assumption: OOTB content inventory has been completed (see OOTB Content Reality). Risk if wrong: You can't make good decisions without knowing what exists.
  • Assumption: Phase 1 and Phase 2 are complete for the data sources you plan to detect against. Risk if wrong: Detection without validated data is guessing.
  • Assumption: SOC has capacity to triage new detections. Risk if wrong: Enabling detections nobody can triage wastes everyone's time.

The Four Paths for Every Detection Need

For every security detection requirement, there are exactly four possible paths. Each has different costs, risks, and maintenance burdens. The decision tree below helps you pick the right one.

Path What It Means When to Use Ongoing Cost Upgrade Risk
1. Enable OOTB As-Is Enable the OOTB search exactly as shipped. No modifications. OOTB logic matches your data, thresholds are appropriate, backtest looks clean 🟢 Lowest — Splunk maintains during upgrades 🟢 None — Upgrades improve it automatically
2. Clone & Tune Copy the OOTB search, modify thresholds/filters, disable original OOTB logic is correct but thresholds or filters need retail adjustments 🟡 Medium — You own the clone. Must review after ES upgrades. 🟡 Medium — Must manually compare with updated OOTB after upgrades
3. Write Custom Build detection from scratch for a specific use case No OOTB covers this threat, OR OOTB logic fundamentally doesn't fit your data 🔴 Highest — Entirely your responsibility to maintain 🟢 None — Custom is independent of ES upgrades
4. Suppress / Disable Leave OOTB disabled with documented justification No data, not relevant, requires RBA, or SOC cannot triage 🟢 Minimal — Just document and re-evaluate quarterly 🟢 None

The Cost of Premature Custom Detections

Building custom detections is expensive. Before writing custom, understand what you're signing up for:

Cost Factor OOTB (Enable As-Is) Clone & Tune Custom
Initial development 30 min (evaluate + enable) 2-4 hours (clone + modify + test) 4-16 hours (research + write + test)
Monitoring period 1-2 weeks 1-2 weeks 2-4 weeks (more unknowns)
Documentation Decision record only Decision record + what was changed Full detection document (logic, rationale, MITRE mapping, runbook)
Ongoing maintenance Splunk handles via upgrades Quarterly review + upgrade comparison Monthly review + threat intel updates + logic updates
Knowledge required ES admin basics ES admin + SPL intermediate Advanced SPL + threat research + data model expertise
Risk of abandonment Low Medium High — no one maintains what they don't understand
⚠️ The "Custom Detection Graveyard"

In almost every enterprise Splunk environment, there are custom detections that:

  • Were built by a consultant who left
  • Nobody understands the logic
  • Haven't been reviewed in over a year
  • Generate notables that nobody triages
  • Consume search concurrency slots for zero value

Every custom detection you write today becomes someone else's mystery tomorrow. Only build custom when OOTB truly cannot work.

When OOTB Is "Good Enough"

OOTB is the right choice when the following conditions are met. Do NOT over-engineer when the standard detection works.

✅ Generic Threat Patterns

Brute force, multiple failed logins, account lockouts — these are universal patterns. If your data maps cleanly to the Authentication data model, OOTB brute force detections work well after threshold tuning.

Example: "Excessive Failed Logins" OOTB works if you adjust the threshold from 5 to 20 (retail has higher baseline).

✅ Threat Intelligence Matching

If you have quality threat intel feeds configured, the OOTB threat intel matching searches work. They match IOCs against network, DNS, and email data. No custom logic needed — the value is in the intel quality.

Example: "Threat Activity Detected" fires when a known-bad IP appears in firewall logs.

✅ Compliance-Driven Detections

Many compliance requirements (PCI-DSS, SOX) specify specific detection types. OOTB "Unauthorized Access Attempt" or "Account Created/Deleted" searches directly map to audit requirements with minimal tuning.

Example: PCI requirement 10.2 — OOTB notable for "User Created" satisfies logging and detection requirements.

✅ Well-Populated Data Models

When your data maps cleanly to CIM data models (Authentication, Network_Traffic, Endpoint), OOTB searches that use tstats queries will work efficiently. The data model abstraction means the OOTB logic applies regardless of the underlying sourcetype.

Example: Any tstats-based OOTB search works if the data model is properly accelerated and populated.

When Custom Detections Are Mandatory

Custom detections are required when OOTB cannot address the threat, regardless of tuning. These are the scenarios where you MUST build custom.

WAF Detection Use Cases (Custom Required)

Use Case Why Custom OOTB Alternative?
Akamai WAF attack pattern correlation No OOTB search understands Akamai-specific attack categories, rule IDs, or action codes None — Akamai is not a standard ES data source
WAF bypass detection Detecting when attacks pass through WAF requires correlating WAF logs with web server logs — OOTB doesn't do this None
DDoS traffic pattern detection Retail DDoS patterns (slow-rate attacks on checkout APIs) require custom thresholds based on YOUR traffic baselines OOTB "Network Volumetric Anomaly" exists but doesn't understand retail API patterns
Bot classification and detection Retail needs to distinguish legitimate bots (Googlebot) from malicious bots (credential stuffing). OOTB has no bot classification. None

MFA Detection Use Cases (Custom Required)

Use Case Why Custom OOTB Alternative?
MFA fatigue / push bombing Detecting rapid MFA push requests requires counting push events per user within a window — no OOTB for this specific pattern No OOTB covers MFA push fatigue specifically
MFA bypass via legacy protocols Detecting authentication via legacy protocols (IMAP, SMTP, ActiveSync) that skip MFA requires Entra ID-specific field analysis OOTB "Multiple Authentication Mechanism" exists but doesn't target MFA bypass specifically
Impossible travel with MFA context Standard impossible travel doesn't consider MFA status — an impossible travel WITH successful MFA is higher severity OOTB impossible travel exists but lacks MFA context enrichment
Conditional access policy failures Entra ID Conditional Access failures have specific result codes that require custom mapping to detect policy bypass attempts None

Other Scenarios Requiring Custom

  • Cross-source correlation: When detection requires correlating events from two or more different data sources (e.g., WAF event + authentication failure within 5 minutes)
  • Business-context detections: When detection requires understanding business logic (e.g., "admin access outside business hours for this specific role")
  • Non-standard data sources: When your data source has no CIM mapping and OOTB searches can't see it
  • Retail-specific threats: Point-of-sale skimming patterns, loyalty program fraud, inventory manipulation — OOTB has nothing for these

Account lockout Enable As-Is Account lockout events are specific enough that OOTB thresholds work. Low noise risk.

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • You want to build custom but there IS an OOTB option. Stop and justify why OOTB won't work. Get peer review before committing to custom.
  • A stakeholder demands "enable all OOTB for compliance." Escalate with the anti-patterns from this page. Volume ≠ coverage. Noise ≠ detection.
  • You have more than 10 cloned detections with no owner. Stop adding more. Fix ownership for existing clones first.
  • Custom detection development is taking more than 2 days per detection. Re-evaluate scope. The detection may be too complex for current data quality.
  • SOC is rejecting alerts from a detection you enabled. Disable it, don't argue. Investigate why and fix before re-enabling.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Custom is always better than OOTB" Custom is more expensive to maintain, harder to hand off, and more likely to become a zombie. OOTB that works is the BEST option. Try OOTB first. Clone & tune second. Custom only when nothing else works.
"Clone everything to be safe" Creates massive maintenance burden. After ES upgrades, every clone must be manually reviewed. 50 clones = 50 manual comparisons. Only clone when OOTB needs specific changes. Enable as-is whenever possible.
"We need custom for every MITRE technique" MITRE coverage without data is theater. You can't detect T1059 if you don't have process execution logs. Map detections to available data first, then to MITRE. Coverage follows data, not the matrix.
"Let the consultant build it all custom" When the consultant leaves, nobody maintains or understands the detections. They become zombie searches within months. Consultants should document heavily. Internal team must understand every detection. Prefer OOTB when possible.
"Disable OOTB we don't understand" May disable a working detection that was catching real threats. Loss of visibility without anyone knowing. Investigate before disabling. Check notable output first. If it's catching real things, don't touch it.
