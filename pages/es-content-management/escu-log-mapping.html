ESCU Log Mapping

📋 Page Status: HARDENED — ES CONTENT MANAGEMENT

Last Audit: 2024-02 | Auditor: Detection Engineering Team

Purpose: Maps ESCU detection requirements to the data sources they need. Provides SPL and procedures to discover what logs are required for specific Analytic Stories, perform gap analysis between ESCU requirements and your current log ingestion, and feed gaps back into Phase 1 onboarding priorities. This page bridges Phase 1 (Log Coverage) and Phase 3 (Detection).

Ownership: Detection Engineering (gap analysis) + Platform Engineering (data onboarding)

Preconditions: ESCU is installed. You've read ESCU Overview and Operationalizing ESCU. You have a current log coverage matrix from Phase 1.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: You maintain a log coverage matrix that tracks which data sources are ingested into Splunk. Risk if wrong: Gap analysis requires comparing ESCU requirements against your actual coverage. Without a matrix, you're guessing.
  • Assumption: ESCU detection SPL reliably indicates data source requirements through index, sourcetype, or data model references. Reality: Most do, but some use macros that obscure the data source. You may need to resolve macros to find the real requirement.
  • Assumption: Data source gaps can be addressed (budgeted, technically feasible, approved by data owners). Risk if wrong: Identifying gaps without a path to resolution creates a list of excuses, not a plan.

Step 1: Extracting Data Requirements from ESCU SPL

Every ESCU detection search tells you what data it needs — if you know where to look. There are three patterns:

Pattern A: Direct Index/Sourcetype References

The simplest case. The SPL explicitly names the index and/or sourcetype.

Example: Direct Reference in ESCU SPL 
`comment("ESCU detection example — direct index/sourcetype reference")`
index=windows sourcetype=WinEventLog:Security EventCode=4688
| stats count by New_Process_Name, Process_Command_Line, Creator_Process_Name
| where count > 5

`comment("DATA REQUIREMENT: index=windows, sourcetype=WinEventLog:Security")`
`comment("Specific need: Windows Security event logs with process creation (4688)")`
`comment("TA needed: Splunk Add-on for Microsoft Windows")`

Pattern B: Data Model (tstats) References

Many ESCU detections use | tstats against accelerated data models. The data model name tells you what CIM category is needed.

Example: tstats Reference in ESCU SPL 
`comment("ESCU detection example — data model reference")`
| tstats count from datamodel=Endpoint.Processes where
    Processes.process_name="cmd.exe"
    by Processes.dest, Processes.user, Processes.process
| rename Processes.* AS *

`comment("DATA REQUIREMENT: Endpoint data model, Processes node")`
`comment("Underlying data: Process execution logs (Sysmon, WinEventLog:Security 4688, CrowdStrike, etc.)")`
`comment("Prerequisite: Endpoint DM must be ACCELERATED")`
`comment("CIM fields needed: process_name, dest, user, process")`

Pattern C: Macro-Obscured References

Some ESCU detections use macros that hide the actual data source. You need to resolve the macro to find the requirement.

SPL: Resolve a Macro to Find Data Requirements 
`comment("If an ESCU detection uses a macro like:")`
`comment("  `security_content_summariesonly` `security_content_ctime(firstTime)` ")`
`comment("Resolve the macro to see what it actually does:")`

| rest /services/admin/macros splunk_server=local
| search title="security_content_summariesonly" OR title="security_content_ctime*"
| table title, definition, args
| eval note = "This shows what the macro resolves to — use the definition to find the real data requirement"

Step 2: Automated Data Requirement Extraction

SPL: Extract Data Model Requirements from All ESCU Detections 
`comment("Scans all ESCU correlation searches and extracts data model references")`
`comment("Shows which data models your ESCU content depends on")`

| rest /services/saved/searches splunk_server=local
| search eai:acl.app="DA-ESS-ContentUpdate"
| where isnotnull(action.correlationsearch.enabled)
| eval data_model = case(
    match(search, "(?i)datamodel\s*=\s*Endpoint"), "Endpoint",
    match(search, "(?i)datamodel\s*=\s*Network_Traffic"), "Network_Traffic",
    match(search, "(?i)datamodel\s*=\s*Network_Resolution"), "Network_Resolution",
    match(search, "(?i)datamodel\s*=\s*Authentication"), "Authentication",
    match(search, "(?i)datamodel\s*=\s*Web"), "Web",
    match(search, "(?i)datamodel\s*=\s*Email"), "Email",
    match(search, "(?i)datamodel\s*=\s*Change"), "Change",
    match(search, "(?i)datamodel\s*=\s*Malware"), "Malware",
    match(search, "(?i)datamodel\s*=\s*Risk"), "Risk",
    match(search, "(?i)tstats"), "Uses tstats (resolve manually)",
    match(search, "(?i)index\s*="), "Direct index reference",
    true(), "Unknown — review SPL manually"
)
| stats dc(title) AS detection_count,
    values(title) AS sample_detections
    BY data_model
| sort - detection_count
SPL: Extract Index/Sourcetype Requirements from ESCU Detections 
`comment("For ESCU detections that use direct index references")`
`comment("Extracts the index and sourcetype patterns from the SPL")`

| rest /services/saved/searches splunk_server=local
| search eai:acl.app="DA-ESS-ContentUpdate"
| where isnotnull(action.correlationsearch.enabled) AND match(search, "(?i)index\s*=")
| rex field=search "index\s*=\s*(?\w+)"
| rex field=search "sourcetype\s*=\s*(?[^\s\|]+)"
| table title, required_index, required_sourcetype
| fillnull value="(not explicit)"
| sort required_index, required_sourcetype

Step 3: Gap Analysis — ESCU Requirements vs Your Coverage

Manual Gap Analysis Procedure

  1. Run the extraction SPL from Step 2 to get your ESCU data requirements by data model and by index
  2. For each data model requirement, check if the model is accelerated:
    SPL: Check Data Model Acceleration Status 
    | rest /services/datamodel/model splunk_server=local
| table title, acceleration, "acceleration.earliest_time",
    eai:acl.app
| eval accel_status = case(
    acceleration="1", "✅ Accelerated",
    acceleration="0", "❌ NOT Accelerated",
    true(), "❓ Unknown"
)
| sort title
  3. For each direct index requirement, verify data exists:
    SPL: Verify Data Exists in Required Indexes 
    `comment("Replace YOUR_INDEX with each required index from Step 2")`

| tstats count WHERE index=YOUR_INDEX BY sourcetype
| eval status = if(count > 0, "✅ Data present", "❌ No data")
| sort - count
  4. Build the gap matrix:

Gap Matrix Template

ESCU Requirement Type Available? Accelerated? ESCU Detections Blocked Gap Classification Action
Endpoint.Processes Data Model ✅ Yes ✅ Yes — — No gap. Proceed with evaluation.
Network_Resolution Data Model ✅ Yes ❌ No DNS Tunneling, Suspicious DNS Query, ... Quick Win Enable DM acceleration. Data exists; acceleration is the only gap.
index=sysmon Index ❌ No N/A Living Off the Land, Process Injection, ... Planned Sysmon deployment project. Add to Phase 1 backlog. ETA: Q2.
Email Data Model ❌ No N/A Phishing campaign detections Blocker Email logs not ingested. Requires O365 connector project + budget approval. Defer ESCU email detections.

💡 Retail / Manufacturing Focus

For a retail environment, the highest-value ESCU story categories are typically: Ransomware (protect POS and supply chain), Credential Access (protect AD and cloud identity), and Network Threat (WAF + DNS visibility). Cloud stories become relevant as you adopt Azure/AWS/GCP services. Insider Threat stories require the broadest data coverage and are typically a later-maturity initiative.

Step 5: Feeding Gaps Back to Phase 1

Every data gap identified through ESCU mapping becomes a Phase 1 onboarding candidate. The key is prioritization: not all gaps are equal.

Gap Prioritization Framework

Priority Criteria Example Action
P1 — Critical Blocks 5+ high-value ESCU detections AND addresses a top-3 threat model risk No Sysmon = no endpoint process detections = no ransomware or credential theft visibility Immediate onboarding project. Escalate to platform team.
P2 — High Blocks 3+ ESCU detections AND addresses a known risk, but existing compensating controls exist No DNS logs = no DNS tunneling detection, but network firewall provides some visibility Next onboarding sprint. Plan and schedule.
P3 — Medium Blocks 1-2 ESCU detections OR addresses a lower-priority threat No email logs = no phishing detections, but email gateway handles most phishing Add to backlog. Address when capacity allows.
P4 — Low / Defer Blocks ESCU detections for threats not in your current threat model, or data source is prohibitively expensive No ICS/SCADA logs for OT-focused ESCU stories (and you have no OT environment) Skip. Document as not applicable. Re-evaluate if threat model changes.

Failure Modes

Failure Mode Symptom Root Cause Impact Fix
Mapping done but never acted on Gap analysis completed 6 months ago, no gaps addressed No ownership, no prioritization, no connection to Phase 1 backlog ESCU detections remain unusable. Analysis was wasted effort. Assign gaps to Phase 1 backlog with owners and deadlines. Track in sprint planning.
Data model assumed available but not accelerated ESCU detections using tstats return zero results Data exists, TA is installed, but data model acceleration is off or incomplete Silent detection failure — search runs, finds nothing Include DM acceleration check as mandatory step in gap analysis. Fix before enabling detections.
CIM field mismatch Data model is accelerated, data exists, but ESCU detection uses field names not present in your data TA version mismatch, or TA doesn't extract the specific CIM field the detection needs Detection silently fails or produces unexpected results Test each field referenced in the SPL against your actual data. Update TA or add field aliases.
Gap analysis scope too broad Team tries to map ALL ESCU content at once, analysis takes months No prioritization by threat model. Boiling the ocean. Analysis paralysis. Nothing gets deployed. Focus on 3-5 analytic stories per quarter based on threat model priorities. Depth over breadth.
Macro resolution missed Extraction SPL identifies data model but ESCU detection actually queries a different data source via macro Macro abstracts the real data source. Automated extraction doesn't resolve macros. Requirements list is incomplete. Some gaps go undetected. For detections flagged as "Uses tstats (resolve manually)" or "Unknown," manually resolve macros and trace to actual data.

Validation SPL & Expected Output

SPL: ESCU Coverage Readiness Score 
`comment("Estimates what percentage of ESCU detections you COULD enable")`
`comment("Based on data model availability and acceleration")`

| rest /services/saved/searches splunk_server=local
| search eai:acl.app="DA-ESS-ContentUpdate"
| where isnotnull(action.correlationsearch.enabled)
| eval uses_dm = if(match(search, "(?i)tstats.*datamodel"), "Yes", "No")
| eval dm_name = case(
    match(search, "(?i)Endpoint"), "Endpoint",
    match(search, "(?i)Network_Traffic"), "Network_Traffic",
    match(search, "(?i)Network_Resolution"), "Network_Resolution",
    match(search, "(?i)Authentication"), "Authentication",
    match(search, "(?i)Web"), "Web",
    match(search, "(?i)Email"), "Email",
    match(search, "(?i)Change"), "Change",
    true(), "Other/Direct"
)
| stats count AS total_detections BY dm_name
| append [
    | rest /services/datamodel/model splunk_server=local
    | eval dm_name = title
    | eval accel = if(acceleration="1", "✅", "❌")
    | table dm_name, accel
]
| stats first(total_detections) AS detections, first(accel) AS accelerated BY dm_name
| fillnull detections value=0
| fillnull accelerated value="N/A"
| eval ready = if(accelerated="✅" AND detections > 0, "✅ Ready", "❌ Gap")
| sort - detections

Rollback Steps

  1. Gap analysis identified wrong requirements: Re-run extraction SPL with manual macro resolution. Correct the gap matrix. Notify Phase 1 team of changes.
  2. Data onboarding completed but ESCU detection still fails: The gap was misidentified. Check CIM field mapping, TA version, and data model acceleration. Return to Step 1 with the specific detection SPL.
  3. Prioritization was wrong (spent effort on low-value gap): Re-prioritize against current threat model. Redirect remaining effort to higher-value gaps. Document lesson learned.

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • P1 gaps have been in the backlog for more than 1 quarter. Critical data sources blocking high-value detections need escalation to Security Manager / CISO. Include the count of detections blocked.
  • ESCU detections were enabled despite known data gaps. Disable immediately. A detection without its data source either does nothing (wasted concurrency) or produces misleading results.
  • More than 50% of ESCU data model requirements are not accelerated. Acceleration is a platform responsibility. Escalate to Splunk admin with the specific DMs needing acceleration and the detection count blocked by each.
  • Gap analysis reveals you need a data source that requires significant budget. This is a business decision. Package the gap analysis as a business case: "X detections for threats Y and Z require data source W. Cost: $__. Risk without: ___."
  • TA updates break CIM mapping for data sources feeding ESCU detections. After any TA update, verify data still maps correctly to CIM fields. If mapping broke, escalate to platform team for immediate fix.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"We'll map all ESCU data requirements at once" ESCU has hundreds of detections. Full mapping takes weeks. Nothing gets deployed during that time. Map per Analytic Story, prioritized by threat model. 3-5 stories per sprint. Deploy what's ready while mapping continues.
"We have the index — we're good" Having data in an index doesn't mean it's CIM-compliant, the right sourcetype, or mapped to the correct data model. Verify the full chain: data exists → sourcetype correct → TA installed → CIM fields extracted → data model accelerated.
"Detection Engineering handles data gaps alone" Data onboarding is a Platform Engineering / Infrastructure responsibility. DE identifies the gap; Platform fills it. DE documents the requirement. Phase 1 backlog entry goes to Platform team with clear acceptance criteria.
"We'll do the gap analysis when we have time" "When we have time" means "never." Gaps persist, detections stay disabled, ESCU provides zero value. Schedule gap analysis as part of the quarterly ESCU evaluation sprint. It's a planned activity, not a stretch goal.
"Skip mapping — just enable and see if it works" If data is missing, the detection silently fails. You think you have coverage; you don't. Worse than no detection at all. Verify data before enabling. Every time. The 10-minute data check saves hours of false-confidence troubleshooting.
