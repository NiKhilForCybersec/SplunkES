Tuning, Noise Reduction & SOC Trust

📋 Page Status: HARDENED — ES CONTENT MANAGEMENT

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This page covers the systematic approach to reducing false positives while preserving detection coverage, specifically calibrated for retail environments where noise sources are amplified.

🚨 CRITICAL: Noise Is Not an Inconvenience — It Is a Security Failure

When analysts stop trusting alerts, they stop investigating them. When they stop investigating, attacks succeed.

  • A SOC that ignores 80% of alerts is a SOC that will ignore a real attack
  • Alert fatigue is the #1 reason real breaches are missed in environments with detection capability
  • The goal is NOT zero false positives — the goal is a FP rate low enough that analysts investigate every alert
  • Target: <30% false positive rate per detection. If higher, the detection needs tuning before production.
⚠️ Assumptions — Verify Before Proceeding
  • Assumption: You have access to notable event data to analyze noise. Verify: Run `notable` | stats count BY search_name.
  • Assumption: SOC provides feedback on alert quality. Risk if wrong: Without SOC input, you're tuning blind.
  • Assumption: Data quality issues have been addressed in Phase 2. Risk if wrong: Tuning bad data doesn't fix bad data. Fix the source first.

Why Noise Destroys SOC Trust

SOC trust is not a feeling — it's a measurable behavior. When trust is high, analysts investigate alerts promptly and thoroughly. When trust is low, they don't. The transition from trust to distrust happens fast and is extremely hard to reverse.

🚨 The Trust Asymmetry

It takes weeks to build SOC trust in a detection. It takes one bad day to destroy it.

One alert storm during a busy Monday morning can permanently poison the SOC's perception of your detections. Rebuild time: 4-8 weeks minimum, if they'll even give you another chance. This is why monitoring-only mode exists — use it.

Common Noise Sources in Retail

Retail environments have unique noise amplifiers that don't exist in corporate/government environments. Every detection must account for these.

Promotional Days & Sales Events

Event Impact on Detection Volume Multiplier Typical Detections Affected Mitigation Strategy
Black Friday Web traffic spikes 20-50x. Auth volume spikes 10-20x. API calls spike 15-30x. 20-50x normal ALL volume-based detections, HTTP anomaly, brute force, API abuse Dynamic thresholds or scheduled threshold overrides. Do NOT deploy new detections during this window.
Weekly flyer promotions 2-5x traffic spike on Thursday-Saturday. Regular weekly pattern. 2-5x normal HTTP volume anomaly, bot detection, API rate detection Use day-of-week baselines. Don't compare Friday to Monday.
Loyalty program events Point multiplier events drive massive login activity from mobile app 3-10x auth volume Brute force, failed login, account lockout Mobile app user-agent exclusions. Separate service account from user detections.
Flash sales / app-only deals Burst traffic patterns that look like DDoS 5-15x in minutes DDoS detection, WAF rate-limit triggers Pre-schedule threshold increases. Coordinate with marketing calendar.

Mobile App Behavior

  • Token refresh storms: When the app pushes an update, millions of devices re-authenticate within hours. This looks like a massive brute force event.
  • Background heartbeat: Mobile apps send periodic health checks that generate auth events even when the user isn't active.
  • Offline queue flush: When a device comes back online, it flushes queued events in burst. Timestamps may be out of order.
  • Geo-diversity: Mobile users authenticate from everywhere. "Impossible travel" detections must account for mobile app auth happening from the user's phone location, not the corporate network.

Legitimate Bots

  • Googlebot, Bingbot, price comparison bots: Generate significant HTTP traffic that WAF detections may flag as scanning or scraping.
  • CDN health checks: Akamai, Cloudflare, and other CDN healthchecks generate repetitive HTTP patterns.
  • API integration partners: Suppliers, logistics partners, and third-party integrations make automated API calls at regular intervals.
  • Monitoring services: Uptime monitoring, synthetic testing, and performance monitoring generate auth events and HTTP requests.
⚠️ Do NOT Hard-Code Bot Exclusions

Attackers spoof bot user-agents. Instead of blanket exclusions based on user-agent strings, use verified bot IP ranges from official sources (e.g., Google's published IP ranges) and maintain these in lookup tables that can be updated without modifying search logic.

Level 1: Data Quality Tuning

Before touching any detection, verify the data feeding it is correct. Most "noisy detections" are actually "bad data" problems.

Data Issue Detection Impact Example in Retail Fix
Missing user field Auth detections trigger on NULL user, grouping all unknowns together POS systems logging auth without user extraction Fix field extraction at props.conf / transforms.conf level
src field shows proxy IP All traffic appears from one IP. Brute force fires constantly for proxy IP. Store traffic routed through regional proxy Extract X-Forwarded-For or original client IP
Mixed success/failure in one sourcetype Detection can't distinguish auth success from failure Custom app logging both outcomes in same event format Create field extraction for action=success vs action=failure
Timestamp parsing wrong Events appear at wrong time. Lookback windows miss them. Store systems in different timezone logging UTC but parsed as local Fix TIME_FORMAT and TZ in props.conf

Level 2: Detection Logic Tuning

If data is clean but the detection is still noisy, the logic needs improvement.

Logic Issue Example Fix
Too broad field matching Detection matches on src=* instead of specific network ranges Narrow to src IN (internal_ranges) or use lookup for scope
No distinction between user types Service accounts and human users evaluated by same logic Add WHERE NOT user IN (service_account_lookup) for human-focused detections
Missing negative conditions Detection fires for password resets (legitimate) along with actual brute force Add WHERE action!="password_reset" to exclude known patterns
Single-event logic for multi-event patterns Fires on every single failed login instead of clustering Use stats count BY src, user | where count > threshold to require pattern

Level 3: Threshold Tuning

⚠️ Threshold Tuning is NOT the First Step

Changing thresholds is the most common tuning action but should NOT be the first. If data quality or logic is the root cause, adjusting thresholds just masks the real problem. Fix Levels 1-2 first.

When threshold tuning is appropriate, use environment data to set values:

SPL: Determine Appropriate Threshold for Failed Login Detection 
`comment("Calculates the natural distribution of failed logins per user")`
`comment("Use this to set thresholds that catch outliers, not normal users")`

| tstats count FROM datamodel=Authentication
  WHERE Authentication.action="failure"
  BY Authentication.user _time span=1h
| stats avg(count) AS avg_failures,
    stdev(count) AS stdev_failures,
    max(count) AS max_failures,
    perc95(count) AS p95_failures,
    perc99(count) AS p99_failures
    BY Authentication.user
| stats avg(avg_failures) AS global_avg,
    avg(p95_failures) AS global_p95,
    avg(p99_failures) AS global_p99,
    max(max_failures) AS absolute_max
| eval recommended_threshold = round(global_p99 * 1.5, 0)
| eval conservative_threshold = round(global_p95 * 2, 0)
| table global_avg, global_p95, global_p99, absolute_max, 
    recommended_threshold, conservative_threshold

Level 4: Throttle Tuning

Throttling is the safest noise reduction mechanism. See Correlation Search Lifecycle for throttle configuration details.

What NOT to Tune First

Tempting First Action Why It's Wrong Correct First Action
"Just increase the threshold" If the FPs are from bad data (e.g., proxy IP), raising the threshold still includes the bad data. The threshold will never be high enough. Check data quality first. Is the src field correct? Is the user field populated?
"Add an allowlist for these IPs" Allowlists are permanent blind spots. If the "safe" IP gets compromised, you'll never detect it. Understand WHY those IPs are triggering. Fix the detection logic to distinguish legitimate vs malicious patterns.
"Suppress the noisy alerts" Suppression hides the problem. The detection still fires, consumes resources, and generates hidden notables. You've just made the problem invisible. Fix the root cause. If you can't fix it now, suppress temporarily but create a ticket to fix properly.
"Disable the detection" You now have a detection gap. Whatever threat it was designed to catch is now unmonitored. Tune before disabling. Only disable if the detection is fundamentally unfit for your environment.

Tuning Anti-Patterns

Hard Allowlists

🚨 Hard Allowlists Are Permanent Blind Spots

A hard allowlist (e.g., WHERE src NOT IN ("10.1.1.1", "10.2.2.2")) means those IPs will NEVER trigger the detection, regardless of what they do. If an attacker compromises one of those systems, you are permanently blind to attacks from that source.

Instead:

  • Use lookup tables instead of hardcoded IPs so allowlists can be updated without modifying search logic
  • Add expiration dates to allowlist entries. Review quarterly.
  • Use "adjusted threshold" instead of "exempt" — e.g., known scanners trigger at 100x instead of 10x, not at never
  • Document every allowlist entry with: who added it, why, and when to review

Blind Suppression

Notable suppression rules that suppress by field value (e.g., suppress all notables where user=svc_account) create invisible gaps:

  • The detection still runs and consumes resources
  • Notables are created but hidden — they exist in the index but not in Incident Review
  • If the service account is compromised, the attack notables are suppressed
  • Suppression rules accumulate over time and nobody audits them
SPL: Audit All Notable Suppression Rules 
`comment("List all active notable suppressions")`
`comment("Review quarterly — stale suppressions are blind spots")`

| rest /services/saved/searches splunk_server=local
| search action.notable.param.suppress=1
| table title, action.notable.param.suppress_fields, 
    action.notable.param.suppress_period, updated
| sort - updated

Over-Throttling

Throttling is safe, but excessive throttling can hide attack patterns:

  • Throttle window too long (>24h): A sustained multi-day attack generates only one notable per day. SOC sees one alert for a week-long attack.
  • Throttle key too broad (just src): An attacker hitting 50 different users from one IP generates only one notable. All 50 compromised accounts hidden.
  • Fix: Use compound throttle keys (src + user) and keep windows under 4 hours for most detections.

SPL: Weekly Tuning Health Dashboard Query

SPL: Detection Portfolio Health Summary 
`comment("Weekly health check for all active detections")`
`comment("Identifies noisy detections and quiet detections")`

`notable`
| stats count AS notable_count,
    dc(src) AS unique_sources,
    dc(user) AS unique_users
    BY search_name
| eval daily_avg = round(notable_count / 7, 1)
| eval health = case(
    daily_avg > 50, "🔴 CRITICAL — Noise",
    daily_avg > 20, "🟡 WARNING — Review",
    daily_avg > 0.1, "🟢 Healthy",
    daily_avg > 0, "⚪ Low Volume",
    true(), "⚫ Not Firing"
)
| eval action_needed = case(
    daily_avg > 50, "Disable immediately. Tune offline.",
    daily_avg > 20, "Review this week. Tune thresholds.",
    daily_avg > 0.1, "No action needed.",
    daily_avg > 0, "Verify detection is still relevant.",
    true(), "Check if data source exists. May be broken."
)
| sort - daily_avg
| table search_name, notable_count, daily_avg, health, 
    unique_sources, unique_users, action_needed

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • Total notable volume exceeds 200/day. SOC cannot keep up. Disable the noisiest detections first, then tune offline.
  • SOC stops investigating ES alerts entirely. This is an emergency. Disable all non-critical detections. Rebuild trust starting with 3-5 high-quality detections.
  • A single detection generates >100 notables/day. Disable it immediately. This is an alert storm, not a detection.
  • Tuning a detection requires >3 iterations with no improvement. The detection may be fundamentally unsuitable. Escalate for rewrite decision.
  • Marketing or business team schedules an event you weren't told about. Escalate to establish a coordination process. Unannounced promo events cause false positive spikes.
