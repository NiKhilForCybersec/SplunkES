ES Health, Search Reliability & Performance

📋 Page Status: HARDENED — ES CONTENT MANAGEMENT

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This page covers how to monitor the health of the ES platform itself — not individual detections, but the infrastructure that runs them. A detection is only as reliable as the platform executing it.

🚨 CRITICAL: Platform Issues Silently Kill Detections

If the platform is unhealthy, your detections aren't running — and nobody knows.

  • Skipped searches don't generate alerts — they generate nothing. Silence.
  • Stale data models mean tstats queries return old data. Detections look healthy but are blind.
  • Search concurrency limits mean your most important detection may be the one that gets skipped.
  • Ingestion lag means events arrive after the detection window has closed.

You MUST monitor ES health independently of detection output. A detection that fires zero notables might be working perfectly (no threats) or completely broken (can't run). Without health monitoring, you can't tell the difference.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: You have read access to _internal and _audit indexes. Verify: Run index=_internal | head 1. Risk if wrong: You cannot monitor ES health without internal indexes.
  • Assumption: Splunk Cloud admin has not restricted scheduler log access. Verify: Run index=_internal sourcetype=scheduler | head 1.
  • Assumption: Data model acceleration is configured. Verify: Settings → Data Models → check acceleration status.

ES Health Check Framework

Run these health checks on a regular cadence. The daily checks are non-negotiable. Weekly and monthly checks prevent slow-building problems.

Daily Health Checks

Check 1: Skipped Correlation Searches

🚨 This Is the Single Most Important Health Check

A skipped search means a detection did not run. Events during that window were never evaluated. You have a gap in coverage and you don't know about it unless you check.

SPL: Daily Skipped Search Report 
`comment("RUN DAILY — First thing every morning")`
`comment("Any result = detection gap. Investigate immediately.")`

index=_internal sourcetype=scheduler status="skipped" earliest=-24h
| eval search_name = savedsearch_name
| stats count AS skip_count,
    latest(_time) AS last_skip,
    values(reason) AS skip_reasons
    BY search_name, app
| where skip_count > 0
| eval severity = case(
    skip_count > 10, "🔴 CRITICAL — Persistent gaps",
    skip_count > 3, "🟡 WARNING — Multiple gaps",
    true(), "⚪ Single skip — monitor"
)
| eval gap_hours = round(skip_count * 0.25, 1)
| sort - skip_count
| table search_name, app, skip_count, gap_hours, severity, 
    skip_reasons, last_skip
| rename gap_hours AS "Est. Gap (hours)"

Check 2: Notable Volume Sanity Check

SPL: 24-Hour Notable Volume vs 7-Day Average 
`comment("Compares today's notable volume against 7-day rolling average")`
`comment("Major deviations indicate either a real event or a platform problem")`

`notable`
| eval period = if(_time > relative_time(now(), "-24h"), "today", "baseline")
| stats count AS total BY search_name, period
| xyseries search_name period total
| fillnull value=0
| eval change_pct = if(baseline > 0, round(((today - baseline/6) / (baseline/6)) * 100, 1), "NEW")
| eval status = case(
    today = 0 AND baseline > 0, "🔴 STOPPED FIRING — investigate",
    change_pct > 200, "🔴 SPIKE — possible storm",
    change_pct > 100, "🟡 ELEVATED — review",
    change_pct < -80, "🟡 SIGNIFICANT DROP — review",
    true(), "🟢 Normal"
)
| where status != "🟢 Normal"
| sort - today
| table search_name, today, baseline, change_pct, status

Check 3: Active Scheduled Search Count

SPL: Currently Active Scheduled Searches 
`comment("How many scheduled searches are active right now?")`
`comment("Compare against known concurrency limit")`

| rest /services/saved/searches splunk_server=local
| search disabled=0 is_scheduled=1
| stats count AS total_active,
    dc(eai:acl.app) AS source_apps
| eval concurrency_limit = 24
| eval utilization_pct = round((total_active / concurrency_limit) * 100, 0)
| eval risk = case(
    utilization_pct > 90, "🔴 CRITICAL — near limit, skips likely",
    utilization_pct > 70, "🟡 WARNING — getting crowded",
    true(), "🟢 Healthy"
)
| table total_active, concurrency_limit, utilization_pct, risk, source_apps

Weekly Health Checks

Check 4: Search Runtime Analysis

SPL: Correlation Search Runtime Trends (7 Days) 
`comment("Identifies searches that are getting slower over time")`
`comment("A search that takes longer than its cron interval WILL skip")`

index=_internal sourcetype=scheduler status="success" earliest=-7d
| eval runtime_sec = run_time
| eval runtime_min = round(runtime_sec / 60, 2)
| stats avg(runtime_min) AS avg_runtime,
    max(runtime_min) AS max_runtime,
    perc95(runtime_min) AS p95_runtime,
    perc50(runtime_min) AS median_runtime,
    count AS executions
    BY savedsearch_name
| eval health = case(
    max_runtime > 30, "🔴 CRITICAL — 30+ min runs detected",
    p95_runtime > 15, "🔴 WARNING — P95 exceeds 15 min",
    p95_runtime > 10, "🟡 REVIEW — P95 exceeds 10 min",
    avg_runtime > 5, "🟡 MONITOR — Avg above 5 min",
    true(), "🟢 Healthy"
)
| where health != "🟢 Healthy"
| sort - max_runtime
| table savedsearch_name, executions, median_runtime, avg_runtime, 
    p95_runtime, max_runtime, health

Check 5: Data Model Acceleration Status

SPL: Data Model Acceleration Health 
`comment("Data model acceleration MUST be current for tstats to work")`
`comment("If acceleration is behind, detections are using stale data")`

| rest /services/datamodel/acceleration splunk_server=local
| table title, acceleration.enabled, acceleration.earliest_time,
    acceleration.backfill_time, eai:acl.app
| rename acceleration.enabled AS enabled,
    acceleration.earliest_time AS earliest,
    acceleration.backfill_time AS backfill
| eval status = case(
    enabled = 0, "⚫ NOT ACCELERATED",
    backfill = "None" OR isnull(backfill), "🟢 Current",
    true(), "🟡 BACKFILLING — " . backfill
)
| sort status
| table title, enabled, earliest, backfill, status, eai:acl.app

Check 6: Search Concurrency Over Time

SPL: Search Concurrency Heatmap (7 Days) 
`comment("Shows concurrency utilization patterns by hour of day")`
`comment("Identifies peak times when skipping is most likely")`

index=_internal sourcetype=scheduler earliest=-7d
| eval hour = strftime(_time, "%H")
| eval day = strftime(_time, "%A")
| bin _time span=5m
| stats dc(sid) AS concurrent BY _time, hour, day
| stats avg(concurrent) AS avg_concurrent,
    max(concurrent) AS peak_concurrent
    BY hour
| eval risk = case(
    peak_concurrent > 24, "🔴 Over limit at peak",
    peak_concurrent > 20, "🟡 Near limit at peak",
    true(), "🟢 Healthy"
)
| sort hour
| table hour, avg_concurrent, peak_concurrent, risk

Check 7: Ingestion Lag Detection

SPL: Detect Ingestion Lag by Sourcetype (Critical Sources) 
`comment("Compares event time (_time) with index time (_indextime)")`
`comment("Lag > 5 minutes means detections may miss events")`

index=* sourcetype IN ("akamai:waf", "azure:aad:signin", "WinEventLog:Security")
    earliest=-1h
| eval lag_seconds = _indextime - _time
| eval lag_minutes = round(lag_seconds / 60, 1)
| stats avg(lag_minutes) AS avg_lag,
    max(lag_minutes) AS max_lag,
    perc95(lag_minutes) AS p95_lag,
    count AS events
    BY sourcetype
| eval health = case(
    p95_lag > 15, "🔴 CRITICAL — detections likely missing events",
    p95_lag > 5, "🟡 WARNING — increase lookback buffer",
    p95_lag > 2, "🟢 Normal — minor lag",
    true(), "🟢 Healthy"
)
| table sourcetype, events, avg_lag, p95_lag, max_lag, health

Monthly Health Checks

Check 8: Lookup Table Freshness

SPL: Check Lookup Table Update Timestamps 
`comment("Stale lookups = stale enrichment = broken detections")`
`comment("Identity and asset lookups should update daily")`

| rest /services/data/lookup-table-files splunk_server=local
| eval last_updated = strftime(updated, "%Y-%m-%d %H:%M")
| eval age_days = round((now() - updated) / 86400, 1)
| eval health = case(
    age_days > 30, "🔴 STALE — 30+ days old",
    age_days > 7, "🟡 AGING — 7+ days old",
    true(), "🟢 Current"
)
| where age_days > 7
| sort - age_days
| table title, eai:acl.app, last_updated, age_days, health

Check 9: Context-Generating Search Health

SPL: Context-Gen Search Status 
`comment("Context-gen searches feed identity, asset, and threat intel lookups")`
`comment("If these break, ALL enrichment-dependent detections are affected")`

| rest /services/saved/searches splunk_server=local
| search title="*Identity*" OR title="*Asset*" OR title="*Threat*Gen*"
| eval status = if(disabled=0, "ENABLED", "DISABLED")
| table title, status, eai:acl.app, cron_schedule, next_scheduled_time
| sort title

When to Pause Detection Work and Escalate

🛑 STOP All Detection Engineering Work When:
  • More than 20% of correlation searches skipped in the last 24 hours. The platform cannot reliably run detections. Adding more will make it worse.
  • Any critical data source has stopped ingesting. Detections without data are useless. Fix the pipeline first.
  • An ES upgrade is in progress or scheduled within 48 hours. All changes may be overwritten or conflict. Wait until post-upgrade validation is complete.
  • Search head CPU consistently above 90%. The platform is overloaded. Adding searches will degrade everything.
  • License usage above 90% of daily limit. Risk of indexing block. Focus on reducing ingestion, not adding detection load.

Performance Optimization Quick Reference

When searches are running slow, use this table to identify and fix the most common causes:

Symptom Likely Cause Fix Impact
Search takes >10 min Using search instead of tstats Rewrite to use | tstats with accelerated data model 10-100x faster
Search scans too much data Lookback window too large or missing index constraint Match lookback to cron interval. Always specify index= 2-10x faster
Join/subsearch timeout Using join or subsearch with large datasets Rewrite using stats, lookup, or append 5-50x faster
High memory usage stats with very high cardinality BY fields Pre-filter data. Reduce cardinality with bin or eval Prevents search failure
Slow lookup enrichment Large CSV lookup with no optimization Use KV store instead of CSV for >100K rows. Add outputnew. 2-5x faster
Wildcard in early filter | search field="*pattern*" on raw events Move wildcards later in pipeline. Use indexed field extraction. 5-20x faster

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"I don't need to check _internal" Without checking scheduler logs, you have zero visibility into skipped searches. You are flying blind. Daily skipped search check. Non-negotiable. Automate it if possible.
"The dashboards look fine, so ES is healthy" ES dashboards show what detections found. They don't show what detections MISSED because they didn't run. Health monitoring is separate from detection monitoring. Check both.
"Add more searches — we have capacity" Capacity isn't just about current utilization. Peak-hour concurrency may already be near limits. Check concurrency heatmap before adding. Schedule new searches at off-peak times.
"Data model is accelerated, so it's fine" Acceleration can fall behind, fail to rebuild, or exclude recent data. "Accelerated" ≠ "current." Check acceleration freshness weekly. Verify tstats results match raw search counts.
"Splunk Cloud handles performance — not my problem" Splunk Cloud manages infrastructure, not your search efficiency. A bad search on Splunk Cloud still times out and skips. Optimize searches. Use tstats. Match lookback to cron. This is your responsibility.
