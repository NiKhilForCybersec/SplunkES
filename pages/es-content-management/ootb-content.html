Splunk ES Out-of-the-Box Content — Reality & Risks

📋 Page Status: HARDENED — ES CONTENT MANAGEMENT

This page covers what ES ships with, why it is NOT safe to enable blindly, and exactly how to evaluate OOTB content for a retail production environment.

☁️ Splunk Cloud Safety Box — ES Content Management

✅ Allowed in Cloud: All ES content management workflows are UI-based and work identically in Cloud. Correlation search creation, enablement, tuning, suppression, ESCU deployment, and content lifecycle management all use the ES UI. No differences from Enterprise.

⚠️ Restricted in Cloud: If this page references savedsearches.conf file edits, btool debugging, or filesystem-level backup procedures, those apply only to customer-managed infrastructure. You cannot edit .conf files directly in Splunk Cloud.

🔄 Cloud-Safe Alternative: All correlation search management is via Configure → Content → Content Management. For backup/versioning, export searches via the ES UI or REST API and store in Git. Use | rest /services/saved/searches to inspect search configurations programmatically. Deploy content updates as packaged apps via SSAI.

🚨 CRITICAL: OOTB Content Is NOT Plug-and-Play

Splunk ES ships with hundreds of correlation searches. Enabling them without review WILL cause:

  • Alert storms: Dozens of noisy detections firing on benign activity
  • SOC distrust: Analysts learn to ignore ES alerts entirely
  • Performance degradation: Concurrent searches overloading search heads
  • False sense of security: Enabled but unconfigured detections catching nothing real

Every OOTB correlation search must be individually evaluated, tested, and approved before enabling in this environment.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: Splunk ES is installed with default content packs. Verify: Check installed apps and add-ons.
  • Assumption: No OOTB correlation searches have been modified by previous admins. Verify: Run the inventory SPL below.
  • Assumption: No custom Security Essentials (SSE) content has been deployed. Verify: Check SSE app for content.
  • Risk if wrong: Unknown modifications can create unpredictable behavior, duplicates, or gaps.

🚨 Common Misconception

"ES has X detections out of the box, so we're covered." This is dangerously wrong. The majority of OOTB correlation searches are:

  • Disabled by default (for good reason)
  • Written for generic environments, not retail
  • Dependent on data models that may not be accelerated or populated
  • Using thresholds that are either too sensitive or too broad for your data

What Is Enabled vs. Disabled by Default

Understanding the default state of OOTB content is critical because some searches MAY already be running and consuming resources without anyone monitoring their output.

Typically Enabled by Default

Content Type Examples Risk Action Required
Context-generating searches Identity lookup gen, asset lookup gen, threat intel updates Low (background operations) Verify they run. Fix if broken. They feed everything.
Data model acceleration Authentication, Network_Traffic, Endpoint, Web Medium (resource cost) Verify acceleration is building. Disable unused models.
Threat intelligence framework Threat intel matching searches Medium (depends on intel quality) Review intel sources. Many default sources are stale.

Typically Disabled by Default

Content Type Examples Why Disabled Action Required
Most correlation searches Brute Force Access Behavior, Excessive Failed Logins, Abnormally High HTTP Methods Noisy without tuning. Thresholds don't match real environments. Evaluate individually. See decision tree below.
Network-based detections DNS tunneling, port scanning, lateral movement Requires specific network data that may not exist Only enable if data source exists AND is quality-validated.
Endpoint detections Process injection, PowerShell obfuscation, unusual parent-child Requires EDR data (Sysmon, CrowdStrike, etc.) Only enable after Phase 1 endpoint onboarding complete.

Why Retail Environments Amplify OOTB Noise

OOTB correlation searches are designed for "average" corporate environments. Retail enterprises are NOT average. Every noise factor is amplified:

🛒 E-Commerce Traffic

Web traffic spikes 10-50x during promotions. OOTB thresholds for "abnormal" HTTP activity are calibrated for steady-state corporate environments. Every sale day triggers volume-based detections.

📱 Mobile App Behavior

Millions of mobile app users generate authentication events constantly. Failed logins from token refresh, app updates, and session timeouts create massive volumes that look like brute force to OOTB detections.

🏪 Store Systems & POS

Thousands of store endpoints (POS, self-checkout, kiosks) generate repetitive patterns. Service accounts authenticate repeatedly. Normal store operations look like lateral movement to generic detections.

🤖 Legitimate Bots

Price comparison bots, SEO crawlers, and legitimate API integrations generate traffic patterns that OOTB web attack detections flag as malicious. Without bot classification, the SOC drowns in bot alerts.

📅 Seasonal Patterns

Retail has extreme seasonality: Black Friday, holiday shopping, back-to-school. Baselines calculated during quiet periods will generate false positives during EVERY busy period unless manually adjusted.

🔑 Service Account Density

Retail environments have hundreds of service accounts for POS, inventory, supply chain, and loyalty systems. OOTB identity-based detections flag service accounts as "suspicious" because they authenticate at unusual times — which is normal for service accounts.

How to Inventory OOTB Content Safely

Before making ANY decisions about OOTB content, you must understand what exists in this environment. Run these queries to build a complete inventory.

Inventory All Correlation Searches

SPL: Complete Correlation Search Inventory 
`comment("Run this FIRST to understand what OOTB content exists")`
`comment("This lists ALL correlation searches, their state, and origin")`

| rest /services/saved/searches splunk_server=local
| search action.correlationsearch.enabled=1 OR action.correlationsearch.enabled=true
| eval status = if(disabled=0, "ENABLED", "DISABLED")
| eval is_scheduled = if(isnotnull(cron_schedule) AND cron_schedule!="", "Yes", "No")
| eval origin = case(
    match(eai:acl.app, "^DA-ESS"), "OOTB (Domain Add-on)",
    match(eai:acl.app, "^SA-"), "OOTB (Supporting Add-on)",
    match(eai:acl.app, "SplunkEnterpriseSecuritySuite"), "OOTB (ES Suite)",
    match(eai:acl.app, "Splunk_SA"), "OOTB (SA App)",
    true(), "CUSTOM (" . eai:acl.app . ")"
)
| eval last_modified = strftime(updated, "%Y-%m-%d %H:%M")
| eval actions = if(isnotnull(actions), actions, "none")
| table title, status, origin, eai:acl.app, cron_schedule, is_scheduled, 
    actions, description, last_modified
| sort origin, title

Check What Is Currently Running (and Consuming Resources)

SPL: Currently Running Correlation Searches 
`comment("Shows searches that are actively scheduled and running")`
`comment("IMPORTANT: These are consuming search concurrency slots")`

| rest /services/saved/searches splunk_server=local
| search action.correlationsearch.enabled=1 disabled=0 is_scheduled=1
| eval cron_readable = case(
    cron_schedule="*/5 * * * *", "Every 5 min",
    cron_schedule="*/10 * * * *", "Every 10 min",
    cron_schedule="*/15 * * * *", "Every 15 min",
    cron_schedule="*/30 * * * *", "Every 30 min",
    cron_schedule="0 * * * *", "Every hour",
    true(), cron_schedule
)
| eval dispatch_window = if(isnotnull(dispatch.earliest_time), 
    dispatch.earliest_time . " to " . dispatch.latest_time, "Not set")
| table title, eai:acl.app, cron_readable, dispatch_window, actions
| sort cron_readable, title

Check for Modified OOTB Content

SPL: Detect Modified OOTB Searches 
`comment("Shows OOTB searches that have local overrides")`
`comment("Modified OOTB = someone changed it. Find out who and why.")`

| rest /services/saved/searches splunk_server=local
| search eai:acl.app="DA-ESS-*" OR eai:acl.app="SA-*"
| where isnotnull(updated)
| eval has_local_override = if(match(eai:acl.sharing, "app") OR match(eai:acl.sharing, "user"), "YES", "Maybe")
| eval last_change = strftime(updated, "%Y-%m-%d")
| table title, eai:acl.app, has_local_override, last_change, eai:acl.owner
| sort - last_change

Notable Event Volume by Source

SPL: Correlation Search Notable Output Volume (30 days) 
`comment("Shows which correlation searches are generating notables")`
`comment("High volume = potential noise problem")`

`notable`
| stats count AS notable_count,
    dc(src) AS unique_sources,
    dc(dest) AS unique_destinations,
    dc(user) AS unique_users,
    latest(_time) AS last_fired,
    earliest(_time) AS first_fired
    BY search_name
| eval daily_avg = round(notable_count / 30, 1)
| eval noise_risk = case(
    daily_avg > 50, "🔴 HIGH — Likely Noise",
    daily_avg > 10, "🟡 MEDIUM — Review",
    daily_avg > 0, "🟢 Normal",
    true(), "⚪ Not Firing"
)
| sort - notable_count
| table search_name, notable_count, daily_avg, noise_risk, 
    unique_sources, unique_destinations, unique_users,
    first_fired, last_fired

Rules for OOTB Content Decisions

When OOTB Can Be Enabled As-Is

An OOTB correlation search can be enabled without modification ONLY when ALL of the following are true:

  • The required data source exists and has been validated in Phase 1
  • The data model is accelerated and populated (Phase 2)
  • A 30-day backtest produces reasonable volume (< 10 per day average)
  • Sample results show >70% true positive rate
  • The detection has completed 1-2 weeks in monitoring mode
  • SOC has reviewed sample results and agreed to triage
  • A triage runbook has been created or mapped

When OOTB Must Be Cloned

Clone the OOTB search and create a modified version when:

  • Thresholds need adjustment for retail traffic patterns
  • Allowlists are needed for known service accounts or systems
  • The detection needs retail-specific filtering (e.g., exclude POS IPs)
  • You need to change the schedule or lookback window
  • The original detection would be overwritten during ES upgrades
⚠️ CRITICAL Cloning Rule

When you clone an OOTB search, you MUST:

  • Use a naming convention: CUSTOM - [Original Name] - [Company]
  • Disable the original OOTB search
  • Document what was changed and why
  • Assign ownership to a person or team
  • Know that ES upgrades will NOT update your clone

When OOTB Must Remain Disabled

Disable and document (do NOT delete) when:

  • The required data source does not exist in this environment
  • The detection is not relevant to retail (e.g., SCADA-specific detections)
  • The detection requires RBA (out of scope for this project)
  • The detection has no triage runbook and the SOC cannot action it
  • The detection fundamentally doesn't work with your data patterns

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • You discover OOTB searches running that nobody knows about. Escalate to Splunk admin. These may be consuming resources or generating unmonitored notables.
  • Modified OOTB content with no documentation. Escalate to previous admin. Someone changed something and you need to understand why before touching it.
  • Notable event volume exceeds 100/day from a single search. Disable immediately and investigate. This is a noise problem, not a detection.
  • OOTB content references lookups or macros that don't exist. The content pack may be incomplete or corrupted. Escalate to Splunk support.
  • ES upgrade is planned. Freeze all OOTB modifications until after upgrade. Upgrades can overwrite or conflict with local changes.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Enable all OOTB to show coverage" Creates hundreds of noisy notables. SOC ignores everything. Auditors see volume but no quality. Enable selectively based on data availability and SOC capacity. 5 working detections > 50 noisy ones.
"We'll tune later" "Later" never comes. SOC has already lost trust. Disabling after the fact looks like a step backward. Tune BEFORE enabling. Monitoring mode exists for this reason.
"Delete OOTB we don't use" ES upgrades recreate them. Audit trail is lost. Future enablement loses context. DISABLE, don't delete. Document reason for disabling.
"Modify OOTB in place" ES upgrades overwrite your changes. No diff history. Can't revert to original. CLONE, then modify the clone. Disable original. Use CUSTOM prefix.
"OOTB count = detection coverage" Enabled ≠ working. A disabled detection with no data is 0% coverage regardless of what it "detects." Measure coverage by data sources actually monitored, not by enabled search count.
