ES Change Management & Rollback

📋 Page Status: HARDENED — ES CONTENT MANAGEMENT

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This page defines how every ES detection change is planned, executed, rolled back, and communicated. In a single production environment, this IS your safety net.

☁️ Splunk Cloud Safety Box — ES Content Management

✅ Allowed in Cloud: All ES content management workflows are UI-based and work identically in Cloud. Correlation search creation, enablement, tuning, suppression, ESCU deployment, and content lifecycle management all use the ES UI. No differences from Enterprise.

⚠️ Restricted in Cloud: If this page references savedsearches.conf file edits, btool debugging, or filesystem-level backup procedures, those apply only to customer-managed infrastructure. You cannot edit .conf files directly in Splunk Cloud.

🔄 Cloud-Safe Alternative: All correlation search management is via Configure → Content → Content Management. For backup/versioning, export searches via the ES UI or REST API and store in Git. Use | rest /services/saved/searches to inspect search configurations programmatically. Deploy content updates as packaged apps via SSAI.

🚨 CRITICAL: Every Detection Change Is a Production Change

There is no DEV, no UAT, no staging. When you modify, enable, or disable a correlation search, you are changing production security monitoring. The SOC sees the effect immediately. An auditor can ask about any change at any time.

  • One bad enablement = alert storm in production SOC
  • One bad disable = detection gap nobody knows about
  • One undocumented change = audit finding

This page is your change management framework. Follow it for every change, every time.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: You have a change log or registry to record changes. Risk if wrong: Changes become untrackable. Set up at minimum a shared spreadsheet.
  • Assumption: SOC has an agreed communication channel (email, Slack, Teams). Risk if wrong: Changes surprise the SOC.
  • Assumption: There is a named escalation contact for "emergency stop" scenarios. Verify: Confirm who to call at 2 AM if a detection goes wrong.

Change Classification

Not all changes carry the same risk. Classify every change before executing it to determine the required approval level and communication.

Classification Examples Approval SOC Notice Rollback Plan
🟢 Low Risk Adjust throttle window, modify description, update inline comments, disable a search that is already not producing results Self-approved. Document in change log. Informational (post-change email) Revert setting. Immediate.
🟡 Medium Risk Modify detection thresholds, add allowlist entries, change cron schedule, enable an OOTB search after monitoring period Peer review recommended. Document with rationale. Pre-change notification (24 hours) Documented. Tested. Can execute in <15 min.
🔴 High Risk Enable new detection in production, modify SPL logic, disable an active detection, bulk enable/disable, deploy custom detection Peer review required. SOC sign-off required. Pre-change meeting or detailed email (48 hours) Full rollback procedure documented and rehearsed.
🔴🔴 Emergency Alert storm in progress, detection causing SOC overload, false positives impacting operations Act first, document immediately after. Immediate notification (Slack/call during change) Kill switch: disable search immediately. Investigate after.

Rollback Procedures — Step by Step

Scenario 1: Disable a Detection (Alert Storm / Noise)

Time to execute: < 5 minutes

  1. Disable the search immediately:
    • Settings → Searches, Reports, and Alerts
    • Find the search by name
    • Click Edit → Disable
    • OR via CLI: splunk edit saved-search "SEARCH_NAME" -disabled 1
  2. Verify it stopped:
    SPL: Confirm Search is Disabled 
    | rest /services/saved/searches splunk_server=local
| search title="YOUR_SEARCH_NAME"
| table title, disabled, next_scheduled_time
  3. Notify SOC: "Detection [name] has been disabled due to [reason]. No further alerts from this search. Will investigate and re-enable after fix."
  4. Log the change: Record in change log: what, when, why, who.
  5. Create a ticket: Track the fix and re-enablement plan.

Scenario 2: Revert a Threshold Change

Time to execute: < 10 minutes

  1. Open the search: Settings → Searches → Find search → Edit Search
  2. Locate the previous version from:
    • Inline SPL version header (see Lifecycle page)
    • Description field backup
    • Change log entry for the previous version
  3. Revert the threshold value to the previous number.
  4. Update the version header: Increment version, document rollback reason.
  5. Verify the change took effect: Wait for next scheduled run, confirm results match expected behavior.
  6. Notify SOC if the threshold change had caused noise: "Threshold reverted. Volume should return to normal within [cron interval]."

Scenario 3: Revert an SPL Logic Change

Time to execute: < 15 minutes

  1. Retrieve the previous SPL version from:
    • Description field backup (if saved there before the change)
    • Detection registry document
    • For OOTB clones: the original OOTB search is still present (disabled) as reference
  2. Replace the current SPL with the previous version.
  3. If no backup exists:
    • Disable the search immediately
    • Recreate from the last known good version in documentation
    • Run through backtest before re-enabling
  4. Run an immediate test: Execute the reverted search manually over the last hour to verify it works.
  5. Update version header and change log.

Scenario 4: Undo a Bulk Enablement

Time to execute: 15-30 minutes depending on count

🚨 This Scenario Should Never Happen

Bulk enablement of detections without individual evaluation violates the OOTB evaluation process. If you're in this situation, something went wrong upstream.

  1. Identify all recently enabled searches:
    SPL: Find Recently Enabled Correlation Searches 
    | rest /services/saved/searches splunk_server=local
| search action.correlationsearch.enabled=1 disabled=0
| eval last_modified = strftime(updated, "%Y-%m-%d %H:%M")
| where updated > relative_time(now(), "-24h")
| table title, eai:acl.app, last_modified, eai:acl.owner
| sort - last_modified
  2. Disable ALL recently enabled searches one by one. Verify each is disabled.
  3. Notify SOC: "Multiple detections have been disabled pending proper evaluation. This was a correction."
  4. Re-evaluate each search individually using the OOTB evaluation decision tree.

Emergency Stop Procedures

🚨 EMERGENCY: When to Use the Kill Switch

Use emergency stop when:

  • A detection is generating >50 notables per hour and climbing
  • SOC is being overwhelmed by false positives from a specific detection
  • A detection is causing Splunk performance degradation (long runtimes, search queue backup)
  • A detection is creating notables that cause automated response actions (email floods, ticket storms)

Emergency Stop Steps

Step Action Time
1 DISABLE the search. Settings → Searches → Find → Edit → Disable. This is the kill switch. Do it first, ask questions later. < 2 min
2 Notify SOC immediately. Slack/call: "Detection [name] has been emergency disabled. Alert storm stopped. No further notables from this search." < 1 min
3 Check for cascading effects. Did the search trigger adaptive response actions? Check for email floods, ticket creation, or automated blocks. < 5 min
4 Bulk-close the storm notables. In Incident Review, filter by search name, select all, set status to "Closed — False Positive" with note "Alert storm — disabled [date]". 5-15 min
5 Document the incident. Change log entry: what happened, when detected, time to disable, root cause (if known), impact assessment. 15 min
6 Root cause analysis. What changed? Data volume spike? Threshold too low? New data source? Fix the root cause BEFORE re-enabling. 1-4 hours
7 Re-enable through full lifecycle. Treat re-enablement as a new deployment: backtest → monitoring → production. Do NOT just re-enable. 1-2 weeks

Preserving Historical Context

When you disable, modify, or retire a detection, the historical notables and the context around them must be preserved for audit and investigation purposes.

What to Preserve

Artifact Where It Lives Retention Action on Retirement
Historical notables notable index Follows index retention (typically 90-365 days) No action needed — notables persist in the index
Search SPL (last version) Saved search object Until deleted or overwritten by ES upgrade Export to detection registry BEFORE retiring
Search SPL (all versions) Detection registry / change log Permanent Already preserved if versioning was followed
Tuning history Change log Permanent Add final entry: "Retired on [date] for [reason]"
SOC feedback Emails, tickets, meeting notes Per organizational retention Summarize key feedback in retirement record
⚠️ Never Delete — Always Disable

Deleting a saved search removes it from Splunk entirely. There is no undo. Disabling preserves the search object, SPL, and settings for future reference or re-enablement.

  • OOTB searches: Disable only. ES upgrades may restore deleted OOTB, creating duplicates.
  • Custom searches: Disable and export SPL to registry before any cleanup.
  • Cloned searches: Disable both the clone and verify the original OOTB is also disabled.

Change Freeze Handling

Retail environments have mandatory change freezes around critical business periods. During these windows, NO changes should be made to detection content.

Freeze Calendar

Freeze Period Typical Dates Duration What Is Frozen Exceptions
Black Friday / Cyber Monday Last week of November through first week of December ~2 weeks ALL detection changes: enable, disable, modify, deploy Emergency stop only (alert storm affecting SOC operations)
Holiday season December 15 through January 5 ~3 weeks ALL detection changes Emergency stop only
ES upgrade windows As scheduled by Splunk Cloud 1 week before through 1 week after All OOTB modifications. Custom changes with caution. Post-upgrade validation searches OK
Major promotional events Varies (coordinate with marketing) Day before through day after Volume-sensitive detections Non-volume detections can proceed with caution

What to Do During Freeze

  • Develop offline: Write and document new detections, but do NOT deploy.
  • Prepare backtests: Run historical queries to validate logic, save results for post-freeze deployment.
  • Audit existing content: Review detection health metrics, identify tuning candidates for post-freeze.
  • Update documentation: Complete runbooks, registry entries, and change logs.
  • Plan post-freeze sprint: Queue up changes for the first safe deployment window after freeze lifts.

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • A change was made without documentation and you discover it. Stop all work. Investigate who made the change and why. Update registry. This is an audit risk.
  • SOC reports they were not notified about a detection change. Communication failure. Apologize, fix the process, add SOC confirmation to your checklist.
  • An emergency stop was required more than once in a month. Something is systematically wrong: either the monitoring process is insufficient or the environment is changing faster than detections can keep up. Escalate for process review.
  • A change freeze exception is requested. Require written business justification. Default answer is NO. Only emergency stops are permitted during freeze.
  • An ES upgrade is happening and you have modified OOTB content. Freeze all OOTB modifications. After upgrade, verify all clones still work. Compare updated OOTB with your clones.

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Quick fix, I'll document later" "Later" never comes. Undocumented changes become mystery changes that the next person has to reverse-engineer. Document BEFORE the change (pre-change record) and update AFTER (result record). It takes 5 minutes.
"Friday afternoon deployment" If something goes wrong, nobody is available over the weekend. SOC gets hit with an alert storm on Saturday with no detection engineer to fix it. Deploy Tuesday-Wednesday only. Full coverage period after deployment.
"Batch enable 10 detections at once" If something goes wrong, you can't tell which detection caused the problem. Debugging becomes a nightmare. Enable ONE detection at a time. Wait at least 24 hours between enablements.
"Skip SOC notification — it's a minor change" The SOC sees new or different alerts and doesn't know why. Trust erodes. They assume the detection platform is unreliable. Always notify. Even low-risk changes get an informational note.
"Re-enable after emergency stop without monitoring" The same problem will recur. You just re-introduced the alert storm you just stopped. Full lifecycle after any emergency stop: fix → backtest → monitor → enable.
