Definitions — Read Before Proceeding

⚠️ These Terms Are Not Interchangeable

API Polling = A collector process (running on an HF, Lambda, or other host) that calls the Akamai SIEM Integration REST API to pull security event JSON from the Akamai Security Events Collector (ASEC). The collector is responsible for authentication, offset tracking, pagination, retry logic, and forwarding events to Splunk.

HEC (HTTP Event Collector) = A Splunk-side ingest endpoint. Data is posted to HEC over HTTPS. HEC does not fetch data from anywhere — it is a receiver. The collector (or DataStream push) sends data to HEC.

Add-on / Connector = A Splunk app package that may include one or more of: a modular input (the polling logic), props/transforms (parsing rules), field aliases (CIM mapping), and saved searches. The Akamai SIEM Integration add-on on Splunkbase (App ID 4310) includes both a Java-based modular input and CIM-format parsing via props.conf.

Critical distinction: Installing an add-on is NOT the same as configuring HEC. The add-on's modular input pulls from the Akamai SIEM API and writes to a Splunk index directly (via the Splunk SDK, not via HEC). If you are using a custom collector that posts to HEC, you still need the add-on's props/transforms for parsing — but the modular input is not involved.

Step 0 — Which Akamai Logging Product Are We Using?

Akamai has two fundamentally different log delivery products. Using the wrong one is the single most common onboarding mistake. Per Akamai's official product documentation:

Product What It Delivers When to Use
SIEM Integration Security events from the Akamai platform — attack detections, WAF rule triggers, bot detections, rate-limit actions. Events are generated by App & API Protector, Kona Site Defender, Client Reputation, Web Application Protector, Bot Manager, and Account Protector. (Source: Akamai techdocs — SIEM Integration overview) Use this when the goal is security event visibility in your SIEM: WAF blocks, DDoS mitigation, bot scoring, credential-stuffing detection. This is the correct product for ES correlation searches.
DataStream 2 Transactional/edge performance logs — every HTTP request's status code, response time, cache hit ratio, bytes transferred. Delivery performance metrics and CDN health data. (Source: Akamai techdocs — DataStream 2 overview) Use this when the goal is CDN performance monitoring, traffic analytics, or edge delivery troubleshooting. DataStream 2 does include a security rules field, but it contains only rule ID and action — not the full forensic context (no request headers, no rule messages, no attack payload data).

SIEM Integration API — Critical Behaviors

These behaviors are documented in Akamai's techdocs and directly affect your collector design. Ignoring them causes data loss, duplicates, or silent gaps.

BehaviorDetails (from Akamai techdocs)
Two fetch modes Offset mode uses an opaque offset string returned in the ResponseContext of each response. Time-based mode uses from and to epoch parameters. Both modes order events by storage time in the Akamai database, not by the time the event actually occurred.
5-second latency Both modes have a built-in 5-second latency. In offset mode, subsequent calls recover those 5 seconds. In time-based mode, events from the last 5 seconds before your requested range are permanently omitted. Therefore, offset mode is the recommended steady-state mode.
12-hour replay window The Akamai Security Events Collector (ASEC) retains events for 12 hours. If your collector goes offline, you can use time-based mode to replay any events from the past 12 hours. After 12 hours, events are gone.
600,000 event max per request The API returns at most 600,000 events per call. During high-traffic periods, configurations may generate far more. The connector must call the API continuously, using the returned offset, to keep up. The default limit is 10,000; maximum is 600,000.
2-minute response timeout Edge servers stop sending the response after 2 minutes. An incomplete response may lack the ResponseContext offset on the final line. If this happens: re-call with the previous offset and a lower limit to get a complete response.
Multi-JSON response format Each response is newline-delimited JSON (NDJSON): one JSON object per line for each event, and the last line is the ResponseContext object containing total, offset, and limit. Your parser must handle this — it is NOT a JSON array.
Base64-encoded fields Several attackData fields (ruleActions, ruleData, ruleMessages, ruleSelectors, ruleTags) are base64-encoded and semicolon-delimited. Each semicolon-separated segment corresponds to one triggered rule. Decode before indexing or at search time.
Rate limiting (429) The API may apply rate limiting. Excess requests return HTTP 429 with a JSON error body including "title": "Too many requests". The API does NOT provide an X-RateLimit-Reset header — the client must implement its own backoff.

Collector Configuration Checklist

✓SettingGuidance
Query mode Use offset mode for steady-state collection (leave epoch time fields blank in the add-on). Reserve time-based mode only for replaying missed events after an outage (within the 12-hour window).
Checkpoint / cursor handling The offset string from ResponseContext must be persisted between polls. The Akamai Splunk add-on stores this in KVStore. Custom collectors must store it durably (file, database, S3 state object). A lost offset means restarting collection — potentially causing duplicates or a gap.
Limit per request Default is 10,000; maximum is 600,000. Start with 10,000–50,000. If the collector cannot ingest within 2 minutes, lower the limit. If falling behind (every response returns limit = true in ResponseContext), increase the limit or poll more frequently.
Multi-JSON parsing Split response on newlines. Parse each line as an individual JSON object. The last line is the ResponseContext — do not send it to Splunk as an event. Akamai strongly recommends using a standard JSON parser to handle schema changes.
Retries and backoff On HTTP 429: implement exponential backoff (e.g., 30s → 60s → 120s). On 5xx: retry up to 3 times with backoff. On incomplete response (no ResponseContext): retry with same offset and lower limit. On network failure: retry with same offset.
Deduplication strategy If you switch from offset mode to time-based mode for replay, expect duplicates in the overlap window. Akamai's Splunk connector documentation explicitly warns about this. Mitigate by deduplicating on httpMessage.requestId + attackData.configId at search time, or by carefully managing the time window to minimize overlap.
Poll interval Call the API continuously as long as it returns events. Only pause (e.g., 30 seconds) when no new events are returned. Do not set fixed long intervals — you will fall behind during traffic spikes.
Connection/socket timeouts The Akamai Splunk connector (v1.4.14+) supports AKAMAI_SIEM_HTTP_CONNECTION_TIMEOUT and AKAMAI_SIEM_HTTP_SOCKET_TIMEOUT environment variables (in seconds). Custom collectors should set a socket timeout ≥ 120s (matching the 2-minute edge server limit) and a connection timeout of 30s.

⚠️ Known Issues with the Add-on

PKIX certificate errors: Multiple Splunk Community reports document PKIX path building failed errors on versions > 1.4.15. Workarounds include: (a) downgrading to v1.4.15, (b) importing the Akamai certificate into the JRE's cacerts keystore, or (c) adding disable_splunk_cert_check = true to each input stanza.

Splunk Cloud IDM limitation: Some users report that after installing the add-on on Splunk Cloud IDM, the data input for Akamai does not appear in Settings → Data Inputs. VERIFY: Check with Splunk Cloud support whether Java-based modular inputs are permitted on your specific Cloud stack (Victoria vs. Classic).

Input cannot be edited after enabling: Akamai's docs note that once a data input is enabled, you cannot edit and re-run it. Instead, disable the input, clone it, make changes to the clone, then enable the clone.

What to Do If CIM Fields Are Missing

If the add-on is installed and data is flowing but CIM data model fields are not populated:

StepAction

2Run | datamodel Web search | where sourcetype="akamaisiem" | head 5 — check if any fields are populated.

Validation SPL — Pass/Fail Checks

Run these queries after data has been flowing for at least 1 hour. Each query includes a pass/fail interpretation. Replace index=akamai_waf and sourcetype=akamaisiem with your actual values.

V1 — Ingestion Count Trend (Are Events Arriving?)

index=akamai_waf sourcetype=akamaisiem earliest=-24h
| timechart span=1h count AS event_count
| eval status=if(event_count>0, "PASS", "FAIL — no events this hour")

PASS: Every hour shows > 0 events with no sustained gaps. FAIL: Gaps > 2 hours indicate collector outage, credential expiry, or API issue.

V2 — Ingestion Lag Percentiles (How Stale Is the Data?)

index=akamai_waf sourcetype=akamaisiem earliest=-4h
| eval lag_seconds = _indextime - _time
| stats p50(lag_seconds) AS p50_lag, p90(lag_seconds) AS p90_lag, p99(lag_seconds) AS p99_lag, max(lag_seconds) AS max_lag
| eval status=if(p90_lag < 600, "PASS", "FAIL — p90 lag exceeds 10 minutes")

PASS: p90 lag < 600 seconds (10 min). FAIL: High lag means the collector is falling behind — increase the limit parameter or poll frequency. If max_lag > 43,200 (12h), you may have replayed stale events.

V3 — Duplicate Indicator

index=akamai_waf sourcetype=akamaisiem earliest=-24h
| stats count BY httpMessage.requestId attackData.configId
| where count > 1
| stats count AS duplicate_groups, sum(count) AS total_duplicate_events
| eval status=if(duplicate_groups=0, "PASS", "FAIL — ".duplicate_groups." groups with duplicates")

PASS: 0 duplicate groups. FAIL: Duplicates usually indicate a mode switch between offset and time-based, or a cursor reset. Investigate the collector's offset state management.

V4 — Sourcetype Consistency

index=akamai_waf earliest=-24h
| stats count BY sourcetype
| eval status=if(sourcetype="akamaisiem" OR sourcetype="akamai:siem", "PASS", "FAIL — unexpected sourcetype: ".sourcetype)

PASS: Only the expected sourcetype appears. FAIL: Mixed sourcetypes indicate misconfigured inputs or data landing in the wrong index.

V5 — Minimum Viable Field Set

index=akamai_waf sourcetype=akamaisiem earliest=-1h
| head 100
| eval has_clientIP=if(isnotnull('attackData.clientIP'), 1, 0)
| eval has_configId=if(isnotnull('attackData.configId'), 1, 0)
| eval has_policyId=if(isnotnull('attackData.policyId'), 1, 0)
| eval has_ruleActions=if(isnotnull('attackData.ruleActions'), 1, 0)
| eval has_httpMethod=if(isnotnull('httpMessage.method'), 1, 0)
| eval has_httpHost=if(isnotnull('httpMessage.host'), 1, 0)
| eval has_httpPath=if(isnotnull('httpMessage.path'), 1, 0)
| eval has_httpStatus=if(isnotnull('httpMessage.status'), 1, 0)
| eval has_geo=if(isnotnull('geo.country'), 1, 0)
| stats avg(has_clientIP) AS pct_clientIP, avg(has_configId) AS pct_configId, avg(has_policyId) AS pct_policyId, avg(has_ruleActions) AS pct_ruleActions, avg(has_httpMethod) AS pct_httpMethod, avg(has_httpHost) AS pct_httpHost, avg(has_httpPath) AS pct_httpPath, avg(has_httpStatus) AS pct_httpStatus, avg(has_geo) AS pct_geo
| eval status=if(pct_clientIP>0.95 AND pct_configId>0.95 AND pct_ruleActions>0.90, "PASS", "FAIL — critical fields below 95% population")

PASS: Core fields > 95% populated. FAIL: Missing fields suggest parsing failures, wrong sourcetype, or base64-encoded fields not being decoded.

V6 — Config ID Coverage

index=akamai_waf sourcetype=akamaisiem earliest=-24h
| stats dc(attackData.configId) AS unique_configs, values(attackData.configId) AS config_ids
| eval status=if(unique_configs >= 1, "PASS — receiving from ".unique_configs." config(s): ".config_ids, "FAIL — no configId values found")

PASS: Count matches the number of configIds you provided to the collector. FAIL: Missing configIds mean those security configurations are not emitting events — re-check SIEM enablement in Control Center.

Why DataStream 2 Is Not the Default for Security Events

DataStream 2 is Akamai's log delivery product for transactional/edge performance data. It captures every HTTP request's delivery metrics and pushes them to destinations (including Splunk HEC) at 30- or 60-second intervals.

While DataStream 2 includes a securityRules field, this field contains only rule IDs and actions in a condensed format (e.g., ULnR_28976|3900000:3900001|). It does not include:

Missing from DataStream 2Available in SIEM Integration
Full attack payload / rule dataattackData.ruleData (base64-decoded matched content)
Rule messagesattackData.ruleMessages (human-readable rule descriptions)
Rule selectorsattackData.ruleSelectors (which part of the request matched)
Rule tags (OWASP classification)attackData.ruleTags (e.g., OWASP_CRS/WEB_ATTACK/SQL_INJECTION)
Bot score & bot classificationbotData.score, botData.responseSegment
Client reputation risk detailsclientData fields (app bundle, SDK version, telemetry type)
User risk data (Account Protector)userRiskData.username, userRiskData.originUserId
🔍 Verification: Is DataStream 2 Appropriate for Your Use Case?

Answer YES to all three of these:

1. You need CDN performance metrics (response time, cache hit ratio, bytes transferred) — not security forensics.

2. You do NOT need to build ES correlation searches on attack rule details, bot scores, or attack payloads.

3. Your compliance or SOC requirements do NOT mandate full WAF event detail in the SIEM.

If any answer is NO → use SIEM Integration, not DataStream 2.

Note: You can run both. DataStream 2 for operational CDN monitoring, and SIEM Integration for security event analysis in ES. They serve different purposes and should land in different indexes with different sourcetypes.

Failure Modes Reference

This section catalogs every known failure mode for Akamai → Splunk ingestion, organized by origin (API-side vs. Splunk-side). Each entry includes detection method and remediation.

API-Side Failures

#FailureSymptoms & DetectionRemediation
F1 HTTP 429 — Rate limited API returns 429 with JSON body: "title": "Too many requests", "detail": "Too many requests made from clients of this account". Collector logs show repeated 429s. Events stop flowing. Implement exponential backoff. Reduce poll frequency. Check if multiple collectors or API clients from the same account are competing. Akamai does not publish a specific rate limit number for the SIEM API — contact the account team to understand current limits.
F2 Expired / revoked API credentials API returns 401 or 403. Collector logs show authentication failures. No new events in Splunk. Re-provision credentials in Control Center → Identity & access → API clients. Update all four credential values (client_token, client_secret, access_token, hostname) in the connector config. Restart the collector.
F3 Cursor/offset reset — duplicates V3 validation shows spike in duplicates. Collector was restarted without persisted offset, or KVStore was cleared. If offset is lost: switch to time-based mode to replay from the last known good timestamp (within 12-hour window). Accept that duplicates may occur in the overlap. Implement dedup at search time on httpMessage.requestId.
F4 Time-based mode returns older/stale logs V2 shows large max_lag after a mode switch. Events with timestamps far in the past appear. This is expected behavior — the API orders by storage time, not event time. After replay is complete, switch back to offset mode. Ensure your time-based from and to parameters are within the 12-hour window.
F5 Offset mode gap — events missed V1 shows gap in event count trend. Collector was offline for > 12 hours, or offset became invalid. If within 12 hours: use time-based mode to replay the gap. If beyond 12 hours: events are permanently lost — document the gap. The Sumo Logic documentation notes that an offset token can become invalid if a collector stops for an extended period.
F6 Timezone / timestamp shift V2 shows consistent negative lag (events appear to be from the future) or exactly N-hour offset. Akamai SIEM event timestamps (httpMessage.start) are epoch seconds (UTC). Verify your props.conf uses TIME_FORMAT = %s and TZ = UTC. The add-on handles this for sourcetype akamaisiem.
F7 Multi-JSON parsing failure V5 shows missing fields on most events. Raw events in Splunk contain multiple JSON objects concatenated on one line, or the ResponseContext is indexed as an event. The collector's JSON parser is not splitting on newlines correctly. Each line is one event. The last line (ResponseContext) must be consumed by the collector, not forwarded to Splunk. If using HEC, ensure each event is sent as a separate HEC event, not the entire response body as one event.
F8 2-minute timeout — incomplete response Collector logs show truncated responses. Offset is not updated (ResponseContext missing from response). Events may be partially ingested and then re-fetched, causing duplicates. Lower the limit parameter so the API returns fewer events per call, completing within the 2-minute window. Akamai's documentation explicitly states: re-call with the previous offset and a lower limit.

If using a custom collector: decode base64 fields before sending to HEC, or add search-time EVAL in props.conf. Each base64 field is semicolon-delimited (one segment per triggered rule).
F14 Java / KVStore failure on HF (add-on path) Splunkd.log shows Unable to initialize modular input "TA-Akamai_SIEM" or Permission denied for TA-Akamai_SIEM.sh. Verify: (a) Java 8+ is installed and in PATH — run java -version as the Splunk user, (b) KVStore is running — splunk show kvstore-status, (c) the .sh script is executable — chmod +x bin/TA-Akamai_SIEM.sh, (d) no Universal Forwarder is installed on the same host.
F15 PKIX certificate error (add-on path) Collector logs show PKIX path building failed: SunCertPathBuilderException. Data input cannot be saved or started. Import Akamai's certificate into the JRE cacerts: keytool -importcert -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit -file akamai-cert.crt. Alternatively, add disable_splunk_cert_check = true to the input stanza. Some users report success by downgrading to add-on version 1.4.15.
