🏗️ Architecture: Two Paths for Akamai → Splunk Cloud

Akamai SIEM Integration (Splunkbase App 4310) is a single app that provides both a Java-based modular input (data collection) and props.conf/transforms.conf (parsing and CIM mapping). Where you install it and how you configure it determines which role it plays.

🅰️ Path A — Splunk Cloud Native (App 4310 on Search Head)

  • App 4310 installed on all Splunk Cloud indexers (for index-time parsing) and on one search head (for data input + search-time parsing).
  • Data input enabled on exactly one search head. API credentials (EdgeGrid) configured in the app's data input UI.
  • The search head runs the modular input (Java-based), polls the Akamai SIEM API, and ingests events directly.
  • No external collector host required.
  • ⚠️ Requires Java 8+ (JRE 1.8) on the search head — verify with Splunk Support that your tenant has Java available.
  • ⚠️ Requires sourcetype akamaisiem — this is how the app's props.conf is configured.

🅱️ Path B — Heavy Forwarder (Fallback)

  • App 4310 installed on an on-prem Heavy Forwarder. HF runs the modular input and forwards events to Splunk Cloud.
  • App 4310 also installed on Splunk Cloud indexers (for parsing) and optionally on search heads (for search-time field extractions, without data input enabled).
  • Works on both Victoria and Classic Splunk Cloud.
  • Use this path if: Java is not available on your Cloud SH, Splunk Support restricts app execution on SH, or the modular input fails to register on your tenant.

Splunk Cloud Execution Notes

What is App 4310?Akamai SIEM Integration — a single Splunk app from Splunkbase that provides both a Java-based modular input (for polling the Akamai SIEM API) and parsing/CIM configuration (props.conf, transforms.conf, eventtypes, tags). It is both the "connector" and the "TA" in one package.
Can it run on Splunk Cloud SH?Yes, for Victoria tenants (Option 2 per Splunkbase). The app can be installed on Splunk Cloud search heads with data input enabled on one SH. Requires Java 8+ on the SH. Verify with Splunk Support. Note: Community reports indicate some tenants experience issues with data inputs not appearing — if this occurs, fall back to Path B.
Where do API credentials live?Path A: In the App 4310 data input configuration UI on the Splunk Cloud search head (Settings → Data Inputs → Akamai Security Incident Event Manager API). Path B: On the Heavy Forwarder in the same UI or in inputs.conf.
Is a separate "collector" needed?Path A: No. The modular input inside App 4310 IS the collector. Path B: The Heavy Forwarder IS the collector host. There is no separate binary to download — the app is the connector.
Where does parsing happen?Index-time: Timestamp and sourcetype assignment. App 4310 must be on indexers. Search-time: Field extraction, FIELDALIAS, EVAL, CIM mapping — App 4310 on the search head. The same app handles both layers.
What sourcetype must I use?akamaisiem — as documented on Splunkbase. The app's props.conf is configured for this sourcetype. Using a different sourcetype will break parsing.
Can data input be enabled on multiple SHs?No. Splunkbase explicitly states: "make sure only on one search head data input is enabled." Enabling on multiple SHs causes duplicate events.
What about the "Splunk Add-on for Akamai" (App 4186)?App 4186 is a different app that was previously available on Splunkbase. App 4310 is Akamai's official SIEM Integration connector. Use 4310.

Section 1 — What Akamai WAF Logs Actually Are

Before configuring anything in Splunk, understand what you are onboarding.

What Is Akamai?

Akamai Technologies operates one of the world's largest CDN (Content Delivery Network) and edge computing platforms. Enterprise websites route traffic through Akamai's global edge servers, which provide performance, availability, and security services — including WAF, DDoS mitigation, bot management, and API protection.

What Is Akamai WAF?

Akamai WAF (Web Application Firewall) inspects HTTP/HTTPS traffic at the edge. When a request matches a security rule (SQL injection, XSS, protocol violation, rate limit, etc.), the WAF evaluates it against the configured security policies and takes an action: alert, deny, custom deny, redirect, etc. Each action generates a security event.

What Is a "WAF Security Event"?

AttributeValue
SourceAkamai edge server that processed the request
TriggerA security rule matched (WAF rule, rate control, bot detection, reputation score, custom rule)
ContentClient IP, request URL, HTTP method, matched rules, rule actions, user agent, geo data, attack metadata
FormatJSON (via SIEM API). Some fields are base64-encoded (ruleActions, ruleData, ruleMessages, ruleSelectors, ruleTags).
DeliveryVia the SIEM Integration API (REST). Events are NOT pushed automatically — they must be pulled by a polling mechanism.
Retention12 hours in Akamai's Security Events Collector (ASEC). After 12 hours, events are permanently dropped.

What Akamai Security Products Generate These Events?

ProductEvent TypesTypical Volume
App & API Protector (AAP)WAF rule triggers, adaptive security, API protectionHigh
Kona Site Defender (KSD)WAF rule triggers, rate controlsHigh
Web Application Protector (WAP)Simplified WAF eventsMedium
Bot ManagerBot classification, challenge actions (BETA in SIEM)Very High
Client ReputationIP reputation scoring eventsLow-Medium
Account ProtectorCredential stuffing, account takeover eventsMedium

Why Do Enterprises Send These Logs to a SIEM?

CorrelationCombine WAF events with endpoint, identity, network data to detect multi-stage attacks.
DetectionWrite ES correlation searches that fire notable events when WAF patterns match known attack campaigns.
InvestigationSOC analysts need WAF context when triaging incidents (was this IP blocked at the edge?).
CompliancePCI DSS, SOC 2, and other frameworks require centralized logging of web security events.
ForensicsPost-incident analysis requires searching WAF events alongside other sources in a single timeline.

Section 2 — How Akamai Exposes WAF Security Events

Akamai Does NOT Push Logs Automatically

Unlike some vendors that can POST events directly to a SIEM endpoint, Akamai's SIEM Integration works via a pull model. Events are stored temporarily in Akamai's Security Events Collector (ASEC) and exposed through a RESTful API. A polling mechanism must call this API on a schedule to retrieve events.

Where Akamai Stores Security Events

The Akamai Security Events Collector (ASEC) aggregates security events from edge servers globally. Events are available for retrieval within approximately 5 seconds of occurrence. ASEC retains events for 12 hours only — if your polling mechanism stops for longer than 12 hours, events are lost permanently.

The Akamai SIEM Integration API

PropertyValue
EndpointGET /siem/v1/configs/{configId}
AuthenticationAkamai OPEN EdgeGrid — requires client_token, client_secret, access_token, hostname
Response FormatNDJSON (newline-delimited JSON). Last line contains ResponseContext with the offset for the next call.
Max Events/Request600,000 (configurable, default 10,000)
Rate LimitingHTTP 429 — no reset header. Use exponential backoff.
Response Timeout2 minutes. If exceeded, reduce the limit parameter.
Base64 FieldsruleActions, ruleData, ruleMessages, ruleSelectors, ruleTags — semicolon-delimited after decoding.
Polling ModesOffset-based (use ResponseContext offset) or Time-based (epoch time range for replay).

What About DataStream 2?

⚠️ DataStream 2 ≠ SIEM Integration

DataStream 2 is Akamai's delivery mechanism for operational/performance logs (CDN traffic, cache hits, origin response times). It can push to S3, Azure Blob, Splunk HEC, etc.

SIEM Integration delivers security events only (WAF triggers, bot actions, DDoS mitigations) via the pull-based SIEM API.

They are different products, different data, different delivery methods. This page covers SIEM Integration only.

Section 3 — Understanding the Components

Before you configure anything, understand what App 4310 actually is and how its components work together.

App 4310 Is BOTH the Connector AND the TA

💡 Key Insight — One App, Two Roles

The most common source of confusion in Akamai + Splunk deployments is treating the "connector" and the "TA" as two separate pieces of software. They are the same app — Splunkbase App 4310 (Akamai SIEM Integration).

The app contains: (A) A Java-based modular input that polls the Akamai SIEM API and ingests events. (B) props.conf and transforms.conf that parse ingested JSON into structured fields. (C) Eventtypes, tags, and field aliases for CIM mapping.

Where you install the app and whether you enable the data input determines which capabilities are active.

ComponentWhat It IsWhat It Is NOT
App 4310 — Data Input (Modular Input) A Java-based modular input inside the app that authenticates to the Akamai SIEM API using EdgeGrid credentials, polls for new events on a schedule, and writes them into Splunk. A separate downloadable binary. It is part of App 4310. When you install the app, the modular input code is included.
App 4310 — Parsing Configuration props.conf and transforms.conf that define how Akamai's JSON events are parsed into structured Splunk fields at index time and search time. Automatically active without installing the app. If the app is not on indexers, index-time parsing won't happen.
App 4310 — CIM Mapping FIELDALIAS definitions, eventtypes, and tags that map Akamai fields to CIM-compliant field names (e.g., src, dest, action) for ES data model population. A guarantee that ALL CIM fields will be populated. Coverage varies — you may need a custom override app for gaps.
HEC (HTTP Event Collector) Splunk's built-in HTTPS endpoint for receiving data via POST requests. Used in Path B and Path C when events are forwarded from an external host. Needed in Path A. When the modular input runs on the SH, events are written directly — no HEC required.

Section 4 — Akamai Prerequisites (Step by Step)

These prerequisites are the same regardless of whether you choose Path A or Path B. Complete all of them before touching Splunk.

Step 4.1 — Verify SIEM Integration Is Enabled

WHATConfirm that SIEM data collection is turned ON for each security configuration you want to monitor.
WHEREAkamai Control Center → WEB & DATA CENTER SECURITY → Security Configuration → [select config] → Advanced Settings → Data collection for SIEM Integrations.
HOWToggle must show On. Select "All Security Policies" or choose specific policies. Optionally include Bot Manager events (excluded by default). If you use Account Protector, decide on the "Include username" checkbox.
WHYIf SIEM is not enabled, the API returns no events. This is the most common "zero events" root cause.
VERIFYThe toggle shows On. The Configuration ID field displays a numeric value.

Step 4.2 — Verify Configuration Is Activated to Production

WHATPush your security configuration changes to the Akamai production network so events are actually generated.
WHERESecurity Configuration page → Activate → Network: Production → Activate.
WHYChanges to SIEM settings only take effect after activation. Staging-only activation means real traffic won't generate SIEM events.
VERIFYThe configuration version shows "Active on Production" status.

Step 4.3 — Identify All configIds in Scope

Action: For each security configuration with SIEM enabled, copy the Web Security Configuration ID value. You will configure one data input per configId (or pass multiple comma-separated configIds to a single input).

Step 4.4 — Create API Credentials

WHATEdgeGrid API credentials that authenticate the Splunk app when calling the SIEM API. Four values required: client_token, client_secret, access_token, hostname.
WHEREAkamai Control Center → ACCOUNT ADMIN → Identity & access → Create API client (or assign to existing user).
HOWCreate or select an API client. Assign the SIEM Integration API with READ-WRITE access. Generate credentials. Record all four values securely.
WHYWithout valid EdgeGrid credentials, the modular input in App 4310 cannot authenticate to the Akamai API. READ-WRITE is needed for offset management.
VERIFYYou have all four credential values recorded. The API client has the "Manage SIEM" role assigned.

Step 4.5 — Verify the API User Has the Correct Role

WHERE: Akamai Control Center → ACCOUNT ADMIN → Identity & access → Users and API Clients tab → [select user] → Edit roles → Confirm Manage SIEM role is assigned for the appropriate group.

Step 4.6 — Verify Network Path

The host running the modular input (Splunk Cloud SH for Path A, or your HF for Path B) must be able to reach Akamai's API endpoints over HTTPS (port 443). Ensure your firewall and proxy allow traffic to:

  • *.cloudsecurity.akamaiapis.net
  • *.luna.akamaiapis.net

Path A note: If your Splunk Cloud SH cannot reach these domains (e.g., tenant egress restrictions), the modular input will fail silently. This is a strong signal to fall back to Path B.

Path B note: Your Heavy Forwarder must have outbound HTTPS access to these domains.

Offset-based (default)Each API response includes a ResponseContext.offset value. The next request uses this offset to fetch only new events. The modular input stores the offset in KVStore or a checkpoint file.Normal continuous operation. This is the default and recommended mode.

Why Akamai Changes Can Break ES (and How We Avoid It)

🔴 CIM Is Shared Infrastructure — Handle With Care

Enterprise Security does not maintain separate CIM configurations per data source. When you add a FIELDALIAS, EVAL, eventtype, or tag for Akamai, those rules operate at the sourcetype level across the entire search head. If your changes are incorrect, they can affect every data source that shares the same CIM data model or field names.

How Akamai CIM Changes Can Break ES

#RiskWhat HappensPrevention
1Incorrect FIELDALIAS mappingIf you create FIELDALIAS-src = some_wrong_field AS src for the Akamai sourcetype, every event from that sourcetype gets a wrong src value. ES correlation searches that join on src produce false positives or false negatives.Validate every alias in Dev with real data before deploying to Prod.
2Overly broad tagsAdding the web tag to an eventtype with a loose constraint (e.g., sourcetype=akamai*) may accidentally pull non-WAF Akamai events into the Web data model, polluting it with events that lack required CIM fields.Scope eventtypes narrowly. Test in Dev with | datamodel Web search | stats count by sourcetype.
3Conflicting EVAL overridesAn EVAL-action definition for Akamai could conflict with another TA's EVAL-action if both target the same field name at the global level. In Splunk, the last-loaded conf wins — order depends on app precedence.Always scope EVAL/FIELDALIAS to a specific [sourcetype] stanza in props.conf. Never use [default] or [source::...] stanzas for CIM mappings.
4Data model acceleration corruptionIf CIM tags are added, removed, or changed on a sourcetype that is already accelerated in a data model, the acceleration summaries become stale. ES continues using old summaries until acceleration rebuilds — during which time correlation searches produce inconsistent results.After any CIM tag change in Dev, rebuild acceleration and verify with | tstats before promoting to Prod.
5Editing vendor TA directlyIf you modify the Akamai TA's props.conf directly, your changes are silently overwritten when the TA is updated via SSAI. This creates a "worked yesterday, broken today" failure mode.Never edit vendor TA files. All custom mappings go in SA-akamai-cim-overrides (Step 11.4).

The Safe Change Protocol

StepActionDetail
1Make the change in Dev onlyAdd FIELDALIAS, EVAL, tag, or eventtype to the custom CIM app. Deploy via SSAI to Dev search head.
2Run CIM validation (Step 11.1)Confirm target fields populate correctly. Confirm non-target fields are unaffected.
3Check data model impactRun | datamodel Web search | stats count by sourcetype in Dev. Verify only expected sourcetypes appear. No unexpected sources pulled in.

💡 Principle: Minimal Changes, Maximum Scoping

Prefer the smallest possible CIM change. One FIELDALIAS per missing field. One EVAL per transformation. Scoped to one [sourcetype] stanza. Deployed in a single custom app with a clear name. No global overrides. No default stanzas. This discipline is what separates "works in Dev" from "survives in Prod."

Section 11 — CIM & ES Readiness (Verify, Do Not Assume)

What Is CIM and Why Does ES Need It?

The Common Information Model (CIM) is a set of standard field names that Splunk ES uses across all data sources. Without CIM mapping, ES cannot find your events — its dashboards, correlation searches, and threat intelligence all query CIM field names, not vendor-specific ones.

For example, the attacker's IP address might be stored as attackData.clientIP in the raw Akamai event. ES does not know that field name. ES looks for src. CIM mapping creates the bridge: attackData.clientIP → src.

CIM mapping does NOT happen automatically. It requires either a TA that defines FIELDALIAS/EVAL rules for your sourcetype, or manual configuration.

What the Akamai TA Provides (and What It Doesn't)

The Akamai SIEM Integration add-on (Splunkbase App ID 4310) is installed on the Splunk Cloud search head. When installed and the sourcetype matches, it provides:

What the TA ProvidesDetail
JSON field extractionAutomatic extraction of nested Akamai JSON fields — attackData.*, httpMessage.*, geo.*, ruleActions, etc. Driven by props.conf with KV_MODE = json or equivalent.
CIM field aliasesVendor-provided FIELDALIAS definitions that map Akamai field names to CIM standard names. For example: attackData.clientIP → src. These are defined in the TA's props.conf.
Eventtypes and tagsEventtype definitions (e.g., akamai_siem_attack) and associated tags (e.g., web, attack) that place events into ES data models like Web.
Lookup definitionsMay include lookup tables for Akamai-specific value normalization (e.g., action code mapping).
⚠️ What the TA Does NOT Guarantee

The TA provides vendor-documented CIM mappings. It does NOT guarantee that every CIM field ES needs is fully populated for your specific security configuration. You MUST validate the following — do not assume the TA handles everything:

#What Must Be ValidatedWhy
1CIM field populationEven with the TA installed, some CIM fields may be empty if the underlying vendor field is absent in your events (e.g., http_user_agent may not be included by all Akamai security products).
2Sourcetype matchApp 4310's props.conf targets sourcetype akamaisiem. If events arrive with a different sourcetype, the parsing rules never fire. Always use akamaisiem.
3Tag assignmentCIM tags like web, attack must be present for data model inclusion. Verify with | table tag::*.
4Data model populationTags + CIM fields + index allow list must all align for events to appear in the Web or Network_Traffic data model. Partial mapping = silent failure.
5Missing or partial CIM coverageSome fields ES uses (e.g., vendor_product, app) may not be mapped by the TA. These require manual CIM extension via a custom app.

Step 11.4 — When and How to Add Manual CIM Mappings

🚨 Never Edit the Vendor TA

Do NOT modify the Akamai add-on's (App ID 4310) props.conf or transforms.conf directly. Vendor TA updates will overwrite your changes. Instead, create a separate custom app that layers additional CIM mappings on top of the TA.

When is manual mapping needed? Manual CIM mapping is normal — it is not an error or a workaround. It is needed when:

1The TA does not map a CIM field that ES requires (e.g., vendor_product, app)
2A vendor field name changed between Akamai product versions but the TA has not been updated
3You need to normalize a vendor-specific value to a CIM-standard value (e.g., Akamai deny → CIM blocked)
4An additional CIM field is needed for a custom correlation search

[<your_sourcetype>]
# ── CIM FIELD ALIASES ──────────────────────────────────
# Map Akamai vendor field → CIM standard field
# Use FIELDALIAS when the vendor field exists and just needs renaming

FIELDALIAS-akamai_src       = attackData.clientIP AS src
FIELDALIAS-akamai_dest      = httpMessage.host AS dest
FIELDALIAS-akamai_url       = httpMessage.path AS url
FIELDALIAS-akamai_method    = httpMessage.method AS http_method
FIELDALIAS-akamai_status    = httpMessage.status AS status
FIELDALIAS-akamai_ua        = httpMessage.requestHeaders.User-Agent AS http_user_agent

# ── CIM EVAL FIELDS ───────────────────────────────────
# Use EVAL when the CIM field requires transformation, not just renaming

# Map Akamai action values to CIM standard (allowed/blocked)
EVAL-action = case( \
    match(attackData.action, "(?i)^deny$"), "blocked", \
    match(attackData.action, "(?i)^alert$"), "allowed", \
    match(attackData.action, "(?i)^monitor$"), "allowed", \
    match(attackData.action, "(?i)^mitigated$"), "blocked", \
    true(), attackData.action)

# Set static vendor identification
EVAL-vendor_product = "Akamai WAF"
EVAL-app            = "Akamai App & API Protector"

# ── NOTES ──────────────────────────────────────────────
# 1. FIELDALIAS only works when the source field exists
# 2. EVAL overrides FIELDALIAS if both map to same CIM field
# 3. These rules layer ON TOP of the vendor TA — they don't replace it
# 4. After deploying, re-run Step 11.1 to verify population

What Must Be True Before Writing Detections

Every statement above must be verified by a passing gate in both Dev and Prod — not assumed. If any gate was skipped or showed FAIL, go back and fix it. Writing correlation searches against broken data creates false confidence.

What Should NOT Be Done Yet

Do not enable RBA risk scoringRBA is not in use yet. Adding risk scores before the RBA framework is operational creates noise.
Do not build complex multi-source correlationsUntil other data sources (VPN, endpoint, identity) are also onboarded and CIM-mapped, cross-source detection will not work reliably.
Do not tune detection thresholds yetLet the data flow for at least 1–2 weeks to establish baselines before setting alert thresholds.
