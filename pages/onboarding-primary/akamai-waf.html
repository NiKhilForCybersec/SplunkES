Section 1 — What Akamai WAF Logs Actually Are

No Splunk terms in this section. No APIs. Just the fundamentals.

What Is Akamai?

Akamai Technologies operates one of the world's largest content delivery networks (CDN). When a company like a large retail enterprise puts its website and applications behind Akamai, all customer traffic flows through Akamai's global edge servers before reaching the company's own servers. This means Akamai sits between the internet and the company — it sees every request.

What Is Akamai WAF?

Akamai offers a Web Application Firewall (WAF) as part of its edge security products. The WAF inspects every HTTP request passing through the edge and decides whether the request is legitimate traffic or an attack. It applies security rules to detect threats like SQL injection, cross-site scripting (XSS), command injection, path traversal, and other web application attacks defined by standards like the OWASP Top 10.

When the WAF detects something suspicious, it takes an action — it might block the request, allow it with a warning, rate-limit the source, or trigger a captcha challenge. Every one of these decisions generates a security event.

What Is a "WAF Security Event"?

A security event is a record of a decision the WAF made about a specific HTTP request. Each event contains:

InformationWhat It Tells You
Who made the requestSource IP address, geographic location (country, city), ASN (network owner).
What the request looked likeHTTP method (GET/POST), URL path, query parameters, user-agent, referrer, request headers.
Where it was goingTarget hostname, destination port.
What rules triggeredWhich security rules matched (rule IDs, rule messages describing the threat type), what the attack payload looked like.
What action was takenAlert (logged only), deny (blocked), slow (rate-limited), or other configured actions.
Additional contextBot scores (if Bot Manager is enabled), client reputation scores, the Akamai configuration that processed the request.

What Akamai Security Products Generate These Events?

The security events do not come from just one product — several Akamai products feed into the same event stream:

ProductWhat It Does
App & API ProtectorCurrent-generation WAF. Inspects HTTP traffic for application-layer attacks.
Kona Site DefenderPrevious-generation WAF. Same purpose, older product. Still widely deployed.
Web Application ProtectorSimplified WAF for smaller sites. Generates the same event format.
Bot ManagerDetects and classifies bots. Adds bot score and classification to events.
Client ReputationScores source IPs based on historical behavior across Akamai's network.
Account ProtectorDetects account takeover attempts on login pages.

All of these products write to the same security event stream. When you collect Akamai security events, you get events from whichever products are enabled on the client's Akamai configuration.

Why Do Enterprises Send These Logs to a SIEM?

Akamai's own dashboard shows security events, but it is not a detection and response platform. Enterprises send these logs to a SIEM (like Splunk) because they need to:

Correlate with other sourcesA blocked WAF request from IP 1.2.3.4 is interesting. That same IP also failing VPN logins and scanning internal ports is a campaign. The SIEM connects these.
Detect patterns over timeCredential stuffing attacks trickle in slowly — 10 requests per minute across 50 IPs. The WAF sees each request individually. The SIEM sees the pattern.
Build automated alertsWhen attack volume from a country spikes 10x in an hour, the SIEM triggers an alert. Akamai's dashboard does not do this.
Feed incident response workflowsInvestigations need searchable, retainable logs. Akamai retains security events for only 12 hours. The SIEM retains them for months or years.

Section 2 — How Akamai Exposes WAF Security Events

Akamai Does NOT Push Logs to You

This is the most important thing to understand upfront: Akamai does not send security events anywhere automatically. There is no "enable forwarding to Splunk" toggle. Akamai stores security events temporarily on its platform, and you must actively pull them out.

Where Akamai Stores Security Events

When a security event is generated at the edge, Akamai writes it to a short-term buffer called the Akamai Security Events Collector (ASEC). ASEC retains events for exactly 12 hours. After 12 hours, events are permanently deleted — there is no archive, no backup, no way to recover them. This 12-hour window is the hard constraint that drives everything about your collection strategy.

The Akamai SIEM Integration API

The supported way to extract security events from ASEC is the SIEM Integration API. This is a REST API with these characteristics:

ProtocolHTTPS REST API (authenticated with Akamai EdgeGrid)
DirectionPull — your code calls Akamai. Akamai does not call you.
Response formatNewline-delimited JSON (NDJSON). One JSON object per line per event. The last line is a ResponseContext object with pagination data.
AuthenticationAkamai OPEN EdgeGrid — requires four credential values: client_token, client_secret, access_token, and hostname.
Retention12 hours. Non-negotiable. Miss the window and events are gone forever.
Max events per request600,000 (default: 10,000, configurable via the limit parameter).
Inherent latency5 seconds — the API intentionally delays delivery by 5 seconds.
Response timeout2 minutes — Akamai's edge stops sending after 2 minutes per request.

What About DataStream 2?

⚠️ DataStream 2 Is NOT Security Events — Do Not Confuse Them

DataStream 2 is a separate Akamai product that delivers CDN performance and delivery metrics — things like edge response times, cache hit ratios, origin health. It includes only rule IDs and actions as metadata, NOT the full attack payloads, rule messages, bot scores, or client reputation data that the SIEM Integration API provides.

If someone on the client team says "we already send Akamai logs to Splunk via DataStream" — those are performance logs, not security events. You still need the SIEM Integration API for WAF detection.

DataStream 2 is a separate onboarding with a different index, sourcetype, and data model. It is out of scope for this page.

TermWhat It Means (Plain English)

Everything in this section happens in the Akamai Control Center (the Akamai web UI). You need a login with sufficient permissions. If you do not have access, request it from the client's Akamai account administrator.

AspectDetail

WHEREAkamai Control Center → WEB & DATA CENTER SECURITY → Security Configuration → select the configuration → Advanced Settings → Data Collection for SIEM Integrations.
HOWThe toggle must show On. If it is Off, turn it on and activate the configuration to production (next step). Record the configId displayed on this page — you will need it later.

AspectDetail
WHATAn Akamai security configuration must be active on the production network to generate events. Configurations in staging or draft mode do not produce security events.

VERIFYProduction status shows "Active" with a recent activation timestamp.

Step 4.3 — Identify All configIds in Scope

Each Akamai security configuration has a unique configId. The SIEM API fetches events per configId. A large enterprise may have multiple security configurations — one per domain, one per application, or one per business unit.

Action: Ask the client's Akamai administrator how many security configurations are in scope. Record every configId. You will pass these to your collector.

Step 4.4 — Create API Credentials

AspectDetail
WHATAPI credentials that authenticate your collector when calling the SIEM Integration API. Akamai uses its own authentication scheme called EdgeGrid, which requires four values.
WHEREAkamai Control Center → ACCOUNT ADMIN → Identity & access → API clients → Create API Client.
HOWSelect the SIEM API service → set access to READ-WRITE. Click Create. Akamai shows four values once: client_token, client_secret, access_token, hostname. Copy all four immediately — client_secret cannot be retrieved again.
WHYWithout these credentials, the collector cannot authenticate. Without READ-WRITE scope, the collector cannot manage offsets.
VERIFYYou have all four values saved in a secure location (vault, secrets manager, encrypted file).

Step 4.5 — Verify the API User Has the Correct Role

WHERE: Control Center → Identity & access → Users → select the user → Edit roles.

VERIFY: The Manage SIEM role is assigned. Without this role, API calls will return 403 Forbidden even with valid credentials.

Step 4.6 — Verify Network Path (Collector → Akamai API)

The machine that will run your collector must be able to reach Akamai's API endpoints over HTTPS (port 443). Ensure your firewall and proxy allow traffic to:

*.cloudsecurity.akamaiapis.netPrimary SIEM API endpoint domain.
*.luna.akamaiapis.netLegacy API endpoint (some configurations still use this).

Section 5 — Where the Collector Runs

The Fundamental Rule

The collector does NOT run inside Splunk Cloud. In Splunk Cloud, you do not have OS access to the search heads or indexers. You cannot install arbitrary software, run scripts, or execute cron jobs on the Splunk Cloud infrastructure. The collector must run on infrastructure you control.

Where Can the Collector Run?

OptionDescriptionBest For
Client VM / ServerA dedicated VM (Linux or Windows) on the client's network or in their cloud account (AWS EC2, Azure VM, GCP Compute).Most enterprise deployments. Easy to manage and troubleshoot.
ContainerDocker container running the collector process. Can be deployed on ECS, EKS, AKS, or any container platform.Teams that prefer containerized infrastructure.
Serverless FunctionAWS Lambda, Azure Function, or GCP Cloud Function. Runs on a schedule (every 30–60 seconds).Lightweight deployments. Good for lower event volumes. Requires stateless offset management.
Customer Heavy ForwarderA Splunk Heavy Forwarder running on client infrastructure. The HF is customer-managed, not part of Splunk Cloud.Teams that already have an HF for other data sources.

What About the Splunk Add-on's Modular Input?

⚠️ The Akamai Add-on Modular Input Has Constraints in Splunk Cloud

The Akamai SIEM Integration add-on (Splunkbase App ID 4310) includes a Java-based modular input that can act as a collector — it polls the Akamai API and writes events directly into Splunk. However, running this inside Splunk Cloud has significant restrictions:

Classic Experience: Modular inputs can only run on the IDM (Inputs Data Manager) or a customer-managed HF — NOT on the search head.

Victoria Experience: Modular inputs can run on the SH if the add-on is Cloud-vetted. However, the Akamai add-on uses Java, which has additional compatibility requirements.

Recommendation: Unless you have confirmed with Splunk support that the Akamai add-on's modular input works in your specific Cloud environment, use an external collector. The external collector approach is universally reliable.

What Does the Collector Do?

Regardless of where it runs, the collector has exactly four responsibilities:

#ResponsibilityDetail
1Poll the APICall the Akamai SIEM Integration API on a regular schedule (every 30–60 seconds). Pass the configId(s) and credentials.
2Track checkpointsStore the offset from each API response. Pass it in the next request. This prevents duplicate collection and ensures no events are skipped.
3Handle failuresImplement retry logic for rate limits (HTTP 429), timeouts, and network errors. If the collector goes offline, use time-based replay to catch up within the 12-hour window.
4Forward to SplunkPOST each event as JSON to the Splunk Cloud HEC endpoint with the correct index, sourcetype, and HEC token.

Section 6 — API Polling Mechanics

No Splunk configuration in this section. This is about how the Akamai API works and what your collector must handle.

Two Polling Modes

ModeHow It WorksWhen to Use
Offset-based (recommended)Each API response contains a ResponseContext object (the last line) with an offset string. You store this offset and pass it in the next request. The API returns only events that occurred after that offset.Steady-state collection. This is the normal operating mode.
Time-basedYou pass from and to epoch timestamps. The API returns all events in that time range.Catching up after collector downtime. Replaying a specific time window. Initial backfill.

Critical API Behaviors Your Collector Must Handle

BehaviorWhat Your Collector Must Do
NDJSON formatThe response body is newline-delimited JSON. Each line except the last is one security event. The last line is the ResponseContext — consume it for offset/pagination, do NOT send it to Splunk.
5-second latencyThe API has a built-in 5-second delay. In offset mode, the next call recovers those 5 seconds. Do not try to compensate for this.
600K event capDefault limit is 10,000. If your response consistently contains "limit": true in the ResponseContext, you are not keeping up — increase the limit (up to 600,000) or poll more frequently.
2-minute timeoutAkamai's edge servers stop sending after 2 minutes per request. A truncated response has no ResponseContext on the last line. Re-call with the same offset and a lower limit.
HTTP 429 — Rate limitedAkamai returns 429 with no X-RateLimit-Reset header. Implement exponential backoff: wait 30s → 60s → 120s before retrying.
Base64-encoded fieldsFields ruleActions, ruleData, ruleMessages, ruleSelectors, ruleTags are base64-encoded. Each contains semicolon-delimited values (one per triggered rule). Decode in the collector before posting, or leave encoded and decode at search time.
12-hour replayIf the collector goes offline, events remain available for 12 hours. Use time-based mode with from and to epochs to replay. After 12 hours, events are permanently lost.
Offset persistenceIf the offset is lost (e.g., disk failure), you must fall back to time-based mode. Use the last known collection time as the from parameter. Accept that some duplicates may occur.

Section 7 — Configuring Splunk Cloud HEC

What Is HEC and Why Is It the Right Choice?

HEC (HTTP Event Collector) is Splunk's built-in HTTPS endpoint for receiving data. It accepts JSON payloads over HTTPS and routes them to a configured index. In Splunk Cloud, HEC is the primary supported ingestion method for external data — you do not have alternative options like file monitoring or TCP inputs on the Cloud infrastructure.

Step 7.1 — Create a Dedicated Index

AspectDetail
WHATA new index specifically for Akamai security events. Isolating WAF data in its own index makes searching faster, retention management easier, and access control clearer.
WHERESplunk Cloud → Settings → Indexes → New Index.
HOWChoose a descriptive name. Set retention per your compliance policy. Leave other settings at defaults unless instructed otherwise.
WHYIf WAF events land in main or a shared index, they become difficult to manage, hard to find, and impossible to set separate retention.
VERIFY| eventcount index=<your_index> — this confirms the index exists (count will be 0 initially).

Record your value: Index name = <your_index> = ________________

Step 7.2 — Choose a Sourcetype

The sourcetype is the label Splunk uses to determine how to parse the data. You set this at the HEC token level. Choose a descriptive name that conveys the vendor and data type. The name itself is arbitrary — what matters is that it matches any parsing configuration (TA stanza) on the search head.

If you plan to install a vendor TA that expects a specific sourcetype, discover what it expects first (see Section 10) and use that. If you are not using a TA, choose any descriptive name.

Record your value: Sourcetype = <your_sourcetype> = ________________

Step 7.3 — Create the HEC Token

AspectDetail
WHATA HEC token is an authentication key that the collector includes in every POST request to prove it is authorized to send data to this Splunk Cloud instance.
WHERESplunk Cloud → Settings → Data Inputs → HTTP Event Collector → New Token.
HOWName: descriptive (e.g., "Akamai WAF Collector"). Source type: set to <your_sourcetype>. Allowed indexes: select <your_index>. Default index: <your_index>. Click Submit. Record the generated token value.
WHYThe token controls what the collector can write to. By restricting it to a single index and sourcetype, you prevent accidental data landing in wrong locations.
VERIFYThe token appears in the HEC list with status "Enabled".

Step 7.4 — Record the HEC Endpoint URL

Your Splunk Cloud HEC endpoint URL follows this pattern:

https://http-inputs-<your-stack>.splunkcloud.com:443/services/collector

Check your Splunk Cloud admin panel for the exact URL. Record it — the collector needs this.

Step 7.5 — Test HEC Independently

Before connecting the collector, verify HEC works by sending a test event from the collector machine:

curl -k "https://<HEC_ENDPOINT>/services/collector/event" \
  -H "Authorization: Splunk <HEC_TOKEN>" \
  -d '{"event":"HEC test from collector host","sourcetype":"<your_sourcetype>","index":"<your_index>"}'

Expected response: {"text":"Success","code":0}

Verify in Splunk:

index=<your_index> "HEC test" earliest=-5m

If you see the test event, HEC is working. If not, check: token enabled? Correct URL? Firewall allows HTTPS to Cloud? Index name spelled correctly?

Payload Format

The collector should POST each Akamai event to HEC as a JSON envelope:

{
  "index": "<your_index>",
  "sourcetype": "<your_sourcetype>",
  "event": { ... the Akamai security event JSON ... }
}

Timestamp Handling

Akamai events include an epoch timestamp. The collector should extract it and pass it as the time field in the HEC payload. If omitted, Splunk uses the time it received the event (index time), which is always later than the actual event time and creates lag in your data.

Start the Collector

Start the collector and monitor its logs for the first 5–10 minutes. Look for:

✅ Good signsSuccessful API calls, events returned, successful HEC POSTs, offset advancing.
❌ Bad signsHTTP 401/403 from Akamai (credentials issue — back to Step 4.4). HTTP 403 from HEC (token issue — back to Step 7.3). Empty responses (SIEM not enabled — back to Step 4.1). Timeouts (network issue — back to Step 4.6).

Where Parsing Happens in Splunk Cloud

In Splunk Cloud, you cannot configure parsing on the indexers. You have three possible parsing locations:

LocationWhat HappensWho Controls It
Collector (before Splunk)Your collector code transforms the Akamai JSON — flattening nested objects, decoding base64, renaming fields — before POSTing to HEC.You. Full control.

Section 11 — CIM & ES Readiness (Verify, Do Not Assume)

What Is CIM and Why Does ES Need It?

The Common Information Model (CIM) is a set of standard field names that Splunk ES uses across all data sources. Without CIM mapping, ES cannot find your events — its dashboards, correlation searches, and threat intelligence all query CIM field names, not vendor-specific ones.

For example, the attacker's IP address might be stored as attackData.clientIP in the raw Akamai event. ES does not know that field name. ES looks for src. CIM mapping creates the bridge: attackData.clientIP → src.

CIM mapping does NOT happen automatically. It requires either a TA that defines FIELDALIAS/EVAL rules for your sourcetype, or manual configuration.

Step 11.1 — Check If CIM Fields Exist

index=<your_index> sourcetype=<your_sourcetype> earliest=-1h
| head 50
| eval has_src=if(isnotnull(src),1,0), has_dest=if(isnotnull(dest),1,0),
       has_action=if(isnotnull(action),1,0), has_http_method=if(isnotnull(http_method),1,0),
       has_url=if(isnotnull(url),1,0), has_status=if(isnotnull(status),1,0),
       has_vendor=if(isnotnull(vendor_product),1,0), has_app=if(isnotnull(app),1,0)
| stats avg(has_src) AS src, avg(has_dest) AS dest, avg(has_action) AS action,
        avg(has_http_method) AS http_method, avg(has_url) AS url,
        avg(has_status) AS status, avg(has_vendor) AS vendor_product, avg(has_app) AS app
| foreach * [eval <<FIELD>>=round(<<FIELD>>*100,0)."%"]

Pass: src and action near 100%. http_method, url, dest > 80% for web-type events.

Fail: If all CIM fields are at 0%, the TA is either not installed, not mapping your sourcetype, or missing.
