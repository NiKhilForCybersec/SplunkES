🔴 Important: How Akamai Logs Are Actually Collected in Splunk Cloud

Splunk Cloud does NOT poll the Akamai API. Splunk Cloud does NOT store Akamai API credentials. Splunk Cloud is a destination — it receives events via HEC. It does not reach out to Akamai.

Why a collector is required: Akamai does not push security events anywhere. Events are stored temporarily in Akamai's Security Events Collector (ASEC) and exposed via a REST API. A collector process must actively poll that API on a schedule to retrieve events.

Why Splunk Cloud does not run it: Splunk Cloud is a managed SaaS platform. You have no OS access, no ability to install arbitrary processes, and no ability to store third-party API secrets on Splunk infrastructure. The polling process must execute on infrastructure you control.

What Akamai provides: The SIEM Integration API (the data endpoint) and the Akamai SIEM connector software (an official collector that runs on a Linux VM or container). Akamai publishes this connector specifically for pulling events from their API and forwarding them to SIEMs.

What we operate: We deploy, configure, and maintain the Akamai SIEM connector on customer-managed infrastructure (Linux VM, Docker container, or equivalent). This connector holds the EdgeGrid credentials (client_token, client_secret, access_token, hostname) and posts events to Splunk Cloud HEC over HTTPS.

Where credentials live: Akamai EdgeGrid API credentials live only on the collector host — never in Splunk Cloud. The HEC token lives in Splunk Cloud (Settings → Data Inputs → HTTP Event Collector). These are two separate credential sets with two separate owners.

Where failures must be monitored: Collection failures happen on the collector — not inside Splunk. If events stop arriving, check the collector host first: process health, credential expiry, network connectivity to Akamai, disk space for offset storage. Splunk Cloud has no visibility into why the collector stopped posting.

What the Akamai Splunk Add-on does: The add-on (Splunkbase App ID 4310) is installed on the Splunk Cloud search head for parsing and CIM mapping only. It provides field extraction rules, FIELDALIAS definitions, eventtypes, and tags that make Akamai events compatible with ES data models. It does NOT perform collection in this architecture.

Section 1 — What Akamai WAF Logs Actually Are

No Splunk terms in this section. No APIs. Just the fundamentals.

What Is Akamai?

Akamai Technologies operates one of the world's largest content delivery networks (CDN). When a company like a large retail enterprise puts its website and applications behind Akamai, all customer traffic flows through Akamai's global edge servers before reaching the company's own servers. This means Akamai sits between the internet and the company — it sees every request.

What Is Akamai WAF?

Akamai offers a Web Application Firewall (WAF) as part of its edge security products. The WAF inspects every HTTP request passing through the edge and decides whether the request is legitimate traffic or an attack. It applies security rules to detect threats like SQL injection, cross-site scripting (XSS), command injection, path traversal, and other web application attacks defined by standards like the OWASP Top 10.

When the WAF detects something suspicious, it takes an action — it might block the request, allow it with a warning, rate-limit the source, or trigger a captcha challenge. Every one of these decisions generates a security event.

What Is a "WAF Security Event"?

A security event is a record of a decision the WAF made about a specific HTTP request. Each event contains:

InformationWhat It Tells You
Who made the requestSource IP address, geographic location (country, city), ASN (network owner).
What the request looked likeHTTP method (GET/POST), URL path, query parameters, user-agent, referrer, request headers.
Where it was goingTarget hostname, destination port.
What rules triggeredWhich security rules matched (rule IDs, rule messages describing the threat type), what the attack payload looked like.
What action was takenAlert (logged only), deny (blocked), slow (rate-limited), or other configured actions.
Additional contextBot scores (if Bot Manager is enabled), client reputation scores, the Akamai configuration that processed the request.

What Akamai Security Products Generate These Events?

The security events do not come from just one product — several Akamai products feed into the same event stream:

ProductWhat It Does
App & API ProtectorCurrent-generation WAF. Inspects HTTP traffic for application-layer attacks.
Kona Site DefenderPrevious-generation WAF. Same purpose, older product. Still widely deployed.
Web Application ProtectorSimplified WAF for smaller sites. Generates the same event format.
Bot ManagerDetects and classifies bots. Adds bot score and classification to events.
Client ReputationScores source IPs based on historical behavior across Akamai's network.
Account ProtectorDetects account takeover attempts on login pages.

All of these products write to the same security event stream. When you collect Akamai security events, you get events from whichever products are enabled on the client's Akamai configuration.

Why Do Enterprises Send These Logs to a SIEM?

Akamai's own dashboard shows security events, but it is not a detection and response platform. Enterprises send these logs to a SIEM (like Splunk) because they need to:

Correlate with other sourcesA blocked WAF request from IP 1.2.3.4 is interesting. That same IP also failing VPN logins and scanning internal ports is a campaign. The SIEM connects these.
Detect patterns over timeCredential stuffing attacks trickle in slowly — 10 requests per minute across 50 IPs. The WAF sees each request individually. The SIEM sees the pattern.
Build automated alertsWhen attack volume from a country spikes 10x in an hour, the SIEM triggers an alert. Akamai's dashboard does not do this.
Feed incident response workflowsInvestigations need searchable, retainable logs. The Akamai Collector stores security event data for only 12 hours. The SIEM retains them for months or years.

Section 2 — How Akamai Exposes WAF Security Events

Akamai Does NOT Push Logs to You

This is the most important thing to understand upfront: Akamai does not send security events anywhere automatically. There is no "enable forwarding to Splunk" toggle. Akamai stores security events temporarily on its platform, and you must actively pull them out.

Where Akamai Stores Security Events

When a security event is generated at the edge, Akamai captures it in the Akamai Security Events Collector (ASEC) — a component that aggregates security events across edge servers and exposes them via the SIEM API. Per Akamai's documentation, the Collector stores security event data for up to 12 hours, enabling you to go back and capture missed events if necessary (source: Akamai SIEM Integration Guide). If your connection is disrupted, you can use time-based mode to replay security events from within the past 12 hours (source: Fetch Security Events API). The documentation does not specify what happens to events beyond this window — treat the 12-hour replay window as the operational constraint that drives your entire collection strategy.

The Akamai SIEM Integration API

The supported way to retrieve security events from the Collector is the SIEM Integration API. This is a REST API with these characteristics:

ProtocolHTTPS REST API (authenticated with Akamai EdgeGrid)
DirectionPull — your code calls Akamai. Akamai does not call you.
Response formatNewline-delimited JSON (NDJSON). One JSON object per line per event. The last line is a ResponseContext object with pagination data.
AuthenticationAkamai OPEN EdgeGrid — requires four credential values: client_token, client_secret, access_token, and hostname.
RetentionThe Collector stores security event data for up to 12 hours, enabling replay of missed events within that window (Akamai Guide). The docs do not state what happens beyond this window.
Max events per request600,000 (default: 10,000, configurable via the limit parameter).
Inherent latency5 seconds — the API intentionally delays delivery by 5 seconds.
Response timeout2 minutes — Akamai's edge stops sending after 2 minutes per request.

What About DataStream 2?

⚠️ DataStream 2 Is NOT Security Events — Do Not Confuse Them

DataStream 2 is a separate Akamai product that delivers CDN performance and delivery metrics — things like edge response times, cache hit ratios, origin health. It includes only rule IDs and actions as metadata, NOT the full attack payloads, rule messages, bot scores, or client reputation data that the SIEM Integration API provides.

If someone on the client team says "we already send Akamai logs to Splunk via DataStream" — those are performance logs, not security events. You still need the SIEM Integration API for WAF detection.

DataStream 2 is a separate onboarding with a different index, sourcetype, and data model. It is out of scope for this page.

Section 11 — CIM & ES Readiness (Verify, Do Not Assume)

What Is CIM and Why Does ES Need It?

The Common Information Model (CIM) is a set of standard field names that Splunk ES uses across all data sources. Without CIM mapping, ES cannot find your events — its dashboards, correlation searches, and threat intelligence all query CIM field names, not vendor-specific ones.

For example, the attacker's IP address might be stored as attackData.clientIP in the raw Akamai event. ES does not know that field name. ES looks for src. CIM mapping creates the bridge: attackData.clientIP → src.

CIM mapping does NOT happen automatically. It requires either a TA that defines FIELDALIAS/EVAL rules for your sourcetype, or manual configuration.

What the Akamai TA Provides (and What It Doesn't)

The Akamai SIEM Integration add-on (Splunkbase App ID 4310) is installed on the Splunk Cloud search head. When installed and the sourcetype matches, it provides:

What the TA ProvidesDetail
JSON field extractionAutomatic extraction of nested Akamai JSON fields — attackData.*, httpMessage.*, geo.*, ruleActions, etc. Driven by props.conf with KV_MODE = json or equivalent.
CIM field aliasesVendor-provided FIELDALIAS definitions that map Akamai field names to CIM standard names. For example: attackData.clientIP → src. These are defined in the TA's props.conf.
Eventtypes and tagsEventtype definitions (e.g., akamai_siem_attack) and associated tags (e.g., web, attack) that place events into ES data models like Web.
Lookup definitionsMay include lookup tables for Akamai-specific value normalization (e.g., action code mapping).

The TA provides vendor-documented CIM mappings. It does NOT guarantee that every CIM field ES needs is fully populated for your specific security configuration. You MUST validate the following — do not assume the TA handles everything:

Step 11.4 — When and How to Add Manual CIM Mappings

🚨 Never Edit the Vendor TA

Do NOT modify the Akamai add-on's (App ID 4310) props.conf or transforms.conf directly. Vendor TA updates will overwrite your changes. Instead, create a separate custom app that layers additional CIM mappings on top of the TA.

When is manual mapping needed? Manual CIM mapping is normal — it is not an error or a workaround. It is needed when:

1The TA does not map a CIM field that ES requires (e.g., vendor_product, app)
2A vendor field name changed between Akamai product versions but the TA has not been updated
3You need to normalize a vendor-specific value to a CIM-standard value (e.g., Akamai deny → CIM blocked)
4An additional CIM field is needed for a custom correlation search
