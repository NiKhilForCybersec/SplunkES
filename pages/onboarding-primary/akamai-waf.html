📊 Phase 1 — Log Coverage

Akamai WAF Onboarding

🛡️ Source Overview

Akamai Web Application Firewall (WAF / Kona Site Defender) provides security event logs including blocked attacks, rate limiting events, bot detections, and DDoS mitigation activities. This is a critical data source for web application security monitoring in retail environments.

VendorAkamai Technologies
Log TypeSecurity Events (JSON via SIEM Integration)
Delivery MethodSIEM Integration (Push to HEC) or API Polling
Splunk TASplunk Add-on for Akamai (Splunkbase ID: 4186)
CIM Data ModelsWeb, Intrusion Detection
Typical Volume10-500 GB/day depending on traffic and event verbosity
Typical Latency<2 minutes (SIEM Integration) or 5-15 minutes (API polling)

Why Akamai WAF Onboarding Matters

Business Justification

For retail organizations, the web storefront is often the primary revenue channel and the most exposed attack surface. Akamai WAF sits in front of these critical assets and sees every attack attempt before it reaches your infrastructure. Without these logs in Splunk:

  • Blind to attacks that are being blocked. WAF is blocking SQL injection and credential stuffing attacks right now—but without visibility, you can't understand attack patterns, escalate persistent threats, or correlate with other data sources.
  • No early warning for DDoS. Akamai sees volumetric attacks before they impact origin servers. Without this data, you only find out about DDoS when customers start complaining.
  • Missing correlation data. A successful account takeover often follows hundreds of blocked credential stuffing attempts. Without WAF logs, you only see the successful login—missing the full attack chain.
  • Compliance gaps. PCI DSS requires logging and monitoring of all access to cardholder data environments. WAF logs are often part of this compliance evidence.

Security Justification

Akamai WAF logs are essential for detecting:

  • Web Application Attacks: SQL injection, XSS, command injection, path traversal
  • Credential Attacks: Credential stuffing, brute force against login endpoints
  • Bot Activity: Scraping, inventory hoarding, gift card enumeration
  • DDoS Indicators: Volumetric attacks, application-layer floods, rate limiting events
  • API Abuse: Rate limiting violations, unauthorized API access attempts

What Breaks If This Is Not Done Correctly

Prerequisites

🚨 STOP — Verify Contract Before Starting

SIEM Integration is a paid Akamai feature. Many Akamai contracts do NOT include it. Before doing ANY work:

  1. Contact your Akamai account team or check your contract
  2. Confirm "SIEM Integration" or "Security Event Reporting" is included
  3. If not included, adding it can take 2-4 weeks and requires budget approval

Do not waste time configuring Splunk if the feature isn't licensed.

Contract Verification Steps

How to Verify SIEM Integration is Licensed 
METHOD 1: Check Akamai Control Center
1. Log in to control.akamai.com
2. Navigate to ☰ Menu → Security → SIEM Integration
3. If the menu option exists and is accessible, feature is enabled
4. If menu option is missing or grayed out, feature is NOT enabled

METHOD 2: Contact Account Team
1. Email your Akamai account manager
2. Subject: "Confirm SIEM Integration Feature Status"
3. Ask: "Is SIEM Integration / Security Event Reporting enabled for our account?"
4. Request written confirmation

METHOD 3: Check Contract Documents
1. Review your Akamai MSA or SOW
2. Search for "SIEM Integration" or "Security Event Reporting" or "Log Delivery"
3. If not found, it's likely not included

TIMELINE IF NOT ENABLED:
- Contract amendment: 1-2 weeks
- Technical enablement: 1-3 days after contract
- Total: Plan for 2-4 weeks if feature needs to be added

What MUST Already Exist

Hard Requirements — Verify These Before Starting

Volume Estimation Before Enabling

⚠️ License Impact Warning

Akamai WAF can generate 10-500+ GB/day depending on traffic and event verbosity. ALWAYS estimate volume before enabling to avoid license surprises.

Volume Estimation Guide 
ESTIMATION METHODS:

Method 1: Akamai Reporting (Preferred)
1. Akamai Control Center → Security → Security Reports
2. Run report for last 30 days: Total security events
3. Calculate: (Total events / 30) = daily events
4. Estimate: ~2KB per event average
5. Daily volume = (daily events × 2KB) / 1,000,000 = GB/day

Method 2: Ask Akamai Account Team
1. Request: "Estimated SIEM event volume for our security configurations"
2. They can provide historical event counts

Method 3: Start with Sampling
1. Enable SIEM Integration for ONE config only
2. Monitor for 24 hours
3. Extrapolate to all configs

| Traffic Level        | Attacks/Day | Estimated Volume |
|---------------------|-------------|------------------|
| Low (small retail)  | 10K-50K     | 20-100 MB/day    |
| Medium (regional)   | 100K-500K   | 200MB-1GB/day    |
| High (enterprise)   | 1M-10M      | 2-20 GB/day      |
| Very High (peak)    | 10M+        | 20-100+ GB/day   |

What Often Does NOT Exist (Plan For This)

⚠️ Enterprise Reality Check

Based on real deployments, these are commonly missing or incorrect. Budget time to address:

  • SIEM Integration not in contract: Many Akamai contracts don't include SIEM Integration by default. If your stakeholder says "we have Akamai WAF" that doesn't mean SIEM Integration is enabled. Verify with account team—can take 2-4 weeks to add if missing.
  • HEC endpoint not internet-accessible: Splunk Cloud HEC is typically internet-accessible, but on-prem Splunk may be behind a firewall. You may need to work with Network team to allow inbound HTTPS from Akamai IP ranges.
  • Multiple Akamai accounts: Large enterprises often have multiple Akamai accounts (acquired companies, different business units). Each needs separate configuration.
  • Unclear which security configs to enable: Akamai has many WAF "security configurations" (per-property policies). Nobody may know which ones protect production vs. dev environments.
  • API credentials that work: If using API polling, existing credentials may be expired, have wrong permissions, or belong to someone who left the company.

Network Requirements

Direction Source Destination Port Purpose
Inbound (SIEM Integration) Akamai SIEM IPs* Splunk HEC Endpoint 443/TCP Event delivery
Outbound (API Polling) Heavy Forwarder *.luna.akamaiapis.net 443/TCP API data retrieval

Step-by-Step Execution

Step 1: Create Dedicated Index in Splunk

Create a dedicated index for Akamai WAF data. This allows for proper access control, retention management, and search performance optimization.

Splunk Web: Settings → Indexes → New Index 
Index Name: waf_akamai
Home Path: $SPLUNK_DB/waf_akamai/db
Cold Path: $SPLUNK_DB/waf_akamai/colddb
Thawed Path: $SPLUNK_DB/waf_akamai/thaweddb
Max Data Size: auto_high_volume
Frozen Time Period (seconds): 7776000  # 90 days - adjust per retention policy
💡 Index Naming Convention

Use consistent naming like waf_akamai, sec_waf_akamai, or prod_security_akamai. Document your choice in the project wiki so future team members can find the data.

Step 2: Create HEC Token

Create a dedicated HEC token for Akamai. Using a dedicated token allows you to track ingestion volume and troubleshoot independently.

Via Splunk Web

  1. Navigate to Settings → Data Inputs → HTTP Event Collector
  2. Click New Token
  3. Configure as follows:
HEC Token Configuration 
Name: akamai_waf_ingest
Description: Akamai WAF SIEM Integration - Production
Source Type: akamai:siem
Index: waf_akamai
Allowed Indexes: waf_akamai
Enable Indexer Acknowledgement: Yes (recommended for production)
Enable Token: Yes
⚠️ Enable Indexer Acknowledgement

For production deployments, enable indexer acknowledgement. This ensures Akamai receives confirmation that events were successfully indexed. Without this, events could be lost during Splunk issues without any error indication.

Record the HEC Endpoint URL

You'll need this for Akamai configuration:

Splunk Cloud HEC URL Format 
# Splunk Cloud
https://http-inputs-<your-stack>.splunkcloud.com:443/services/collector/event

# Splunk Enterprise (on-prem)
https://<your-hec-endpoint>:8088/services/collector/event

# With Indexer Acknowledgement
https://http-inputs-<your-stack>.splunkcloud.com:443/services/collector/event?channel=<channel-guid>

Step 4: Configure Akamai SIEM Integration

This step requires Akamai Control Center access. Work with your Network/Web Operations team if you don't have access.

4.1: Access SIEM Integration Settings

  1. Log in to Akamai Control Center (https://control.akamai.com)
  2. Navigate to ☰ Menu → Security → SIEM Integration
  3. If you don't see this option, SIEM Integration may not be enabled in your contract—contact Akamai account team

4.2: Create New SIEM Connector

SIEM Connector Configuration 
Connector Name: Splunk-Production-WAF
Connector Type: Splunk (native integration)

Splunk Settings:
  HEC URL: https://http-inputs-<stack>.splunkcloud.com:443/services/collector/event
  HEC Token: <your-hec-token-from-step-2>
  Enable SSL: Yes (always)
  Verify SSL Certificate: Yes (production) / No (testing only)

Event Settings:
  Format: JSON
  Compress Events: Yes (reduces bandwidth, Splunk handles decompression)

Security Configurations to Include:
  [Select ALL production WAF configurations]
  - Example: "www.example.com_WAF"
  - Example: "api.example.com_WAF"
  - Example: "checkout.example.com_WAF"

Event Types to Include:
  ☑ Attack Data (WAF triggers) - REQUIRED
  ☑ Bot Manager Events - Recommended
  ☑ Client Reputation - Recommended
  ☑ Rate Limiting Events - Recommended
  ☑ Slow POST Attacks - Optional

Event Filter:
  Action: All (deny AND alert) - IMPORTANT: Don't filter to deny-only
  
  Reasoning: Alert events show reconnaissance and attacks that weren't 
  blocked. You need both to understand the full attack picture.
🚨 Critical: Select All Security Configurations

The most common misconfiguration is only selecting some security configurations. If you have 10 WAF policies and only enable SIEM Integration for 3, attacks against the other 7 are invisible. Get a complete list of production security configurations and enable all of them.

4.3: Identify All Security Configurations

If you're unsure which security configurations exist, run this in Akamai Control Center:

  1. Navigate to Security → Security Configurations
  2. Export the list of all configurations
  3. Review with Web Operations to confirm which are production
  4. Enable SIEM Integration for ALL production configurations

4.4: Test the Connector

  1. Save the SIEM connector configuration
  2. Akamai provides a "Test Connection" button—use it
  3. If test fails, verify:
    • HEC URL is correct (including /services/collector/event path)
    • HEC token is correct (no extra spaces)
    • HEC endpoint is internet-accessible
    • SSL certificate is valid (if using verify SSL)

Step 6: Verify props.conf Configuration

The Splunk Add-on for Akamai includes default parsing, but verify and customize as needed:

props.conf (Verify/Customize) 
[akamai:siem]
# Timestamp extraction
TIME_FORMAT = %s
TIME_PREFIX = "httpMessage":\s*\{[^}]*"start":\s*"
MAX_TIMESTAMP_LOOKAHEAD = 20
TZ = UTC

# Line breaking (one event per line)
SHOULD_LINEMERGE = false
LINE_BREAKER = ([\r\n]+)
TRUNCATE = 999999

# Field extractions handled by TA
KV_MODE = json

# CIM Field Aliases (verify these exist in TA)
FIELDALIAS-akamai_src = attackData.clientIP AS src
FIELDALIAS-akamai_dest = httpMessage.host AS dest
FIELDALIAS-akamai_url = httpMessage.path AS url
FIELDALIAS-akamai_http_method = httpMessage.method AS http_method
FIELDALIAS-akamai_status = httpMessage.status AS http_response_code
FIELDALIAS-akamai_action = attackData.action AS action
FIELDALIAS-akamai_user_agent = httpMessage.requestHeaders.User-Agent AS http_user_agent

# Calculated fields for CIM compliance
EVAL-vendor = "Akamai"
EVAL-vendor_product = "Kona Site Defender"
EVAL-dvc = "Akamai Edge"

# Severity mapping
EVAL-severity = case(
    'attackData.action'=="deny", "high",
    'attackData.action'=="alert", "medium",
    'attackData.action'=="monitor", "low",
    true(), "informational"
)

Validation & Acceptance

Validation Step 1: Confirm Data Arrival

SPL: Basic Data Validation 
index=waf_akamai sourcetype=akamai:siem earliest=-1h
| stats count BY sourcetype, index
| eval status = if(count > 0, "✓ Data Flowing", "✗ NO DATA")

Expected Result: Count > 0. If zero, check SIEM Integration configuration and HEC token.

Validation Step 2: Check Volume and Consistency

SPL: Volume Over Time 
index=waf_akamai sourcetype=akamai:siem earliest=-24h
| timechart span=1h count AS events
| eval status = case(
    events == 0, "GAP - No Data",
    events < 100, "LOW - Verify expected",
    events > 100000, "HIGH - Check for duplicates",
    true(), "NORMAL"
)

Expected Result: Consistent event flow without gaps. Significant gaps indicate connectivity or configuration issues.

Validation Step 3: Verify All Security Configurations

SPL: Events by Security Configuration 
index=waf_akamai sourcetype=akamai:siem earliest=-24h
| spath output=config_id path=attackData.configId
| stats count BY config_id
| sort - count

Action: Compare this list against your documented production security configurations. Any missing config_ids indicate SIEM Integration wasn't enabled for those policies.

Validation Step 4: Check Event Types

SPL: Event Type Distribution 
index=waf_akamai sourcetype=akamai:siem earliest=-24h
| spath output=event_type path=type
| spath output=action path=attackData.action
| stats count BY event_type, action
| sort - count

Expected Result: Should see both "deny" and "alert" actions. If you only see "deny", the SIEM Integration filter may be misconfigured.

Validation Step 5: Measure Latency

SPL: Ingestion Latency Analysis 
index=waf_akamai sourcetype=akamai:siem earliest=-4h latest=-1h
| eval latency_seconds = _indextime - _time
| where latency_seconds > 0 AND latency_seconds < 86400
| stats 
    count AS events,
    avg(latency_seconds) AS avg_latency,
    perc50(latency_seconds) AS median_latency,
    perc95(latency_seconds) AS p95_latency,
    max(latency_seconds) AS max_latency
| eval avg_latency_min = round(avg_latency/60, 2)
| eval p95_latency_min = round(p95_latency/60, 2)
| eval status = case(
    p95_latency < 120, "✓ EXCELLENT (<2 min)",
    p95_latency < 300, "✓ ACCEPTABLE (<5 min)",
    p95_latency < 900, "⚠️ MARGINAL (5-15 min)",
    true(), "✗ HIGH (>15 min)"
)

Expected Result: P95 latency should be <2 minutes for SIEM Integration, <10 minutes for API polling.

Validation Step 6: Verify Critical Fields

SPL: Field Population Check 
index=waf_akamai sourcetype=akamai:siem earliest=-24h
| head 10000
| eval has_src = if(isnotnull(src) AND src!="", 1, 0)
| eval has_dest = if(isnotnull(dest) AND dest!="", 1, 0)
| eval has_url = if(isnotnull(url) AND url!="", 1, 0)
| eval has_action = if(isnotnull(action) AND action!="", 1, 0)
| eval has_method = if(isnotnull(http_method) AND http_method!="", 1, 0)
| stats 
    count AS total,
    sum(has_src) AS with_src,
    sum(has_dest) AS with_dest,
    sum(has_url) AS with_url,
    sum(has_action) AS with_action,
    sum(has_method) AS with_method
| eval src_pct = round(with_src/total*100,1)."%"
| eval dest_pct = round(with_dest/total*100,1)."%"
| eval url_pct = round(with_url/total*100,1)."%"
| eval action_pct = round(with_action/total*100,1)."%"
| eval method_pct = round(with_method/total*100,1)."%"
| table total, src_pct, dest_pct, url_pct, action_pct, method_pct

Expected Result: All critical fields should be >95% populated. Low percentages indicate field extraction issues.

Validation Step 7: CIM Compliance

SPL: Verify Web Data Model Mapping 
| tstats count FROM datamodel=Web WHERE earliest=-24h BY sourcetype
| search sourcetype="akamai:siem"
| eval cim_status = if(count > 0, "✓ Mapped to Web Data Model", "✗ NOT MAPPED")

Expected Result: Events should appear in the Web data model. If not, check that the TA's tags.conf is properly configured.

Acceptance Criteria Checklist

Akamai WAF Onboarding — Exit Criteria

Failure Modes & Fixes

Failure Mode 1: Zero Events After Configuration

Symptom

SIEM Integration configured, but index=waf_akamai returns zero events.

Why It Happens:

  • HEC URL is incorrect (missing /services/collector/event path)
  • HEC token is incorrect or disabled
  • Firewall blocking inbound HTTPS from Akamai
  • SIEM Integration connector not activated
  • No security events occurring (quiet period)

How to Diagnose:

SPL: Check HEC Input Health 
index=_internal sourcetype=splunkd component=HttpInputDataHandler
| stats count BY status, source
| sort - count

Resolution Steps:

  1. Verify HEC endpoint is accessible: curl -k https://<hec-url>/services/collector/health
  2. Test HEC token manually: curl -k https://<hec-url>/services/collector/event -H "Authorization: Splunk <token>" -d '{"event":"test"}'
  3. Check Akamai SIEM connector status in Control Center
  4. Request Akamai support to verify event delivery attempts

When NOT to Fix: If the issue is that there genuinely are no WAF events (no attacks occurring), verify by checking Akamai's own reporting dashboard. Some environments have very low attack volumes.

Failure Mode 2: Events Arriving But Missing Fields

Symptom

Events exist but src, dest, or action fields are empty.

Why It Happens:

  • Splunk Add-on for Akamai not installed on indexers
  • props.conf field aliases not applied
  • Different event format than expected (API version change)

How to Diagnose:

SPL: Check Raw Event Structure 
index=waf_akamai sourcetype=akamai:siem earliest=-1h
| head 1
| table _raw

Resolution Steps:

  1. Verify TA is installed on all indexers (not just search heads)
  2. Check that the sourcetype exactly matches what the TA expects (akamai:siem)
  3. If raw data structure differs from TA expectations, create custom props.conf extractions

Failure Mode 3: Some Security Configurations Missing

Symptom

Events arrive but only from some WAF policies, not all production configurations.

Why It Happens:

  • Not all security configurations selected in SIEM Integration connector
  • Multiple Akamai accounts with separate configurations
  • New configurations added after SIEM Integration setup

How to Diagnose:

SPL: Compare Config IDs 
index=waf_akamai sourcetype=akamai:siem earliest=-7d
| spath output=config_id path=attackData.configId
| stats dc(config_id) AS configs_sending_data, values(config_id) AS config_list

Resolution Steps:

  1. Get complete list of production security configurations from Web Operations
  2. Compare against config IDs in Splunk data
  3. Update SIEM Integration connector to include missing configurations
  4. Set calendar reminder to review when new WAF policies are created

Failure Mode 4: High Latency (>15 Minutes)

Symptom

Events arrive but with significant delay between event time and index time.

Why It Happens:

  • Using API polling instead of SIEM Integration push
  • API polling interval set too high
  • HEC endpoint experiencing backlog
  • Network latency between Akamai and Splunk

How to Diagnose:

SPL: Latency Distribution 
index=waf_akamai sourcetype=akamai:siem earliest=-24h
| eval latency_min = round((_indextime - _time)/60, 1)
| stats count BY latency_min
| where latency_min > 0
| sort latency_min

Resolution Steps:

  1. If using API polling, consider migrating to SIEM Integration push
  2. Reduce API polling interval (minimum 60 seconds recommended)
  3. Check HEC ingestion queue health
  4. Contact Akamai support if SIEM Integration push shows high latency

When NOT to Fix: If you're using API polling and can't switch to push, some latency is inherent. Document the expected latency (polling interval + processing time) and adjust detection scheduling accordingly.

Failure Mode 5: Events Suddenly Stop

Symptom

Data was flowing, but now shows a gap starting at a specific time.

Why It Happens:

  • HEC token was disabled or deleted
  • API credentials expired (if using polling)
  • SIEM Integration connector was modified
  • Network change blocked connectivity
  • Splunk maintenance caused HEC unavailability

How to Diagnose:

SPL: Find When Data Stopped 
index=waf_akamai sourcetype=akamai:siem earliest=-7d
| timechart span=1h count
| where count = 0

Resolution Steps:

  1. Check HEC token is still enabled
  2. Check Akamai SIEM connector status
  3. Check for API credential expiration
  4. Review change logs for network or Splunk changes at the time data stopped

Failure Mode 6: Duplicate Events

Symptom

Same events appearing multiple times, inflating event counts.

Why It Happens:

  • Both SIEM Integration push AND API polling enabled simultaneously
  • Multiple SIEM connectors pointing to same Splunk endpoint
  • HEC acknowledgement failures causing retries

How to Diagnose:

SPL: Check for Duplicates 
index=waf_akamai sourcetype=akamai:siem earliest=-1h
| spath output=event_id path=attackData.ruleActions{}.ruleId
| stats count BY _time, src, dest, event_id
| where count > 1
| stats sum(count) AS duplicate_events

Resolution Steps:

  1. Verify only ONE collection method is active (push OR pull, not both)
  2. Check for multiple SIEM connectors in Akamai Control Center
  3. If duplicates persist, implement deduplication in Splunk (not ideal but workable)

Rollback & Safety

How to Disable Akamai SIEM Integration

If data volume is too high, events are causing issues, or you need to troubleshoot, follow these steps to safely disable:

Rollback Procedure: Disable SIEM Integration 
OPTION 1: Disable in Akamai (Preferred - Stops at Source)
1. Log in to Akamai Control Center
2. Navigate to ☰ Menu → Security → SIEM Integration
3. Find your SIEM connector (e.g., "Splunk-Production-WAF")
4. Click Edit → Set Status to "Disabled"
5. Save changes
6. Events stop within 5-10 minutes

OPTION 2: Disable HEC Token in Splunk (Emergency)
1. Splunk Web → Settings → Data Inputs → HTTP Event Collector
2. Find token (e.g., "akamai_waf_ingest")
3. Click "Disable"
4. Events are rejected but Akamai may continue sending (generates errors on Akamai side)

OPTION 3: Disable Specific Security Configs
1. In SIEM Integration settings, edit connector
2. Uncheck specific security configurations
3. Useful for reducing volume while maintaining some coverage

VERIFICATION AFTER ROLLBACK:
| tstats count WHERE index=waf_akamai earliest=-15m
| eval status = if(count > 0, "Still receiving events - check disable timing", "Events stopped")

COMMUNICATION:
- Notify SOC: "Akamai WAF logs temporarily disabled for [reason]. ETA to restore: [time]"
- Document in incident/change ticket

HEC Token Rotation Procedure

⚠️ HEC Token Security

HEC tokens are credentials. If compromised, an attacker could inject false events or exhaust your license. Rotate tokens periodically (annually minimum) and immediately if suspected compromise.

HEC Token Rotation Procedure (Zero Downtime) 
STEP 1: Create New Token
1. Splunk Web → Settings → Data Inputs → HTTP Event Collector → New Token
2. Name: akamai_waf_ingest_v2 (or increment version)
3. Configure identically to existing token (same index, sourcetype)
4. Enable the new token
5. Record: New token value, creation date, expiration reminder

STEP 2: Update Akamai
1. Akamai Control Center → Security → SIEM Integration
2. Edit existing connector
3. Replace HEC token value with new token
4. Save changes

STEP 3: Verify New Token Working
1. Wait 5-10 minutes for Akamai to start using new token
2. Run: index=waf_akamai earliest=-15m | stats count
3. Confirm events arriving

STEP 4: Disable Old Token
1. Splunk Web → HTTP Event Collector → [old token] → Disable
2. Do NOT delete immediately (keep for audit trail)

STEP 5: Document
- Update password manager/secrets vault with new token
- Set calendar reminder for next rotation (12 months)
- Document rotation in change management system
