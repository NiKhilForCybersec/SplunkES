☁️ Splunk Cloud Safety Box — Syslog via Heavy Forwarder

✅ Allowed in Cloud: All HF configuration steps on this page apply — the HF is YOUR infrastructure. Creating indexes and HEC tokens via Splunk Cloud UI. Installing parsing TAs on Cloud search heads via SSAI.

⚠️ Restricted in Cloud: You cannot deploy a Heavy Forwarder INSIDE Splunk Cloud. All HF instances must be customer-managed. You cannot SSH to Splunk Cloud search heads or indexers. You cannot push index-time configs to Cloud indexers directly — file a support ticket.

🔄 Cloud-Safe Alternative: All $SPLUNK_HOME paths, btool commands, splunk restart commands, and inputs.conf/outputs.conf/props.conf edits on this page apply to YOUR Heavy Forwarder, not to Splunk Cloud. The outputs.conf must use the Splunk Cloud credentials package.

📋 Verify: Download the Splunk Cloud credentials package (universal forwarder credentials) from the Splunk Cloud admin panel. This contains the certificates needed for your HF to connect.

Splunk Cloud Execution Notes — Syslog Collection

Where does the HF run?In your network — on-prem or in your cloud VPC. You have full OS/filesystem/CLI access to the HF. Splunk Cloud does not provide or manage Heavy Forwarders.
Are modular inputs involved?No — syslog collection uses native TCP/UDP inputs on the HF, not modular inputs. No IDM dependency.
Where does parsing happen?On the HF — props.conf and transforms.conf on the HF handle index-time parsing (timestamp, linebreaking, sourcetype assignment) before events are forwarded to Cloud. On the Cloud SH — search-time field extraction and CIM mapping happen via the TA installed on the search head.
Who owns credentials?You manage the HF outputs.conf with the Splunk Cloud credentials package. Splunk provides the certificates; you deploy them on your HF.
Who has restart authority?You restart your HF at will. You cannot restart Splunk Cloud services.
🚨 CRITICAL: Heavy Forwarder Changes Impact ALL Syslog Sources

Heavy Forwarders are shared infrastructure. A misconfiguration can cause data loss for ALL sources routing through that HF. Follow these rules:

  • NEVER make HF changes during business hours without change approval
  • ALWAYS test inputs.conf changes with btool before restart
  • ALWAYS have rollback plan documented before any HF change
  • NEVER restart both HF nodes simultaneously — stagger by 15+ minutes
⚠️ Retail Business Timing — HF Changes

Heavy Forwarder maintenance windows must account for:

  • Firewall log criticality: Never during active incident response
  • PCI compliance: Log gaps may trigger compliance violations
  • Change windows: Tue-Thu 2-6 AM ET only (avoid month-end close)

Overview

Syslog remains the most common method for collecting logs from network infrastructure devices, firewalls, load balancers, and legacy systems. This guide covers syslog collection via Splunk Heavy Forwarder (HF) for forwarding to Splunk Cloud.

Architecture Pattern

Syslog → Heavy Forwarder (on-prem) → Splunk Cloud. The HF acts as both syslog receiver and forwarder, handling parsing, timestamping, and secure transmission to cloud.

Heavy Forwarder Configuration

Step 1: Install Splunk Heavy Forwarder

bash 
# Download and install (RHEL/CentOS)
sudo rpm -ivh splunk-9.x.x-linux-2.6-x86_64.rpm

# Or for Ubuntu/Debian
sudo dpkg -i splunk-9.x.x-linux-2.6-amd64.deb

# Enable boot start and accept license
sudo /opt/splunk/bin/splunk enable boot-start --accept-license --answer-yes

# Start Splunk
sudo /opt/splunk/bin/splunk start

Step 2: Configure Syslog Inputs

Create inputs.conf for syslog reception. Use TCP for reliable delivery where supported, UDP for high-volume/legacy sources.

$SPLUNK_HOME/etc/system/local/inputs.conf 
# ========================================
# Syslog Inputs Configuration
# Heavy Forwarder - Syslog Collection
# ========================================

# TCP Syslog - Primary (Reliable)
[tcp://1514]
connection_host = dns
sourcetype = syslog
index = network

# UDP Syslog - Fallback/Legacy
[udp://514]
connection_host = dns
sourcetype = syslog
index = network

# Device-Specific Ports (Recommended)
# Palo Alto Firewalls
[tcp://5514]
connection_host = dns
sourcetype = pan:traffic
index = pan_logs

[tcp://5515]
connection_host = dns
sourcetype = pan:threat
index = pan_logs

# Cisco ASA
[tcp://6514]
connection_host = dns
sourcetype = cisco:asa
index = cisco_logs

# F5 BIG-IP
[tcp://7514]
connection_host = dns
sourcetype = f5:bigip:syslog
index = f5_logs

# Linux Servers (rsyslog)
[tcp://8514]
connection_host = dns
sourcetype = syslog
index = os_linux
Port Separation Best Practice

Use dedicated ports per device type/vendor. This enables proper sourcetype assignment at ingestion time and prevents parsing errors from mixed log formats on shared ports.

Step 3: Configure Outputs to Splunk Cloud

Use the outputs.conf provided by Splunk Cloud admin. This contains the certificate required for secure communication.

$SPLUNK_HOME/etc/system/local/outputs.conf 
# ========================================
# Outputs Configuration - Splunk Cloud
# NOTE: Replace with actual values from Splunk Cloud admin
# ========================================

[tcpout]
defaultGroup = splunkcloud

[tcpout:splunkcloud]
server = inputs1.your-stack.splunkcloud.com:9997, inputs2.your-stack.splunkcloud.com:9997
compressed = true
sslCertPath = $SPLUNK_HOME/etc/auth/your-stack-cert.pem
sslRootCAPath = $SPLUNK_HOME/etc/auth/your-stack-cacert.pem
sslPassword = ********
sslVerifyServerCert = true
useClientSSLCompression = true

# Indexer acknowledgment (recommended for reliability)
useACK = true

Step 4: Configure Props and Transforms

Define parsing rules for timestamp extraction and field parsing.

$SPLUNK_HOME/etc/system/local/props.conf 
# ========================================
# Props Configuration - Syslog Parsing
# ========================================

[syslog]
TIME_FORMAT = %b %d %H:%M:%S
MAX_TIMESTAMP_LOOKAHEAD = 32
SHOULD_LINEMERGE = false
LINE_BREAKER = ([\r\n]+)
TRUNCATE = 10000

# Palo Alto Traffic
[pan:traffic]
TIME_FORMAT = %Y/%m/%d %H:%M:%S
SHOULD_LINEMERGE = false
LINE_BREAKER = ([\r\n]+)
TRUNCATE = 65535
KV_MODE = none
TRANSFORMS-pan_traffic = pan_traffic_fields

# Cisco ASA
[cisco:asa]
TIME_FORMAT = %b %d %Y %H:%M:%S
MAX_TIMESTAMP_LOOKAHEAD = 32
SHOULD_LINEMERGE = false
LINE_BREAKER = ([\r\n]+)

Splunk Cloud Validation SPL

SPL 
| Syslog Data Arrival Check
index IN (network, pan_logs, cisco_logs, f5_logs, os_linux) sourcetype=syslog OR sourcetype=pan:* OR sourcetype=cisco:* OR sourcetype=f5:*
| stats count by index, sourcetype, host
| sort - count

| Event Latency Check
index=network sourcetype=syslog
| eval latency = _indextime - _time
| stats avg(latency) as avg_latency, max(latency) as max_latency, p95(latency) as p95_latency by host
| where avg_latency > 60
| sort - avg_latency

| Timestamp Quality Check
index=network sourcetype=syslog
| eval hour_diff = abs(round((_time - now())/3600))
| where hour_diff > 24
| stats count by host, sourcetype
| sort - count

Troubleshooting

  1. Verify network connectivity: telnet <source_ip> <port> from source
  2. Check firewall rules between source and HF
  3. Verify Splunk is listening: netstat -tulpn | grep <port>
  4. Check inputs.conf syntax: /opt/splunk/bin/splunk btool inputs list --debug
  5. Review splunkd.log for errors
  1. Check HF → Cloud connectivity: telnet inputs1.your-stack.splunkcloud.com 9997
  2. Verify certificate validity and placement
  3. Check outputs.conf configuration
  4. Review metrics.log for forwarding errors
  5. Check queue blockage: splunk show queue-usage
  1. Verify TIME_FORMAT in props.conf matches actual log format
  2. Check timezone settings on source devices
  3. Use | eval _raw_time = strftime(_time, "%Y-%m-%d %H:%M:%S") to debug
  4. Consider TZ= setting in props.conf if source timezone differs
  1. Check HF resource utilization (CPU, memory, disk I/O)
  2. Review queue sizes in metrics.log
  3. Consider adding HF capacity or load balancing
  4. Check network bandwidth between HF and Splunk Cloud
  5. Enable compression if not already: compressed = true

Acceptance Criteria

Phase 1 Gate Requirements

Rollback & Safety

Emergency: Disable Syslog Input on HF

Emergency Procedure 
SCENARIO: Syslog input causing issues (volume spike, parsing errors, HF overload)

OPTION 1: Disable Specific Input (Preferred)
─────────────────────────────────────────────
1. SSH to Heavy Forwarder
2. Identify problematic input in inputs.conf
3. Edit: $SPLUNK_HOME/etc/apps/[app]/local/inputs.conf
4. Add: disabled = 1 to the stanza
5. Reload: $SPLUNK_HOME/bin/splunk reload inputs

OPTION 2: Block at Firewall (Immediate)
───────────────────────────────────────
If HF is overwhelmed and unresponsive:
1. Block source IP at network firewall
2. This stops data immediately but may alert source team
3. Coordinate with network team

OPTION 3: Stop Splunk Process (Last Resort)
───────────────────────────────────────────
⚠️ WARNING: This stops ALL data collection on this HF
1. SSH to HF: $SPLUNK_HOME/bin/splunk stop
2. Data will queue at sources (if TCP) or be lost (if UDP)
3. Fix issue, then restart: $SPLUNK_HOME/bin/splunk start

COMMUNICATION:
- Notify SOC immediately (log gap occurring)
- Notify network/security teams
- Document start/end time of gap for compliance

Safe HF Configuration Change Procedure

Safe Change Procedure 
BEFORE ANY HF CHANGE:

STEP 1: Backup Current Configuration
─────────────────────────────────────
tar -czvf /backup/splunk_etc_$(date +%Y%m%d_%H%M).tar.gz $SPLUNK_HOME/etc/

STEP 2: Validate New Configuration (BEFORE Applying)
─────────────────────────────────────────────────────
# Check inputs.conf syntax
$SPLUNK_HOME/bin/splunk btool inputs list --debug | grep -i "error\|warning"

# Check props.conf syntax  
$SPLUNK_HOME/bin/splunk btool props list --debug | grep -i "error\|warning"

# Check outputs.conf syntax
$SPLUNK_HOME/bin/splunk btool outputs list --debug | grep -i "error\|warning"

STEP 3: Apply Change During Window
──────────────────────────────────
1. Make configuration change
2. Reload (if supported): $SPLUNK_HOME/bin/splunk reload inputs
3. Or restart: $SPLUNK_HOME/bin/splunk restart

STEP 4: Validate Immediately After
──────────────────────────────────
# Check listening ports
netstat -tulpn | grep splunkd

# Check for errors
tail -100 $SPLUNK_HOME/var/log/splunk/splunkd.log | grep -i "error\|warning"

# Check queue health
$SPLUNK_HOME/bin/splunk show queue-usage

# Verify data in Splunk Cloud (wait 2-5 minutes)
index=[target_index] earliest=-10m | stats count by sourcetype

HF Failover Testing Procedure

HA Validation 
TEST HF HIGH AVAILABILITY (Before Go-Live)

PREREQUISITE: Schedule during maintenance window with SOC awareness

STEP 1: Baseline Data Flow
──────────────────────────
# Record current event rate per HF
index=[target_index] earliest=-1h | stats count by splunk_server

STEP 2: Fail Primary HF
───────────────────────
1. Stop Splunk on HF1: $SPLUNK_HOME/bin/splunk stop
2. Wait 2 minutes for failover

STEP 3: Verify Failover Success
───────────────────────────────
# Data should now flow through HF2
index=[target_index] earliest=-5m | stats count by splunk_server
# Expect: HF2 count should match pre-failover total rate

STEP 4: Restore Primary
───────────────────────
1. Start Splunk on HF1: $SPLUNK_HOME/bin/splunk start
2. Verify both HFs receiving data again

STEP 5: Document Results
────────────────────────
- Failover time: _____ seconds
- Data loss during failover: _____ events (should be 0 for TCP)
- Any issues observed: _____

ACCEPTANCE: Failover completes in <60 seconds with zero data loss for TCP sources

Volume Explosion Response

Emergency: Volume Spike 
SCENARIO: Syslog source suddenly sending 10x+ normal volume

DIAGNOSIS:
1. Identify source: index=[target_index] earliest=-1h | stats count by host | sort - count | head 10
2. Check if legitimate (config change, attack, audit enabled)

IF LEGITIMATE BUT UNEXPECTED:
1. Contact source owner to understand change
2. May need to add HF capacity
3. May need to filter at source

IF ILLEGITIMATE (Misconfiguration/Loop):
1. Disable input immediately (see Emergency Disable above)
2. Contact source owner
3. Do not re-enable until root cause fixed

IF LICENSE IMPACT:
1. Disable input if approaching license limit
2. Escalate to Splunk admin and license owner
3. May need emergency license increase
