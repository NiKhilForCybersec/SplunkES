Phase 1: Log Coverage

Endpoint Telemetry

Windows Event Logs, EDR telemetry, and endpoint data collection via Universal Forwarder

📋 Page Status: HARDENED

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This page includes explicit validation criteria, volume management guidance, and enterprise deployment considerations.

🚨 CRITICAL: Endpoint Data Can Explode License Usage

Unfiltered endpoint logs from 10,000+ endpoints can consume 100+ GB/day. Before enabling endpoint collection:

  • ALWAYS calculate expected volume before onboarding (use estimates below)
  • NEVER enable "collect all events" without volume filtering
  • ALWAYS start with a pilot group (50-100 endpoints) before full rollout
  • VERIFY license headroom with Splunk admin before large-scale deployment
⚠️ Retail Business Timing — UF Deployment

Universal Forwarder mass deployment impacts endpoints and may require restarts:

  • POS systems: Deploy during overnight maintenance windows only
  • Store systems: Never during store hours or promotions
  • Domain Controllers: Stagger deployment, never all DCs at once
  • Deployment Server changes: Test on pilot group first

Overview

Endpoint telemetry is foundational for security monitoring—it provides visibility into process execution, authentication events, file access, and registry changes that are critical for threat detection. This guide covers collection of Windows Event Logs and EDR telemetry via Splunk Universal Forwarder (UF).

Architecture Pattern

Endpoint → Universal Forwarder → Deployment Server (config management) → Splunk Cloud. For EDR integrations, data may flow via vendor API or syslog depending on the product.

Prerequisites

Windows Event Log Configuration

Critical Event IDs for Security Monitoring

Event ID Description Detection Use Case
4624 Successful Logon Authentication tracking, lateral movement
4625 Failed Logon Brute force detection
4648 Explicit Credential Logon Credential theft detection
4672 Special Privileges Assigned Privilege escalation
4688 Process Creation Command execution (requires audit policy)
4697 Service Installed Persistence detection
4698/4702 Scheduled Task Created/Updated Persistence detection
4720 User Account Created Rogue account detection
4732 Member Added to Security-Enabled Group Privilege escalation
7045 Service Installed (System Log) Persistence detection
Audit Policy Requirement

Event ID 4688 (Process Creation) requires "Audit Process Creation" policy enabled. For command-line logging, enable "Include command line in process creation events" in Group Policy.

Server Classes Configuration

serverclass.conf 
# ========================================
# Server Classes for Endpoint Deployment
# $SPLUNK_HOME/etc/system/local/serverclass.conf
# ========================================

# All Windows Endpoints - Base config
[serverClass:Windows_All]
whitelist.0 = *
machineTypesFilter = windows-x64

[serverClass:Windows_All:app:TA_outputs_cloud]
restartSplunkd = true

[serverClass:Windows_All:app:TA_windows_inputs]
restartSplunkd = true

# Workstations - Standard collection
[serverClass:Windows_Workstations]
whitelist.0 = WS*
whitelist.1 = DESKTOP*
machineTypesFilter = windows-x64

[serverClass:Windows_Workstations:app:TA_sysmon_inputs]
restartSplunkd = true

# Servers - Enhanced collection
[serverClass:Windows_Servers]
whitelist.0 = SRV*
whitelist.1 = SVR*
machineTypesFilter = windows-x64

[serverClass:Windows_Servers:app:TA_sysmon_inputs]
restartSplunkd = true

# Domain Controllers - Critical assets
[serverClass:Domain_Controllers]
whitelist.0 = DC*
machineTypesFilter = windows-x64

[serverClass:Domain_Controllers:app:TA_windows_dc_inputs]
restartSplunkd = true

EDR Integration Patterns

CrowdStrike Falcon

Integration Method

CrowdStrike data can be collected via the Falcon Data Replicator (FDR) to S3, then ingested via Splunk Add-on for AWS, or via the CrowdStrike Falcon Event Streams API.

Expected Sourcetypes - CrowdStrike

Microsoft Defender for Endpoint

Integration Method

MDE data flows via Microsoft Defender XDR → Azure Event Hub → Splunk Add-on for Microsoft Cloud Services, or via the Microsoft 365 Defender Streaming API.

Validation

SPL - Endpoint Data Validation 
| Coverage Check - Windows Event Logs
index=wineventlog sourcetype=WinEventLog:*
| stats dc(host) as unique_hosts count by sourcetype
| sort - count

| Critical Event IDs Present
index=wineventlog sourcetype=WinEventLog:Security EventCode IN (4624, 4625, 4648, 4672, 4688, 4720, 4732)
| stats count by EventCode
| lookup eventcode_lookup EventCode OUTPUT description
| sort EventCode

| Process Creation with Command Line
index=wineventlog sourcetype=WinEventLog:Security EventCode=4688
| stats count by host
| where count > 0
| stats count as hosts_with_4688

| Sysmon Coverage
index=sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational
| stats dc(host) as unique_hosts count by EventCode
| sort EventCode

| Endpoint Reporting Health
index=wineventlog OR index=sysmon
| stats latest(_time) as last_seen by host
| eval hours_since = round((now() - last_seen)/3600, 1)
| where hours_since > 24
| sort - hours_since
| head 20

Volume Control

Endpoint data can explode license usage. Use whitelist/blacklist in inputs.conf, tune Sysmon config, and consider filtering noisy Event IDs (like 4689 - Process Termination) at the source.

Troubleshooting

  1. Verify deploymentclient.conf points to correct DS
  2. Check network connectivity to DS on TCP 8089
  3. Review serverclass.conf whitelist patterns
  4. Check DS logs: $SPLUNK_HOME/var/log/splunk/splunkd.log
  5. Force phone-home: splunk reload deploy-server
  1. Verify Windows Audit Policy via auditpol /get /category:*
  2. Enable "Audit Process Creation" in Group Policy
  3. Enable command-line logging: Computer Configuration → Administrative Templates → System → Audit Process Creation
  4. Check Security Log size and retention policy
  1. Identify top talkers: index=wineventlog | stats count by host | sort - count
  2. Filter noisy EventCodes in inputs.conf with blacklist
  3. Tune Sysmon config to reduce noise
  4. Consider sampling for low-value events
  5. Move verbose logs to summary index
  1. Verify Sysmon service is running: sc query sysmon64
  2. Check Sysmon config loaded: sysmon64 -c
  3. Verify Event Log exists in Event Viewer
  4. Check inputs.conf channel name matches exactly
  5. Test with default Sysmon config first

Acceptance Criteria

Phase 1 Gate Requirements

Rollback & Safety

Emergency: Stop Endpoint Data Collection

Emergency Procedure 
SCENARIO: Endpoint data causing license overrun or performance issues

OPTION 1: Disable via Deployment Server (Preferred)
───────────────────────────────────────────────────
1. On Deployment Server, edit serverclass.conf
2. Set: disabled = 1 for the inputs app server class
3. Reload: $SPLUNK_HOME/bin/splunk reload deploy-server
4. Wait for UFs to check in (default: 10 min intervals)

OPTION 2: Push Empty Inputs.conf
────────────────────────────────
1. Create app with empty/disabled inputs.conf
2. Deploy via serverclass to affected endpoints
3. This overrides existing collection

OPTION 3: Disable Individual UF (Single Endpoint)
─────────────────────────────────────────────────
On the endpoint:
1. Stop UF service: net stop SplunkForwarder
2. Or disable specific input in local\inputs.conf

OPTION 4: Block at Network (Emergency)
──────────────────────────────────────
Block outbound TCP 9997 from endpoint subnet
⚠️ WARNING: This stops ALL UF traffic from that subnet

COMMUNICATION:
- Notify SOC (detection gaps occurring)
- Notify security team (endpoint visibility lost)
- Document affected endpoints and duration

Safe Deployment Server Change Procedure

Safe Change Procedure 
BEFORE ANY DEPLOYMENT SERVER CHANGE:

STEP 1: Backup Current Configuration
─────────────────────────────────────
tar -czvf /backup/ds_etc_$(date +%Y%m%d_%H%M).tar.gz $SPLUNK_HOME/etc/deployment-apps/
tar -czvf /backup/ds_serverclass_$(date +%Y%m%d_%H%M).tar.gz $SPLUNK_HOME/etc/system/local/serverclass.conf

STEP 2: Test on Pilot Group First
─────────────────────────────────
1. Create test server class for pilot endpoints (50-100 systems)
2. Deploy new config to pilot only
3. Validate data flow and volume from pilot
4. Wait 24 hours to observe volume patterns

STEP 3: Staged Rollout
──────────────────────
Deploy to production in phases:
- Phase 1: 10% of endpoints (non-critical)
- Phase 2: 50% of endpoints (if Phase 1 successful)
- Phase 3: 100% of endpoints

Wait minimum 4 hours between phases to observe volume impact.

STEP 4: Volume Validation After Each Phase
──────────────────────────────────────────
index=wineventlog OR index=sysmon earliest=-1h
| stats count by index
| eval GB_per_day = round(count * 0.5 / 1024 / 1024 * 24, 2)  `comment("Rough estimate")`

Compare to license allocation before proceeding.

Volume Reduction Emergency Procedures

License Emergency: Reduce Endpoint Volume 
SCENARIO: Endpoint data exceeding license allocation

IMMEDIATE ACTIONS (Pick based on severity):

LEVEL 1: Filter Noisy Event IDs (Low Impact)
────────────────────────────────────────────
Add to inputs.conf blacklist:
[WinEventLog:Security]
blacklist1 = EventCode="4689"   # Process termination (high volume, low value)
blacklist2 = EventCode="5156"   # Windows Filtering Platform connection (very high volume)
blacklist3 = EventCode="5158"   # Windows Filtering Platform bind

LEVEL 2: Reduce Sysmon Verbosity (Medium Impact)
────────────────────────────────────────────────
Deploy tuned Sysmon config that excludes:
- Image loads from trusted paths (Event 7)
- File creates in temp directories (Event 11)
- Registry events from trusted processes (Events 12, 13, 14)

LEVEL 3: Disable Non-Critical Sources (High Impact)
───────────────────────────────────────────────────
In order of detection value (disable lowest first):
1. WinEventLog:System (usually low detection value)
2. WinEventLog:Application (rarely needed for security)
3. Sysmon registry events (if not actively used)

LEVEL 4: Sample High-Volume Sources (Emergency)
───────────────────────────────────────────────
props.conf:
[WinEventLog:Security]
# Only index 10% of events (EMERGENCY ONLY)
TRANSFORMS-sample = sample_10_percent

transforms.conf:
[sample_10_percent]
REGEX = .
DEST_KEY = queue
FORMAT = nullQueue

⚠️ WARNING: Sampling causes detection gaps - use only in license emergency

UF Health Monitoring Query

SPL: Monitor UF Fleet Health 
`comment("Create scheduled alert to detect silent UF failures")`

| tstats latest(_time) AS last_seen WHERE index=wineventlog BY host
| eval hours_since = round((now() - last_seen)/3600, 1)
| where hours_since > 4
| sort - hours_since
| eval alert = case(
    hours_since > 24, "🔴 CRITICAL: No data >24h",
    hours_since > 8, "🟠 WARNING: No data >8h",
    hours_since > 4, "🟡 NOTICE: No data >4h"
)
| table host, last_seen, hours_since, alert

`comment("Schedule this to run every hour and alert on results > 0")`
