📊 Phase 1 — Log Coverage

Authentication & MFA Log Onboarding

🔐 Multi-Provider Guide

This guide covers onboarding authentication and MFA logs from multiple identity providers commonly found in enterprise environments. Most organizations have 2-4 authentication sources that need to be correlated for complete visibility.

Supported Providers

Provider Log Types Delivery Method Splunk Add-on Typical Use
Microsoft Entra ID
(formerly Azure AD)		 Sign-in logs, Audit logs, MFA logs, Risky sign-ins Event Hub → HEC, or Graph API polling Splunk Add-on for Microsoft Cloud Services Primary IdP for M365 environments
CyberArk Identity
(formerly Idaptive)		 Authentication events, MFA challenges, Session logs SIEM Integration (push) or API polling Splunk Add-on for CyberArk Privileged access MFA
Okta System logs (auth, MFA, admin events) Event Hook (push) or API polling Splunk Add-on for Okta Workforce identity, SSO

Why Authentication Log Onboarding Matters

Business Justification

Authentication is the front door to your organization. Every account takeover, every unauthorized access, every insider threat begins with an authentication event. In retail environments with distributed workforce, seasonal employees, and customer-facing systems, authentication visibility is non-negotiable:

  • Account takeover is the #1 attack vector. Credential stuffing, phishing, and password spray attacks target authentication systems daily. Without logs, you're blind to these attacks.
  • MFA fatigue attacks are increasing. The Uber (2022) and Cisco (2022) breaches both involved MFA fatigue—repeatedly sending push notifications until users approve. You cannot detect this without MFA-specific logs.
  • Compliance mandates visibility. PCI DSS, SOX, and internal audit requirements all demand authentication logging and monitoring.
  • Insider threat detection requires auth context. Unusual login times, impossible travel, and access from new devices all require authentication log analysis.

Security Justification

Authentication logs enable detection of:

  • Credential Attacks: Brute force, password spray, credential stuffing
  • MFA Attacks: MFA fatigue/prompt bombing, MFA bypass, SIM swapping indicators
  • Account Compromise: Impossible travel, new device login, suspicious IP geolocation
  • Privilege Escalation: Unusual admin access, service account abuse
  • Policy Violations: Legacy protocol usage, conditional access bypass attempts

The Multi-Provider Challenge

⚠️ Enterprise Reality: You Probably Have Multiple IdPs

Most enterprises don't have a single authentication system. Common patterns include:

  • Entra ID + CyberArk: Entra for regular users, CyberArk for privileged access
  • Okta + Duo: Okta for SSO, Duo as MFA provider
  • Entra ID + On-Prem AD: Hybrid identity with cloud and legacy systems
  • Multiple Entra tenants: Acquired companies, separate business units

Each provider has different log formats, field names, and delivery mechanisms. Your detection logic must account for ALL of them—an attacker won't limit themselves to one.

What Breaks If This Is Not Done Correctly

Misconfiguration Impact Detection Gap
Only onboarding one IdP when multiple exist Partial visibility Attacks against other IdPs invisible
Missing MFA-specific logs No MFA event detail Cannot detect MFA fatigue attacks
Username format mismatch between providers Correlation fails Cannot link events for same user across systems
Only collecting success events Missing failures Cannot detect brute force or spray attacks
High latency (>15 min) Delayed detection Attacker has access before alert fires

🚨 STOP — Complete IdP Discovery Before Starting

The #1 mistake in authentication log onboarding is missing an IdP. Before configuring anything, complete a full identity provider inventory. Attackers will target whichever system you're not monitoring.

⚠️ Enterprise Reality Check

Based on real deployments, these are commonly missing. Budget 1-2 weeks extra for discovery and remediation:

  • Complete IdP inventory: "We use Entra ID" often becomes "We use Entra ID, plus CyberArk for admins, plus legacy ADFS for one app, plus a separate tenant for the acquired company." Always ask: "Is this the ONLY authentication system?"
  • MFA log access: Many organizations have Entra ID sign-in logs but NOT the detailed MFA logs (authenticationDetails array). Verify MFA details are included.
  • Azure Event Hub: The recommended delivery method for Entra ID requires Event Hub, which may not exist. Cloud team may need 1-2 weeks to provision.
  • API credentials with correct permissions: Okta/CyberArk API keys often exist but have read-only permissions that don't include the log types you need.
  • Username consistency: Entra uses UPN (user@domain.com), CyberArk might use SAMAccountName (DOMAIN\user), on-prem AD uses various formats. Correlation requires understanding these differences.
  • Working diagnostic settings: Azure diagnostic settings may have been configured once and broken by subscription changes, policy updates, or Event Hub deletions.

Provider 1: Microsoft Entra ID (Azure AD)

📘 Entra ID Log Types

Entra ID provides multiple log categories. For security monitoring, you need at minimum: Sign-in logs and Audit logs. For MFA detection, you need the detailed authenticationDetails within sign-in logs.

Entra ID Log Categories

Log Category Contents Security Use Cases Required?
SignInLogs Interactive user sign-ins Brute force, impossible travel, MFA fatigue ✓ Required
NonInteractiveUserSignInLogs Token refreshes, background auth Session hijacking, token theft ✓ Required
ServicePrincipalSignInLogs Application/service account auth Compromised service principals Recommended
ManagedIdentitySignInLogs Azure managed identity auth Cloud resource compromise Recommended
AuditLogs Directory changes, user/group modifications Privilege escalation, persistence ✓ Required
RiskyUsers Identity Protection risk assessments Compromised account indicators Optional (P2 license)
RiskyServicePrincipals Service principal risk assessments Compromised app indicators Optional (P2 license)

Step 5: Verify Entra ID Data

SPL: Validate Entra ID Sign-in Logs 
index=auth_azure sourcetype="azure:aad:signin" earliest=-1h
| stats count BY category
| eval expected = case(
    category=="SignInLogs", "Interactive sign-ins",
    category=="NonInteractiveUserSignInLogs", "Token refreshes",
    category=="ServicePrincipalSignInLogs", "Service principals",
    category=="ManagedIdentitySignInLogs", "Managed identities",
    true(), "Other"
)
| table category, expected, count

Step 6: Verify MFA Details Are Present

SPL: Check MFA Field Availability (Critical for MFA Fatigue Detection) 
index=auth_azure sourcetype="azure:aad:signin" category="SignInLogs" earliest=-24h
| head 1000
| spath output=mfa_detail path=authenticationDetails{}.authenticationMethod
| spath output=mfa_result path=authenticationDetails{}.succeeded
| eval has_mfa_detail = if(isnotnull(mfa_detail), 1, 0)
| stats 
    count AS total,
    sum(has_mfa_detail) AS with_mfa_detail
| eval mfa_detail_pct = round(with_mfa_detail/total*100, 1)."%"
| eval status = if(with_mfa_detail > 0, "✓ MFA Details Available", "✗ MFA Details Missing - Check Diagnostic Settings")
⚠️ MFA Details Not Always Present

The authenticationDetails array is only populated for interactive sign-ins where MFA was challenged. If your query shows 0 MFA details but you have sign-in events, verify that MFA is actually being triggered (check Conditional Access policies). If MFA is configured but details are missing, the diagnostic setting may need to be recreated.

inputs.conf (Domain Controllers)

start_from = oldest
current_only = 0
evt_resolve_ad_obj = 1
checkpointInterval = 5
# Filter to security-relevant events to manage volume
whitelist = 4624,4625,4634,4648,4672,4720,4722,4723,4724,4725,4726,4728,4732,4733,4738,4740,4756,4767,4768,4769,4770,4771,4776

[WinEventLog://System]

current_only = 0

⚠️ Volume Warning

Domain Controller Security logs can generate massive volume (100GB+/day for large enterprises). Use the whitelist parameter to filter to security-relevant events. Monitor license impact before enabling on all DCs.

Cross-Provider Field Normalization

The biggest challenge in multi-provider authentication monitoring is correlating events for the same user across different systems. Each provider uses different field names and username formats.

Username Format Mapping

Provider Field Name Format Example
Entra ID userPrincipalName UPN (email-like) john.smith@contoso.com
CyberArk user Variable (often UPN) john.smith@contoso.com
Okta actor.alternateId UPN or email john.smith@contoso.com
Windows AD Account_Name SAMAccountName jsmith
Windows AD TargetUserName SAMAccountName jsmith

CIM Normalization

Use the Authentication data model with consistent field aliases:

props.conf: Normalize to CIM Authentication Fields 
# Entra ID
[azure:aad:signin]
FIELDALIAS-user = userPrincipalName AS user
FIELDALIAS-src = ipAddress AS src
FIELDALIAS-dest = resourceDisplayName AS dest
FIELDALIAS-app = appDisplayName AS app
EVAL-action = case('status.errorCode'==0, "success", true(), "failure")
EVAL-authentication_method = 'authenticationDetails{}.authenticationMethod'

# Okta
[OktaIM2:log]
FIELDALIAS-user = actor.alternateId AS user
FIELDALIAS-src = client.ipAddress AS src
EVAL-action = case(outcome.result=="SUCCESS", "success", true(), "failure")

# Windows Security
[WinEventLog:Security]
FIELDALIAS-user = Account_Name AS user
FIELDALIAS-src = Source_Network_Address AS src
EVAL-action = case(EventCode==4624, "success", EventCode==4625, "failure", true(), "unknown")

Username Correlation Lookup

For environments where username formats differ, create a lookup table:

identity_lookup.csv 
upn,samaccountname,employee_id,display_name
john.smith@contoso.com,jsmith,EMP001,John Smith
jane.doe@contoso.com,jdoe,EMP002,Jane Doe
...
SPL: Cross-Provider User Activity 
| tstats count FROM datamodel=Authentication WHERE earliest=-24h BY Authentication.user, Authentication.action, sourcetype
| rename Authentication.* AS *
| lookup identity_lookup upn AS user OUTPUT employee_id, display_name
| stats sum(count) AS events, values(sourcetype) AS sources BY employee_id, display_name, action

Validation & Acceptance

Comprehensive Validation Query

SPL: Multi-Provider Authentication Health Check 
| tstats count WHERE index IN (auth_azure, auth_cyberark, auth_okta, auth_windows) earliest=-24h BY index, sourcetype
| stats sum(count) AS events BY index, sourcetype
| eval provider = case(
    index=="auth_azure", "Entra ID",
    index=="auth_cyberark", "CyberArk",
    index=="auth_okta", "Okta",
    index=="auth_windows", "On-Prem AD",
    true(), index
)
| eval status = if(events > 0, "✓ Data Flowing", "✗ NO DATA")
| table provider, index, sourcetype, events, status

Latency Check Across Providers

SPL: Authentication Log Latency 
| tstats count WHERE index IN (auth_azure, auth_cyberark, auth_okta, auth_windows) earliest=-4h latest=-1h BY index, _time span=5m
| join type=left index 
    [search index IN (auth_azure, auth_cyberark, auth_okta, auth_windows) earliest=-4h latest=-1h
     | eval latency = _indextime - _time
     | stats avg(latency) AS avg_latency, perc95(latency) AS p95_latency BY index]
| stats values(avg_latency) AS avg_latency, values(p95_latency) AS p95_latency BY index
| eval avg_latency_min = round(avg_latency/60, 1)
| eval p95_latency_min = round(p95_latency/60, 1)
| eval status = case(
    p95_latency < 300, "✓ Acceptable (<5 min)",
    p95_latency < 900, "⚠️ Marginal (5-15 min)",
    true(), "✗ High (>15 min)"
)
| table index, avg_latency_min, p95_latency_min, status

Authentication Onboarding — Exit Criteria

Failure Modes & Fixes

Failure Mode 1: Event Hub Not Receiving Data

Symptom

Entra ID diagnostic settings configured, but no events in Splunk.

Why It Happens:

  • Diagnostic setting not properly saved
  • Event Hub namespace in different subscription than Entra tenant
  • Event Hub has no consumer reading messages (messages expire)
  • Permissions issue between Entra and Event Hub

How to Diagnose:

  1. Check Event Hub metrics in Azure Portal: Incoming Messages should be > 0
  2. Verify diagnostic setting shows "Enabled" status (not just configured)
  3. Check Event Hub access policies include RootManageSharedAccessKey

Resolution:

  1. Delete and recreate diagnostic setting
  2. Ensure Event Hub is in same subscription or has proper cross-subscription permissions
  3. Verify Splunk consumer is running and connected

Failure Mode 2: MFA Details Missing from Entra Logs

Symptom

Sign-in events arrive but authenticationDetails array is empty or missing.

Why It Happens:

  • MFA not triggered for these sign-ins (no Conditional Access requiring MFA)
  • Old events (MFA details only in recent log format)
  • Non-interactive sign-ins don't include MFA details
  • Service principal sign-ins don't have MFA

How to Diagnose:

SPL: Check Event Types with MFA Details 
index=auth_azure sourcetype="azure:aad:signin" earliest=-7d
| spath output=mfa_methods path=authenticationDetails{}.authenticationMethod
| eval has_mfa = if(isnotnull(mfa_methods), "Yes", "No")
| stats count BY category, has_mfa
| sort category

Resolution:

  1. Verify Conditional Access policies require MFA for target users
  2. Focus MFA fatigue detection on SignInLogs category only
  3. Accept that some sign-ins won't have MFA details (this is expected)

Failure Mode 3: API Token Expiration (Okta/CyberArk)

Symptom

Data was flowing, then stopped. API-based collection returns authentication errors.

Why It Happens:

  • API tokens have expiration dates (Okta: no expiration by default but can be revoked; CyberArk: typically 90 days)
  • Token revoked by admin unaware of SIEM integration
  • Password rotation on service account

How to Diagnose:

SPL: Check for API Errors 
index=_internal sourcetype=splunkd component=*okta* OR component=*cyberark*
| search "error" OR "unauthorized" OR "401" OR "403"
| table _time, component, message

Resolution:

  1. Generate new API token with appropriate permissions
  2. Update Splunk add-on configuration with new credentials
  3. Document token expiration dates and set calendar reminders for renewal
  4. Consider using service accounts with longer/no expiration where possible

Failure Mode 4: Username Format Mismatch Breaking Correlation

Symptom

Cannot correlate events for same user across Entra (UPN) and Windows AD (SAMAccountName).

Why It Happens:

  • Different identity systems use different username formats
  • No identity lookup table configured
  • CIM user field populated with different values per source

Resolution:

  1. Export identity data from AD/Entra with all username formats
  2. Create lookup table mapping UPN ↔ SAMAccountName ↔ Employee ID
  3. Use lookup in searches to normalize user identity
  4. Consider using Splunk ES Identity Manager for enterprise identity correlation

Failure Mode 5: Missing One of Multiple Entra Tenants

Symptom

Entra logs flowing, but attacks against users in acquired company's tenant are not visible.

Why It Happens:

  • Multiple Entra tenants exist (common after acquisitions)
  • Diagnostic settings only configured for primary tenant
  • Different Azure subscriptions with separate logging

How to Diagnose:

SPL: Check Tenant IDs in Logs 
index=auth_azure sourcetype="azure:aad:signin" earliest=-7d
| spath output=tenant_id path=tenantId
| stats count BY tenant_id
| lookup tenant_names.csv tenant_id OUTPUT tenant_name

Resolution:

  1. Inventory all Entra tenants in the organization
  2. Configure diagnostic settings in each tenant
  3. Use separate Event Hubs or same Event Hub with different consumer groups
  4. Document which tenant IDs map to which business units

Failure Mode 6: Domain Controller Logs Overwhelming License

Symptom

Splunk license usage spikes dramatically after enabling Windows Security logs on Domain Controllers.

Why It Happens:

  • Domain Controllers generate massive volume of authentication events
  • Default Windows Security logging includes many non-security-relevant events
  • Service account activity creates continuous stream of events

Resolution:

  1. Implement whitelist filtering in inputs.conf for security-relevant Event IDs only
  2. Consider sampling for extremely high-volume service accounts
  3. Use Splunk data routing to separate index for volume management
  4. Discuss license increase with Splunk account team if security-critical events can't be reduced

Rollback & Safety

How to Disable Authentication Log Collection

If you need to stop collection due to volume issues, troubleshooting, or other reasons:

Provider How to Disable Time to Stop Data Impact
Entra ID (Event Hub) Azure Portal → Entra ID → Diagnostic Settings → Delete/Disable setting 5-10 minutes Events continue in Event Hub buffer briefly
Entra ID (API) Splunk → inputs.conf → disabled = 1 → restart Immediate No new polls; gap until re-enabled
CyberArk CyberArk Admin Portal → SIEM Integration → Disable 5-10 minutes No loss; events resume when re-enabled
Okta Splunk TA → inputs.conf → disabled = 1 Immediate API polling stops
Windows AD (UF) Stop Splunk forwarder service on DC Immediate Local queue builds until resumed

Entra ID Diagnostic Settings Rollback

Disable Entra ID Log Export 
AZURE PORTAL METHOD:
1. Azure Portal → Microsoft Entra ID
2. Monitoring → Diagnostic settings
3. Find your diagnostic setting (e.g., "splunk-security-logs")
4. Click "Edit setting"
5. Either: Uncheck log categories you want to stop
   Or: Click "Delete" to remove entirely
6. Save

AZURE CLI METHOD (faster for automation):
# List diagnostic settings
az monitor diagnostic-settings list --resource /subscriptions/[sub]/providers/microsoft.aadiam/diagnosticSettings/[name]

# Delete diagnostic setting
az monitor diagnostic-settings delete --name "splunk-security-logs" --resource /subscriptions/[sub]/providers/microsoft.aadiam/diagnosticSettings/[name]

VERIFICATION:
- Events should stop arriving within 10 minutes
- Run: index=auth_azure earliest=-15m | stats count
- If count continues high, check for other diagnostic settings

API Credential Expiration Tracking

⚠️ API Tokens Expire Silently

Authentication API tokens (Okta, CyberArk, Graph API) can expire without warning, causing silent data loss. Track expiration dates proactively.

Credential Expiration Tracking Template 
TRACK IN YOUR PASSWORD MANAGER OR WIKI:

| Provider      | Credential Type      | Created    | Expires    | Owner     | Renewal Reminder |
|---------------|---------------------|------------|------------|-----------|------------------|
| Entra ID      | App Registration    | 2024-01-15 | 2026-01-15 | IAM Team  | 2025-12-15      |
| CyberArk      | API Client Secret   | 2024-02-01 | 2024-05-01 | IAM Team  | 2024-04-15      |
| Okta          | API Token           | 2024-01-20 | Never*     | IAM Team  | N/A             |

* Okta tokens don't expire by default but can be revoked

MONITORING FOR CREDENTIAL FAILURES:
Set up this Splunk alert to detect API authentication failures:

index=_internal sourcetype=splunkd 
  (component=*azure* OR component=*okta* OR component=*cyberark*)
  (error OR unauthorized OR "401" OR "403" OR "invalid_client")
| stats count BY component, message
| where count > 5

PROACTIVE RENEWAL PROCESS:
1. Set calendar reminder 30 days before expiration
2. Generate new credential in IdP admin portal
3. Update Splunk add-on configuration
4. Verify data flow resumes
5. Revoke old credential after 24 hours of successful collection

Emergency: MFA Logs Missing During Active Attack

Emergency Verification Procedure 
IF SOC REPORTS MFA LOGS NOT ARRIVING DURING SUSPECTED ATTACK:

STEP 1: Verify Last Event Time (30 seconds)
index=auth_azure sourcetype="azure:aad:signin" 
| stats max(_time) AS last_event 
| eval minutes_ago = round((now() - last_event) / 60, 1)
| eval status = if(minutes_ago > 15, "⚠️ Data gap detected", "✓ Recent data")

STEP 2: Check Alternative Sources (if primary failing)
- Entra ID Audit Logs (Azure Portal direct access)
- Entra ID Sign-in Logs (Azure Portal)
- Office 365 Admin Center Activity Logs

STEP 3: Direct Azure Query (if Splunk pipeline broken)
# Use Azure CLI or Azure Portal → Entra ID → Sign-in logs
# Filter to suspected user/IP for immediate investigation

STEP 4: Escalate if Complete Blindness
- Contact Azure/Cloud team for portal access
- Contact IdP vendor support if logs not generating
- Document gap for post-incident review

DO NOT WAIT for Splunk pipeline to be fixed during active incident.
Use direct console access to continue investigation.
