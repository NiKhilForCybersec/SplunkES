📊 Phase 1 — Log Coverage

Universal Onboarding Framework

📋 Page Status: HARDENED

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This framework includes explicit validation criteria, failure modes, and rollback procedures for all onboarding stages.

🚨 HARD GATE — Every Stage Must Complete Before Proceeding

DO NOT skip stages or proceed with partial completion. Each stage has explicit exit criteria. The most common onboarding failures occur because teams rush to "data flowing" without completing validation and documentation.

Minimum Time for Full Onboarding:

  • Simple source (vendor TA exists, syslog): 1-2 weeks
  • Complex source (custom parsing, API): 2-4 weeks
  • Enterprise source (multiple instances, cross-team coordination): 4-8 weeks
⚠️ Retail Business Timing — Onboarding Windows

Log source onboarding can impact Splunk performance and may require network changes. Follow these timing constraints:

  • Heavy Forwarder changes: During maintenance windows only (Tue-Thu 2-6 AM ET)
  • High-volume sources: Never during month-end close or quarter-end
  • Network/firewall changes: Follow change advisory board process
📋 Framework Purpose

This framework applies to ALL log source onboarding regardless of source type. Every onboarding follows these six stages before logs are considered "production ready."

Stage 1: Discovery

Identify all data sources and gather technical requirements.

Discovery Checklist
⚠️ Volume Estimation

Always validate vendor estimates against reality. Request 24-48 hours of sample data where possible. Vendor documentation often underestimates real-world volumes by 2-5x.

Stage 2: Design

Define the technical architecture for data ingestion.

Key Design Decisions

Decision Point Options Guidance
Ingestion Method Heavy Forwarder, Universal Forwarder, HEC, Syslog, API Polling See Decision Guides
Index Strategy Dedicated vs. Shared Index Dedicated for high-volume (>50GB/day)
Sourcetype Existing TA vs. Custom Always prefer official TAs
Parsing Location Source, Heavy Forwarder, Indexers Parse at HF for syslog; parse at indexers for HEC

Index Naming Convention

Standard 
<environment>_<category>_<source>

Examples:
prod_security_akamai
prod_security_entra
prod_network_firewall
prod_endpoint_defender

Stage 3: Configure

Implement the technical configuration in Splunk.

Inputs.conf Template

inputs.conf 
# Syslog Input Example
[udp://514]
sourcetype = syslog
index = prod_network_syslog
connection_host = dns
no_priority_stripping = true

# Monitor Input Example
[monitor:///var/log/application/*.log]
sourcetype = custom_app
index = prod_apps_custom
disabled = false
followTail = 0

Props.conf Template

props.conf 
[sourcetype_name]
TIME_FORMAT = %Y-%m-%dT%H:%M:%S.%3N%z
MAX_TIMESTAMP_LOOKAHEAD = 30
SHOULD_LINEMERGE = false
LINE_BREAKER = ([\r\n]+)
TRUNCATE = 999999

# Field Extractions
REPORT-fields = extract_custom_fields

# CIM Compliance
FIELDALIAS-src = source_ip AS src
FIELDALIAS-dest = destination_ip AS dest
EVAL-action = case(status="200", "allowed", status="403", "blocked", true(), "unknown")

Stage 4: Validate

Verify data is flowing correctly with acceptable quality.

Validation SPL Queries

1. Data Flow Verification

SPL 
| tstats count WHERE index=prod_security_* by index, sourcetype, host
| sort -count

2. Latency Check

SPL 
index=prod_security_akamai
| eval latency_sec = _indextime - _time
| stats avg(latency_sec) as avg_latency, max(latency_sec) as max_latency, 
        perc95(latency_sec) as p95_latency by sourcetype
| eval acceptable = if(p95_latency < 300, "✓ Pass", "✗ Fail")

3. Timestamp Accuracy

SPL 
index=prod_security_akamai earliest=-1h
| eval time_diff = abs(_time - now())
| where time_diff > 86400
| stats count as future_events by sourcetype
| eval issue = if(count > 0, "⚠️ Timestamp Issues Detected", "✓ OK")

4. Field Population Check

SPL 
index=prod_security_akamai earliest=-24h
| fieldsummary
| where count > 0
| eval coverage_pct = round((count / max_count) * 100, 1)
| table field, count, distinct_count, coverage_pct
| sort -coverage_pct

Stage 6: Sign-Off

Formal acceptance that the data source is production-ready.

✓ Sign-Off Criteria

All of the following must be true before signing off:

Criterion Validation Method Status
Data is flowing continuously 48-hour continuous monitoring ☐
Latency is acceptable P95 < 5 minutes ☐
Required fields are populated CIM compliance check ☐
Documentation complete Runbook review ☐
Stakeholder accepts Email/ticket confirmation ☐

Common Pitfalls

🚫 Avoid These Mistakes
Pitfall Impact Prevention
Skipping validation Silent data gaps Always run full validation suite
Wrong timezone Correlation failures Verify TZ in sample data
Missing line breaks Event merging Test LINE_BREAKER with real data
No monitoring Undetected outages Create data availability alerts
Vendor TA blind trust Missing fields Validate TA against your data

Rollback & Safety

Emergency: Disable Data Ingestion

Procedure: Emergency Stop for Any Data Source 
SCENARIO: New data source is causing issues (volume spike, parsing errors, performance impact)

STEP 1: IDENTIFY INGESTION METHOD
─────────────────────────────────
- Syslog → Stop at Heavy Forwarder
- HEC → Disable HEC token
- API Polling → Disable inputs.conf
- Universal Forwarder → Stop forwarder service
- SIEM Integration → Disable in vendor portal

STEP 2: DISABLE AT SOURCE
─────────────────────────

FOR SYSLOG (Heavy Forwarder):
1. SSH to Heavy Forwarder
2. Edit inputs.conf: [udp://514] → disabled = 1
3. Restart: $SPLUNK_HOME/bin/splunk restart

FOR HEC:
1. Splunk Web → Settings → Data Inputs → HTTP Event Collector
2. Find token → Disable
3. Effect: Immediate (returns 403 to sender)

FOR API POLLING (TA):
1. Edit $SPLUNK_HOME/etc/apps/[TA]/local/inputs.conf
2. Set disabled = 1 for relevant stanza
3. Restart Splunk or: splunk _internal call /services/data/inputs/[input]/disable

FOR UNIVERSAL FORWARDER:
1. On source system: $SPLUNK_HOME/bin/splunk stop
2. Or disable specific input in local/inputs.conf

STEP 3: VERIFY INGESTION STOPPED
────────────────────────────────
| tstats count WHERE index=[problem_index] earliest=-5m BY sourcetype
`comment("Should show zero or rapidly declining count")`

STEP 4: COMMUNICATE
───────────────────
1. Notify Splunk admin team
2. Notify data owner/source team
3. Document reason for disable
4. Plan remediation before re-enabling

Rollback: Undo Onboarding Changes

Procedure: Remove a Data Source Completely 
SCENARIO: Onboarding failed and you need to clean up all configuration

STEP 1: DISABLE INGESTION (See Above)
─────────────────────────────────────

STEP 2: REMOVE CONFIGURATION FILES
──────────────────────────────────
# List all config files for the source
find $SPLUNK_HOME/etc/apps -name "*[sourcetype]*" -o -name "*[source_name]*"

# Backup before removing
cp -r $SPLUNK_HOME/etc/apps/[TA_name] /backup/

# Remove TA if dedicated to this source
rm -rf $SPLUNK_HOME/etc/apps/[TA_name]

# Or remove specific stanzas from:
# - inputs.conf (ingestion)
# - props.conf (parsing)
# - transforms.conf (field extraction)
# - tags.conf (CIM mapping)

STEP 3: REMOVE INDEX (Optional)
───────────────────────────────
# Only if index is dedicated to this source AND you want to delete all data
# WARNING: This permanently deletes all data in the index
$SPLUNK_HOME/bin/splunk remove index [index_name]

# Or just disable the index (preserves data):
# Edit indexes.conf: [index_name] disabled = true

STEP 4: CLEAN UP NETWORK/FIREWALL
─────────────────────────────────
1. Remove any firewall rules added for this source
2. Remove DNS entries if created
3. Document changes for network team

STEP 5: UPDATE DOCUMENTATION
───────────────────────────
1. Mark source as "Onboarding Failed" in tracking spreadsheet
2. Document what went wrong
3. Archive onboarding documentation for future reference

Onboarding Failure Escalation Matrix

Failure Type Symptoms First Response Escalate To
No data arriving Zero events in index Check network connectivity, firewall logs Network team, Source system owner
Parsing failures Events in wrong format, timestamps incorrect Review props.conf, check LINE_BREAKER Splunk admin, TA vendor
Volume explosion 10x+ expected volume Disable ingestion immediately Splunk admin, License owner
Performance impact Slow searches, indexer lag Reduce volume or disable source Splunk admin
Missing fields CIM fields not populated Check TA version, verify field extraction Detection engineering, TA vendor

Data Availability Monitoring

After successful onboarding, create a data availability alert to detect future gaps:

SPL: Data Availability Alert Template 
`comment("Alert if no data received in last 30 minutes")`
`comment("Customize index and sourcetype for your source")`

| tstats latest(_time) AS last_event WHERE index=[your_index] sourcetype=[your_sourcetype]
| eval minutes_since_last = round((now() - last_event) / 60, 0)
| where minutes_since_last > 30
| eval alert_message = "⚠️ No data received from [source_name] for ".minutes_since_last." minutes"
| table alert_message, last_event, minutes_since_last

`comment("
ALERT SETTINGS:
- Schedule: Every 15 minutes
- Trigger: If results > 0
- Action: Email SOC + Splunk admin
")`
