⚡ Phase 4 — Automation

Automation & Response

📋 Page Status: HARDENED

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This page includes safety guardrails, rollback procedures, and explicit validation requirements for all automation actions.

🚨 CRITICAL SAFETY WARNING — Automation Can Cause Outages

Automated response actions can disable accounts, block IPs, and isolate systems. A misconfigured automation can cause widespread business disruption. Follow these mandatory rules:

  • NEVER deploy auto-response without extensive monitoring mode first (minimum 4 weeks)
  • ALWAYS have a manual override — SOC must be able to stop any automation
  • NEVER auto-disable executive accounts without human approval
  • ALWAYS have rollback procedures documented before enabling automation
⚠️ Retail Business Timing — Automation Deployment

Do NOT enable new automated response actions during:

  • Black Friday / Holiday periods — Risk of blocking legitimate customer activity
  • Major system changes — False positives likely during migrations
  • SOC staffing gaps — Must have coverage to handle automation failures

Recommended: Enable new automation on Tuesday-Wednesday with full SOC coverage.

📋 Phase Overview

Phase 4 transforms manual SOC workflows into automated responses. This includes enrichment automation (adding context to alerts), response automation (taking action on threats), and SOAR integration for orchestrated playbooks.

Why This Phase Exists

Business Justification

  • Reduce Mean Time to Respond (MTTR): Automated enrichment and response happen in seconds, not minutes or hours
  • Scale SOC capacity: Automation handles repetitive tasks so analysts can focus on complex investigations
  • Consistent response: Playbooks ensure every alert gets the same quality investigation
  • 24/7 coverage: Automation responds to threats even when analysts aren't available

Types of Automation

1. Enrichment Automation

Automatically add context to alerts so analysts don't have to look it up manually.

Enrichment Type Data Source Value Added Implementation
Threat Intelligence MISP, VirusTotal, AbuseIPDB Is source IP known malicious? ES Threat Intelligence framework or SOAR
Asset Context CMDB, ES Asset Inventory What system is affected? Priority? ES Asset/Identity framework
Identity Context HR system, AD, ES Identity Who is affected? VIP? Admin? ES Identity framework
Geolocation MaxMind, IP2Location Where is source IP? Expected? Splunk iplocation command or lookup
Historical Context Previous alerts, investigations Have we seen this before? Notable event correlation

2. Response Automation

Take action on threats automatically or with one-click analyst approval.

Response Type Risk Level Automation Approach Example
Block IP at Firewall Medium Analyst-approved or auto for known-bad Block attacker IP after confirmed attack
Disable User Account High Analyst-approved (business impact) Disable compromised account
Isolate Endpoint High Analyst-approved Network isolate infected host
Reset Password Medium Analyst-approved or auto for MFA fatigue Force password reset after credential compromise
Create Ticket Low Full automation Auto-create ServiceNow incident
Send Notification Low Full automation Page on-call for critical alerts
🚨 Automation Risk Warning

Automated response actions that affect business operations (blocking users, isolating systems) should NEVER be fully automated without human approval until the detection has proven extremely reliable (<1% false positive rate over 6+ months).

Custom Adaptive Response Actions

Create custom response actions for your environment:

Example: Custom Action to Block IP at Firewall 
# File: $SPLUNK_HOME/etc/apps/SA-CustomActions/default/alert_actions.conf

[block_ip_firewall]
is_custom = 1
label = Block IP at Firewall
description = Adds IP to firewall block list via API
icon_path = block.png
payload_format = json
param.ip_field = src
param._cam = {"task": ["block_ip"], "subject": ["ip"]}

# File: $SPLUNK_HOME/etc/apps/SA-CustomActions/bin/block_ip_firewall.py

import sys
import json
import requests

def main():
    payload = json.loads(sys.stdin.read())
    ip_to_block = payload.get('result', {}).get('src')
    
    if ip_to_block:
        # Call firewall API to block IP
        response = requests.post(
            'https://firewall.company.com/api/block',
            json={'ip': ip_to_block, 'reason': 'Automated block from Splunk ES'},
            headers={'Authorization': 'Bearer TOKEN'}
        )
        
        if response.status_code == 200:
            print(f"Successfully blocked {ip_to_block}")
        else:
            print(f"Failed to block {ip_to_block}: {response.text}")

if __name__ == '__main__':
    main()

Example Playbook: MFA Fatigue Response

MFA Fatigue Playbook Pseudocode 
═══════════════════════════════════════════════════════════════════
PLAYBOOK: MFA Fatigue Attack Response
TRIGGER: Notable event from MFA Fatigue detection
═══════════════════════════════════════════════════════════════════

STEP 1: VALIDATION
─────────────────────────────────────────
□ Check user field is populated
□ Check if duplicate alert in last 1 hour
  → If duplicate: Link to existing case, exit

STEP 2: ENRICHMENT
─────────────────────────────────────────
□ Lookup user in identity system:
  - Department, manager, VIP status
  - Is this a privileged account?
  
□ Lookup source IP:
  - Geolocation
  - Threat intel reputation
  - Is this a known corporate IP?
  
□ Get historical context:
  - Previous MFA fatigue alerts for this user?
  - Other recent security alerts for this user?

STEP 3: DECISION LOGIC
─────────────────────────────────────────
□ IF attack_succeeded == "YES":
  → CRITICAL PATH: Go to Step 4a
  
□ IF source_ip is known corporate AND user is NOT privileged:
  → Lower severity, route to Tier 1
  
□ IF user is privileged (admin, exec):
  → Escalate to Tier 2 regardless of outcome

STEP 4a: CRITICAL RESPONSE (Attack Succeeded)
─────────────────────────────────────────
□ AUTOMATED (no approval needed):
  - Revoke all user sessions (Entra ID API)
  - Send Slack alert to security channel
  - Create P1 ServiceNow incident
  - Page on-call security analyst
  
□ ANALYST APPROVAL REQUIRED:
  - Disable user account
  - Force password reset
  
□ Notify user's manager via email

STEP 4b: STANDARD RESPONSE (Attack Blocked)
─────────────────────────────────────────
□ AUTOMATED:
  - Create P3 ServiceNow incident
  - Send user awareness email (template)
  
□ IF source_ip is external AND reputation is bad:
  - Queue for firewall block (analyst approval)

STEP 5: CLOSURE
─────────────────────────────────────────
□ Update ServiceNow ticket with:
  - All enrichment data
  - Actions taken
  - Analyst notes
  
□ Update metrics:
  - Log playbook execution time
  - Log outcome (TP/FP/auto-closed)
  
□ Close notable event in ES

Playbook Best Practices

💡 Playbook Design Guidelines
  • Start simple: Begin with enrichment-only playbooks, add response actions after proving reliability
  • Always have an escape hatch: Every automated decision should have a path for analyst review
  • Log everything: Every playbook action should be logged for audit and debugging
  • Test in staging: Never deploy new playbooks directly to production
  • Version control: Keep playbook code in Git for change tracking
  • Error handling: What happens if an API call fails? Always handle failures gracefully
  • Rate limiting: Ensure playbooks can't overwhelm external APIs during alert storms

Automation Priority Matrix

Not everything should be automated immediately. Prioritize based on volume and complexity:

Priority Alert Type Automation Level ROI
1 (High) High volume, simple triage Full enrichment + auto-close if benign High — saves most analyst time
2 High volume, moderate complexity Enrichment + decision support Medium-High
3 Low volume, critical response needed Enrichment + one-click response Medium — speed matters more than time saved
4 (Low) Low volume, complex investigation Enrichment only Low — manual investigation still needed

Quick Wins: Start Here

  1. Threat intel enrichment on all alerts: Auto-lookup source IPs against threat feeds
  2. Asset/identity enrichment: Auto-populate asset criticality and user info
  3. Duplicate detection: Auto-link related alerts to reduce volume
  4. Auto-ticket creation: Create ServiceNow tickets for all medium+ alerts
  5. Notification routing: Page on-call for critical, email for medium

Measuring Automation Success

Key Metrics

Metric What It Measures Target
Mean Time to Respond (MTTR) Time from alert to response action <5 min for critical, <30 min for medium
Automation Rate % of alerts with automated enrichment >90%
Auto-Close Rate % of alerts closed without analyst 20-40% (higher risks missing things)
Analyst Time per Alert Average time analyst spends on each alert <10 min for enriched alerts
Playbook Success Rate % of playbook runs that complete without error >95%

Automation Dashboard Query

SPL: Automation Metrics Dashboard 
`comment("Track automation effectiveness")`

index=notable earliest=-30d
| eval time_to_first_action = if(isnotnull(first_action_time), first_action_time - _time, null())
| eval auto_enriched = if(isnotnull(threat_intel_enriched) OR isnotnull(asset_enriched), 1, 0)
| eval auto_closed = if(status_label="Closed - Auto", 1, 0)

| stats 
    count AS total_alerts,
    avg(time_to_first_action) AS avg_mttr,
    sum(auto_enriched) AS enriched_alerts,
    sum(auto_closed) AS auto_closed_alerts
    
| eval enrichment_rate = round(enriched_alerts/total_alerts*100, 1)."%"
| eval auto_close_rate = round(auto_closed_alerts/total_alerts*100, 1)."%"
| eval avg_mttr_min = round(avg_mttr/60, 1)

| table total_alerts, enrichment_rate, auto_close_rate, avg_mttr_min

Rollback & Safety

Emergency: Disable All Automation

Procedure: Emergency Automation Shutdown 
SCENARIO: Automation is causing widespread issues (false disables, incorrect blocks, etc.)

STEP 1: DISABLE ADAPTIVE RESPONSE ACTIONS (Immediate)
──────────────────────────────────────────────────────
ES → Configure → Incident Management → Adaptive Response Actions
Bulk disable all active response actions

STEP 2: DISABLE SOAR PLAYBOOKS (If Applicable)
──────────────────────────────────────────────
In SOAR platform (Phantom/XSOAR/etc.):
1. Navigate to playbook management
2. Disable all active playbooks
3. Set all playbook triggers to "Manual Only"

STEP 3: VERIFY AUTOMATION STOPPED
─────────────────────────────────
index=_audit action=adaptive_response_action earliest=-15m
| stats count BY action_name
| where count > 0
`comment("Should return zero results after disable")`

STEP 4: ASSESS DAMAGE
─────────────────────
1. List all automated actions taken in last hour:
   index=_audit action=adaptive_response_action earliest=-1h | table _time, action_name, search_name, user
2. Identify affected users/systems
3. Begin manual remediation if needed

STEP 5: COMMUNICATE
───────────────────
- Notify SOC: "All automation disabled due to [reason]. Manual response required."
- Notify Security Management
- Open incident ticket for tracking

STEP 6: ROOT CAUSE BEFORE RE-ENABLING
─────────────────────────────────────
DO NOT re-enable automation until:
- Root cause identified
- Fix tested in monitoring mode
- Approval from Security Manager

Rollback: Undo Automated Account Disable

Procedure: Restore Disabled Account 
SCENARIO: Automation incorrectly disabled a user account

FOR ENTRA ID:
─────────────
1. Azure Portal → Microsoft Entra ID → Users → [username]
2. Properties → Account enabled = Yes
3. Save
4. Verify user can authenticate

FOR ON-PREMISES AD:
───────────────────
1. Active Directory Users and Computers
2. Find user → Properties → Account tab
3. Uncheck "Account is disabled"
4. Apply

FOR CYBERARK:
─────────────
1. CyberArk Admin Portal → Users
2. Find user → Edit
3. Status = Active
4. Save

DOCUMENTATION REQUIRED:
───────────────────────
Always document in ticket:
- Why account was disabled (what triggered automation)
- Why it was a false positive
- What tuning is needed to prevent recurrence

Rollback: Undo Automated IP Block

Procedure: Unblock IP Address 
SCENARIO: Automation incorrectly blocked an IP (customer, partner, VPN egress)

FOR FIREWALL BLOCK:
───────────────────
1. Identify where block was applied (perimeter FW, WAF, host FW)
2. Remove block rule:
   - Palo Alto: Objects → Address Groups → Remove from block list
   - Akamai: Security → IP Allow/Block Lists → Remove IP
   - Windows FW: netsh advfirewall firewall delete rule name="Block_[IP]"
3. Verify IP can connect

FOR SPLUNK ES THREAT LIST:
──────────────────────────
1. ES → Configure → Data Enrichment → Threat Intelligence
2. Find local threat list used for blocking
3. Remove IP from list
4. If KVStore: | inputlookup threat_list.csv | search NOT ip="[IP]" | outputlookup threat_list.csv

VERIFICATION:
─────────────
1. Test connectivity from the IP
2. Check logs for successful connections
3. Notify affected party that block is removed

PREVENT RECURRENCE:
───────────────────
1. Add IP to allowlist if legitimate
2. Review detection that triggered block
3. Adjust threshold or add exclusion
