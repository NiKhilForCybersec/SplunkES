🚨 MANDATORY: Complete Data Reality Check Before Each Use Case

MFA detections are uniquely sensitive to data completeness. Missing the authenticationDetails array means MFA Fatigue detection is IMPOSSIBLE. DO NOT build detections if the reality check fails.

⚠️ Multi-Provider Complexity Warning

Most enterprises have multiple identity providers (Entra ID + CyberArk + possibly Okta/Duo). Each provider:

  • Uses different field names for the same concept (user, username, userPrincipalName)
  • Has different event types for MFA success/failure
  • Logs at different verbosity levels

Detections must be tested against EACH provider separately before cross-provider correlation.

Critical Severity | MITRE T1621 | Breaches: Uber 2022, Cisco 2022, Microsoft 2022

Key Lessons from Uber Breach:

  • The attack was technically simple—just spamming MFA prompts
  • Human fatigue is a vulnerability that technology alone doesn't solve
  • The critical detection point is: many MFA prompts in short time
  • Social engineering component (WhatsApp) wouldn't appear in authentication logs
  • Detection window: Over an hour of continuous MFA prompts before success

Why This Detection is Critical for Retail:

  • Retail employees often have MFA fatigue from legitimate high-volume prompts
  • Seasonal workers may be less security-aware
  • After-hours attacks target employees who just want the notifications to stop
  • Privileged accounts (store managers, finance) are high-value targets

1.2 Data Reality Check: Verify MFA Details Exist

SPL: Verify MFA Push Events Are Logged 
`comment("This query verifies that MFA challenge events are being captured")`

index=auth_azure sourcetype="azure:aad:signin" earliest=-7d
| spath output=mfa_methods path=authenticationDetails{}.authenticationMethod
| spath output=mfa_succeeded path=authenticationDetails{}.succeeded
| spath output=error_code path=status.errorCode

`comment("Filter to events where MFA was involved")`
| search mfa_methods=* OR error_code IN (50074, 50076, 50079, 50072)

| stats count BY mfa_methods, mfa_succeeded
| sort - count

`comment("
Expected Results:
- Should see 'Mobile app notification' or 'Microsoft Authenticator App' in mfa_methods
- Should see both 'true' and 'false' for mfa_succeeded
- If this returns empty, MFA details are NOT being logged
")`
🚨 STOP: If MFA Methods Are Empty

If the above query returns no results or mfa_methods is always empty, you CANNOT detect MFA fatigue attacks. Common causes:

  • Conditional Access policies don't require MFA (check Entra ID policies)
  • Diagnostic settings don't include SignInLogs (only NonInteractive)
  • Log retention is too short

Return to Authentication Onboarding and fix data collection before proceeding.

1.3 Detection Logic (Enterprise-Safe SPL)

SPL: MFA Fatigue Attack Detection — Correlation Search 
`comment("
===============================================================================
DETECTION: MFA Fatigue (Push Bombing) Attack
AUTHOR: Detection Engineering Team
VERSION: 1.0
MITRE: T1621 - Multi-Factor Authentication Request Generation
===============================================================================
ATTACK SIGNATURE:
- Multiple MFA challenges to same user in short window
- High ratio of denied/failed prompts
- Eventually followed by successful authentication (compromise indicator)
===============================================================================
THRESHOLDS:
- Default: 5+ MFA prompts in 15 minutes triggers alert
- High-security: 3+ MFA prompts in 15 minutes
- Automatic escalation: Any success after 5+ failures
===============================================================================
")`

index=auth_azure sourcetype="azure:aad:signin" earliest=-20m latest=now()
| spath output=user path=userPrincipalName
| spath output=src_ip path=ipAddress
| spath output=error_code path=status.errorCode
| spath output=mfa_method path=authenticationDetails{}.authenticationMethod
| spath output=mfa_result path=authenticationDetails{}.succeeded
| spath output=app path=appDisplayName
| spath output=location path=location.city

`comment("Filter to MFA-related events")`
| search error_code IN (0, 50074, 50076, 50079, 50072, 500121) 
    OR mfa_method IN ("*push*", "*notification*", "*Authenticator*", "*Mobile*")

`comment("Classify each event")`
| eval mfa_event_type = case(
    error_code==0 AND mfa_result=="true", "MFA_SUCCESS",
    error_code==0 AND mfa_result=="false", "MFA_DENIED",
    error_code IN (50076, 500121), "MFA_DENIED",
    error_code==50074, "MFA_REQUIRED",
    error_code==50079, "MFA_REGISTRATION_REQUIRED",
    true(), "OTHER"
)

`comment("Aggregate by user")`
| stats 
    count AS total_mfa_events,
    sum(eval(if(mfa_event_type=="MFA_DENIED", 1, 0))) AS mfa_denied,
    sum(eval(if(mfa_event_type=="MFA_SUCCESS", 1, 0))) AS mfa_success,
    sum(eval(if(mfa_event_type=="MFA_REQUIRED", 1, 0))) AS mfa_required,
    dc(src_ip) AS unique_source_ips,
    values(src_ip) AS source_ips,
    values(app) AS targeted_apps,
    values(location) AS locations,
    earliest(_time) AS first_event,
    latest(_time) AS last_event
    BY user

`comment("Detection threshold: 5+ MFA events indicates potential fatigue attack")`
| where total_mfa_events >= 5

`comment("Calculate attack metrics")`
| eval attack_duration_min = round((last_event - first_event) / 60, 1)
| eval prompts_per_minute = round(total_mfa_events / (attack_duration_min + 0.1), 2)
| eval denial_rate = round(mfa_denied / total_mfa_events * 100, 1)

`comment("Determine if attack succeeded (MFA approved after multiple failures)")`
| eval attack_succeeded = if(mfa_success > 0 AND mfa_denied >= 3, "YES - POTENTIAL COMPROMISE", "No - Attack blocked")

`comment("Severity assignment")`
| eval severity = case(
    attack_succeeded=="YES - POTENTIAL COMPROMISE", "critical",
    total_mfa_events >= 20, "high",
    total_mfa_events >= 10, "high",
    total_mfa_events >= 5, "medium",
    true(), "low"
)

`comment("Generate alert description")`
| eval description = case(
    attack_succeeded=="YES - POTENTIAL COMPROMISE", 
        "🚨 MFA FATIGUE ATTACK SUCCEEDED: User ".user." approved MFA after ".mfa_denied." denied prompts. IMMEDIATE INVESTIGATION REQUIRED.",
    true(),
        "MFA Fatigue attempt detected: ".total_mfa_events." MFA prompts to ".user." in ".attack_duration_min." minutes. ".mfa_denied." denied."
)

| table _time, user, total_mfa_events, mfa_denied, mfa_success, attack_duration_min, prompts_per_minute, attack_succeeded, severity, source_ips, locations, targeted_apps, description

Understanding Entra ID Error Codes

Error Code Meaning Detection Relevance
0 Success Check mfa_result for actual MFA outcome
50074 Strong authentication required MFA was triggered
50076 MFA denied by user User actively denied the push
50079 User must enroll in MFA May indicate new device/attack
500121 Authentication failed during MFA challenge MFA prompt expired or denied

| lookup mfa_fatigue_allowlist.csv user OUTPUT reason AS allowlist_reason, max_threshold

🚨 Never Fully Suppress Privileged Accounts

Even if an admin has legitimate high MFA volume, NEVER fully suppress alerts for privileged accounts. Use higher thresholds instead. An attacker specifically targets admin accounts because they know defenders might ignore the alerts.

Use Case 2: Brute Force Authentication

High Severity | MITRE T1110.001 | Target: Individual Account

2.1 Attack Context

Brute force attacks target a single account with many password guesses. Unlike password spray (many accounts, few passwords), brute force is characterized by high failure volume against one user.

2.2 Detection Logic

SPL: Brute Force Authentication Detection 
`comment("
===============================================================================
DETECTION: Brute Force Authentication
MITRE: T1110.001 - Brute Force: Password Guessing
===============================================================================
")`

index=auth_azure sourcetype="azure:aad:signin" earliest=-15m latest=now()
| spath output=user path=userPrincipalName
| spath output=src_ip path=ipAddress
| spath output=error_code path=status.errorCode
| spath output=failure_reason path=status.failureReason

`comment("Filter to authentication failures")`
| search error_code IN (50126, 50053, 50055, 50056, 50057, 50058, 50059, 50064)
`comment("
50126 = Invalid username or password
50053 = Account locked
50055 = Password expired
50057 = User disabled
")`

| stats 
    count AS failed_attempts,
    dc(src_ip) AS unique_source_ips,
    values(src_ip) AS source_ips,
    values(failure_reason) AS failure_reasons,
    earliest(_time) AS first_failure,
    latest(_time) AS last_failure
    BY user

`comment("Threshold: 10+ failures against single user")`
| where failed_attempts >= 10

| eval attack_duration_min = round((last_failure - first_failure) / 60, 1)
| eval failures_per_minute = round(failed_attempts / (attack_duration_min + 0.1), 2)

| eval severity = case(
    failed_attempts >= 100, "critical",
    failed_attempts >= 50, "high",
    failed_attempts >= 10, "medium",
    true(), "low"
)

| eval description = "Brute force attack: ".failed_attempts." failed login attempts against ".user." from ".unique_source_ips." IP(s) in ".attack_duration_min." minutes"

| table _time, user, failed_attempts, unique_source_ips, failures_per_minute, severity, source_ips, failure_reasons, description

2.3 Check for Subsequent Success

SPL: Brute Force with Subsequent Success (Compromise Indicator) 
`comment("Did the brute force attack succeed? Check for success after failures")`

index=auth_azure sourcetype="azure:aad:signin" earliest=-1h
| spath output=user path=userPrincipalName
| spath output=src_ip path=ipAddress
| spath output=error_code path=status.errorCode
| eval outcome = if(error_code==0, "success", "failure")

| stats 
    sum(eval(if(outcome=="failure", 1, 0))) AS failures,
    sum(eval(if(outcome=="success", 1, 0))) AS successes,
    values(src_ip) AS ips
    BY user

| where failures >= 10 AND successes > 0
| eval alert = "⚠️ POTENTIAL COMPROMISE: ".user." had ".failures." failures followed by ".successes." successful login(s)"
| table user, failures, successes, ips, alert

3.2 Detection Logic

SPL: Password Spray Detection 
`comment("
===============================================================================
DETECTION: Password Spray Attack
MITRE: T1110.003 - Brute Force: Password Spraying
===============================================================================
SIGNATURE: Single IP attempting to authenticate as many different users
with low failure count per user (avoiding lockout)
===============================================================================
")`

index=auth_azure sourcetype="azure:aad:signin" earliest=-30m latest=now()
| spath output=user path=userPrincipalName
| spath output=src_ip path=ipAddress
| spath output=error_code path=status.errorCode

`comment("Filter to authentication failures")`
| search error_code IN (50126, 50053)

`comment("Aggregate by source IP")`
| stats 
    count AS total_failures,
    dc(user) AS unique_users_targeted,
    values(user) AS targeted_users,
    avg(eval(1)) AS avg_failures_per_user
    BY src_ip

`comment("Password spray signature: many users, few attempts each")`
| where unique_users_targeted >= 10 AND total_failures >= 10

`comment("Calculate spray ratio")`
| eval spray_ratio = round(unique_users_targeted / total_failures * 100, 1)
| eval failures_per_user = round(total_failures / unique_users_targeted, 1)

`comment("High spray ratio = likely password spray (not brute force)")`
| eval attack_type = if(spray_ratio >= 50, "Password Spray", "Mixed/Brute Force")

| eval severity = case(
    unique_users_targeted >= 100, "critical",
    unique_users_targeted >= 50, "high",
    unique_users_targeted >= 10, "medium",
    true(), "low"
)

| eval description = attack_type.": ".src_ip." attempted login to ".unique_users_targeted." unique accounts (".failures_per_user." attempts/account avg)"

| table _time, src_ip, unique_users_targeted, total_failures, failures_per_user, spray_ratio, attack_type, severity, description

3.3 Successful Password Spray Detection

SPL: Password Spray with Success (Compromise) 
`comment("Find accounts compromised by password spray")`

index=auth_azure sourcetype="azure:aad:signin" earliest=-1h
| spath output=user path=userPrincipalName
| spath output=src_ip path=ipAddress
| spath output=error_code path=status.errorCode
| eval outcome = if(error_code==0, "success", "failure")

| stats 
    sum(eval(if(outcome=="failure", 1, 0))) AS failures,
    sum(eval(if(outcome=="success", 1, 0))) AS successes,
    dc(user) AS users_attempted,
    values(eval(if(outcome=="success", user, null()))) AS compromised_users
    BY src_ip

| where users_attempted >= 10 AND successes > 0

| eval alert = "🚨 PASSWORD SPRAY SUCCESS: ".src_ip." compromised ".successes." account(s) after ".failures." failures across ".users_attempted." users"

| table src_ip, users_attempted, failures, successes, compromised_users, alert

Use Case 4: Impossible Travel Detection

Medium-High Severity | MITRE T1078 | Indicator: Account Compromise

4.1 Attack Context

Impossible travel detects when a user authenticates from two geographically distant locations within a timeframe that makes physical travel impossible. This often indicates credential theft or account sharing.

4.2 Detection Logic

SPL: Impossible Travel Detection 
`comment("
===============================================================================
DETECTION: Impossible Travel
MITRE: T1078 - Valid Accounts
===============================================================================
LOGIC: User authenticates from two locations that would require travel
faster than physically possible (e.g., London and Tokyo 30 min apart)
===============================================================================
")`

index=auth_azure sourcetype="azure:aad:signin" earliest=-24h latest=now()
| spath output=user path=userPrincipalName
| spath output=src_ip path=ipAddress
| spath output=city path=location.city
| spath output=country path=location.countryOrRegion
| spath output=latitude path=location.geoCoordinates.latitude
| spath output=longitude path=location.geoCoordinates.longitude
| spath output=error_code path=status.errorCode

`comment("Only successful logins for impossible travel")`
| search error_code==0

`comment("Need location data")`
| where isnotnull(city) AND isnotnull(country)

| sort user, _time
| streamstats current=f last(_time) AS prev_time, last(city) AS prev_city, last(country) AS prev_country, last(latitude) AS prev_lat, last(longitude) AS prev_lon BY user

`comment("Calculate time difference and distance")`
| eval time_diff_hours = round((_time - prev_time) / 3600, 2)
| eval time_diff_min = round((_time - prev_time) / 60, 0)

`comment("Haversine formula for distance calculation")`
| eval lat1_rad = latitude * 3.14159 / 180
| eval lat2_rad = prev_lat * 3.14159 / 180
| eval lon_diff = (longitude - prev_lon) * 3.14159 / 180
| eval lat_diff = (latitude - prev_lat) * 3.14159 / 180
| eval a = pow(sin(lat_diff/2), 2) + cos(lat1_rad) * cos(lat2_rad) * pow(sin(lon_diff/2), 2)
| eval distance_km = 2 * 6371 * asin(sqrt(a))

`comment("Calculate required speed")`
| eval required_speed_kmh = if(time_diff_hours > 0, round(distance_km / time_diff_hours, 0), 9999)

`comment("Impossible travel: >800 km/h (faster than commercial flights)")`
| where distance_km > 500 AND required_speed_kmh > 800

| eval severity = case(
    required_speed_kmh > 2000, "high",
    required_speed_kmh > 1000, "medium",
    true(), "low"
)

| eval description = "Impossible travel: ".user." logged in from ".city." (".country.") and ".prev_city." (".prev_country.") ".time_diff_min." minutes apart (".round(distance_km,0)." km, would require ".required_speed_kmh." km/h)"

| table _time, user, city, country, prev_city, prev_country, time_diff_min, distance_km, required_speed_kmh, severity, description

Use Case 5: Privileged Account MFA Failure

High Severity | MITRE T1078.004 | Target: Admin Accounts

5.1 Attack Context

Privileged accounts (Domain Admins, Global Admins, DBA accounts) are high-value targets. Any MFA failure against these accounts warrants immediate investigation—attackers specifically target admin credentials.

5.2 Detection Logic (CyberArk)

SPL: Privileged Account MFA Failure (CyberArk) 
`comment("
===============================================================================
DETECTION: Privileged Account MFA Failure
MITRE: T1078.004 - Valid Accounts: Cloud Accounts
===============================================================================
LOGIC: Any MFA failure against privileged/admin accounts should alert.
Lower threshold than standard accounts due to high-value target.
===============================================================================
")`

index=auth_cyberark sourcetype="cyberark:identity" earliest=-15m latest=now()
| search event_type IN ("mfa_*", "authentication_*")
| search result IN ("denied", "failed", "timeout", "rejected")

| lookup privileged_accounts.csv user OUTPUT is_privileged, account_type

`comment("Only privileged accounts")`
| where is_privileged=="true"

| stats 
    count AS mfa_failures,
    values(event_type) AS failure_types,
    values(result) AS results,
    dc(src_ip) AS unique_sources
    BY user, account_type

`comment("Lower threshold for privileged accounts: even 2 failures is concerning")`
| where mfa_failures >= 2

| eval severity = "high"
| eval description = "🚨 PRIVILEGED ACCOUNT MFA FAILURE: ".user." (".account_type.") had ".mfa_failures." MFA failures"

| table _time, user, account_type, mfa_failures, failure_types, unique_sources, severity, description

Common Authentication Detection Failure Modes

These are the most common reasons authentication detections fail in production. Review before deployment.

Failure Mode 1: Missing MFA Event Details

Symptom

MFA Fatigue detection returns zero results despite known MFA prompts occurring.

Cause: Entra ID sign-in logs don't include the authenticationDetails array by default in all configurations.

Diagnosis:

SPL: Verify MFA Details Exist 
index=auth_azure sourcetype="azure:aad:signin" earliest=-24h
| spath output=auth_details path=authenticationDetails{}
| stats count AS total_events, 
        count(eval(isnotnull(auth_details))) AS events_with_mfa_details
| eval mfa_detail_rate = round(events_with_mfa_details/total_events*100, 1)."%"
| eval status = if(events_with_mfa_details > 0, "✓ MFA details present", "✗ NO MFA DETAILS - Detection impossible")

Fix: Verify Azure diagnostic settings include "SignInLogs" category with full detail. Check if Entra ID P1/P2 license is present (required for some log details).

Failure Mode 2: Username Format Mismatch Across Providers

Symptom

Cross-provider correlation returns zero results for users that should match.

Cause: Different providers use different username formats:

  • Entra ID: john.smith@contoso.com (UPN)
  • CyberArk: john.smith (SAMAccountName)
  • Windows AD: CONTOSO\john.smith (Domain\SAM)

Diagnosis:

SPL: Compare Username Formats Across Sources 
| multisearch 
    [search index=auth_azure sourcetype="azure:aad:signin" earliest=-1h | head 100 | eval source="Entra ID" | table source, userPrincipalName]
    [search index=auth_cyberark sourcetype="cyberark:identity" earliest=-1h | head 100 | eval source="CyberArk" | table source, user]
| stats values(*) AS * BY source
| transpose

Fix: Create identity lookup table that maps all username formats. Use | lookup identity_mapping.csv to normalize before correlation.

Failure Mode 3: Time Window Too Narrow for Latency

Symptom

MFA Fatigue detection misses attacks because MFA prompts appear spread across time.

Cause: Detection window (e.g., 5 minutes) is narrower than the ingestion latency difference between providers.

Diagnosis:

SPL: Compare Latency Across Auth Sources 
| multisearch
    [search index=auth_azure sourcetype="azure:aad:signin" earliest=-4h | eval source="Entra ID"]
    [search index=auth_cyberark sourcetype="cyberark:identity" earliest=-4h | eval source="CyberArk"]
| eval latency = _indextime - _time
| stats avg(latency) AS avg_latency, perc95(latency) AS p95_latency BY source
| eval avg_latency_min = round(avg_latency/60, 1)
| eval p95_latency_min = round(p95_latency/60, 1)

Fix: If Provider A has 2-min latency and Provider B has 8-min latency, your correlation window must be at least 10 minutes to reliably correlate events.

Failure Mode 4: Privileged Account List Stale

Symptom

Privileged account detection misses admins or alerts on former admins.

Cause: The privileged_accounts.csv lookup is not updated when admins are added/removed.

Diagnosis:

SPL: Compare Lookup to Current Entra ID Admins 
`comment("Get current Global Admins from Entra ID audit logs")`
index=auth_azure sourcetype="azure:aad:audit" "Add member to role" "Global Administrator" earliest=-30d
| spath output=added_user path=targetResources{}.userPrincipalName
| dedup added_user
| lookup privileged_accounts.csv user AS added_user OUTPUT is_privileged
| where isnull(is_privileged)
| eval warning = "⚠️ Admin in Entra ID but NOT in privileged_accounts.csv lookup"
| table added_user, warning

Fix: Automate privileged account lookup refresh from Entra ID group membership. Schedule weekly sync at minimum.

Failure Mode 5: VPN/Proxy Causing False Impossible Travel

Symptom

Impossible travel alerts flood SOC for users on VPN or corporate proxy.

Cause: User's real location is masked by VPN/proxy IP, making every login appear from datacenter location.

Diagnosis:

SPL: Find High-Volume Locations (Likely VPN/Proxy) 
index=auth_azure sourcetype="azure:aad:signin" earliest=-7d
| iplocation ipAddress
| stats dc(userPrincipalName) AS unique_users, count AS total_logins BY City, Country, ipAddress
| where unique_users > 50
| sort - unique_users
| eval likely_vpn = "⚠️ High user count from single IP = likely VPN/Proxy"

Fix: Add VPN egress IPs and corporate proxy IPs to impossible travel allowlist. Consider using Entra ID's built-in "atypical travel" which accounts for known locations.
