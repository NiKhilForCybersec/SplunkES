SPL: WAF Data Reality Check 
index=waf_akamai sourcetype=akamai:siem earliest=-24h
| head 10000
| eval has_src = if(isnotnull(src) AND src!="", 1, 0)
| eval has_dest = if(isnotnull(dest) OR isnotnull('httpMessage.host'), 1, 0)
| eval has_action = if(isnotnull(action) OR isnotnull('attackData.action'), 1, 0)
| eval has_url = if(isnotnull(url) OR isnotnull('httpMessage.path'), 1, 0)
| eval has_rule = if(isnotnull('attackData.rules{}.ruleId') OR isnotnull('attackData.ruleActions{}.ruleId'), 1, 0)
| eval has_method = if(isnotnull(http_method) OR isnotnull('httpMessage.method'), 1, 0)
| eval has_status = if(isnotnull(status) OR isnotnull('httpMessage.status'), 1, 0)
| eval has_user_agent = if(isnotnull(http_user_agent) OR isnotnull('httpMessage.requestHeaders.User-Agent'), 1, 0)
| stats 
    count AS total_events,
    sum(has_src) AS with_src,
    sum(has_dest) AS with_dest,
    sum(has_action) AS with_action,
    sum(has_url) AS with_url,
    sum(has_rule) AS with_rule,
    sum(has_method) AS with_method,
    sum(has_status) AS with_status,
    sum(has_user_agent) AS with_user_agent
| foreach with_* 
    [eval <<FIELD>>_pct = round('<<FIELD>>'/total_events*100, 1)."%"]
| table total_events, with_src_pct, with_dest_pct, with_action_pct, with_url_pct, with_rule_pct, with_method_pct, with_status_pct, with_user_agent_pct

Minimum Thresholds for Detection Viability:

  • src (source IP): Must be >99% — cannot detect attacks without attacker IP
  • action: Must be >99% — cannot distinguish blocked vs. allowed
  • url/path: Must be >95% — needed for attack pattern analysis
  • rule: Should be >80% — helps identify attack type
🚨 STOP If Data Check Fails

If critical fields are below threshold, DO NOT proceed with detection implementation. Return to Akamai WAF Onboarding and fix field extraction issues first.

High Severity | MITRE T1190 | Retail Impact: Data Breach Risk

SQL injection against retail web applications typically follows this pattern:

Why This Matters in Retail:

  • Retail databases contain customer PII, payment data, and loyalty program information
  • A successful SQLi can lead to mass data breach and PCI compliance violations
  • Even blocked attacks indicate active targeting—attackers will try bypass techniques
  • Patterns of SQLi attempts often precede successful breaches (attackers testing defenses)

Why WAF Alone Doesn't Stop This:

  • WAF rules can be bypassed with encoding, case variation, or novel payloads
  • WAF in "alert mode" doesn't block, just logs
  • Application vulnerabilities may allow SQLi that WAF rules don't cover
  • WAF doesn't protect against insider threats or compromised admin credentials

| sort - count

Expected Output: You should see rule IDs and messages containing "SQL", "injection", "SQLi". If this returns zero results, either:

  • No SQL injection attempts have occurred (unlikely for internet-facing retail site)
  • WAF rules for SQLi are not enabled
  • Field extraction is broken — check raw events

1.3 Detection Logic (Enterprise-Safe SPL)

SPL: SQL Injection Campaign Detection — Correlation Search 
`comment("
===============================================================================
DETECTION: SQL Injection Campaign
AUTHOR: Detection Engineering Team
VERSION: 1.0
LAST_UPDATED: 2024-01-15
MITRE: T1190 - Exploit Public-Facing Application
===============================================================================
LOGIC: Detects multiple SQL injection attempts from a single source IP within
a short time window. Threshold set conservatively to reduce false positives
from legitimate security scanners while catching real attack campaigns.
===============================================================================
TUNING NOTES:
- Threshold of 5 in 10 minutes catches most attacks while filtering scanners
- Adjust threshold UP if authorized scanners trigger alerts
- DO NOT adjust threshold below 3 — will generate excessive noise
===============================================================================
")`

index=waf_akamai sourcetype=akamai:siem earliest=-15m latest=now()
| spath output=action path=attackData.action
| spath output=rules path=attackData.rules{}.ruleId
| spath output=rule_msg path=attackData.rules{}.ruleMessage
| spath output=src path=attackData.clientIP
| spath output=dest path=httpMessage.host
| spath output=url path=httpMessage.path
| spath output=method path=httpMessage.method

`comment("Filter to SQL injection related rules")`
| search rule_msg=*SQL* OR rule_msg=*injection* OR rules IN ("950001", "950007", "950901", "959071", "959072", "959073")

`comment("Aggregate by source IP")`
| stats 
    count AS sqli_attempts,
    dc(url) AS unique_urls_targeted,
    dc(dest) AS unique_hosts_targeted,
    values(action) AS actions,
    values(url) AS targeted_urls,
    values(rule_msg) AS rule_messages,
    latest(_time) AS last_attempt,
    earliest(_time) AS first_attempt
    BY src

`comment("Apply detection threshold — minimum 5 attempts")`
| where sqli_attempts >= 5

`comment("Calculate attack duration and velocity")`
| eval attack_duration_sec = last_attempt - first_attempt
| eval attack_velocity = round(sqli_attempts / (attack_duration_sec + 1) * 60, 2)

`comment("Determine if attack was fully blocked")`
| eval fully_blocked = if(mvcount(mvfilter(match(actions, "deny|block"))) == mvcount(actions), "Yes", "No - SOME REQUESTS MAY HAVE SUCCEEDED")

`comment("Assign severity based on volume and blocking status")`
| eval severity = case(
    fully_blocked=="No - SOME REQUESTS MAY HAVE SUCCEEDED", "critical",
    sqli_attempts >= 100, "high",
    sqli_attempts >= 20, "high",
    sqli_attempts >= 5, "medium",
    true(), "low"
)

`comment("Build alert description")`
| eval description = "SQL Injection campaign detected: ".sqli_attempts." attempts from ".src." targeting ".unique_hosts_targeted." host(s). ".fully_blocked." blocked."

| table _time, src, sqli_attempts, unique_urls_targeted, unique_hosts_targeted, fully_blocked, severity, attack_velocity, targeted_urls, rule_messages, description

SPL Explanation (Why Each Clause Exists)

Clause Purpose Why It Matters
earliest=-15m 10-minute window with 5-min overlap Catches attacks spanning schedule boundaries
search rule_msg=*SQL* Filter to SQLi-related events Reduces noise from other WAF rules
where sqli_attempts >= 5 Minimum threshold Single probes are noise; 5+ indicates campaign
fully_blocked calculation Identify if any requests succeeded Unblocked requests = potential compromise
severity escalation Dynamic severity based on context Unblocked attacks are always critical

Safe Defaults and Alternate Thresholds

Environment Threshold Rationale
Standard retail (this detection) 5 attempts / 10 min Balances detection vs. scanner noise
High-security (PCI environment) 3 attempts / 10 min Lower threshold, accept more false positives
High-traffic (Black Friday) 10 attempts / 10 min Reduce noise during traffic spikes

1.4 Historical Backtesting

Before enabling this detection in production, backtest against historical data to understand baseline and tune thresholds.

SPL: SQLi Detection Backtest (30 Days) 
`comment("Backtest: How many alerts would this detection have generated?")`

index=waf_akamai sourcetype=akamai:siem earliest=-30d latest=now()
| spath output=rule_msg path=attackData.rules{}.ruleMessage
| spath output=src path=attackData.clientIP
| search rule_msg=*SQL* OR rule_msg=*injection*

`comment("Bucket into 10-minute windows")`
| bin _time span=10m

`comment("Count per source per window")`
| stats count AS attempts BY _time, src

`comment("Apply same threshold as detection")`
| where attempts >= 5

`comment("Summarize: How many alerts per day?")`
| timechart span=1d count AS daily_alerts

`comment("Expected result: 0-10 alerts/day is manageable; 50+/day needs tuning")`

Backtest Interpretation:

  • 0-5 alerts/day: Detection is well-tuned. Proceed to monitoring mode.
  • 5-20 alerts/day: Acceptable for initial deployment. Plan for tuning.
  • 20-50 alerts/day: High volume. Identify top sources—may need allowlist for scanners.
  • >50 alerts/day: Too noisy. Increase threshold or add filters before deployment.

Why Credential Stuffing Works Against Retail:

  • Customers reuse passwords across sites — credentials from unrelated breaches work
  • Retail loyalty accounts have monetary value (points, gift cards, saved payment)
  • E-commerce sites prioritize frictionless login over security
  • Attack volume is massive — even 0.1% success rate yields thousands of compromised accounts

2.3 Detection Logic

SPL: Credential Stuffing Attack Detection 
`comment("
===============================================================================
DETECTION: Credential Stuffing Attack
MITRE: T1110.004 - Credential Stuffing
===============================================================================
LOGIC: Detects high volume of failed login attempts from single source IP,
with additional scoring for distributed attacks and bot-like behavior.
===============================================================================
")`

index=waf_akamai sourcetype=akamai:siem earliest=-15m latest=now()
| spath output=url path=httpMessage.path
| spath output=method path=httpMessage.method
| spath output=status path=httpMessage.status
| spath output=src path=attackData.clientIP
| spath output=user_agent path=httpMessage.requestHeaders.User-Agent
| spath output=action path=attackData.action
| spath output=dest path=httpMessage.host

`comment("Filter to login endpoint POST requests")`
| search url IN ("*/login*", "*/signin*", "*/auth*", "*/authenticate*", "*/api/v*/auth*") 
| search method="POST"

`comment("Identify failed vs successful attempts by HTTP status")`
| eval auth_result = case(
    status IN ("200", "201", "302"), "success",
    status IN ("401", "403", "400", "429"), "failure",
    true(), "unknown"
)

`comment("Aggregate by source IP")`
| stats 
    count AS total_attempts,
    sum(eval(if(auth_result=="failure", 1, 0))) AS failed_attempts,
    sum(eval(if(auth_result=="success", 1, 0))) AS successful_attempts,
    dc(user_agent) AS unique_user_agents,
    dc(dest) AS unique_targets,
    values(dest) AS targeted_hosts,
    latest(_time) AS last_seen
    BY src

`comment("Calculate metrics")`
| eval failure_rate = round(failed_attempts / total_attempts * 100, 1)
| eval success_rate = round(successful_attempts / total_attempts * 100, 1)

`comment("Detection thresholds")`
| where total_attempts >= 20 AND failure_rate >= 80

`comment("Scoring: Higher score = more confidence in attack")`
| eval attack_score = 0
| eval attack_score = attack_score + case(total_attempts >= 1000, 30, total_attempts >= 100, 20, total_attempts >= 20, 10, true(), 0)
| eval attack_score = attack_score + case(failure_rate >= 99, 30, failure_rate >= 95, 20, failure_rate >= 80, 10, true(), 0)
| eval attack_score = attack_score + case(unique_user_agents >= 10, 20, unique_user_agents >= 5, 10, unique_user_agents == 1, 5, true(), 0)
| eval attack_score = attack_score + if(successful_attempts > 0, 20, 0)

`comment("Severity based on score and successful logins")`
| eval severity = case(
    successful_attempts > 0, "critical",
    attack_score >= 70, "high",
    attack_score >= 40, "medium",
    true(), "low"
)

`comment("Alert if score threshold met")`
| where attack_score >= 40

| eval description = "Credential stuffing detected: ".total_attempts." attempts (".failure_rate."% failed) from ".src.". ".successful_attempts." successful logins."

| table _time, src, total_attempts, failed_attempts, successful_attempts, failure_rate, unique_user_agents, attack_score, severity, targeted_hosts, description

2.4 Correlation with Authentication Logs

For complete visibility, correlate WAF detections with backend authentication logs to identify which accounts were compromised:

SPL: Cross-Source Credential Stuffing Correlation 
`comment("Find accounts that had successful login following credential stuffing from same IP")`

index=waf_akamai sourcetype=akamai:siem earliest=-1h
| spath output=src path=attackData.clientIP
| spath output=url path=httpMessage.path
| search url IN ("*/login*", "*/signin*") 
| stats count AS waf_events BY src

| join type=left src 
    [search index=auth_* sourcetype IN ("azure:aad:signin", "app:auth:*") earliest=-1h
     | search action="success"
     | stats count AS successful_logins, values(user) AS compromised_users BY src]

| where waf_events >= 20 AND successful_logins > 0

| eval alert = "⚠️ POTENTIAL ACCOUNT COMPROMISE: ".successful_logins." successful logins from credential stuffing source"

| table src, waf_events, successful_logins, compromised_users, alert

2.5 Monitoring-Only Mode

Follow the same monitoring-only process as SQLi detection:

  1. Deploy as scheduled report (not alert)
  2. Collect results to summary index for trend analysis
  3. Monitor for 1-2 weeks
  4. Review false positive rate and tune thresholds
  5. Promote to production when criteria met

2.6 False Positive Patterns in Retail

Pattern Why It Happens Mitigation
Corporate proxy IP with many users All users appear from same IP; multiple login failures look like attack Allowlist known corporate egress IPs
Mobile carrier NAT Thousands of mobile users share IP; normal failures aggregate Increase threshold for known carrier ranges
Password reset campaigns Mass password reset causes login failures as users adapt Suppress during planned password campaigns
Load testing Performance tests hit login endpoints Allowlist load test source IPs; time-based suppression
SSO integration issues Broken SSO causes cascade of failures Correlate with SSO health metrics; don't alert during known issues

Use Case 3: Rate Limiting / DDoS Indicator

Medium Severity | MITRE T1498/T1499 | Retail Impact: Service Availability

3.1 Attack Context

Rate limiting events indicate sources exceeding configured thresholds. This can signal DDoS attacks, aggressive scraping, or API abuse. In retail, this often manifests during:

  • Flash sales: Bots attempting to buy limited inventory faster than humans
  • Price scraping: Competitors scraping product/price data at scale
  • Inventory checking: Scalpers checking stock levels continuously
  • DDoS attacks: Volumetric attacks overwhelming infrastructure

3.2 Detection Logic

SPL: Rate Limit / DDoS Indicator Detection 
`comment("
===============================================================================
DETECTION: Rate Limiting / DDoS Indicator
MITRE: T1498 (Network DoS), T1499 (Application DoS)
===============================================================================
")`

index=waf_akamai sourcetype=akamai:siem earliest=-10m latest=now()
| spath output=action path=attackData.action
| spath output=src path=attackData.clientIP
| spath output=dest path=httpMessage.host
| spath output=url path=httpMessage.path
| spath output=status path=httpMessage.status

`comment("Filter to rate-limited requests")`
| search action IN ("rate_limit", "deny") OR status="429"

| stats 
    count AS rate_limited_requests,
    dc(url) AS unique_paths,
    dc(dest) AS unique_hosts,
    values(dest) AS targeted_hosts,
    values(url) AS sample_paths
    BY src

`comment("Detection threshold: 100+ rate-limited requests in 10 min")`
| where rate_limited_requests >= 100

`comment("Calculate request velocity")`
| eval requests_per_second = round(rate_limited_requests / 600, 2)

`comment("Severity based on volume")`
| eval severity = case(
    requests_per_second >= 100, "high",
    requests_per_second >= 10, "medium",
    true(), "low"
)

`comment("Classify attack type")`
| eval attack_type = case(
    requests_per_second >= 100, "Volumetric DDoS",
    requests_per_second >= 10 AND unique_paths <= 5, "Targeted Application Attack",
    unique_paths >= 50, "Aggressive Scraping/Crawling",
    true(), "Rate Limit Violation"
)

| eval description = attack_type.": ".rate_limited_requests." rate-limited requests from ".src." (".requests_per_second." req/sec)"

| table _time, src, rate_limited_requests, requests_per_second, unique_paths, attack_type, severity, targeted_hosts, description

3.3 Seasonal Considerations for Retail

📅 Adjust Thresholds for Retail Events

Retail traffic patterns have predictable spikes. Adjust detection thresholds to avoid alert fatigue during high-traffic periods:

Period Expected Traffic Recommended Threshold Adjustment
Normal operations Baseline 100 requests / 10 min (default)
Black Friday / Cyber Monday 10-50x baseline 500-1000 requests / 10 min
Boxing Day (Canada) 5-20x baseline 300-500 requests / 10 min
Flash sales / Limited drops Variable, often 10x+ Consider time-based suppression
New product launches 5-10x baseline 200-300 requests / 10 min
SPL: Dynamic Threshold Based on Time 
`comment("Adjust threshold based on known high-traffic periods")`

| eval threshold = case(
    `comment("Black Friday: 4th Thursday of November +/- 3 days")`
    strftime(_time, "%m") == "11" AND tonumber(strftime(_time, "%d")) >= 22 AND tonumber(strftime(_time, "%d")) <= 28, 500,
    
    `comment("Boxing Day: Dec 26")`
    strftime(_time, "%m-%d") == "12-26", 300,
    
    `comment("Default threshold")`
    true(), 100
)

| where rate_limited_requests >= threshold

Use Case 4: Malicious Bot Activity

Medium Severity | MITRE T1595 | Retail Impact: Inventory Fraud, Scraping

4.1 Attack Context

Akamai Bot Manager classifies traffic as human, good bot (search engines), or bad bot. Bad bot activity in retail includes:

  • Scalper bots: Automated purchasing of limited inventory (sneakers, GPUs, concert tickets)
  • Price scrapers: Competitors monitoring pricing for competitive intelligence
  • Account creation bots: Creating fake accounts for promotion abuse
  • Gift card checkers: Testing stolen gift card numbers at scale

4.2 Detection Logic

SPL: Malicious Bot Detection 
index=waf_akamai sourcetype=akamai:siem earliest=-15m latest=now()
| spath output=bot_score path=botData.botScore
| spath output=bot_category path=botData.category
| spath output=src path=attackData.clientIP
| spath output=dest path=httpMessage.host
| spath output=url path=httpMessage.path
| spath output=user_agent path=httpMessage.requestHeaders.User-Agent

`comment("Filter to detected bot traffic")`
| search bot_score >= 80 OR bot_category IN ("bad_bot", "malicious", "impersonator")

| stats 
    count AS bot_requests,
    dc(url) AS unique_paths,
    values(bot_category) AS bot_categories,
    values(user_agent) AS user_agents,
    values(url) AS sample_urls
    BY src, dest

| where bot_requests >= 50

`comment("Classify bot behavior")`
| eval bot_behavior = case(
    match(sample_urls, "(?i)(add-to-cart|checkout|purchase)"), "Scalper Bot",
    match(sample_urls, "(?i)(price|product|catalog)"), "Scraper Bot",
    match(sample_urls, "(?i)(account|register|signup)"), "Account Creation Bot",
    match(sample_urls, "(?i)(gift|card|balance)"), "Gift Card Checker",
    true(), "General Bad Bot"
)

| eval severity = case(
    bot_behavior IN ("Scalper Bot", "Gift Card Checker"), "high",
    bot_requests >= 500, "high",
    bot_requests >= 100, "medium",
    true(), "low"
)

| table _time, src, dest, bot_requests, bot_behavior, bot_categories, severity, sample_urls

Use Case 5: Command Injection Attempt

Critical Severity | MITRE T1059 | Retail Impact: Full System Compromise

5.1 Attack Context

Command injection is one of the most severe web attacks. Unlike SQLi which targets the database, command injection targets the operating system. A successful command injection can lead to complete server compromise, lateral movement, and data exfiltration.

Any command injection attempt—even blocked—warrants immediate investigation.

5.2 Detection Logic

SPL: Command Injection Detection (Critical Alert) 
`comment("
===============================================================================
DETECTION: Command Injection Attempt
MITRE: T1059 - Command and Scripting Interpreter
SEVERITY: CRITICAL — Even blocked attempts require investigation
===============================================================================
")`

index=waf_akamai sourcetype=akamai:siem earliest=-10m latest=now()
| spath output=rule_msg path=attackData.rules{}.ruleMessage
| spath output=rules path=attackData.rules{}.ruleId
| spath output=action path=attackData.action
| spath output=src path=attackData.clientIP
| spath output=dest path=httpMessage.host
| spath output=url path=httpMessage.path
| spath output=method path=httpMessage.method

`comment("Filter to command injection rules")`
| search rule_msg IN ("*command*injection*", "*os*command*", "*remote*code*", "*rce*", "*shell*injection*")
    OR rules IN ("950002", "950006", "959001", "959002")

`comment("Even single attempt is concerning for command injection")`
| stats 
    count AS attempts,
    values(action) AS actions,
    values(rule_msg) AS attack_signatures,
    values(url) AS targeted_urls,
    values(method) AS methods
    BY src, dest

`comment("Check if any requests were NOT blocked")`
| eval all_blocked = if(mvcount(mvfilter(match(actions, "deny|block"))) == mvcount(actions), "Yes", "NO - POTENTIAL COMPROMISE")

`comment("Always critical severity for command injection")`
| eval severity = if(all_blocked=="Yes", "high", "critical")

| eval description = "⚠️ COMMAND INJECTION ATTEMPT: ".attempts." attempts from ".src." targeting ".dest.". Blocked: ".all_blocked

| table _time, src, dest, attempts, all_blocked, severity, attack_signatures, targeted_urls, description

5.3 Triage — Command Injection is ALWAYS Urgent

🚨 Command Injection Response Protocol

Unlike other WAF detections where blocked = lower priority, command injection requires immediate investigation regardless of blocking status:

  1. If blocked: Investigate targeted endpoint for vulnerabilities. Attacker may try alternate payloads.
  2. If unblocked: IMMEDIATE ESCALATION to IR team. Assume system compromise until proven otherwise.
  3. Check application logs for the targeted endpoint during same timeframe
  4. Review server processes if any requests reached the application

Common WAF Detection Failure Modes

These are the most common reasons WAF detections fail in production. Review before deployment.

Failure Mode 1: Missing Security Configurations

Symptom

Detection works for some sites but misses attacks on others.

Cause: Not all Akamai security configurations are enabled for SIEM Integration.

Diagnosis:

SPL: Find Which Security Configs Are Sending Events 
index=waf_akamai sourcetype=akamai:siem earliest=-7d
| spath output=config_id path=attackData.configId
| stats count, dc(src) AS unique_attackers BY config_id
| sort - count

Fix: Compare against your Akamai security configuration inventory. Enable SIEM Integration for missing configs.

Failure Mode 2: Threshold Too Low for Traffic Volume

Symptom

Detection generates hundreds of alerts during promotional events or traffic spikes.

Cause: Thresholds set based on normal traffic don't account for legitimate spikes.

Diagnosis:

SPL: Analyze Detection Trigger Volume Over Time 
index=waf_akamai sourcetype=akamai:siem earliest=-30d
| spath output=src path=attackData.clientIP
| spath output=action path=attackData.action
| where action="deny"
| timechart span=1d dc(src) AS unique_blocked_ips
| eventstats avg(unique_blocked_ips) AS baseline, stdev(unique_blocked_ips) AS stdev
| eval anomaly = if(unique_blocked_ips > baseline + (3 * stdev), "SPIKE", "normal")

Fix: Use dynamic thresholds (standard deviations above baseline) instead of static counts, or add retail calendar awareness to exclude promotional periods.

Failure Mode 3: CDN/Proxy IP Masking Real Source

Symptom

Multiple "attacks" appear from same IP, but it's actually a legitimate CDN or proxy.

Cause: Akamai logs the connecting IP which may be a downstream CDN, not the real attacker IP.

Diagnosis:

SPL: Find High-Volume Source IPs 
index=waf_akamai sourcetype=akamai:siem earliest=-7d
| spath output=src path=attackData.clientIP
| stats count BY src
| where count > 10000
| iplocation src
| table src, count, Country, City
`comment("Look for internal networks, CDN providers, or partner IPs")`

Fix: Add known CDN/proxy IPs to allowlist. Check for X-Forwarded-For or True-Client-IP headers if available.

Failure Mode 4: Rule Noise from Security Scanners

Symptom

Constant stream of SQL injection / XSS alerts from the same IP ranges.

Cause: Legitimate security scanning (vulnerability assessments, pen tests) triggering WAF rules.

Diagnosis:

SPL: Identify Systematic Scanning Patterns 
index=waf_akamai sourcetype=akamai:siem earliest=-24h
| spath output=src path=attackData.clientIP
| spath output=rule_id path=attackData.rules{}.ruleId
| stats dc(rule_id) AS unique_rules, values(rule_id) AS rules_triggered BY src
| where unique_rules > 10
| sort - unique_rules
`comment("High unique rule count = likely scanner, not targeted attack")`

Fix: Coordinate with security team to get approved scanner IP ranges. Add to time-bounded allowlist during scheduled scans.

Retail Traffic Pattern Awareness

⚠️ WAF Detections Must Account for Retail Traffic Patterns

Retail websites have extreme traffic variation. Static thresholds will fail. Consider these patterns:

Period Traffic Multiplier Detection Impact Recommendation
Black Friday / Cyber Monday 5-20x normal All volume-based detections will fire Use percentage-based thresholds or disable volume alerts
Flash Sales 2-5x normal Rate limiting detections trigger Pre-tune thresholds or add temporary allowances
Weekly Flyer Launch 1.5-2x normal Minor impact Baseline should account for weekly patterns
Overnight (2-6 AM) 0.1x normal Low traffic makes attacks more visible Lower thresholds acceptable overnight

Dynamic Baseline Query for Thresholds

SPL: Calculate Dynamic Threshold Based on Time of Day/Week 
`comment("Build baseline that accounts for day-of-week and hour-of-day patterns")`

index=waf_akamai sourcetype=akamai:siem earliest=-30d
| spath output=action path=attackData.action
| where action="deny"
| eval day_of_week = strftime(_time, "%A")
| eval hour_of_day = strftime(_time, "%H")
| stats count BY day_of_week, hour_of_day
| stats avg(count) AS avg_blocks, stdev(count) AS stdev_blocks BY day_of_week, hour_of_day
| eval dynamic_threshold = round(avg_blocks + (3 * stdev_blocks), 0)
| table day_of_week, hour_of_day, avg_blocks, stdev_blocks, dynamic_threshold

`comment("Use this lookup to set time-aware thresholds in your detections")`

Global Rollback Procedures

Use these procedures to safely disable any WAF detection:

Emergency Disable (All WAF Detections)

Procedure: Disable All WAF Correlation Searches 
SCENARIO: WAF detections generating excessive load or false positives

OPTION 1: Disable Individual Detection
──────────────────────────────────────
1. ES → Configure → Content → Content Management
2. Filter: "WAF" or specific detection name
3. Select detection → Edit → Enabled = No → Save

OPTION 2: Disable All WAF Detections
────────────────────────────────────
1. ES → Configure → Content → Content Management
2. Filter by source: "waf_akamai"
3. Multi-select all WAF detections
4. Bulk action: Disable

OPTION 3: Stop Data Collection (Emergency)
──────────────────────────────────────────
If issue is at ingestion level, disable HEC token:
1. Settings → Data Inputs → HTTP Event Collector
2. Find: akamai_waf_ingest token
3. Disable token (stops all ingestion)
⚠️ WARNING: This creates data gap — use only in emergency

COMMUNICATION:
Always notify SOC and management when disabling detections
