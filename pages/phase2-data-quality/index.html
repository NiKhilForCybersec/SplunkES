⚠️ Quality Gate — Don't Skip This Phase

Data exists ≠ Data is usable. Phase 1 confirmed logs are flowing. Phase 2 confirms they're accurate, consistent, and ready for detection. Skip this phase and you'll build detections on broken foundations—timestamps off by hours, fields misaligned, correlation impossible.

Why This Phase Exists

Business Justification

In enterprise environments with dozens of log sources from different vendors, data quality problems are the norm, not the exception. Every detection depends on:

  • Accurate timestamps: A detection that correlates events within 5 minutes fails if one source has timestamps 6 hours off
  • Consistent field names: Entra ID calls it "ipAddress", Akamai calls it "clientIP", Windows calls it "Source_Network_Address"—you need them all as "src"
  • Proper data model mapping: Splunk ES relies on CIM data models. Unmapped data is invisible to ES correlation searches
  • Field value consistency: Username formats must match for user-based correlation across sources

Security Justification

Data quality directly impacts detection effectiveness:

  • Timestamp issues: Attacker activity might appear out of sequence, making attack chains invisible
  • Missing CIM mapping: ES out-of-box detections won't see your data
  • Field inconsistency: Cross-source correlation fails—you can't link WAF events to authentication events for the same user
  • False negatives: Real attacks go undetected because data doesn't match detection logic expectations

Step 1: Timestamp Validation

Timestamp accuracy is the foundation of all time-based detection. If timestamps are wrong, every correlation, threshold, and timeline is broken.

1.1: Check Timestamp Extraction

SPL: Verify Timestamp is Extracted from Event (Not Index Time) 
`comment("Events should have _time from the event itself, not _indextime")`

index=waf_akamai sourcetype=akamai:siem earliest=-1h
| eval time_diff = _indextime - _time
| stats 
    count,
    avg(time_diff) AS avg_diff,
    min(time_diff) AS min_diff,
    max(time_diff) AS max_diff,
    stdev(time_diff) AS stdev_diff
| eval avg_diff_sec = round(avg_diff, 0)
| eval assessment = case(
    avg_diff < 0, "⚠️ PROBLEM: _time is AFTER _indextime (future timestamps)",
    avg_diff > 3600, "⚠️ PROBLEM: Avg latency > 1 hour - check timestamp extraction",
    stdev_diff > 1800, "⚠️ PROBLEM: High variance suggests inconsistent timestamps",
    true(), "✓ Timestamps appear consistent"
)
| table count, avg_diff_sec, min_diff, max_diff, stdev_diff, assessment

Interpretation:

  • avg_diff near 0: Timestamps extracted correctly, minimal latency
  • avg_diff 60-300: Normal ingestion latency (1-5 minutes)
  • avg_diff > 3600: Either high latency OR timestamp extraction broken
  • avg_diff negative: Future timestamps—timezone problem
  • High stdev: Inconsistent timestamps—some events extracted correctly, others not

1.3: Fixing Timestamp Issues

Scenario: Timestamps Extracted as Index Time

props.conf: Configure Timestamp Extraction 
[sourcetype_name]
# Tell Splunk where to find the timestamp
TIME_PREFIX = "timestamp":\s*"
TIME_FORMAT = %Y-%m-%dT%H:%M:%S
MAX_TIMESTAMP_LOOKAHEAD = 30
TZ = UTC

# If timestamp is epoch (seconds since 1970)
# TIME_FORMAT = %s

# If timestamp is milliseconds epoch
# TIME_FORMAT = %s%3N

Scenario: Wrong Timezone Applied

props.conf: Force Correct Timezone 
[sourcetype_name]
# Force UTC interpretation
TZ = UTC

# Or for specific timezone
TZ = America/Toronto
TZ = Europe/London

# Common issue: Source logs in local time but Splunk assumes UTC
# Fix: Set TZ to match source system's timezone
💡 Timestamp Fix Testing

After changing props.conf, new events will use new settings, but existing events are already indexed. To test, use | makeresults to simulate events, or wait for new data and compare before/after.

Step 2: CIM Compliance Verification

Splunk Enterprise Security uses Common Information Model (CIM) data models for its dashboards and correlation searches. Data that isn't CIM-compliant is invisible to ES.

2.1: Check Data Model Acceleration Status

SPL: Verify Data Models Are Accelerated 
| rest /services/admin/summarization by_tstats=t splunk_server=local
| search datamodel_name IN ("Authentication", "Web", "Network_Traffic", "Endpoint", "Intrusion_Detection")
| table datamodel_name, summary.is_inprogress, summary.complete, summary.access_time, summary.size
| rename summary.is_inprogress AS building, summary.complete AS complete_pct, summary.access_time AS last_access, summary.size AS size_mb
| eval status = case(
    building=="1", "⏳ Building",
    complete_pct >= 0.9, "✓ Ready",
    complete_pct >= 0.5, "⚠️ Partially Complete",
    complete_pct > 0, "⚠️ Low Completion",
    true(), "✗ Not Accelerated"
)
| table datamodel_name, status, complete_pct, size_mb, last_access

2.2: Check Which Sourcetypes Map to Data Models

SPL: Verify Your Sourcetypes Appear in Authentication Model 
`comment("Check if your auth sourcetypes are in the Authentication data model")`

| tstats count FROM datamodel=Authentication WHERE earliest=-24h BY sourcetype
| sort - count
| eval cim_mapped = "✓ Yes"
| table sourcetype, count, cim_mapped

| append 
    [| makeresults

     | eval sourcetype=mvappend(sourcetype, "cyberark:identity", "OktaIM2:log", "WinEventLog:Security")
     | mvexpand sourcetype
     | table sourcetype, expected]
| stats values(cim_mapped) AS cim_mapped, values(expected) AS expected, sum(count) AS count BY sourcetype

| sort - count

2.4: Fixing CIM Mapping Issues

If Data Model Is Empty

  1. Check TA installation: Ensure vendor TA is installed on search heads AND indexers
  2. Verify tags.conf: TA should have tags.conf mapping sourcetype to data model
  3. Check eventtypes.conf: TA should define eventtypes that match the data
  4. Rebuild data model: If tags added after data ingested, rebuild acceleration

Manual CIM Tagging (If TA Doesn't Cover)

# Then tag in tags.conf
[eventtype=custom_auth_events]
authentication = enabled
default = enabled

[eventtype=custom_waf_events]

attack = enabled

Step 3: Field Normalization

For detections to correlate events across sources, critical fields must have consistent names. The CIM defines standard field names that all sources should map to.

3.1: Critical CIM Fields to Verify

CIM Field Purpose Common Source Fields
src Source IP address ipAddress, clientIP, Source_Network_Address, src_ip
dest Destination host/IP hostname, host, target, destination
user Username userPrincipalName, Account_Name, userName, actor.alternateId
action Action taken result, status, outcome, action
app Application name appDisplayName, application, service
vendor Vendor name Usually set via EVAL
product Product name Usually set via EVAL

3.2: Verify CIM Field Population

SPL: Check CIM Field Population Across Sources 
`comment("Check if critical CIM fields are populated for each sourcetype")`

index IN (waf_akamai, auth_azure, auth_cyberark) earliest=-24h
| head 10000
| eval has_src = if(isnotnull(src) AND src!="", 1, 0)
| eval has_dest = if(isnotnull(dest) AND dest!="", 1, 0)
| eval has_user = if(isnotnull(user) AND user!="", 1, 0)
| eval has_action = if(isnotnull(action) AND action!="", 1, 0)
| eval has_app = if(isnotnull(app) AND app!="", 1, 0)
| stats 
    count AS total,
    sum(has_src) AS with_src,
    sum(has_dest) AS with_dest,
    sum(has_user) AS with_user,
    sum(has_action) AS with_action,
    sum(has_app) AS with_app
    BY sourcetype
| foreach with_* 
    [eval <<FIELD>>_pct = round('<<FIELD>>'/total*100, 0)."%"]
| table sourcetype, total, with_src_pct, with_dest_pct, with_user_pct, with_action_pct, with_app_pct

If CIM fields aren't populated, create field aliases in props.conf:

[akamai:siem]
FIELDALIAS-akamai_src = attackData.clientIP AS src
FIELDALIAS-akamai_dest = httpMessage.host AS dest
FIELDALIAS-akamai_url = httpMessage.path AS url
FIELDALIAS-akamai_http_method = httpMessage.method AS http_method
FIELDALIAS-akamai_action = attackData.action AS action
EVAL-vendor = "Akamai"
EVAL-product = "Kona Site Defender"

# Entra ID Sign-in
[azure:aad:signin]
FIELDALIAS-azure_src = ipAddress AS src
FIELDALIAS-azure_user = userPrincipalName AS user
FIELDALIAS-azure_app = appDisplayName AS app
FIELDALIAS-azure_dest = resourceDisplayName AS dest
EVAL-action = case('status.errorCode'==0, "success", true(), "failure")
EVAL-vendor = "Microsoft"
EVAL-product = "Entra ID"

# Windows Security
[WinEventLog:Security]
FIELDALIAS-win_src = Source_Network_Address AS src
FIELDALIAS-win_user = Account_Name AS user
FIELDALIAS-win_dest = Workstation_Name AS dest
EVAL-action = case(EventCode IN (4624, 4648), "success", EventCode==4625, "failure", true(), "unknown")
EVAL-vendor = "Microsoft"

3.4: Username Format Normalization

Different systems use different username formats. For cross-source correlation, normalize to a common format:

SPL: Analyze Username Formats Across Sources 
index IN (auth_azure, auth_cyberark, auth_windows) earliest=-24h
| stats values(user) AS sample_users BY sourcetype
| eval sample_users = mvindex(sample_users, 0, 9)
| table sourcetype, sample_users

`comment("
Look for format differences:
- Entra ID: john.smith@contoso.com (UPN)
- CyberArk: john.smith@contoso.com or jsmith
- Windows: DOMAIN\\jsmith or jsmith
")`

Create Username Normalization Lookup

identity_correlation.csv 
upn,samaccountname,email,employee_id,display_name,department,is_privileged
john.smith@contoso.com,jsmith,john.smith@contoso.com,EMP001,John Smith,IT,false
admin.john@contoso.com,admin.john,admin.john@contoso.com,EMP001,John Smith,IT,true
jane.doe@contoso.com,jdoe,jane.doe@contoso.com,EMP002,Jane Doe,Finance,false
transforms.conf: Identity Lookup Definition 
[identity_correlation]
filename = identity_correlation.csv
case_sensitive_match = false
max_matches = 1
SPL: Use Lookup for Cross-Source Correlation 
index IN (auth_azure, auth_cyberark, auth_windows) earliest=-24h
| eval user_normalized = lower(user)
| lookup identity_correlation.csv upn AS user_normalized OUTPUT employee_id, display_name, is_privileged
| lookup identity_correlation.csv samaccountname AS user_normalized OUTPUT employee_id AS emp_id2, display_name AS name2
| eval employee_id = coalesce(employee_id, emp_id2)
| eval display_name = coalesce(display_name, name2)
| stats count BY employee_id, display_name, sourcetype
| sort employee_id

Failure Modes & Fixes

Failure Mode 1: Data Model Shows Zero Events

Symptom

| tstats count FROM datamodel=Authentication returns 0 despite auth events flowing.

Causes:

  • TA not installed on search heads (field extractions missing)
  • TA installed but eventtypes/tags not defined for your sourcetype
  • Data model acceleration not enabled or not completed
  • Data model constraint doesn't match your index

Fix:

  1. Verify TA installed: | rest /services/apps/local | search title=*TA*
  2. Check if eventtype matches: | search sourcetype="azure:aad:signin" | tags
  3. Verify data model constraint includes your index in datamodels.conf
  4. Rebuild acceleration after fixes

Failure Mode 2: Timestamps Hours Off

Symptom

Events show timestamps that are consistently offset by fixed hours (e.g., always 5 hours ahead).

Causes:

  • Source system logs in local time, Splunk interprets as UTC
  • TZ setting in props.conf is wrong
  • Source system timezone changed (DST transitions)

Fix:

  1. Identify source system's timezone
  2. Set correct TZ in props.conf for that sourcetype
  3. Note: Fix only applies to new events; existing data keeps wrong timestamps

Failure Mode 3: Field Aliases Not Working

Symptom

FIELDALIAS in props.conf doesn't populate the CIM field.

Causes:

  • Source field name wrong (check exact JSON path)
  • props.conf not on search heads
  • App precedence: another app's props.conf overriding
  • Syntax error in props.conf

Fix:

  1. Verify source field exists: | head 1 | fields *
  2. Check exact field name (case sensitive for nested JSON)
  3. Restart Splunk or use | btool props list sourcetype to verify

Failure Mode 4: Cross-Source Correlation Fails

Symptom

Join/correlation between sources returns no results despite matching data.

Causes:

  • Username format mismatch (UPN vs SAMAccountName)
  • Case sensitivity (user vs USER)
  • Timestamp mismatch (correlation window too narrow for latency)
  • Field not actually populated in one source

Fix:

  1. Use identity lookup for username normalization
  2. Use lower(user) for case-insensitive matching
  3. Widen correlation time window to account for latency
  4. Verify field population in both sources

Rollback & Safety

⚠️ Configuration Changes Can Break Data Parsing

Phase 2 involves modifying Splunk configuration files. Bad changes can break timestamp extraction, field parsing, or data model mapping. Always have a rollback plan.

Safe props.conf Deployment Procedure

Procedure: Deploy props.conf Changes Safely 
STEP 1: DOCUMENT CURRENT STATE
──────────────────────────────
# On search head, capture current effective configuration
$SPLUNK_HOME/bin/splunk btool props list [sourcetype] --debug > /tmp/props_before.txt

# Record current field extraction behavior
index=* sourcetype=[sourcetype] earliest=-1h | head 10 | table _raw, _time, src, dest, user

STEP 2: TEST IN DEV/STAGING FIRST
─────────────────────────────────
# If dev environment exists:
1. Deploy props.conf to dev search head
2. Run validation queries against dev data
3. Verify no regressions in existing field extractions

STEP 3: BACKUP PRODUCTION CONFIG
────────────────────────────────
# Backup current app before changes
cp -r $SPLUNK_HOME/etc/apps/[your_app] /tmp/[your_app]_backup_$(date +%Y%m%d)

STEP 4: DEPLOY TO PRODUCTION
────────────────────────────
# Deploy during change window
# Option A: Via Splunk Web (Settings → Data inputs → Source types → Edit)
# Option B: Direct file edit + restart
1. Edit $SPLUNK_HOME/etc/apps/[your_app]/local/props.conf
2. Restart Splunk or use debug/refresh endpoint:
   curl -k -u admin:password https://localhost:8089/services/admin/config-refresh

STEP 5: VALIDATE
────────────────
# Immediately after deployment:
1. Run validation queries from Step 1
2. Compare before/after results
3. Check _internal for parsing errors:
   index=_internal sourcetype=splunkd "ERROR" "[sourcetype]" earliest=-15m

STEP 6: MONITOR FOR 24 HOURS
────────────────────────────
# Watch for issues:
- Field population rates changing
- Timestamp distribution shifting
- Data model acceleration errors

props.conf Rollback Procedure

Emergency Rollback: Undo props.conf Changes 
IF CHANGES BROKE DATA PARSING:

OPTION 1: Restore from Backup (Preferred)
─────────────────────────────────────────
1. Stop Splunk (if safe): $SPLUNK_HOME/bin/splunk stop
2. Restore backup: cp -r /tmp/[your_app]_backup_[date]/* $SPLUNK_HOME/etc/apps/[your_app]/
3. Start Splunk: $SPLUNK_HOME/bin/splunk start
4. Verify restoration: $SPLUNK_HOME/bin/splunk btool props list [sourcetype]

OPTION 2: Revert Specific Settings
──────────────────────────────────
1. Edit props.conf
2. Remove or comment out the problematic stanza
3. Refresh: curl -k -u admin:password https://localhost:8089/services/admin/config-refresh
4. Test immediately

OPTION 3: Override in local/props.conf
──────────────────────────────────────
If you can't modify the original file, create override:
1. Create $SPLUNK_HOME/etc/apps/[your_app]/local/props.conf
2. Add corrected stanza (local overrides default)
3. Refresh configuration

NOTE: Rollback only affects NEW events
──────────────────────────────────────
Events already indexed with wrong timestamps/fields cannot be fixed.
Options for historical data:
- Re-index from raw data (if available)
- Document the data quality gap for affected time range
- Build detections that account for the issue

TA Version Verification

⚠️ Enterprise Issue: Mismatched TA Versions

One of the most common enterprise data quality issues is having different TA versions on search heads vs. indexers. This causes field extraction mismatches.

SPL: Verify TA Versions Across All Splunk Servers 
| rest /services/apps/local splunk_server=*
| search title IN ("Splunk_TA_*", "TA-*")
| stats values(version) AS versions, dc(version) AS version_count, values(splunk_server) AS servers BY title
| where version_count > 1
| eval issue = "⚠️ VERSION MISMATCH - Update to consistent version across all servers"
| table title, versions, version_count, servers, issue

Comprehensive Quality Validation Query

SPL: Phase 2 Quality Gate Validation (Run Before Sign-Off) 
`comment("Comprehensive data quality check for all security-relevant sourcetypes")`

| tstats count WHERE index IN (waf_akamai, auth_azure, auth_cyberark, auth_okta) earliest=-24h BY index, sourcetype
| join type=left sourcetype 
    [search index IN (waf_akamai, auth_azure, auth_cyberark, auth_okta) earliest=-4h
     | eval latency = _indextime - _time
     | stats avg(latency) AS avg_latency, perc95(latency) AS p95_latency BY sourcetype]
| join type=left sourcetype
    [search index IN (waf_akamai, auth_azure, auth_cyberark, auth_okta) earliest=-24h
     | head 10000
     | eval has_src = if(isnotnull(src) AND src!="", 1, 0)
     | eval has_user = if(isnotnull(user) AND user!="", 1, 0)
     | eval has_action = if(isnotnull(action) AND action!="", 1, 0)
     | stats 
         avg(has_src) AS src_pct,
         avg(has_user) AS user_pct,
         avg(has_action) AS action_pct
         BY sourcetype]
| eval avg_latency_min = round(avg_latency/60, 1)
| eval p95_latency_min = round(p95_latency/60, 1)
| eval src_pct = round(src_pct*100, 1)."%"
| eval user_pct = round(user_pct*100, 1)."%"
| eval action_pct = round(action_pct*100, 1)."%"
| eval timestamp_status = case(p95_latency < 300, "✓ OK", p95_latency < 900, "⚠️ Marginal", true(), "✗ FAIL")
| eval cim_status = case(src_pct >= 90 AND user_pct >= 90 AND action_pct >= 90, "✓ OK", true(), "⚠️ Check fields")
| table sourcetype, count, avg_latency_min, p95_latency_min, timestamp_status, src_pct, user_pct, action_pct, cim_status
