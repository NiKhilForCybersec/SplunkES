🎯 Phase 3 — Detection Engineering

Detection Engineering

📋 Page Status: HARDENED

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This page has been audited and hardened for solo enterprise delivery. All sections include explicit validation criteria, failure modes, and rollback procedures.

🚨 HARD GATE — DO NOT SKIP MONITORING MODE

Every detection MUST go through monitoring mode before production. Deploying untested detections directly to production causes:

  • Alert storms that overwhelm SOC and destroy trust
  • False positives that train analysts to ignore alerts
  • Missed attacks due to logic errors only visible in production data

Minimum monitoring period: 1-2 weeks with daily review of results.

⚠️ Retail Business Timing — Detection Deployment

Do NOT deploy new detections to production during:

  • Black Friday / Holiday freeze periods — No new alerts to triage
  • Major promotional events — Traffic spikes cause false positives
  • SOC staff shortages — Ensure coverage to triage new alerts

Best deployment windows: Mid-week (Tue-Wed), after staff meetings, with full SOC coverage.

📋 Phase Overview

This is the core of what detection engineers do: building detections that find real attacks while minimizing false positives. This phase covers the methodology, lifecycle, and best practices for creating production-ready detections in Splunk Enterprise Security.

Why This Phase Exists

Business Justification

Phases 1 and 2 ensured data flows correctly and meets quality standards. But data without detection is just expensive storage. Phase 3 transforms that data into actionable security alerts that protect the organization:

  • Convert visibility into protection: Data only has value when it drives action
  • Meet compliance requirements: Regulations require not just logging but active monitoring
  • Reduce time to detect: Automated detection finds threats faster than manual review
  • Enable SOC efficiency: Well-tuned detections create actionable work, not noise

What Makes Detection Engineering Difficult

Writing a query that matches an attack pattern is easy. Building a production detection that works reliably is hard:

  • False positives destroy SOC trust: Too many false alerts and analysts ignore everything
  • False negatives miss real attacks: Overly restrictive logic lets attackers through
  • Environment drift: What worked last month breaks as infrastructure changes
  • Attack evolution: Adversaries adapt to bypass known detection logic
  • Scale challenges: Detection that works on 100 events may fail on 100 million

Detection Lifecycle

Every detection follows this lifecycle. Skipping stages leads to production failures, SOC burnout, and missed detections.

1.2: Attack Signature Definition

The attack signature is the specific pattern that distinguishes attack from normal. Be precise:

Detection Bad Attack Signature Good Attack Signature
Brute Force "Many failed logins" "≥10 failed logins to same account from same IP within 10 minutes"
MFA Fatigue "Lots of MFA prompts" "≥5 MFA challenges to same user within 15 minutes with ≥80% denied"
Password Spray "Failed logins from one IP" "Single IP with failed logins to ≥10 unique accounts within 30 minutes, ≤3 attempts per account"
SQLi Campaign "SQL injection attempts" "≥5 WAF events with SQL injection rule triggers from same IP within 10 minutes"

Stage 2: Detection Development

2.1: SPL Best Practices

Use Inline Documentation

Every detection should be self-documenting. Future you (or your replacement) will thank you:

SPL: Well-Documented Detection Example 
`comment("
===============================================================================
DETECTION: Brute Force Authentication
AUTHOR: Detection Engineering Team
VERSION: 1.2
LAST_UPDATED: 2024-06-15
MITRE: T1110.001 - Brute Force: Password Guessing
===============================================================================
LOGIC: Detects multiple failed authentication attempts against a single
account from the same source IP within a short time window.
===============================================================================
THRESHOLDS:
- Default: 10 failures in 10 minutes
- Can adjust via threshold macro or lookup
===============================================================================
KNOWN FALSE POSITIVES:
- Legitimate users who forgot password (usually <10 attempts)
- Service accounts with expired credentials (investigate config)
- Broken SSO causing retry loops (check app field)
===============================================================================
CHANGELOG:
- v1.0 (2024-01-01): Initial detection
- v1.1 (2024-03-15): Added app field to identify SSO issues
- v1.2 (2024-06-15): Increased threshold from 5 to 10 based on FP analysis
===============================================================================
")`

index=auth_azure sourcetype="azure:aad:signin" earliest=-15m latest=now()
| spath output=user path=userPrincipalName
| spath output=src path=ipAddress
| spath output=error_code path=status.errorCode
| spath output=app path=appDisplayName

`comment("Filter to authentication failures")`
| search error_code IN (50126, 50053, 50055)

`comment("Aggregate by user and source IP")`
| stats 
    count AS failed_attempts,
    values(app) AS applications,
    earliest(_time) AS first_failure,
    latest(_time) AS last_failure
    BY user, src

`comment("Apply threshold - configurable via lookup if needed")`
| where failed_attempts >= 10

`comment("Calculate attack metrics")`
| eval attack_duration_min = round((last_failure - first_failure) / 60, 1)

`comment("Generate severity and description")`
| eval severity = case(failed_attempts >= 50, "high", failed_attempts >= 20, "medium", true(), "low")
| eval description = "Brute force attack: ".failed_attempts." failed logins against ".user." from ".src

| table _time, user, src, failed_attempts, attack_duration_min, severity, applications, description

SPL Optimization Rules

Rule Why Example
Filter early Reduce data before expensive operations Put search before stats
Use tstats when possible 10-100x faster than raw search | tstats count FROM datamodel=Authentication
Avoid wildcards at start Can't use index optimization Use src=192.168.* not src=*192.168*
Limit time range Correlations rarely need 24h+ earliest=-15m for correlation searches
Use summary indexing Pre-aggregate for dashboards | collect index=summary

2.2: Threshold Management

Hardcoded thresholds make tuning difficult. Use one of these approaches:

Option 1: Macro-Based Thresholds

macros.conf 
[brute_force_threshold]
definition = 10

[mfa_fatigue_threshold]
definition = 5

[password_spray_user_threshold]
definition = 10
SPL: Using Macro Threshold 
| where failed_attempts >= `brute_force_threshold`

Option 2: Lookup-Based Thresholds

detection_thresholds.csv 
detection_name,threshold,time_window_min,last_updated,updated_by
brute_force,10,10,2024-06-15,security_team
mfa_fatigue,5,15,2024-06-01,security_team
password_spray_users,10,30,2024-05-20,security_team
sqli_campaign,5,10,2024-04-01,security_team
SPL: Using Lookup Threshold 
| lookup detection_thresholds.csv detection_name AS "brute_force" OUTPUT threshold
| where failed_attempts >= threshold

Stage 3: Validation

3.1: Data Reality Check

Before testing logic, verify required data exists:

SPL: Generic Data Reality Check Template 
`comment("Replace index, sourcetype, and fields with your detection requirements")`

index=YOUR_INDEX sourcetype=YOUR_SOURCETYPE earliest=-24h
| head 10000
| eval has_field1 = if(isnotnull(FIELD1) AND FIELD1!="", 1, 0)
| eval has_field2 = if(isnotnull(FIELD2) AND FIELD2!="", 1, 0)
| eval has_field3 = if(isnotnull(FIELD3) AND FIELD3!="", 1, 0)
| stats 
    count AS total,
    sum(has_field1) AS with_field1,
    sum(has_field2) AS with_field2,
    sum(has_field3) AS with_field3
| eval field1_pct = round(with_field1/total*100, 1)."%"
| eval field2_pct = round(with_field2/total*100, 1)."%"
| eval field3_pct = round(with_field3/total*100, 1)."%"
| table total, field1_pct, field2_pct, field3_pct

`comment("All critical fields should be >95% populated")`

3.2: Historical Backtesting

Run the detection against 30 days of historical data to understand baseline:

SPL: Backtest Template 
`comment("Run your detection logic against 30 days")`

[YOUR DETECTION SPL HERE with earliest=-30d]

`comment("Summarize: How many alerts per day?")`
| bin _time span=1d
| stats count AS daily_alerts BY _time
| stats 
    avg(daily_alerts) AS avg_per_day,
    max(daily_alerts) AS max_per_day,
    min(daily_alerts) AS min_per_day,
    stdev(daily_alerts) AS stdev

`comment("
INTERPRETATION:
- avg <10/day: Good for SOC workload
- avg 10-30/day: Acceptable, plan for tuning
- avg >30/day: Too noisy, adjust thresholds before monitoring mode
")`

Stage 4: Monitoring Mode

⚠️ MANDATORY: Never Skip Monitoring Mode

Deploying a detection directly to production without monitoring mode is the #1 cause of SOC alert fatigue and detection distrust. Always run in monitoring mode for at least 1-2 weeks.

4.1: Deploy as Scheduled Report

Splunk ES: Monitoring Mode Configuration 
NAME: MONITOR_[Detection_Name]
TYPE: Scheduled Report (NOT Correlation Search)
SCHEDULE: Same as intended production schedule
TIME RANGE: Same as intended production
ACTIONS: 
  - Send to summary index: YES
  - Send email: NO
  - Create notable: NO

SUMMARY INDEX COLLECTION:
| collect index=summary source="detection_monitor" marker="detection=[name]"

  - Status: new

5.2: Notable Event Configuration

Notable Event Field Mapping 
REQUIRED FIELDS FOR GOOD NOTABLES:
- src: Source of attack (for ES asset lookup)
- dest: Target of attack (for ES asset lookup)
- user: Affected user (for ES identity lookup)
- description: Human-readable summary
- severity: informational/low/medium/high/critical

OPTIONAL BUT RECOMMENDED:
- urgency: Override calculated urgency
- owner: Auto-assign to specific analyst/group
- status: Usually "new"
- drilldown_name: Link to investigation search
- drilldown_search: Search to run for more context

5.3: Track Detection Metrics

SPL: Detection Performance Metrics 
`comment("Track key metrics for each detection")`

index=notable earliest=-30d
| search search_name="[Detection_Name]"
| stats 
    count AS total_alerts,
    dc(src) AS unique_sources,
    dc(user) AS unique_users
| join type=left 
    [search index=notable earliest=-30d search_name="[Detection_Name]"
     | stats count BY status_label
     | eval true_positive = if(status_label IN ("Resolved - True Positive", "Closed - True Positive"), count, 0)
     | eval false_positive = if(status_label IN ("Resolved - False Positive", "Closed - False Positive"), count, 0)
     | stats sum(true_positive) AS tp, sum(false_positive) AS fp]
| eval total_dispositioned = tp + fp
| eval fp_rate = if(total_dispositioned > 0, round(fp / total_dispositioned * 100, 1), "N/A")
| table total_alerts, unique_sources, unique_users, tp, fp, fp_rate

Rollback & Safety

Emergency Detection Disable Procedure

Procedure: Disable a Detection Immediately 
SCENARIO: Detection is generating excessive alerts or false positives

OPTION 1: Disable via ES UI (Preferred)
───────────────────────────────────────
1. ES → Configure → Content → Content Management
2. Search for detection name
3. Click detection → Edit → Enabled = No → Save
4. Effect: Immediate (no new alerts generated)

OPTION 2: Disable via REST API (Faster for Automation)
──────────────────────────────────────────────────────
curl -k -u admin:password -X POST \
  https://localhost:8089/servicesNS/nobody/SplunkEnterpriseSecuritySuite/saved/searches/[detection_name] \
  -d disabled=1

OPTION 3: Modify Throttling (Reduce Alert Volume)
─────────────────────────────────────────────────
If detection is valid but too noisy:
1. Edit detection → Throttle Settings
2. Increase throttle window (e.g., 1 hour → 4 hours)
3. Add throttle key field (e.g., per-user instead of global)

COMMUNICATION REQUIRED:
───────────────────────
When disabling a detection:
1. Notify SOC: "[Detection Name] disabled due to [reason]. Expected restore: [time]"
2. Create ticket/incident for tracking
3. Document what triggered the disable decision
4. Schedule review to re-enable after fix

Detection Rollback: Return to Previous Version

Procedure: Rollback Detection to Previous Version 
IF DETECTION UPDATE CAUSED ISSUES:

STEP 1: Identify Previous Version
─────────────────────────────────
# Check ES Content Management for version history
# Or check source control if using Git for detection-as-code

STEP 2: Revert SPL Logic
────────────────────────
1. ES → Configure → Content → Content Management
2. Find detection → Edit
3. Replace current SPL with previous working version
4. Save

STEP 3: Revert Threshold/Settings
─────────────────────────────────
If thresholds were changed:
1. Document current thresholds before reverting
2. Restore previous threshold values
3. Save and enable

STEP 4: Validate Rollback
─────────────────────────
1. Run detection manually against last 24 hours
2. Verify alert volume matches pre-change behavior
3. Confirm no new issues

BEST PRACTICE: Version Control
──────────────────────────────
Maintain detection versions in Git repository:
- Store SPL, thresholds, runbooks together
- Commit changes with meaningful messages
- Tag releases for easy rollback
- Example: git checkout v1.2.0 -- detections/mfa_fatigue.yml

Alert Storm Response

Emergency Response: Detection Generating Alert Storm 
IF DETECTION IS FLOODING SOC WITH ALERTS:

STEP 1: DISABLE IMMEDIATELY (30 seconds)
────────────────────────────────────────
ES → Configure → Content → Content Management → [Detection] → Disable

STEP 2: ASSESS SCOPE (5 minutes)
────────────────────────────────
index=notable search_name="[Detection_Name]" earliest=-1h
| stats count BY _time span=5m
| timechart count

STEP 3: IDENTIFY ROOT CAUSE (15 minutes)
────────────────────────────────────────
Common causes:
- Infrastructure change triggered mass alerts
- Threshold too low for production data
- Missing allowlist for legitimate activity
- Bug in SPL logic (e.g., missing field causes all events to match)

STEP 4: BULK CLOSE FALSE POSITIVES (if appropriate)
───────────────────────────────────────────────────
# Only if confirmed false positive pattern
index=notable search_name="[Detection_Name]" earliest=-1h status="new"
| eval status="closed", status_label="Closed - False Positive"
| collect index=notable

⚠️ WARNING: Use bulk close carefully - ensure you're not closing real attacks

STEP 5: FIX AND RE-ENABLE
─────────────────────────
1. Fix the root cause (add allowlist, adjust threshold, fix SPL)
2. Test fix in monitoring mode for 24 hours minimum
3. Re-enable to production only after validation
