Edge Processor Decision Guide

📋 Page Status: HARDENED — DECISION GUIDE

Last Audit: 2024-02 | Auditor: Detection Engineering Team

Purpose: Decide when to use the Splunk Edge Processor versus a traditional Heavy Forwarder or Universal Forwarder architecture. Covers data routing, filtering, masking, and transformation at the edge — with a focus on how these decisions impact detection engineering (data availability, CIM compliance, search performance).

Ownership: Platform Engineering (architecture decisions) + Detection Engineering (data requirements input)

Preconditions: Familiarity with Phase 1 — Log Coverage and the Universal Onboarding Framework.

⚠️ Assumptions — Verify Before Proceeding
  • Assumption: You're evaluating Edge Processor for a Splunk Cloud or Splunk Enterprise deployment. Note: Edge Processor is a Splunk Cloud-native feature. On-prem availability depends on your Splunk version and licensing.
  • Assumption: Your environment processes enough data volume to benefit from edge-side processing. Threshold: Edge Processor adds the most value at >100 GB/day where filtering, routing, or masking at the edge reduces indexing cost or improves data quality.
  • Assumption: Edge Processor is generally available for your Splunk Cloud stack. Verify: Check with your Splunk account team or Splunk Cloud admin. Feature availability varies by stack type and contract.
  • Assumption: Detection Engineering has defined data requirements. Risk if wrong: Edge filtering decisions made without DE input may drop data needed for detections.

What Is the Edge Processor?

The Splunk Edge Processor is a data processing layer that sits between your data sources and the Splunk indexing tier. It receives data from Universal Forwarders (or direct sources like syslog/HEC), applies transformations (filtering, routing, masking, field extraction) at the edge, and forwards the processed data to Splunk Cloud (or other destinations).

Think of it as a cloud-managed Heavy Forwarder — but with a UI-driven pipeline builder instead of props/transforms configuration files.

Capability Universal Forwarder (UF) Heavy Forwarder (HF) Edge Processor (EP)
Data collection ✅ Collects from local sources (files, scripts, WMI) ✅ Collects from local + network sources (syslog, HEC, dbconnect) ✅ Receives from UFs, syslog, HEC, and other sources
Data filtering ❌ Minimal (can blacklist by sourcetype/path) ✅ Full — props.conf, transforms.conf, SEDCMD ✅ Full — UI-based SPL2 pipeline rules
Data routing ❌ Routes to configured indexers only ✅ Can route to different indexes/destinations based on content ✅ Route to Splunk Cloud, S3, other destinations based on content
Data masking ❌ No ✅ Via SEDCMD and transforms ✅ Via pipeline rules (regex-based masking)
Field extraction ❌ No (happens at search time) ✅ Index-time extractions via props/transforms ✅ Extract and transform fields before indexing
Management Deployment server / CLI Deployment server / CLI / conf files Cloud-hosted UI with visual pipeline builder
Resource footprint Light (< 256 MB RAM) Heavy (dedicated server, 8-32+ GB RAM) Medium (container-based, scales horizontally)
Configuration complexity Low High (props/transforms expertise required) Medium (UI-driven, SPL2-based pipelines)

Edge Processor Use Cases for Detection Engineering

Use Case What Edge Processor Does DE Impact Risk to Monitor
Volume reduction — Drop noisy events Filter out known-benign events at the edge (e.g., heartbeat logs, debug messages, health checks) before they consume indexing license ✅ Positive: Reduces index noise, improves search performance. Detections against remaining data are more efficient. 🔴 Risk: If filtering criteria are too broad, security-relevant events may be dropped before reaching the index. DE must review all filter rules.
Data masking — PII/PCI compliance Mask credit card numbers, SSNs, or PII fields before data reaches the index (compliance with PCI DSS, GDPR, etc.) ✅ Positive: Compliance with data protection requirements. DE can still detect on patterns without seeing raw PII. 🟡 Risk: Over-masking can remove fields needed for correlation. Mask only the sensitive portion, preserve the field structure.
Data routing — Multi-index or multi-destination Route high-fidelity security events to the security index (fast, expensive) and verbose operational logs to a lower-cost tier or S3 ✅ Positive: Security-relevant data stays in fast indexes. Cost savings on operational data. 🟡 Risk: Routing rules may misclassify events. Security-relevant events routed to low-cost tier may not be available for detections within required search windows.
Field enrichment — Add context at ingestion Add lookup-based enrichment (e.g., asset owner, criticality tier, business unit) at the edge before indexing ✅ Positive: Enriched data enables better correlation and reduces search-time lookup overhead. 🟡 Risk: Enrichment lookups must be kept current. Stale enrichment = stale context in indexed events (hard to fix retroactively).
Schema normalization Normalize field names to CIM at the edge, before indexing. Events arrive CIM-compliant. ✅ Positive: Data models work immediately. No search-time field aliasing needed. 🟡 Risk: Normalization errors at the edge are baked into the indexed data. Unlike search-time props, index-time errors require re-indexing to fix.
Aggregation — Reduce event volume Aggregate repetitive events (e.g., 1000 identical firewall denies → 1 summary event with count) ⚠️ Mixed: Reduces volume, but individual event details are lost. Some detections need raw events. 🔴 Risk: Aggregation destroys granularity. Detections that need individual event timestamps, source/destination pairs, or payload content will fail against aggregated data.

Detection Engineering Requirements for Edge Processing Decisions

🚨 Critical Rule: DE Reviews All Edge Filter Rules

Every filter rule, routing rule, masking rule, or aggregation rule applied at the edge MUST be reviewed by Detection Engineering before deployment. Edge processing happens before data reaches the index — once data is dropped, it's gone. There is no search-time recovery.

DE Approval Checklist for Edge Rules

✅ Review Item Question to Answer Red Flag
☐ 1. Filter scope What events will be dropped? Is the filter specific enough (e.g., EventCode AND source) or overly broad (e.g., entire sourcetype)? Filtering an entire sourcetype that contains any security-relevant events
☐ 2. Detection dependency Do any active or planned detections depend on the events being filtered? Dropping events referenced by an ESCU detection or a planned custom detection
☐ 3. Investigation dependency Would a SOC analyst need these events during incident investigation (even if no detection directly fires on them)? Dropping context events (e.g., successful logins around a failed-login detection)
☐ 4. Compliance requirement Are there retention or audit requirements that mandate keeping these events? Dropping audit-relevant events (access logs, change logs) in a PCI or SOX environment
☐ 5. Masking impact If fields are being masked, does the masked version still allow detection to work? (e.g., can you still match on a masked IP range?) Masking a field that a detection uses for correlation (e.g., masking src_ip in a brute-force detection)
☐ 6. Routing destination SLA If events are routed to a low-cost tier, are they still searchable within the detection's time window? Events routed to S3 with 24-hour query latency, but detection needs 15-minute lookback
☐ 7. Aggregation granularity If events are aggregated, does the summary event preserve enough detail for detection? Aggregating individual auth events when the detection needs per-event timestamps for fatigue pattern detection

Architecture Comparison: When Each Makes Sense

Scenario Best Choice Why
Simple collection from Windows/Linux endpoints UF → Indexer No edge processing needed. UF is lightweight and reliable. Let TAs handle field extraction at search time.
Syslog from network devices (firewall, WAF, switches) UF/Syslog → HF or EP → Indexer Network syslog often needs parsing, filtering (drop health checks), and routing. HF or EP handles this.
High-volume data with PCI masking requirement (retail) UF → EP → Splunk Cloud EP masks PCI data before it reaches the index. UI-based rules are auditable. Cloud-native management.
Multi-destination routing (Splunk + S3 + SIEM migration) UF → EP → Splunk Cloud + S3 EP can route copies of data to multiple destinations simultaneously. HF can do this too, but EP has a cleaner UI for it.
Legacy on-prem environment with no Splunk Cloud UF → HF → Indexer EP is primarily a Splunk Cloud feature. On-prem environments use the traditional HF pipeline.
Reducing indexing volume by 30%+ to manage license UF → EP → Splunk Cloud EP's filtering at the edge reduces data before it counts against license. But DE must approve all filter rules.
Complex conditional routing with environment-specific lookups HF (or EP with enrichment) HF has the most flexibility for complex conditional logic. EP is catching up but may have limitations on complex lookups.

Failure Modes

Failure Mode Symptom Root Cause Impact Fix
Edge filter drops security events Detection that previously worked stops finding results. Investigation queries return fewer events than expected. Edge filter rule too broad. Platform team added a filter without DE review. 🔴 Critical: Detections silently fail. Security events are permanently lost. Emergency: Disable the filter rule. Review all edge rules with DE. Implement mandatory DE sign-off on filter changes.
Masking breaks detection field Correlation search that matches on a specific field now returns zero results because the field is masked to **** Masking applied to a field used in detection logic (e.g., user email, IP address) 🔴 Detection failure. May also break investigation workflows. Mask only the sensitive portion (e.g., mask the middle digits of a CC, not the entire field). Or use hashing instead of masking to allow correlation.
Edge Processor becomes a bottleneck Data ingestion lag increases. Events arrive in Splunk minutes or hours after generation. EP underscaled for data volume. Processing rules too complex. Detections with short lookback windows miss events. Near-real-time alerting degrades. Scale EP horizontally. Simplify complex pipeline rules. Monitor EP throughput and latency metrics.
Aggregation destroys detection granularity MFA fatigue detection stops working because individual push events are aggregated into a single summary per hour Aggregation rule doesn't preserve the event-level detail the detection needs Specific detection patterns that require event-level granularity can no longer be detected Never aggregate security-relevant event types without DE approval. Route a copy of raw events to the security index before aggregating.
Edge normalization error baked into index CIM field mapped incorrectly at the edge. All indexed events have wrong field values. Normalization rule has a bug. Unlike search-time props, the error is in the indexed data. Detections using the wrong field produce false positives or false negatives. Fix requires re-indexing. Test normalization rules in a pipeline preview before deploying. Start with a small subset of data. Validate against CIM expected values.

Validation — After Edge Processor Deployment

SPL: Verify Data Volume Before vs After Edge Processor 
`comment("Run this BEFORE and AFTER Edge Processor deployment")`
`comment("Compare results to understand what was filtered/changed")`

| tstats count WHERE index=* BY index, sourcetype span=1h
| stats avg(count) AS avg_events_per_hour BY index, sourcetype
| sort - avg_events_per_hour
| head 30
| eval note = "Compare this output before and after EP deployment to identify volume changes"
SPL: Verify Detection Data Sources Still Exist Post-EP 
`comment("For each active correlation search, verify its data source still exists")`
`comment("Run this after any Edge Processor rule change")`

| rest /services/saved/searches splunk_server=local
| where disabled=0 AND isnotnull(action.correlationsearch.enabled)
| rex field=search "index\s*=\s*(?\w+)"
| search required_index=*
| dedup required_index
| map search="| tstats count WHERE index=$required_index$ | eval index=\"$required_index$\""
| eval status = if(count > 0, "✅ Data present", "🔴 NO DATA — check Edge Processor filters")

Rollback Steps

  1. Edge filter dropping critical data: Disable the specific filter rule in the EP pipeline immediately. Data flow resumes to the default (unfiltered) path. Verify with a | tstats count WHERE index=affected_index earliest=-15m check.
  2. Edge normalization creating bad data: Disable the normalization rule. Events will arrive un-normalized (search-time TAs will handle field extraction). Accept search-time overhead until the normalization rule is fixed and retested.
  3. Edge Processor outage: UFs should fall back to queuing data locally. When EP recovers, queued data will be forwarded. If EP is down for extended periods, consider routing UFs directly to indexers temporarily (requires deployment server push).

Stop & Escalate Conditions

🛑 STOP and Escalate When:
  • Any edge filter rule is deployed without DE review. Stop. Review the rule. If it drops security-relevant data, disable it immediately and restore the default path.
  • Detection coverage gaps appear after EP deployment. Compare data volumes before/after. If a data source is missing or reduced, trace the cause to an EP rule.
  • EP latency exceeds 5 minutes for security-critical data. Detections with short lookback windows (5-15 min) may miss events. Escalate to platform team for scaling.
  • Aggregation rules are proposed for any security event type. DE must explicitly approve. Default answer is "don't aggregate security events." Route a raw copy first.
  • Edge masking is proposed for fields used in active detections. Test the detection against masked sample data before deploying. If the detection breaks, find an alternative masking strategy (partial masking, hashing).

Common Anti-Patterns

Anti-Pattern Why It's Dangerous What to Do Instead
"Platform team manages edge rules, DE doesn't need to see them" Platform optimizes for cost and performance. DE optimizes for detection coverage. Without DE review, cost savings come at the expense of security visibility. Mandatory DE sign-off on all edge filter, masking, routing, and aggregation rules. Documented in change management.
"Filter everything except what we explicitly need" Allowlist approach at the edge is extremely risky. New data sources, new detections, and investigation queries all need data you haven't predicted. Use a denylist approach: explicitly drop what you're certain is noise. Default to forwarding everything else.
"We'll aggregate at the edge and keep raw in S3" S3 data has hours or days of query latency. Detections need near-real-time data. S3 is for forensics, not detection. Index raw security events in Splunk. Use S3 for long-term retention or compliance archives only.
"Edge Processor replaces all Heavy Forwarders" EP may not support all HF use cases (complex routing, specific TAs, index-time field extractions). Migration must be planned. Evaluate EP capabilities against your specific HF use cases. Migrate incrementally — start with the simplest pipelines.
"We'll figure out what to filter after we deploy EP" Deploying EP without a filtering plan means either no benefit (data flows through unchanged) or reactive filtering that drops the wrong data. Define filter rules before deployment. Review with DE. Test in preview mode. Deploy to a subset first.
