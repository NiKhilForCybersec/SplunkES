DB Connect Integration

Query databases directly for audit logs, application data, and configuration tables using Splunk DB Connect

📋 Page Status: HARDENED

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This page includes database-specific operational guidance, security requirements, and rollback procedures.

🚨 CRITICAL: DB Connect Can Impact Production Databases

Poorly tuned queries can degrade database performance. Before implementing:

  • DBA approval REQUIRED: Get written approval from DBA team for all queries
  • Read-only accounts ONLY: Never use accounts with write permissions
  • Query optimization: All queries must have execution plans reviewed by DBA
  • Connection limits: Respect database connection pool limits
⚠️ Database Credential Security

DB Connect credentials are high-value targets:

  • No shared accounts: Create dedicated service accounts per database
  • Password rotation: Implement 90-day rotation with Splunk credential update
  • Audit access: Ensure database audit logs capture Splunk service account activity
  • Network segmentation: Heavy Forwarder must be in appropriate network zone for database access

Architecture Overview

Splunk DB Connect enables direct JDBC connections to relational databases, allowing you to ingest audit logs, application events, and security-relevant data that doesn't support syslog or API export. This is ideal for legacy applications, database audit trails, and application-specific security events stored in RDBMS.

When to Use DB Connect

DB Connect is best for: database-native audit logs (SQL Server Audit, Oracle Unified Audit), legacy applications without API/syslog export, enrichment lookup tables, and compliance data stored in RDBMS. For high-volume transaction logs, consider database replication to a dedicated logging database first.

Step 1: Install DB Connect

Install Java Runtime

Linux (RHEL/CentOS) 
# Install OpenJDK 11
sudo yum install java-11-openjdk java-11-openjdk-devel -y

# Set JAVA_HOME
echo 'export JAVA_HOME=/usr/lib/jvm/java-11-openjdk' >> /opt/splunk/.bashrc
echo 'export PATH=$JAVA_HOME/bin:$PATH' >> /opt/splunk/.bashrc

# Verify installation
java -version

Install DB Connect App

CLI Installation 
# Download from Splunkbase or use CLI
/opt/splunk/bin/splunk install app splunk-db-connect_3xx.tgz -auth admin:password

# Restart Splunk
/opt/splunk/bin/splunk restart

Configure Java Settings

$SPLUNK_HOME/etc/apps/splunk_app_db_connect/local/db_connect_settings.conf 
[db_connect_settings]
# Java home path
javaHome = /usr/lib/jvm/java-11-openjdk

# JVM heap settings (adjust based on workload)
jvmOptions = -Xms512m -Xmx2048m -XX:+UseG1GC

# Task server settings
taskServerPort = 9998

# Connection validation query interval (seconds)
connectionValidationInterval = 300

Step 5: Configure Database Inputs

Database inputs define the SQL queries and scheduling for data collection. Use rising column or tail mode for incremental collection to avoid duplicate data.

SQL Server Audit Log Input

$SPLUNK_HOME/etc/apps/splunk_app_db_connect/local/db_inputs.conf 
# SQL Server Audit Events - Rising Column Mode
[sqlserver_audit_events]
connection = sqlserver_audit
index = db_audit
sourcetype = mssql:audit
interval = 60
mode = rising
query = SELECT \
    event_time, \
    action_id, \
    succeeded, \
    session_server_principal_name as user_name, \
    server_principal_name as target_user, \
    database_name, \
    schema_name, \
    object_name, \
    statement, \
    client_ip, \
    application_name, \
    host_name \
FROM sys.fn_get_audit_file('/var/opt/mssql/audit/*.sqlaudit', DEFAULT, DEFAULT) \
WHERE event_time > ?

# Column to track for incremental loads
input_timestamp_column_name = event_time
input_timestamp_column_type = timestamp

# Checkpoint settings
tail_rising_column_checkpoint_dir = $SPLUNK_HOME/var/lib/splunk/dbx/checkpoints

Security-Focused SQL Queries

SQL Server - Failed Login Attempts

SQL Server Failed Logins 
SELECT 
    event_time,
    'failed_login' as event_type,
    session_server_principal_name as user_name,
    client_ip as src_ip,
    application_name,
    host_name as src_host,
    'Login failed: ' + CAST(succeeded as VARCHAR) as message
FROM sys.fn_get_audit_file('/var/opt/mssql/audit/*.sqlaudit', DEFAULT, DEFAULT)
WHERE action_id IN ('LGIF', 'LGFL')  -- Login Failed
AND event_time > ?
ORDER BY event_time

SQL Server - Permission Changes

SQL Server Permission Audit 
SELECT 
    event_time,
    action_id,
    session_server_principal_name as changed_by,
    server_principal_name as target_principal,
    database_name,
    schema_name,
    object_name,
    statement as permission_statement,
    client_ip as src_ip
FROM sys.fn_get_audit_file('/var/opt/mssql/audit/*.sqlaudit', DEFAULT, DEFAULT)
WHERE action_id IN ('G', 'R', 'D', 'AL', 'DR')  -- Grant, Revoke, Deny, Alter, Drop
AND event_time > ?
ORDER BY event_time

Oracle - Privileged User Activity

Oracle DBA Activity Monitoring 
SELECT 
    EVENT_TIMESTAMP,
    DBUSERNAME,
    OS_USERNAME,
    USERHOST,
    ACTION_NAME,
    OBJECT_SCHEMA,
    OBJECT_NAME,
    SQL_TEXT,
    RETURN_CODE
FROM UNIFIED_AUDIT_TRAIL
WHERE DBUSERNAME IN (
    SELECT USERNAME FROM DBA_ROLE_PRIVS 
    WHERE GRANTED_ROLE = 'DBA'
)
AND EVENT_TIMESTAMP > ?
ORDER BY EVENT_TIMESTAMP

MySQL - DDL Changes

MySQL Schema Changes 
SELECT 
    event_time,
    user_host,
    thread_id,
    command_type,
    argument as sql_statement
FROM mysql.general_log
WHERE command_type IN ('Query')
AND (argument LIKE 'CREATE%' 
    OR argument LIKE 'ALTER%' 
    OR argument LIKE 'DROP%'
    OR argument LIKE 'GRANT%'
    OR argument LIKE 'REVOKE%')
AND event_time > ?
ORDER BY event_time

Performance Optimization

Database Impact

DB Connect queries run directly against production databases. Always test query performance, use read replicas when possible, and schedule collection during off-peak hours for high-volume queries.

Query Optimization Tips

Optimization Implementation Impact
Index Rising Columns Create indexes on timestamp/ID columns used in WHERE clauses Reduces query execution time significantly
Limit Columns SELECT only required columns, avoid SELECT * Reduces data transfer and memory usage
Batch Size Set appropriate fetch_size (default 1000) Balances memory vs round-trips
Connection Pooling Use shared connections for multiple inputs Reduces database connection overhead
Read Replicas Point queries to read replicas instead of primary Eliminates production database impact

JVM Tuning

High-Volume JVM Settings 
[db_connect_settings]
# For high-volume ingestion (10+ inputs, 1M+ events/day)
jvmOptions = -Xms1024m -Xmx4096m -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:+ParallelRefProcEnabled

# Connection pool settings
maxConnectionPoolSize = 50
connectionTimeout = 30000
idleTimeout = 600000

Troubleshooting

Connection Failed: Authentication Error

Symptoms: "Login failed for user" or "Access denied"

Resolution:

  • Verify credentials in Splunk identity configuration
  • Test connection from Heavy Forwarder: sqlcmd -S host -U user -P password
  • Check database account permissions: must have SELECT on audit tables
  • For SQL Server integrated auth, verify Kerberos configuration
  • Check for password expiration or account lockout
JDBC Driver Not Found

Symptoms: "No suitable driver found" or "ClassNotFoundException"

Resolution:

  • Verify driver JAR is in $SPLUNK_HOME/etc/apps/splunk_app_db_connect/drivers/
  • Check driver file permissions: readable by splunk user
  • Restart Splunk after adding drivers
  • Verify driver version compatibility with Java version
  • Check logs: index=_internal sourcetype=splunkd dbconnect driver
Duplicate Events

Symptoms: Same events appearing multiple times in Splunk

Resolution:

  • Verify rising column mode is configured correctly
  • Check checkpoint file integrity in $SPLUNK_HOME/var/lib/splunk/dbx/checkpoints/
  • Ensure timestamp column has unique, increasing values
  • For batch mode, verify query time boundaries
  • Clear checkpoint and re-ingest if needed: delete checkpoint file and restart input
High Memory Usage

Symptoms: Heavy Forwarder memory exhaustion, OutOfMemoryError

Resolution:

  • Reduce fetch_size parameter (default 1000, try 500)
  • Increase JVM heap: -Xmx4096m
  • Limit max_rows per query execution
  • Add LIMIT clause to queries for testing
  • Monitor JVM stats: 
    index=_internal sourcetype=splunkd component=DbxJava
| stats avg(heap_used_mb) as avg_heap BY host
Slow Query Performance

Symptoms: Long collection intervals, input timeout

Resolution:

  • Add index on rising column in database
  • Review query execution plan: EXPLAIN ANALYZE
  • Reduce collection interval to smaller batches
  • Point to read replica database
  • Consider partitioning large audit tables
  • Monitor query time: 
    index=_internal sourcetype=splunkd component=DbxInputProcessor
| stats avg(query_time_ms) as avg_query_time BY input_name

Rollback & Safety

Emergency: Disable DB Connect Input

Emergency Procedure 
SCENARIO: DB Connect query impacting database performance

OPTION 1: Disable Input via Splunk Web (Preferred)
──────────────────────────────────────────────────
1. Settings → Data Inputs → Splunk DB Connect → Inputs
2. Find problematic input → Edit → Status = Disabled
3. Save

OPTION 2: Disable via Configuration File
────────────────────────────────────────
1. SSH to Heavy Forwarder
2. Edit: $SPLUNK_HOME/etc/apps/splunk_app_db_connect/local/db_inputs.conf
3. Add: disabled = 1 to the input stanza
4. Restart: $SPLUNK_HOME/bin/splunk restart splunk_app_db_connect

OPTION 3: Kill Active Query (Database Side - Emergency)
───────────────────────────────────────────────────────
If query is running and impacting production:

SQL Server:
KILL [session_id]  -- Get from sys.dm_exec_sessions

Oracle:
ALTER SYSTEM KILL SESSION 'sid,serial#';

PostgreSQL:
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE usename='splunk_service';

⚠️ WARNING: Killing queries may corrupt checkpoint. Reset checkpoint after resolution.

COMMUNICATION:
- Notify DBA team immediately (they may need to take action)
- Notify SOC (data gap occurring)
- Document incident for post-mortem

Checkpoint Recovery Procedure

Reset Checkpoint After Issue 
SCENARIO: Need to reset checkpoint (duplicate data or missed data)

⚠️ WARNING: Resetting checkpoint will re-ingest data from the rising column start value

STEP 1: Disable Input
─────────────────────
Disable the input via Splunk Web (see above)

STEP 2: Locate Checkpoint File
──────────────────────────────
ls -la $SPLUNK_HOME/var/lib/splunk/dbx/checkpoints/
# Find file matching your input name

STEP 3: Backup Checkpoint (Optional)
────────────────────────────────────
cp checkpoint_file checkpoint_file.backup

STEP 4: Delete or Edit Checkpoint
─────────────────────────────────
# To re-ingest all data: delete file
rm checkpoint_file

# To re-ingest from specific point: edit rising column value
# (Requires understanding of checkpoint format)

STEP 5: Re-enable Input
───────────────────────
Enable input via Splunk Web

STEP 6: Monitor for Duplicates
──────────────────────────────
index=[target_index] sourcetype=[db_sourcetype] earliest=-1h
| stats count BY [primary_key_field]
| where count > 1
# Should return 0 results (no duplicates)

DB Connect Health Monitoring Query

SPL: Monitor DB Connect Input Health 
`comment("Create scheduled alert to detect DB Connect failures")`

index=_internal sourcetype=splunkd component=DbxInputProcessor earliest=-1h
| stats 
    latest(_time) AS last_run,
    avg(query_time_ms) AS avg_query_ms,
    sum(eval(if(status="success", 1, 0))) AS success_count,
    sum(eval(if(status="error", 1, 0))) AS error_count
    BY input_name
| eval hours_since = round((now() - last_run)/3600, 1)
| eval status = case(
    error_count > 0, "🔴 ERRORS - Check logs",
    hours_since > 2, "🟠 STALE - No activity >2h",
    avg_query_ms > 30000, "🟡 SLOW - Query >30s",
    true(), "✅ Healthy"
)
| table input_name, status, last_run, avg_query_ms, success_count, error_count

`comment("Alert when status contains 🔴 or 🟠")`
