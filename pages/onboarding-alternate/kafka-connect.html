Kafka Connect Integration

Stream data from Apache Kafka to Splunk using the Splunk Connect for Kafka sink connector

📋 Page Status: HARDENED

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This page includes Kafka-specific operational guidance, failure modes, and rollback procedures.

🚨 CRITICAL: Kafka Connect Requires Kafka Expertise

Kafka Connect is NOT a simple integration. Before implementing, ensure:

  • Kafka team ownership: Kafka Connect is managed by Kafka ops team, not Splunk team
  • Consumer lag monitoring: Growing lag means data loss risk
  • Dead Letter Queue: MUST be configured or bad records cause connector failure
  • HEC acknowledgment: Enable indexer acknowledgment to prevent data loss
⚠️ Connector Version Compatibility

Version mismatches cause silent failures:

  • Splunk Connect for Kafka: Must match Kafka Connect framework version
  • Kafka cluster version: Connector has minimum Kafka version requirements
  • Java version: Kafka Connect requires compatible JDK version

Always test upgrades in non-production first.

Architecture Overview

Kafka Connect provides a scalable, reliable method for streaming high-volume data from Apache Kafka into Splunk. This approach is ideal when your organization already uses Kafka as a data pipeline or message broker, enabling real-time ingestion without additional forwarder infrastructure.

Prerequisites

Component Requirement Notes
Kafka Cluster Apache Kafka 2.0+ or Confluent Platform 5.0+ AWS MSK, Azure Event Hubs for Kafka also supported
Kafka Connect Distributed mode cluster with 3+ workers Standalone mode only for testing
Splunk Connect for Kafka Version 2.1+ (latest recommended) Download from Splunkbase or GitHub
Splunk HEC HEC endpoint enabled with valid token Load balancer recommended for HA
Network Connect workers → Splunk HEC (TCP 8088) TLS recommended

Step 1: Install Splunk Connect for Kafka

Download and Deploy

Bash (on each Kafka Connect worker) 
# Download latest release
wget https://github.com/splunk/kafka-connect-splunk/releases/download/v2.1.0/splunk-kafka-connect-v2.1.0.jar

# Copy to Kafka Connect plugins directory
cp splunk-kafka-connect-v2.1.0.jar /opt/kafka/connect-plugins/

# Alternatively, if using Confluent Hub
confluent-hub install splunk/kafka-connect-splunk:2.1.0

# Verify plugin is loaded (after restarting workers)
curl -s localhost:8083/connector-plugins | jq '.[] | select(.class | contains("splunk"))'

Kafka Connect Worker Configuration

connect-distributed.properties 
# Kafka Connect distributed mode configuration
bootstrap.servers=kafka1:9092,kafka2:9092,kafka3:9092
group.id=splunk-connect-cluster

# Plugin path (include Splunk connector)
plugin.path=/opt/kafka/connect-plugins

# Converters
key.converter=org.apache.kafka.connect.storage.StringConverter
value.converter=org.apache.kafka.connect.json.JsonConverter
value.converter.schemas.enable=false

# Internal topic settings
config.storage.topic=splunk-connect-configs
offset.storage.topic=splunk-connect-offsets
status.storage.topic=splunk-connect-status

config.storage.replication.factor=3
offset.storage.replication.factor=3
status.storage.replication.factor=3

# REST interface
rest.advertised.host.name=kafkaconnect1.company.com
rest.port=8083

# Producer settings for HEC batching
producer.batch.size=65536
producer.linger.ms=100

Step 2: Configure Splunk HEC

Create HEC Token for Kafka

inputs.conf (on Indexers or HEC-enabled Heavy Forwarders) 
[http://kafka_ingest]
disabled = 0
token = your-hec-token-here
index = kafka_logs
indexes = kafka_logs,kafka_security,kafka_app
sourcetype = kafka:json
useACK = 1
allowQueryStringAuth = 0
Enable Indexer Acknowledgment

Always enable useACK = 1 for Kafka ingestion. This ensures at-least-once delivery semantics and prevents data loss during indexer restarts or network issues.

Load Balancer Configuration

For high availability, configure a load balancer in front of HEC endpoints:

HAProxy Example 
frontend splunk_hec_frontend
    bind *:8088 ssl crt /etc/haproxy/certs/hec.pem
    default_backend splunk_hec_backend

backend splunk_hec_backend
    balance roundrobin
    option httpchk GET /services/collector/health
    http-check expect status 200
    server idx1 indexer1:8088 check ssl verify none
    server idx2 indexer2:8088 check ssl verify none
    server idx3 indexer3:8088 check ssl verify none

Step 3: Create Splunk Sink Connector

Basic Connector Configuration

splunk-sink-connector.json 
{
  "name": "splunk-sink-security",
  "config": {
    "connector.class": "com.splunk.kafka.connect.SplunkSinkConnector",
    "tasks.max": "4",
    
    "topics": "security-logs,audit-logs,auth-logs",
    
    "splunk.hec.uri": "https://hec-lb.company.com:8088",
    "splunk.hec.token": "your-hec-token-here",
    "splunk.hec.ssl.validate.certs": "true",
    
    "splunk.hec.ack.enabled": "true",
    "splunk.hec.ack.poll.interval": "10",
    "splunk.hec.ack.poll.threads": "2",
    
    "splunk.hec.raw": "false",
    "splunk.hec.json.event.enrichment": "kafka_topic=${topic}",
    
    "splunk.indexes": "{\"security-logs\": \"security\", \"audit-logs\": \"audit\", \"auth-logs\": \"auth\"}",
    "splunk.sourcetypes": "{\"security-logs\": \"kafka:security\", \"audit-logs\": \"kafka:audit\", \"auth-logs\": \"kafka:auth\"}",
    
    "splunk.hec.track.data": "true",
    
    "key.converter": "org.apache.kafka.connect.storage.StringConverter",
    "value.converter": "org.apache.kafka.connect.json.JsonConverter",
    "value.converter.schemas.enable": "false",
    
    "errors.tolerance": "all",
    "errors.deadletterqueue.topic.name": "splunk-dlq",
    "errors.deadletterqueue.context.headers.enable": "true"
  }
}

Deploy Connector via REST API

Bash 
# Create connector
curl -X POST http://kafkaconnect1:8083/connectors \
  -H "Content-Type: application/json" \
  -d @splunk-sink-connector.json

# Check connector status
curl -s http://kafkaconnect1:8083/connectors/splunk-sink-security/status | jq

# List all connectors
curl -s http://kafkaconnect1:8083/connectors | jq

# Pause connector (for maintenance)
curl -X PUT http://kafkaconnect1:8083/connectors/splunk-sink-security/pause

# Resume connector
curl -X PUT http://kafkaconnect1:8083/connectors/splunk-sink-security/resume

# Delete connector
curl -X DELETE http://kafkaconnect1:8083/connectors/splunk-sink-security

Advanced Configurations

Multi-Index Routing

Route different topics to different Splunk indexes:

JSON 
{
  "splunk.indexes": "{
    \"app-logs-prod\": \"app_prod\",
    \"app-logs-dev\": \"app_dev\",
    \"security-*\": \"security\",
    \"default\": \"main\"
  }",
  "splunk.sourcetypes": "{
    \"app-logs-*\": \"kafka:app\",
    \"security-*\": \"kafka:security\"
  }"
}

Field Extraction from Kafka Headers

JSON 
{
  "splunk.hec.json.event.enrichment": "kafka_topic=${topic},kafka_partition=${partition},kafka_offset=${offset}",
  "splunk.header.support": "true",
  "splunk.header.custom": "correlation_id,trace_id,service_name",
  "splunk.header.index": "x-splunk-index",
  "splunk.header.source": "x-splunk-source"
}

Batching and Performance Tuning

JSON 
{
  "splunk.hec.max.batch.size": "500",
  "splunk.hec.max.outstanding.events": "1000000",
  "splunk.hec.max.retries": "10",
  "splunk.hec.socket.timeout": "60000",
  "splunk.hec.total.channels": "4",
  
  "consumer.override.max.poll.records": "500",
  "consumer.override.fetch.min.bytes": "1048576",
  "consumer.override.fetch.max.wait.ms": "500"
}
Tuning Guidelines
  • High throughput: Increase max.batch.size and tasks.max
  • Low latency: Decrease fetch.max.wait.ms and batch sizes
  • Reliability: Enable ACKs, increase retries, configure DLQ

Validation Queries

Verify Data Flow

SPL 
index=security OR index=audit OR index=auth 
    sourcetype="kafka:*" earliest=-1h
| stats count BY index, sourcetype, kafka_topic
| sort -count

Check Ingestion Latency

SPL 
index=security sourcetype="kafka:*" earliest=-1h
| eval ingestion_latency = _indextime - _time
| stats avg(ingestion_latency) as avg_latency_sec,
        max(ingestion_latency) as max_latency_sec,
        p95(ingestion_latency) as p95_latency_sec
    BY kafka_topic
| eval avg_latency_sec = round(avg_latency_sec, 2)

Monitor HEC Health

SPL 
index=_internal sourcetype=splunk_httpinput earliest=-1h
| stats sum(total_bytes) as bytes,
        sum(total_events) as events,
        avg(response_time) as avg_response_ms
    BY channel
| eval MB = round(bytes/1024/1024, 2)
| table channel, events, MB, avg_response_ms

Check Dead Letter Queue

Kafka CLI 
# Check DLQ topic for failed messages
kafka-console-consumer \
  --bootstrap-server kafka1:9092 \
  --topic splunk-dlq \
  --from-beginning \
  --max-messages 10 \
  --property print.headers=true

Connector Monitoring

JMX Metrics

Key JMX metrics to monitor for the Splunk Sink Connector:

Metric Description Alert Threshold
sink-record-send-rate Records sent to Splunk per second Alert if drops >50% baseline
sink-record-active-count Records in-flight to Splunk Alert if exceeds 100,000
offset-commit-success-rate Successful offset commits per second Alert if drops to 0
total-record-failures Total failed records count Alert on any increase

Troubleshooting

Connector Task Failures 
# Check task status and errors
curl -s http://kafkaconnect1:8083/connectors/splunk-sink-security/tasks/0/status | jq

# View connector logs
grep -i "splunk-sink" /var/log/kafka/connect.log | tail -100

# Restart failed task
curl -X POST http://kafkaconnect1:8083/connectors/splunk-sink-security/tasks/0/restart
HEC Connection Errors
  • Verify HEC endpoint is reachable: curl -k https://hec-lb:8088/services/collector/health
  • Check HEC token is valid and not disabled
  • Verify SSL certificate if ssl.validate.certs=true
  • Check firewall rules between Connect workers and HEC
Consumer Lag Growing
  • Increase tasks.max (up to partition count)
  • Increase batch sizes for better throughput
  • Add more Kafka Connect workers
  • Check HEC endpoint capacity
# Check consumer lag
kafka-consumer-groups \
  --bootstrap-server kafka1:9092 \
  --group connect-splunk-sink-security \
  --describe

Rollback & Safety

Emergency: Pause Kafka Connector

Emergency Procedure 
SCENARIO: Connector causing issues (volume spike, bad data, HEC overload)

OPTION 1: Pause Connector (Preferred)
─────────────────────────────────────
# Pause connector - data stays in Kafka topics
curl -X PUT http://kafkaconnect1:8083/connectors/splunk-sink-security/pause

# Verify paused
curl -s http://kafkaconnect1:8083/connectors/splunk-sink-security/status | jq '.connector.state'
# Should return "PAUSED"

# When ready to resume:
curl -X PUT http://kafkaconnect1:8083/connectors/splunk-sink-security/resume

⚠️ NOTE: While paused, consumer lag grows. Data is not lost (retained per Kafka topic retention).

OPTION 2: Delete Connector (If Pause Not Working)
─────────────────────────────────────────────────
# Delete connector
curl -X DELETE http://kafkaconnect1:8083/connectors/splunk-sink-security

# Verify deleted
curl -s http://kafkaconnect1:8083/connectors | jq
# Should not contain splunk-sink-security

⚠️ WARNING: Deleting loses offset tracking. Re-creating will require offset management.

OPTION 3: Block at HEC (If Connector Unresponsive)
──────────────────────────────────────────────────
1. Disable HEC token used by connector
2. Connector will receive 403 errors and pause sending
3. This stops flow immediately

COMMUNICATION:
- Notify Kafka team immediately
- Notify SOC (data gap occurring)
- Monitor consumer lag to track backlog

Consumer Lag Recovery Procedure

Recovery from High Consumer Lag 
SCENARIO: Connector was paused and now has significant lag to catch up

STEP 1: Assess Lag
──────────────────
kafka-consumer-groups \
  --bootstrap-server kafka1:9092 \
  --group connect-splunk-sink-security \
  --describe

# Note LAG column - total records to catch up

STEP 2: Estimate Catchup Time
─────────────────────────────
# Current throughput (records/sec)
# Estimated time = Total Lag / Throughput

STEP 3: Scale Up for Faster Catchup (Optional)
──────────────────────────────────────────────
# Temporarily increase tasks (up to partition count)
curl -X PUT http://kafkaconnect1:8083/connectors/splunk-sink-security/config \
  -H "Content-Type: application/json" \
  -d '{
    ... existing config ...
    "tasks.max": "10"
  }'

STEP 4: Monitor Catchup Progress
────────────────────────────────
watch -n 30 'kafka-consumer-groups --bootstrap-server kafka1:9092 \
  --group connect-splunk-sink-security --describe | grep -E "LAG|TOPIC"'

STEP 5: Restore Normal Configuration
────────────────────────────────────
# Once lag returns to normal, restore original tasks.max

NOTE: During catchup, Splunk may receive high event volume.
Coordinate with Splunk admin to ensure indexer capacity.

Kafka Connect Health Monitoring

SPL: Monitor Kafka Connect Data Arrival 
`comment("Create scheduled alert to detect Kafka Connect failures")`
`comment("Assumes data arrives via HEC with identifiable sourcetype")`

index=kafka_logs OR index=application sourcetype=kafka:* earliest=-1h
| bucket _time span=5m
| stats count BY _time, sourcetype
| streamstats window=3 avg(count) AS avg_count BY sourcetype
| eval pct_change = round(((count - avg_count) / avg_count) * 100, 1)
| where pct_change < -50 OR count = 0
| eval alert = case(
    count = 0, "🔴 NO DATA from Kafka",
    pct_change < -80, "🔴 CRITICAL: Volume drop >80%",
    pct_change < -50, "🟠 WARNING: Volume drop >50%"
)
| table _time, sourcetype, count, avg_count, pct_change, alert

`comment("Alert when any row has alert field populated")`
