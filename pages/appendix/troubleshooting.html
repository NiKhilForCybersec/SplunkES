☁️ Splunk Cloud Safety Box — Appendix / Troubleshooting

✅ Allowed in Cloud: All SPL queries, search-based troubleshooting, and ES UI workflows apply in Cloud. Internal index searches (index=_internal, index=_audit) work in Cloud.

⚠️ Restricted in Cloud: CLI-based troubleshooting (btool, splunkd.log via filesystem, splunk restart) does not apply. Filesystem paths and OS-level commands apply only to customer-managed HFs.

🔄 Cloud-Safe Alternative: Replace filesystem-based log inspection with index=_internal sourcetype=splunkd. Replace btool with | rest /services/configs/conf-[name]. For issues requiring Splunk-side intervention, file a support ticket with evidence from your search-based troubleshooting.

🚨 CRITICAL: Before Making Changes

Troubleshooting should diagnose, not fix. Before making any changes:

  • Document the issue: Screenshot current state before changes
  • Follow change management: Use the Delivery Operating Model for production changes
  • Have a rollback plan: Know how to undo any change you make
  • Communicate: Notify SOC if troubleshooting impacts live detections

Data Onboarding Issues

❌ No Data Appearing in Index

Symptom

Search returns no results: index=YOUR_INDEX earliest=-24h

Diagnostic Steps

  1. Check input status:
    SPL - Input Status 
    | rest /services/data/inputs/all
| search title="*YOUR_INPUT*"
| table title, disabled, index
  2. Verify index exists:
    SPL - Index Check 
    | rest /services/data/indexes
| search title="YOUR_INDEX"
| table title, totalEventCount, currentDBSizeMB
  3. Check for parsing errors:
    SPL - Parsing Errors 
    index=_internal sourcetype=splunkd component=LineBreakingProcessor
| stats count BY message
| sort - count

Common Causes & Solutions

CauseSolution
Input disabledEnable input in Settings → Data Inputs
Wrong index in input configEdit input, correct index name
Index doesn't existCreate index in Settings → Indexes
Network/firewall blockingVerify connectivity from source to Splunk
Permissions issueCheck file permissions for file monitors

❌ Wrong Sourcetype Assigned

Symptom

Data appears with incorrect sourcetype (e.g., shows as generic_json instead of expected type)

Diagnostic Query

SPL - Sourcetype Distribution 
index=YOUR_INDEX earliest=-1h
| stats count BY sourcetype, source
| sort - count

Solutions

  1. Edit input configuration to set explicit sourcetype
  2. Add props.conf stanza with correct sourcetype assignment
  3. If using HEC, ensure sourcetype is set in HEC token or event metadata

❌ Timestamp Parsing Incorrect

Symptom

Events appear with wrong timestamps, often defaulting to indexing time or showing future dates

Diagnostic Query

SPL - Timestamp Analysis 
index=YOUR_INDEX earliest=-1h
| eval index_time=strftime(_indextime, "%Y-%m-%d %H:%M:%S")
| eval event_time=strftime(_time, "%Y-%m-%d %H:%M:%S")
| eval diff_seconds=_indextime - _time
| stats count min(diff_seconds) AS min_diff max(diff_seconds) AS max_diff avg(diff_seconds) AS avg_diff
| eval status=case(
    avg_diff < 0, "FUTURE TIMESTAMPS - Check TZ",
    avg_diff > 86400, "STALE - Using index time?",
    true(), "OK"
)

Solutions

  1. Add TIME_FORMAT in props.conf matching your timestamp format
  2. Set TIME_PREFIX to identify where timestamp appears in event
  3. Configure TZ if source timezone differs from Splunk server
props.conf - Timestamp Configuration 
[your_sourcetype]
TIME_PREFIX = "timestamp":
TIME_FORMAT = %Y-%m-%dT%H:%M:%S.%3N%Z
MAX_TIMESTAMP_LOOKAHEAD = 30
TZ = UTC

Data Model Problems

❌ Data Not in Data Model

Symptom

tstats returns no results but raw search does: | tstats count FROM datamodel=Authentication returns 0

Diagnostic Steps

  1. Verify CIM tags:
    SPL - Check Tags 
    index=YOUR_INDEX sourcetype=YOUR_SOURCETYPE earliest=-1h
| head 1
| tags | fields tag::*
  2. Verify acceleration is enabled:
    SPL - Acceleration Status 
    | rest /services/admin/summarization
| search datamodel_name="Authentication"
| table datamodel_name, summary.complete, summary.is_inprogress

Common Causes & Solutions

CauseSolution
Missing CIM tagsAdd tags.conf: [source::your_source]
authentication = enabled
Acceleration not enabledSettings → Data Models → Edit → Enable Acceleration
Acceleration buildingWait for acceleration to complete (check summary.complete)
Index not in data model constraintEdit data model, add index to constraint

❌ Data Model Acceleration Stuck

Symptom

Acceleration shows is_inprogress=1 but never completes, or completion percentage stays low

Diagnostic Query

SPL - Acceleration Health 
| rest /services/admin/summarization BY splunk_server
| search datamodel_acceleration.enabled=1
| eval complete_pct=round('summary.complete'*100, 1)
| eval size_gb=round('summary.size'/1024/1024/1024, 2)
| eval last_error='summary.last_error'
| table splunk_server, datamodel_name, complete_pct, size_gb, summary.is_inprogress, last_error

Solutions

  1. Check for errors in last_error field
  2. Rebuild acceleration: Disable, wait, re-enable
  3. Check disk space on indexers for TSIDX storage
  4. Verify search head can communicate with all indexers

❌ CIM Fields Not Extracting

Symptom

Raw data has values but CIM fields (user, src, dest) are empty or wrong

Diagnostic Query

SPL - Field Extraction Check 
index=YOUR_INDEX sourcetype=YOUR_SOURCETYPE earliest=-1h
| head 10
| table _raw, user, src, dest, action
| eval user_status=if(isnotnull(user), "✓", "✗")
| eval src_status=if(isnotnull(src), "✓", "✗")

Solutions

  1. Check if Splunk Add-on for the technology is installed
  2. Verify props.conf field extraction configuration
  3. Create field aliases in props.conf to map source fields to CIM fields
props.conf - Field Aliases 
[your_sourcetype]
FIELDALIAS-user = username AS user
FIELDALIAS-src = source_ip AS src
FIELDALIAS-dest = destination_ip AS dest
FIELDALIAS-action = event_result AS action

Detection Issues

❌ Correlation Search Not Running

Symptom

Correlation search shows as enabled but no notables are created and search doesn't appear in Job Inspector

Diagnostic Steps

  1. Check search status:
    SPL - Correlation Search Status 
    | rest /services/saved/searches
| search title="*Your Detection*" AND is_scheduled=1
| table title, disabled, next_scheduled_time, cron_schedule
  2. Check scheduler logs:
    SPL - Scheduler Errors 
    index=_internal sourcetype=scheduler savedsearch_name="*Your Detection*"
| stats count BY status, run_time
| sort - run_time

Common Causes & Solutions

CauseSolution
Search disabledEnable in Content Management
Scheduler skippingCheck concurrent search limits, reduce search load
Search syntax errorRun search manually to identify errors
Permissions issueVerify search owner has required permissions

❌ Too Many False Positives

Symptom

Detection fires constantly, overwhelming SOC with low-value alerts

Diagnostic Query

SPL - False Positive Analysis 
index=notable rule_name="Your Detection"
| stats count BY user, src, dest
| sort - count
| head 20
| eval likely_fp=if(count > 100, "HIGH - Consider exclusion", "Review")

Tuning Strategies

  1. Raise thresholds: If count >= 5 is too sensitive, try count >= 10
  2. Add exclusions: Create lookup for known-good sources/users
  3. Narrow scope: Limit to specific indexes, sourcetypes, or asset classes
  4. Time-based tuning: Suppress during known noisy periods
SPL - Add Exclusion Lookup 
| your detection logic
| lookup detection_exclusions.csv src OUTPUT is_excluded
| where isnull(is_excluded) OR is_excluded!="true"

❌ Detection Too Slow

Symptom

Correlation search takes longer than schedule interval or times out

Diagnostic Query

SPL - Search Performance 
index=_internal sourcetype=scheduler savedsearch_name="Your Detection"
| stats avg(run_time) AS avg_runtime max(run_time) AS max_runtime BY status
| eval avg_runtime=round(avg_runtime, 2)
| eval max_runtime=round(max_runtime, 2)

Performance Improvements

  1. Use tstats: Always use data models with tstats instead of raw search
  2. Reduce time range: Search -6m instead of -1h if detection allows
  3. Add early filters: Filter in search command, not in where
  4. Limit fields: Use | fields to extract only needed fields

Notable Event Problems

❌ Notables Not Creating

Symptom

Correlation search runs and returns results, but no notable events appear in Incident Review

Diagnostic Steps

  1. Verify Adaptive Response configured:
    Check Notable Action 
    Content Management → Correlation Searches → Your Detection
→ Edit → Adaptive Response Actions
→ Verify "Create Notable Event" action exists and is enabled
  2. Check for throttling:
    SPL - Throttle Check 
    index=_internal sourcetype=scheduler savedsearch_name="Your Detection"
| stats count BY status, suppress_count
| where suppress_count > 0

Common Causes & Solutions

CauseSolution
Notable action missingAdd "Create Notable Event" action
Throttling suppressingReview throttle settings, consider different throttle fields
Required fields missingEnsure search outputs required notable fields
Permissions issueVerify user can write to notable index

❌ Notable Missing Fields

Symptom

Notable events are created but key fields (user, src, dest) are blank in Incident Review

Solutions

  1. Ensure fields are included in | table output
  2. Check field names match expected notable field names
  3. Use | rename if source field names differ
SPL - Ensure Notable Fields 
| your detection logic
| rename Authentication.user AS user
| rename Authentication.src AS src
| eval rule_name="Your Detection Name"
| eval severity="high"
| table _time, user, src, dest, rule_name, severity, description

Performance Issues

❌ ES Dashboards Loading Slowly

Symptom

Security Posture, Incident Review, and other ES dashboards take >30 seconds to load

Diagnostic Steps

  1. Check data model acceleration: Ensure all ES data models are accelerated and complete
  2. Review asset/identity lookup size: Large lookups slow ES performance
  3. Check concurrent searches: ES dashboards run many searches simultaneously

Solutions

  • Verify all CIM data models have acceleration enabled and >95% complete
  • Optimize asset and identity lookups (deduplicate, remove stale entries)
  • Increase scheduler search concurrency if capacity allows
  • Consider search head pooling for large environments

❌ Scheduler Backlog Building

Symptom

Correlation searches show "skipped" status, notable events delayed significantly

Diagnostic Query

SPL - Scheduler Health 
index=_internal sourcetype=scheduler
| stats count BY status
| addtotals
| eval skip_rate=round(count/Total*100, 1) WHERE status="skipped"

Solutions

  1. Increase max_searches_per_cpu in limits.conf (carefully)
  2. Stagger correlation search schedules to avoid clustering
  3. Optimize slow-running searches
  4. Consider adding search head capacity

Integration Issues

❌ Webhook Not Firing

Symptom

Adaptive Response webhook action configured but external system not receiving notifications

Diagnostic Steps

  1. Check action logs:
    SPL - Webhook Errors 
    index=_internal sourcetype=splunkd component=sendmodalert action=webhook
| stats count BY log_level, message
| sort - count
  2. Test connectivity: Verify Splunk server can reach webhook URL (firewall, proxy)
  3. Validate payload: Test webhook URL with sample payload using curl

Common Causes

  • Firewall blocking outbound connection
  • SSL certificate validation failure
  • Incorrect webhook URL
  • Malformed JSON payload
  • Authentication required but not configured

❌ HEC Events Rejected

Symptom

HTTP Event Collector returns errors, events not indexed

Diagnostic Query

SPL - HEC Errors 
index=_internal sourcetype=splunkd component=HttpInputDataHandler
| stats count BY log_level, message
| sort - count

Common HEC Errors

ErrorCauseSolution
Invalid tokenToken disabled or incorrectVerify token is enabled and correct
Invalid data formatMalformed JSONValidate JSON payload format
Index not allowedToken not authorized for target indexAdd index to token's allowed indexes
Queue fullIngestion rate exceeds capacityScale indexing tier or reduce event rate
