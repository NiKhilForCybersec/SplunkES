Splunk Cloud + ES: What's Different

Read this before touching any configuration page in this handbook

🛑 STOP — Read This Page First

This handbook was originally written with Splunk Enterprise patterns: direct filesystem access, CLI commands, Heavy Forwarder configuration, and indexer-level operations. Most of those patterns do not apply in Splunk Cloud.

Every page in this handbook now carries a Cloud Safety Box that tells you what is allowed, what is restricted, and what the Cloud-safe alternative is. This page is the master reference for understanding why those distinctions exist.

If you are running Splunk Cloud with Enterprise Security, this page is your ground truth.

1 — Splunk Enterprise vs. Splunk Cloud: Practical Differences

This is not a marketing comparison. This is what matters operationally when you are configuring ES, onboarding data sources, and managing detection content.

Capability Splunk Enterprise Splunk Cloud
OS / filesystem access Full SSH access to all Splunk instances. Can edit any .conf file directly. Can run CLI commands. No OS access. No SSH. No filesystem. No CLI on search heads or indexers. All configuration is via Splunk Web UI, REST API, or support ticket.
Service restarts Admin runs splunk restart at will. Rolling restarts on indexer cluster via CLI. You cannot restart Splunk services. Splunk manages restarts. Some app installations trigger automatic rolling restarts (which may cause brief search disruption).
Index creation Edit indexes.conf on cluster master, push bundle. Create indexes via Splunk Web (Settings → Indexes) or via support ticket. You do not control index storage paths, bucket sizes, or replication factor.
props.conf / transforms.conf Edit files directly on indexers, search heads, HFs. Use btool to debug. Search-time configurations (REPORT, EXTRACT, FIELDALIAS, EVAL, LOOKUP) can be deployed via UI (Settings → Fields) or packaged in an app installed on search heads. Index-time configurations (TRANSFORMS for routing/masking, TIME_FORMAT on indexers) require a Splunk support ticket or a vetted app deployed to indexers via support.
Add-on / TA installation Copy to $SPLUNK_HOME/etc/apps/ on each tier (SH, indexer, HF). Use deployment server for UFs. Search head: Self-Service App Install (SSAI) for Cloud-vetted apps via Splunk Web (Apps → Install App from File or Find More Apps). Indexers: Requires Splunk support ticket — you cannot install apps on indexers yourself. IDM: Requires support ticket (Classic Experience) or install on SH (Victoria Experience).
Modular / scripted inputs Run anywhere: SH, HF, standalone instance. Classic Experience: Must run on IDM (Inputs Data Manager) or customer-managed HF. Victoria Experience: Can run on search head directly. Never on indexers. Java-based modular inputs (like Akamai SIEM connector) may not work on IDM — verify with Splunk support.
Heavy Forwarder Deployed on-prem, managed by customer. Handles parsing, routing, syslog collection. Customer-managed, outside Splunk Cloud. Splunk Cloud does not provide or manage HFs. You deploy and maintain HFs in your own infrastructure. HFs connect to Splunk Cloud via outputs.conf using Splunk-provided certificates.
HEC (HTTP Event Collector) Configured on indexers or HFs. Full control over tokens, acknowledgment, load balancing. Primary ingestion method for Cloud. Create HEC tokens via Splunk Web on the search head. Tokens route to the Cloud indexing tier. Global HEC settings are managed by Splunk. Endpoints use the Cloud-specific HEC URL.
btool $SPLUNK_HOME/bin/splunk btool [conf] list --debug — essential debugging tool. Not available. No CLI access means no btool. Alternative: use | rest /services/configs/conf-props or the Admin's Little Helper app (Splunkbase 6368) to inspect configurations via SPL.
Deployment server Centrally manage UF configurations and app deployments. Splunk Cloud does not include a deployment server. You must run your own deployment server in your infrastructure to manage your UFs. Alternatively, use third-party tools (Puppet, Chef, Ansible) for UF management.
Data model acceleration Full control via datamodels.conf. Can force rebuilds via UI or CLI. Can tune parallel summarization in limits.conf. Acceleration works identically in behavior. Rebuild via UI: Settings → Data Models → expand row → Rebuild. Parallel summarization changes: File a support ticket. Do not manually edit datamodels.conf — use the CIM Setup page or ES Data Model Acceleration Enforcement modular input.
Correlation searches Deploy via UI, conf files, or app packages. Identical behavior. Deploy and manage via ES UI (Configure → Content → Content Management). App-packaged correlation searches work via SSAI. No differences in search logic or scheduling.

2 — What Is NOT Allowed in Splunk Cloud

🚫 Restricted Actions — Do Not Attempt

Attempting these will either silently fail, trigger a support escalation, or violate your Splunk Cloud SLA.

Restricted Action Why It's Restricted & What Happens
Direct indexer access Splunk manages the indexing tier. You have no SSH, no REST API access to indexers, and no ability to deploy apps or edit configs on indexers directly. All indexer-tier changes go through Splunk support or vetted app installation.
Restarting Splunk services There is no splunk restart command available. App installations may trigger automatic restarts. If you need a restart for a config change to take effect, file a support ticket.
Arbitrary modular inputs on search heads (Classic Experience) On Classic Experience, running modular/scripted inputs on search heads impacts search performance and voids support SLAs for search-related issues. Use IDM or a customer-managed HF instead. (Victoria Experience allows modular inputs on SH.)
Unvetted TAs on indexers Only Splunk-vetted, Cloud-certified apps can be installed on the indexing tier. You request installation via support ticket. Unvetted apps cannot be deployed to indexers.
Global props.conf / transforms.conf edits on indexers You cannot edit $SPLUNK_HOME/etc/system/local/ on indexers. Index-time transformations (TRANSFORMS for routing, null-queue, data masking, sourcetype overriding) require a Splunk support ticket to deploy as a packaged app. The app installation triggers a rolling restart.
Editing limits.conf, server.conf, authorize.conf directly System-level configuration files are managed by Splunk. Changes to search limits, concurrent search caps, or system settings require a support ticket. Some settings can be adjusted via the Splunk Cloud admin UI.
Using btool CLI No filesystem access means no btool. Use REST API queries or the Admin's Little Helper app for configuration inspection.
Managing indexer cluster or cluster master The indexer cluster is fully managed by Splunk. You do not interact with the cluster master, push bundles, or manage replication/search factor.
Controlling index storage paths, bucket sizes, or retention via conf files Index retention is set when creating the index. For changes, use Splunk Web or file a support ticket. You do not control tstatsHomePath, homePath, or volume definitions.

3 — What IS Allowed and Preferred in Splunk Cloud

✅ Cloud-Native Patterns — Use These
Allowed Action How to Execute
HEC (HTTP Event Collector) Primary data ingestion path. Create tokens via Splunk Web → Settings → Data Inputs → HTTP Event Collector. Bind tokens to specific indexes and sourcetypes. Use the Cloud-specific HEC endpoint URL provided in your Cloud admin panel.
Edge Processor / Ingest Actions Splunk's cloud-native data transformation layer. Use for routing, filtering, masking, and field extraction before indexing. Configured via Splunk Web — no CLI or conf files needed. Available on newer Cloud stacks.
Cloud-approved add-ons on SH Install via Self-Service App Install (SSAI): Apps → Install App from File (for private apps) or Find More Apps (for Splunkbase). The app must be Cloud-vetted. Search-time knowledge (field extractions, aliases, lookups, tags) takes effect immediately.
Search-time field extraction All REPORT, EXTRACT, FIELDALIAS, EVAL, LOOKUP, and calculated field configurations work on search heads without indexer involvement. Deploy via TAs on the SH, via Settings → Fields, or via apps installed through SSAI.
ES UI-based configuration All ES workflows are UI-driven: correlation search management (Configure → Content → Content Management), data model acceleration (Settings → Data Inputs → Data Model Acceleration Enforcement), notable suppression, adaptive response actions, and risk scoring. No conf file editing is required for ES operations.
Index creation via UI Settings → Indexes → New Index. Set name, retention, and data type. The indexing tier handles storage automatically.
REST API for configuration inspection Use | rest /services/configs/conf-props, | rest /services/data/indexes, and similar REST endpoints from SPL to inspect active configurations. Replaces btool for debugging.
Customer-managed HFs and UFs Deploy Heavy Forwarders and Universal Forwarders in your own infrastructure. Connect them to Splunk Cloud using the credentials package provided by Splunk. HFs handle syslog collection, parsing, and forwarding. UFs handle file monitoring and WinEventLog.
Data Manager (Victoria Experience) Cloud-native data onboarding for supported sources (AWS, Azure, GCP, Salesforce, etc.). Configured via Splunk Web. Automates HEC setup, source configuration, and index-time parsing for supported source types.
CIM Setup page Configure data model acceleration settings, index allow lists, and tag allow lists via Apps → Manage Apps → Splunk Common Information Model → Set Up. Works identically on Cloud and Enterprise.

Pattern A — External API Polling → HEC

Use when: The data source provides a REST API (e.g., Akamai SIEM, CrowdStrike Falcon, vendor APIs).

Architecture: Deploy a collector process (AWS Lambda, EC2 instance, Azure Function, Docker container, or on-prem server) in your infrastructure. The collector polls the vendor API, transforms events as needed, and POSTs them to the Splunk Cloud HEC endpoint over HTTPS.

Cloud advantage: No dependency on Splunk-side modular inputs. You control the collector lifecycle, credentials, and polling logic. HEC handles authentication and indexing.

Pattern B — Vendor Push → HEC

Use when: The vendor supports direct webhook or HTTPS push to an endpoint (e.g., Okta System Log, Duo, many SaaS platforms).

Architecture: Configure the vendor to send events directly to your Splunk Cloud HEC endpoint. Set the HEC token, index, and sourcetype in the vendor's admin console.

Cloud advantage: Zero infrastructure on your side. The vendor pushes directly to Cloud. Ensure the vendor supports custom headers for HEC token authentication.

Pattern C — Cloud-Native Streaming (Event Hub / SQS / Pub/Sub)

Use when: Logs originate in a cloud platform (Azure, AWS, GCP) and are routed through the platform's native streaming service.

Architecture: Use Splunk's Data Manager or the appropriate Splunk add-on (e.g., Splunk Add-on for Microsoft Cloud Services, Splunk Add-on for AWS) to consume from the streaming service. On Victoria Experience, the add-on runs on the search head. On Classic Experience, use IDM.

Pattern D — Syslog → Customer-Managed HF → Cloud

Use when: On-prem devices (firewalls, switches, load balancers) emit syslog.

Architecture: Deploy Heavy Forwarder(s) in your network. HFs receive syslog, apply parsing (props.conf/transforms.conf), and forward parsed events to Splunk Cloud via the encrypted Splunk-to-Splunk connection using the credentials package.

Key point: The HF is YOUR infrastructure — you have full filesystem and CLI access to it. Splunk Cloud does not manage it.

Pattern E — UF → Cloud

Use when: Collecting file-based logs or Windows Event Logs from servers.

Architecture: Deploy Universal Forwarders on endpoints. UFs monitor files or WinEventLog and forward raw data to Splunk Cloud. Parsing happens on the Cloud indexing tier (requires the TA installed on indexers — request via support ticket).

5 — Dangerous Patterns Copied from Enterprise Documentation

⚠️ These Enterprise Patterns Will Fail or Cause Problems in Cloud

If you see these patterns in vendor documentation, Splunk Community posts, or older runbooks, do not follow them in a Splunk Cloud environment.

Dangerous Pattern Why It Fails in Cloud Cloud-Safe Alternative
"SSH to the search head and edit props.conf" No SSH access. No filesystem access. Package the configuration in an app and install via SSAI. Or use Settings → Fields for search-time extractions.
"Run splunk restart after config changes" No CLI access. Cannot restart services. Search-time changes take effect without restart. For index-time changes, file a support ticket (the app install will trigger a rolling restart).
"Deploy TA to indexers via cluster master bundle push" No access to cluster master or indexers. File a support ticket requesting TA installation on indexers. Provide the exact app name and version. Splunk will vet and deploy it.
"Install modular input add-on on the search head" (Classic Experience) On Classic Experience, modular inputs on SH cause search performance degradation and void support SLAs. Use IDM for cloud-based inputs, or deploy a customer-managed HF for on-prem sources. (Victoria Experience allows modular inputs on SH.)
"Use btool props list --debug to verify configuration" No CLI, no btool. Use | rest /services/configs/conf-props from SPL, or install Admin's Little Helper app (Splunkbase 6368).
"Edit indexes.conf to add tstatsHomePath" No access to indexes.conf on indexers. Storage paths are managed by Splunk. Create indexes via UI. For DMA storage tuning, file a support ticket.
"Run splunk rebuild acceleration from CLI" No CLI access. Use Settings → Data Models → expand row → Rebuild. Or use the Data Model Audit dashboard in ES to monitor acceleration status.
"Set up a deployment server to manage UFs" Splunk Cloud does not include a deployment server. Deploy and manage your own deployment server in your infrastructure. Or use configuration management tools (Puppet, Chef, Ansible).
"Edit limits.conf to increase max concurrent searches" System conf files are managed by Splunk. File a support ticket with the specific setting change you need and the business justification.
"Copy the backup to $SPLUNK_HOME/etc/apps/" No filesystem access. Export app configurations via the UI, version them in Git, and redeploy via SSAI if rollback is needed.

6 — Classic vs. Victoria Experience: Know Your Stack

Splunk Cloud comes in two "Experience" types that determine what you can run on the search tier. This matters critically for add-on modular inputs.

Capability Classic Experience Victoria Experience
Modular inputs on SH Not supported. Voids search SLAs. Must use IDM or customer-managed HF. Supported. Can run modular/scripted inputs directly on search head.
IDM (Inputs Data Manager) Required for cloud-based modular inputs. Not required. Upon upgrade from Classic → Victoria, Splunk migrates all IDM apps/configs to the search head and removes the IDM.
Data Manager Available on AWS-hosted Classic stacks. Fully available.
Self-Service App Install Available for SH. IDM app installs require support ticket. Available for SH (which now handles IDM functions).
🔍 How to Check Your Experience Type

Log into Splunk Cloud → click the Splunk logo (top-left) → About. The Experience type is displayed. Alternatively, check with your Splunk account team or look at the Cloud stack provisioning documentation you received.

7 — Enterprise Security Behaviors Identical Across Cloud and Enterprise

The following ES components work identically in Splunk Cloud and Splunk Enterprise. Do not second-guess these — they are the same.

ES Component Cloud Behavior
Correlation searches Search logic, scheduling, throttling, adaptive response actions, and notable event creation are identical. All management is via the ES UI (Configure → Content → Content Management). No conf file editing needed on either platform.
Notable events & Incident Review Identical. Notable events are stored in the notable index. Incident Review dashboard works the same way. Status assignments, urgency calculations, and ownership are identical.
CIM data models Data model definitions (field names, constraints, tags) are identical. The CIM add-on (Splunk_SA_CIM) ships with ES on both platforms.
Data model acceleration Acceleration behavior (TSIDX summarization, tstats queries) is identical. Management differs: in Cloud, use the ES UI for DMA enforcement (Settings → Data Inputs → Data Model Acceleration Enforcement) and the CIM Setup page for index/tag allow lists. Do not attempt to edit datamodels.conf on indexers — file a support ticket if advanced changes are needed.
Risk scoring (RBA) Identical. Risk factors, risk objects, risk index, and risk-based alerting rules work the same way.
Asset & Identity lookups Identical. Upload CSV lookups via Splunk Web or configure lookup inputs. The ES Asset and Identity Framework processes them the same way.
ESCU (Enterprise Security Content Updates) Install via SSAI on the search head. Content is identical. Deployment and enablement workflow is the same UI path.
Suppression rules Identical. Managed via ES UI.
Investigations Identical.

8 — How to Read Cloud Safety Boxes in This Handbook

Every page in this handbook that contains configuration steps now includes a Cloud Safety Box near the top. Here is what the box means:

☁️ Splunk Cloud Safety Box — [Page Topic]

✅ Allowed in Cloud: Actions you can take without restriction.

⚠️ Restricted in Cloud: Actions that require a support ticket, are not possible, or require an alternative approach.

🔄 Cloud-Safe Alternative: What to do instead of the Enterprise pattern described on the page.

📋 Verify: Items you should confirm with Splunk Cloud support or your account team before proceeding.

When you see Enterprise-specific commands (like btool, splunk restart, or filesystem paths), the Cloud Safety Box tells you the Cloud-equivalent approach. The original Enterprise content is preserved because it applies to customer-managed Heavy Forwarders and any hybrid environments.
