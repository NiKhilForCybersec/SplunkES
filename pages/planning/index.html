🚨 HARD GATE — Complete Intake Before ANY Work Begins

DO NOT start detection engineering work without completing the intake checklist below. The most common project failures occur because teams skip planning and discover blockers mid-project. Required before work begins:

  • Stakeholder sign-off on scope document
  • Log source availability confirmed (or onboarding timeline agreed)
  • Success criteria documented in writing
  • SOC capacity confirmed for alert triage
⚠️ Retail Business Timing — Project Scheduling

Detection engineering projects must account for retail business cycles:

  • Avoid go-live during: Black Friday through New Year, major promotions, inventory periods
  • SOC capacity: Verify SOC staffing during monitoring-only period
  • Change freezes: No new detections during code freezes
📋 Purpose

Define scope, stakeholders, and acceptance criteria BEFORE starting any detection engineering work. This prevents scope creep, misaligned expectations, and failed deliveries.

Intake Checklist

Complete this checklist before starting any project:

  • Business Objective Defined What threat or risk does this project address?
  • Stakeholders Identified Who owns approval? Who owns log sources? Who triages alerts?
  • Log Sources Confirmed Are required logs available? If not, what's the onboarding timeline?
  • Success Criteria Documented How will we know the project is complete?
  • Timeline Agreed Realistic delivery dates for each phase
  • Constraints Acknowledged Single Splunk Cloud environment, no RBA, etc.

Acceptance Criteria Framework

Every project phase needs explicit acceptance criteria:

Phase 1: Log Coverage

✅ Phase 1 Complete When:
  • All required log sources identified in coverage matrix
  • Each log source has confirmed ownership
  • Logs are ingesting with <5 minute latency
  • Data volume matches expected baseline (±20%)
  • No critical parsing errors in last 24 hours

Phase 2: Data Quality

✅ Phase 2 Complete When:
  • All required fields are populated (>95% completeness)
  • Timestamps are correctly parsed to _time
  • No timezone offset issues
  • Field names match expected schema

Phase 3: Detection

✅ Phase 3 Complete When:
  • Correlation search passes backtest validation
  • 7-14 day monitoring-only period complete
  • False positive rate <5% (or agreed threshold)
  • Triage runbook documented and reviewed
  • SOC team trained on new detection

Stop & Escalate Conditions

🛑 Stop Work & Escalate When:
  • Missing Log Sources: Required logs are not available and no onboarding timeline exists
  • No Data Owner: Cannot identify who owns the log source
  • Scope Expansion: Stakeholders request additional use cases without timeline adjustment
  • Quality Issues: Data quality issues cannot be resolved with available resources
  • Production Risk: Detection would generate >50 alerts/day without tuning
  • RBA Requests: Stakeholders request RBA features that are out of scope

Escalation Path:

  1. Document the blocker in writing
  2. Notify project stakeholders within 24 hours
  3. Propose alternatives or timeline adjustments
  4. Do not proceed until blocker is resolved or accepted

Project Risk Assessment

Complete this risk assessment during intake to identify potential blockers early:

Risk Category Risk Indicators Mitigation
Data Availability Log source not yet onboarded, vendor TA not available, parsing not validated Add Phase 1 onboarding time to project plan; do not commit detection dates until data confirmed
Data Quality Known timestamp issues, missing fields, high volume/noise Add Phase 2 data quality time; document known limitations
SOC Capacity SOC already at alert capacity, staffing changes planned, training gaps Confirm SOC readiness before monitoring mode; consider phased rollout
Stakeholder Alignment Multiple stakeholders with different priorities, unclear ownership, executive sponsor missing Get written sign-off on scope; identify single decision-maker
Technical Complexity Cross-source correlation required, custom parsing needed, performance concerns Add buffer time; prototype complex detections before committing
Business Timing Project overlaps with holiday freeze, major system changes, SOC training Adjust timeline to avoid conflicts; document constraints

Risk Assessment Checklist

Complete Before Committing to Project Timeline
  • Log source availability verified Confirmed data is flowing OR onboarding timeline agreed
  • Data quality assessed Sample data reviewed for required fields and timestamps
  • SOC capacity confirmed SOC manager acknowledged ability to handle expected alert volume
  • Business timing checked No conflicts with freezes, holidays, or major changes
  • Stakeholder sign-off obtained Written approval on scope, timeline, and success criteria

Project Completion Query

SPL: Generate Project Completion Evidence 
`comment("Run this query to generate evidence of detection deployment")`
`comment("Replace [detection_name] with your correlation search name")`

index=_audit action="correlation_search" search_name="*[detection_name]*" earliest=-30d
| stats 
    min(_time) AS first_run,
    max(_time) AS last_run,
    count AS total_runs,
    dc(search_name) AS detection_count
| eval first_run = strftime(first_run, "%Y-%m-%d %H:%M:%S")
| eval last_run = strftime(last_run, "%Y-%m-%d %H:%M:%S")
| eval evidence = "Detection '".search_name."' has been running since ".first_run." with ".total_runs." executions"
| table evidence, first_run, last_run, total_runs
