Future phase—aggregated risk scoring and behavioral analytics

Out of Scope

Risk-Based Alerting is not in scope for the current detection engineering engagement. This page documents the RBA concept for future reference and planning purposes only.

What is Risk-Based Alerting?

Risk-Based Alerting (RBA) is an advanced ES methodology that shifts from individual alert investigation to aggregated risk scoring. Instead of generating notable events directly, correlation searches contribute risk scores to entities (users, hosts, IPs), and notable events are created only when accumulated risk exceeds thresholds.

Why RBA is Out of Scope

Prerequisites Not Yet Met

RBA requires mature foundational capabilities that must be established first:

RBA Prerequisite Current State Required Phase
Complete Asset Inventory In progress Phase 1
Identity Correlation Partial Phase 2
Validated CIM Compliance Building Phase 2
Tuned Classic Detections In development Phase 3
Baseline False Positive Rates Not established Phase 3

Organizational Readiness

  • SOC Maturity: RBA requires analysts comfortable with risk-based investigation workflows, not alert-by-alert triage
  • Detection Library: Need 50+ validated detections before meaningful risk aggregation
  • Tuning Investment: Risk scores must be calibrated per detection, requiring months of baseline data
Recommended Timeline

RBA implementation typically begins 12-18 months after initial ES deployment, once Phases 1-4 are mature and the organization has baseline data for risk calibration.

RBA Concepts Overview

For planning purposes, here are the key RBA concepts that will be relevant in a future phase:

Risk Factors

Component Description Example
Risk Object Entity receiving risk (user, system, other) jsmith, WORKSTATION01, 10.1.2.3
Risk Score Numeric value added per detection 25, 50, 75, 100
Risk Message Description of risk contribution "Failed authentication from rare country"
Threat Object Source of threat (attacker IP, malware hash) 192.168.1.100, malware.exe

Risk Notable Thresholds

Example - Risk Threshold Configuration 
# Typical Risk Notable Thresholds
# (These would need calibration for your environment)

User Risk Notable:
  24-hour threshold: 100 points
  7-day threshold: 250 points

System Risk Notable:
  24-hour threshold: 75 points
  7-day threshold: 200 points

# Example accumulation:
# User jsmith:
#   - Failed VPN login (25 pts)
#   - Login from new country (30 pts)
#   - Access to sensitive share (20 pts)
#   - Download large file (25 pts)
#   Total: 100 pts → Risk Notable Created

RBA Benefits (Future State)

  • Reduced Alert Volume: 80-90% reduction in notable events reported by mature RBA deployments
  • Context-Rich Investigation: Risk notables include all contributing detections for holistic view
  • Attack Chain Visibility: Correlates multiple tactics into single investigation
  • Reduced False Positives: Single low-confidence detection doesn't alert; patterns do

Preparing for Future RBA

While RBA is out of scope, current work can prepare for future implementation:

Phase 1-4 Preparation Actions

  1. Asset Inventory: Build comprehensive asset database with criticality ratings
  2. Identity Correlation: Ensure user field normalization across all data sources
  3. Detection Categorization: Tag all detections with MITRE ATT&CK techniques
  4. Baseline Documentation: Record detection volumes and false positive rates
  5. Risk-Aware Design: Design detections with eventual risk scoring in mind (even if not implemented)
