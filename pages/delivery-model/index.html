Delivery Operating Model

📋 Page Status: HARDENED

Last Audit: 2024-02 | Auditor: Detection Engineering Team

This page defines the core operating model for detection engineering in a single-environment reality. All other handbook pages reference this model.

🚨 CRITICAL: Single Production Environment — No Safety Net

There is no DEV, UAT, or TEST environment. Every change you make is in production. This requires:

  • Rigorous backtesting before any detection deployment
  • Mandatory monitoring-only mode (minimum 7-14 days)
  • Documented rollback procedures for every change
  • Kill switch readiness — ability to disable in minutes
⚠️ Retail Business Timing — All Production Changes

Production changes follow these timing constraints:

  • No go-live during: Black Friday through New Year, major promotions
  • Preferred window: Tuesday-Wednesday, 10 AM - 2 PM ET
  • SOC coverage required: Never deploy when SOC is understaffed
📋 Purpose

This page defines how detection engineering projects are delivered in a single Splunk Cloud environment without DEV/UAT/TEST tenants. It establishes the phase gates, testing lifecycle, and kill-switch procedures.

Single Environment Reality

Unlike enterprises with multiple Splunk environments, this delivery model operates with one production Splunk Cloud instance only. This constraint shapes everything:

❌ What We Don't Have
  • No DEV environment for experimentation
  • No UAT environment for stakeholder testing
  • No isolated test tenant
✅ What We Must Do Instead
  • Use historical data for backtesting
  • Deploy in monitoring-only mode first
  • Have documented rollback procedures

Stage 1: Backtesting

🔍 Purpose

Validate detection logic against historical data before any production deployment.

Process:

  1. Identify time range with known-good and known-bad events (if available)
  2. Run correlation search SPL as ad-hoc search
  3. Review results for false positives and missed detections
  4. Tune thresholds and logic based on findings
  5. Document baseline metrics
Backtest SPL Template 
| tstats summariesonly=false count from datamodel=Authentication 
    where earliest=-30d@d latest=now() 
    by Authentication.user, Authentication.src, Authentication.action
| rename Authentication.* as *
| where action="failure"
| stats count as failure_count by user, src
| where failure_count > 10
| eval detection_fired=1
| table _time, user, src, failure_count, detection_fired

Stage 2: Monitoring-Only Mode

⚠️ Critical Concept

Monitoring-only mode is a PRACTICE, not a Splunk feature. It means deploying a correlation search that runs on live data but does NOT create notables or trigger alerts.

How to implement monitoring-only:

Setting Production Value Monitoring-Only Value
Create Notable Enabled Disabled
Alert Actions Email/Ticket/etc None
Search Status Enabled Enabled
Output Results Index or lookup Summary index only

Duration: Minimum 7 days, recommended 14 days for seasonal patterns.

Review Monitoring-Only Results 
index=summary source="correlation_search_name"
| stats count by _time, user, src
| timechart span=1h count
| eval status="monitoring_only"

Stage 3: Production Enablement

Only enable production alerting when:

  • Monitoring-only period complete Minimum 7-14 days of observation
  • False positive rate acceptable Less than 5% or as defined in acceptance criteria
  • Triage runbook documented SOC knows how to handle alerts
  • Rollback procedure tested Can disable within minutes if needed

Kill Switch Procedure

🚨 Emergency Disable Procedure

If a detection causes operational issues (alert storms, performance impact, business disruption):

  1. Navigate to: Settings → Content → Content Management
  2. Filter by: Type = Correlation Search
  3. Find: The problematic correlation search
  4. Click: Disable button
  5. Verify: Search status shows "Disabled"
  6. Document: Time, reason, who disabled
SPL: Emergency Notable Suppression 
| makeresults 
| eval search_name="DETECTION_NAME_HERE"
| eval action="emergency_disable"
| eval timestamp=now()
| eval operator="YOUR_NAME"
| collect index=security_audit

ES Terminology Reference

📚 Use Correct Splunk ES Terms

Credibility requires using terms correctly:

Term Definition Common Mistake
Correlation Search Scheduled ES detection that runs SPL to identify security events Calling it "alert" or "rule"
Notable Event ES incident container created when correlation search fires Calling it "incident" or "ticket"
Notable Index Index where notable events are stored (notable index) Confusing with main or summary index
Risk Event RBA concept - OUT OF SCOPE for this project Using RBA concepts when not implemented

Communication Protocols

Before Any Production Change

  • Notify SOC Team Minimum 24 hours notice for new detections
  • Document in Change Log Include: what, when, expected impact, rollback plan
  • Avoid Peak Hours No production changes during promotions, holidays, or weekends

During Issues

  1. Disable detection immediately (Kill Switch above)
  2. Notify stakeholders within 15 minutes
  3. Document timeline in incident log
  4. Post-mortem within 48 hours
